# 决策记录制度草案（D-014）

> 状态：**草案 / 未落实** ｜ 日期：2026-10-22 13:26 ｜ Owner：设计主控 ｜ 关联：[D-014](../../TODO.md) ｜ 层级：治理
> 目的：给“设计系统如何记录决策”一个可讨论的起点，**不现在就改制度**。
> 结论先行：**推荐 C · 混合制**——`00 决策总表`做索引，D 级决策有独立记录，E 级决策只占一行并链接实现；先用提案文件，不搞大迁移。

## 一、为什么现在要做

设计系统已经有 D1–D10 和 E01–E18 两层决策，但记录方式还是“边做边补”：

- D 表有战略判断，E 表有执行选择，但两者都缺少统一的生命周期（谁提的、何时复核、被谁取代）；
- 有些决定只存在于对话，事后才补进文档（例如 v0.1.0 补记、Q5 补记）；
- 决策、变更日志、TODO、讨论记录四者边界不清：同一件事可能在四个地方各写一遍；
- 项目各自有决策表（mainline / LiveFab / website / 游戏实现裁决），体例不同，无法直接横向比较；
- 现有表能“看结论”，但不容易回答“这个结论什么时候被推翻、为什么”。

所以本草案要解决的不是“再多写文档”，而是：**让决策有唯一入口、可追溯状态、可链接细节，同时不增加太多流程**。

### 2.1 共同模式

现有实践其实已经形成了一套“事实上的标准”：

1. **一个索引表**：先看结论；
2. **一个详细段/文件**：看理由、备选、代价；
3. **一个讨论记录**：保留当时的判断与分歧；
4. **一个变更日志**：发布时记“改了什么”；
5. **一个待办**：决定之后还剩什么没做。

问题不在于缺这五样，而在于它们**没有被同一套 ID、状态和链接规则串起来**。

### 2.2 最值得继承的四点

- **“推翻条件”**（future-debris / refu-game）：每条决策都写“什么情况下要重估”，避免把临时判断当永久真理；
- **修订记录**（mainline / LiveFab / website）：只增不改，保留当时的判断；
- **讨论与决策分离**（mainline discussions）：讨论可以很长，决策表只放结论；
- **状态机**（M3）：状态不是装饰，而是“可依赖程度”的声明。

## 三、四种可选方案

| 方案 | 做法 | 成本 | 可追溯 | 适合 |
| --- | --- | --- | --- | --- |
| **A. 现状加强** | 只维护 00 表；D/E 行写得更细 | 最低 | 中 | 决策很少、一个人维护 |
| **B. 全量 ADR** | 每个决策一个文件，00 只做索引 | 最高 | 最高 | 多团队、审计要求高 |
| **C. 混合制（推荐）** | 00 索引；D 级有独立记录；E 级只占一行；提案单独放 | 中 | 高 | 当前规模、长期维护 |
| **D. RFC 流水线** | 提案 → 评审 → 接受 → 实施 → 复核，带 Owner/SLA | 高 | 最高 | 跨团队、需要正式评审节奏 |

### 3.1 A · 现状加强

- 保留 D/E 两层表；
- 每行补 Owner、复核日、取代关系；
- 详细理由继续放实现记录/项目文档。

**优点**：几乎不增加文件；**缺点**：D 级决策的上下文仍散落，表会越来越宽；不适合“多年后回看”。

### 3.2 B · 全量 ADR

每个决策一个 `D-XXX-*.md`，包含 Context / Options / Decision / Consequences / Supersedes；00 只做索引。

**优点**：最可追溯；**缺点**：E 级小决策也开文件，维护成本高，容易变成“为了流程而流程”。

### 3.3 C · 混合制（推荐）

- **D 级（战略/单向门）**：00 表 + 独立记录（Context / Options / Decision / Consequences / 推翻条件 / Supersedes）；
- **E 级（执行/双向门）**：只保留 00 表一行，详据链接到实现记录、代码、CHANGELOG；
- **未决定的事**：先写 `proposals/` 提案，不直接进 00；
- **讨论**：长讨论单独记录，00 只放结论与链接。

这样既不会把 18 条 E 决策都做成 18 个文件，也不会让 D 级决策只有一行结论。

### 3.4 D · RFC 流水线

在 C 之上再加：提案模板、评审人、接受标准、实施 Owner、复核日期、SLA。

**优点**：适合多团队；**缺点**：当前设计系统只有一个人主控，先用 C，等跨团队再升级到 D。

## 四、推荐方案：C + 轻量流程

### 4.1 分层

| 层级 | 用途 | 记录位置 | 例子 |
| --- | --- | --- | --- |
| **D** | 战略/单向门，推翻成本高 | 00 表一行 + `decisions/D-XXX-*.md` | D3 五层 + 三层 token |
| **E** | 执行/双向门，可逆 | 00 表一行，链接实现记录 | E06 8px 面板圆角 |
| **P** | 尚未决定的提案 | `proposals/YYYYMMDD-HHMM-*.md` | 本文件 |
| **R** | 长讨论/评审记录 | 讨论记录或提案附录 | mainline discussions |

> **原则**：**一个决策只有一个 canonical 记录**；其他文件只链接，不复制。00 是索引，不是全文。

### 4.2 状态

建议把“决策状态”和“执行状态”分开，避免一张表里混用“待裁决 / 阻塞 / 已执行”：

**决策状态**（D/E 通用）：

| 状态 | 含义 |
| --- | --- |
| `draft` | 只有想法，尚未成文 |
| `proposed` | 已成文，待裁决 |
| `accepted` | 已采纳，作为依据 |
| `rejected` | 明确不采纳，保留理由 |
| `superseded` | 被新决策取代，保留历史 |
| `retired` | 不再相关，留档 |

**执行状态**（主要用于 E，可选）：

`pending` / `in-progress` / `done` / `blocked`。

这样“决定了吗”和“做了吗”不会混在一起：E06 可以是 `accepted + done`，D-003 可以是 `accepted + pending`。

### 4.3 编号

- 保留现有 `D1–D10`、`E01–E18`，**不重编号**；历史引用不能断；
- 新 D 决策用 `D-011`、`D-012`……；新 E 决策用 `E-019`、`E-020`……；
- 独立记录文件名直接用 ID：`decisions/D-003-five-layer-model.md`；
- 不再引入第二套 `DR-0001` 编号，避免“一个决策两个号”。

### 4.4 目录

```text
design/docs/
├── 00_决策总表.md          # 索引：D/E 两层
├── proposals/              # 未决定：提案、选项、推荐
│   └── YYYYMMDD-HHMM-关键词.md
├── decisions/              # 已接受的 D 级决策（独立记录）
│   ├── README.md
│   └── D-XXX-关键词.md
└── ...                     # 现有实现记录/走查/风格卡
```

- `proposals/` 只放**尚未裁决**的内容；裁决后不删除，状态改为 `accepted/rejected`，并链接到 00。
- `decisions/` 只放 **D 级**的独立记录；E 级不强制开文件。
- 如果未来跨团队，再启用 D 的 RFC 字段，不现在加。

### 4.5 模板

**D 级记录**（建议）：

```markdown
# D-011 · 标题

> 状态：accepted ｜ 日期：YYYY-MM-DD HH:MM ｜ Owner：… ｜ 层级：D ｜ 关联：…
> 取代：D-00X ｜ 被取代：—

## 背景
（为什么必须决定）

## 选项
| 选项 | 优点 | 代价 |
| --- | --- | --- |

## 决定
（选了什么，一句话）

## 后果
（会带来什么，哪些是接受的代价）

## 推翻条件
（什么情况下重估）

## 链接
（实现记录、代码、CHANGELOG、TODO）
```

**E 级行**（沿用现表）：

`# | 时间 | 类别 | 决策 | 选择 | 状态 | 详据`

**提案**（P）：

`背景 / 选项 / 推荐 / 影响 / 需要你决定什么`。

### 4.6 流程

```text
想法
  → proposals/（draft）
  → 讨论 / 评审（proposed）
  → 用户或设计主控裁决
      ├─ D：00 表 + decisions/D-XXX-*.md（accepted）
      └─ E：00 表一行（accepted），执行状态另记
  → 有发布影响：CHANGELOG 记一条，链接决策 ID
  → 还有工作：TODO 记一条，链接决策 ID
  → 被推翻：旧记录标 superseded，新记录写 supersedes
```

- **不删除**被推翻的决策；历史只增不改。
- **不复制**：CHANGELOG 只写“改了什么 + 决策 ID”，不重写理由；TODO 只写“还剩什么”，不重写决定。
- **不提前**：没有真实争议/影响面的小改动，不进决策表；直接做、在 CHANGELOG 记。

### 4.7 角色

| 角色 | 权力 |
| --- | --- |
| 用户 | D 级最终裁决；可推翻任何决定 |
| 设计主控 | E 级批准；D 级技术性否决；维护索引与状态 |
| 提案人 | 写清背景、选项、推荐、影响 |
| 实现者 | 按 accepted 记录执行；发现冲突时回到提案，不静默偏离 |

### 4.8 与现有文件的关系

| 文件 | 负责 | 不负责 |
| --- | --- | --- |
| `00_决策总表` | 索引、状态、一句话选择、链接 | 长篇理由、实现细节 |
| `decisions/` | D 级完整理由、选项、后果、推翻条件 | 发布记录、待办 |
| `proposals/` | 未决定前的选项与推荐 | 已接受的最终结论 |
| `CHANGELOG` | 发布级“改了什么” | 为什么这样选 |
| `TODO` | 还剩什么、谁做、优先级 | 决策本身 |
| 讨论记录 | 当时的判断、分歧、证据 | 最终状态 |

## 五、迁移策略

**推荐：不重写历史，只补链接。**

1. 保留 D1–D10 / E01–E18 现有表，不动编号；
2. 新 D 决策才创建 `decisions/D-XXX-*.md`；
3. 如果要在现有 D 中选一个做样例，建议 **D3（五层 + 三层 token）**——它最能说明“为什么这样分层”；
4. 现有 E 不补文件；需要时把实现记录链接补进“详据”列；
5. 旧状态词（`✅ 已裁决`、`已执行`、`待裁决`）不批量改；新记录用新状态词，旧表加一行映射说明即可；
6. 不一次性搬 18 个 E 决策；那会制造 18 个低价值文件。

## 六、需要你拍板的问题

| # | 问题 | 选项 | 我的建议 |
| --- | --- | --- | --- |
| 1 | 制度范围 | 只设计系统 / 全工作区 | **先设计系统**，跑 1–2 个月再推广 |
| 2 | 独立记录粒度 | 只 D / D+重要 E / 全量 | **只 D**；E 保持一行 |
| 3 | 状态词 | 用 M3 全套 / 简化 6 态 | **简化 6 态**（draft/proposed/accepted/rejected/superseded/retired） |
| 4 | 目录 | `proposals/` + `decisions/` / 只 `proposals/` | **两者都要**；proposals 放未决，decisions 放 D |
| 5 | 迁移 | 只新决策 / 补一个样例 / 全量回填 | **只新决策 + 一个 D3 样例** |
| 6 | 批准权 | 用户批 D 和 E / 用户 D、主控 E | **用户 D、主控 E**；与 D7 一致 |

## 七、最小落地步骤（若你同意）

1. 在 `design/docs/decisions/` 建 `README.md` 与模板；
2. 选 D3 做一篇样例记录（不重写 00 表，只链接）；
3. 更新 `00_决策总表` 的维护说明：D 链接到 decisions，E 只留行；
4. 把 `D-014` 从“草案中”改为“已采纳”，并在 CHANGELOG 记账；
5. 下一次新 D 决策开始使用新流程；E 不强制。

## 八、本草案不做什么

- 不马上建全量 ADR；
- 不重编号 D/E；
- 不把 CHANGELOG 改成决策日志；
- 不要求每个小改动都写提案；
- 不引入外部工具/数据库；先用 Markdown + 链接。
