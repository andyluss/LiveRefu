# 04 · 落地路线：先两个试点，再谈全介质

> 本文对应 [D6 / D10](00_决策总表.md)。原则：**不做大爆炸式换肤；用两个真实产品证明系统，再扩介质。**
> 日期：2026-10-21 ｜ 状态：**P0–P2 已完成；P3 进行中**（LiveFab 与明日频道风格卡已接入；组件契约未开始）｜ 记录：[05](05_实现记录_v0.1.md) / [06](06_实现记录_v0.2.md) ｜ 前置阅读：[02 系统架构](02_系统架构.md)、[03 治理与运营](03_治理与运营.md)

## 一、排序原则

1. **风险优先**：先解决“会不会又变成四套 token”，再解决“好不好看”。
2. **两个极端**：网站覆盖“长文阅读 + 公开品牌”，游戏覆盖“交互 + 强验收 + 多纪元”。两者都过，才说明语法真的通用。
3. **迁移 ≠ 重设计**：`v0.1` 只换取值与接线，不改布局；任何视觉变化单独评审。
4. **每个阶段有退出条件**：没有退出条件就不算完成。
5. **不承诺日历时间**：工时波动大，本路线以**冲刺**为单位，只承诺顺序与完成标准。

## 二、阶段总览

| 阶段 | 目标 | 主要产出 | 退出条件 |
| --- | --- | --- | --- |
| **P0 决策与收编** | 把“要不要做、按什么做”定下来 | 5 个单向门裁决；本目录 5 篇文档；现状盘点 | 你能用一句话说出“设计系统是什么、谁说了算” |
| **P1 地基** | 建立单一事实来源与闸门 | `ref` / `sys` token；一个产品风格卡；CSS + Godot 生成器；4 道闸门 + 自检 | `build --check` 通过；4 道闸门自检全绿；token 文档自动生成 |
| **P2 双试点** | 证明系统能服务阅读与游戏 | 网站迁移；未来残片迁移；迁移说明；视觉回归基线 | 两个产品真实消费生成 token；迁移表面 0 裸值；差异逐项有记录 |
| **P3 扩展** | 覆盖更多产品与组件 | LiveFab + 明日频道接入；3–5 个组件契约；App kit 起步 | 4 个产品接入；组件至少 2 个真实消费者 |
| **P4 印刷** | 让品牌能落纸 | Print kit；品牌书；包装/名片/海报模板；一次真实打样 | 打样通过（颜色/字阶/出血/条码/法务位） |
| **P5 实体** | 让品牌能落物 | CMF 规格；包装结构；周边试产；供应商清单 | 至少一个实体样品通过验收 |

> **P0–P2 是 `v0.1` 的范围**；P3 之后按需推进。任何阶段都可以暂停，但暂停点必须是“已完成”而不是“半套”。

## 三、`v0.1` 的具体范围

### 必须做

**1. Token 地基**
- `design/tokens/core/ref.tokens.json`：原始色板、间距、字阶、圆角、描边、动效；
- `design/tokens/core/sys.tokens.json`：语义角色（bg/text/line/action/feedback/focus 等）；
- `design/tokens/products/future-debris.atomic.tokens.json`：原子纪元风格卡（先做一个，证明映射）；
- `design/tokens/schema/tokens.schema.json`：自描述 schema。

**2. 生成器与闸门**
- `design/tools/build_tokens.ts`：解析别名、输出 CSS / Godot JSON / token 文档；
- `design/tools/check_tokens.ts`：schema、别名、孤儿、字阶；
- `design/tools/check_contrast.ts`：对比度 + 层级亮度 + focus 分离；
- `design/tools/check_no_raw_values.ts`：产品代码裸值扫描（带 allowlist：生成物、第三方、历史冻结）；
- `design/tools/check_generated.ts`：重新生成后无 diff；
- 每个检查器 `--self-test`，负向用例断言错误类型。

**3. 两个试点**
- **网站**：用生成 CSS 替换 [`theme.css`](../../projects/website/app/assets/theme.css) 的颜色定义；修 `--focus` 与 `--line` 的已知缺陷；保持布局与阅读体验不变；截图基线对比。
- **未来残片**：保留 18 个颜色 token 的语义名，映射到 `sys.*`；由 Godot kit 生成主题；保持主题预览与战斗截图一致；现有 `./run.sh contrast` 的断言不降低。

**4. 文档与治理**
- `design/CHANGELOG.md`（`v0.1.0`）；
- 迁移说明（每个产品一篇，含回滚）；
- 例外登记表（哪怕为空，也要有模板）；
- `design/` 的 M1/M2 校验配置（先 `report`，0 违规后转 `block`）。

### 明确不做

- 全组件库、Figma 组件库、设计系统文档站；
- 所有产品换肤、母品牌正式命名、标志重做；
- App / Print / Physical 的完整实现；
- 网站/游戏的视觉重设计；
- `indie/` 项目迁移（默认豁免，按外部消费者处理）。

## 四、为什么选这两个试点

| 试点 | 覆盖的极端 | 能证明什么 | 风险 |
| --- | --- | --- | --- |
| **未来档案（网站）** | 长文阅读、公开品牌、SEO/OG、无障碍 | 双模中的 **Archive** 能工作；token 能服务内容站；公开面不会被“游戏化”拖累 | 网站已有成熟主题，迁移容易变成“重做”；必须只换接线 |
| **未来残片（游戏）** | 交互、多纪元、强验收、Godot 主题、截图断言 | 双模中的 **Console** 能工作；`sys` → `product` 映射能表达玩法语义；闸门能接住 | 已有 8 道闸门，新增 token 层不能降低标准；必须复用现有 `check_contrast` 思路 |

> **不选 LiveFab 做首版试点**：它已经复制了网站 token，接起来最容易，但**证明力最弱**——它不能证明长文，也不能证明游戏。放到 P3 作为“第三人验证”。
> **不选明日频道做首版试点**：它的暖色皮肤是合法的风格卡差异，适合在系统稳定后验证“换风格不换语法”，不适合当第一块试金石。

## 五、`v0.1` 的 Definition of Done

| # | 条件 | 证据 |
| --- | --- | --- |
| 1 | 两个产品真实消费生成物 | 产品代码 import / 读取 `design/tokens/dist/`，不是复制 |
| 2 | 迁移表面 0 个裸色值 | `check_no_raw_values` 通过；allowlist 逐条有理由 |
| 3 | 对比度与层级全绿 | `check_contrast` + 现有产品闸门 |
| 4 | 生成物可复算 | `build_tokens --check` 无 diff |
| 5 | 文档与 token 对账 | 自动生成 token 表；文档不手写值 |
| 6 | 视觉差异逐项有记录 | 迁移前后截图/录屏 + 差异说明（预期内/需评审） |
| 7 | 回滚可用 | 每个产品一篇迁移说明，含回滚命令 |
| 8 | 检查器可信 | 每个 `--self-test` 负向用例通过，且断言错误类型 |
| 9 | 日志完整 | `design/CHANGELOG.md` + 根 `CHANGELOG.md` |
| 10 | 治理可运行 | 决策日志、例外模板、DP 模板可用；至少走通一次 DP |

> **没有第 6 条，就不算迁移完成**：视觉回归不是“看起来差不多”，而是“差异被看见并被解释”。

## 六、风险与缓解

| 风险 | 表现 | 缓解 |
| --- | --- | --- |
| **范围膨胀** | 想一次做全组件库/全产品/实体 | 冻结 `v0.1` 范围；新需求写 DP，进 P3+ |
| **过度抽象** | 为不存在的复用建 token | 只从两个真实产品抽；第三个消费者出现才上移 |
| **迁移变重做** | 网站/游戏顺手改布局 | 迁移 PR 禁止布局改动；视觉变化单独 PR |
| **视觉回归** | “只是换 token”却变了样 | 先存基线截图；逐项 diff；预期变化单独记录 |
| **产品抵触** | “系统拖慢发布” | 给最小合规方案 + 例外；设计主控 2 个工作日内响应 |
| **字体/许可** | 商用/印刷时说不清 | P1 就建字体与资产登记，不等印刷 |
| **实体供应链** | 颜色/材料打样与屏幕差很远 | P4 先做一次真实打样；CMF 以实物样为准 |
| **AI 不一致** | 每次生成的值不同、风格漂移 | token + 闸门 + 人工定稿关键视觉 |
| **治理变瓶颈** | 所有事都等设计主控 | 双向门授权；只升级单向门与跨产品冲突 |
| **文档腐化** | 文档写的值与 token 不同 | 自动生成 token 表；CI 对账；禁止手写值 |

## 七、我需要你提供的三件事（除决策外）

1. **是否使用 Figma / 其它设计工具？** 决定 D4 的“设计面”怎么接；不用也不影响 JSON 为源。
2. **实体产品的时间预期**：半年内 / 一年内 / 还没定？决定 P4/P5 是否提前。
3. **可接受的前期投入**：`v0.1` 是“先做地基、外观基本不变”，你是否接受这段“看不见成果”的投入？

> 如果第 3 条你希望“先看到明显变化”，我建议调整顺序：先做**一个页面的视觉提案**给你看方向，再回到地基；但那样会多一次返工，且不改变“两个试点”的最终路径。

## 八、拍板后我立即做什么

按以下顺序，不再反复问你（除非遇到单向门）：

1. 建 `design/tokens/` 与 `design/tools/` 骨架；
2. 从现有四套定义抽出 `ref` / `sys`，写 schema；
3. 写 `build_tokens.ts` + 两个检查器 + 自检；
4. 生成 CSS 与 Godot token；
5. 做网站迁移 PR（只换接线）；
6. 做游戏迁移 PR（只换接线）；
7. 跑两个产品的现有闸门 + 新闸门；
8. 写迁移说明、更新日志、请求你验收。

## 九、停止条件（什么时候该停下来改方向）

- **token 模型无法表达某个产品的核心语义**：停下来改模型，不硬塞；
- **迁移必须改布局才能套用**：说明抽象错了，回到 L1；
- **两个试点都出现“为了过闸门而破坏设计”**：闸门设计错了，先修闸门；
- **设计评审成为发布瓶颈超过两周**：检查是否管得太细，下放双向门；
- **实体产品时间表突然提前**：暂停 P3，先做 Print/CMF 的最小可用集。

> 这些停止条件不是“失败”，而是系统在告诉你：**抽象与真实产品脱节了**。早停早改，比硬推一年便宜。
