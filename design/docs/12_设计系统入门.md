# 12 · 设计系统入门：从“配色表”到可运行的产品语言

> 这是一篇**入门文章**，不是 LRDS 的规范或决策记录。规范看 [00–11](00_决策总表.md)，本文只负责把设计系统这件事讲清楚。
> 最后更新：2026-10-22 09:54

## 写在前面

如果你第一次听到“设计系统”，可能会想到三样东西：一份配色规范、一个 Figma 组件库，或者大公司才养得起的团队。

它可以是这些的一部分，但都不是核心。

设计系统真正解决的问题是：**当很多人、很多产品、很多平台要一起做界面时，怎样让“同一个意思”长得一样、行为一样、读起来一样，而且还能持续修改而不失控。**

它既不是一张图，也不是一个仓库，更不是一份“大家最好遵守”的 PDF。它是一套**共同语言 + 可复用零件 + 决策机制 + 运行工具**。语言让人能讨论，零件让人能拼装，机制让分歧能被裁决，工具让规则不会靠记忆维持。

这篇文章不追求学术完整，也不打算把设计系统史讲一遍。它想回答的是几个更实际的问题：

- 设计系统到底是什么，不是什么？
- 它由哪些东西组成？
- 从零开始，第一步该做什么，什么不该做？
- 为什么很多设计系统做完就死了？
- 一个人、小团队、多个产品，分别该怎么用？
- 怎么判断它有没有用？

如果你读完只记住一句话，我希望是：

> **设计系统不是“把界面做统一”，而是“把重复发生的决策，变成可复用的约束”。**

## 一、设计系统到底是什么

### 1.1 一个日常类比

想象一家餐厅。

- 菜谱是“原则和决策”：什么菜配什么酱、什么季节用什么食材。
- 厨房设备是“组件”：锅、灶、冰箱，每个都有固定接口和使用方式。
- 出菜流程是“模式”：先冷盘、再热菜、最后甜点，服务员知道什么时候端什么。
- 采购标准是“token”：酱油用哪个等级、油温多少、摆盘用多大的盘子。
- 店规是“治理”：谁可以改菜谱、新菜怎么试、失败了怎么撤。

如果只有菜谱，没有设备和流程，餐厅开不起来；如果只有设备，没有菜谱和店规，今天做川菜、明天做日料，客人记不住你是谁。

设计系统就是这四样东西的合体。它让“做一道菜”不再每次从零发明，也让“换一道菜”不会把厨房砸了。

### 1.2 一个更正式的定义

设计系统是一组**共享的、可执行的界面决策**，包括：

- **原则**：我们优先什么、牺牲什么；
- **基础规则**：颜色、字体、间距、圆角、阴影、动效、图标；
- **组件与模式**：按钮、表单、面板，以及搜索、登录、空状态这类任务配方；
- **介质适配**：Web、游戏、App、打印、实体各自怎么落地；
- **资产**：字体、图标、插画、图片、声音；
- **治理**：谁决策、怎么贡献、怎么版本化、怎么弃用；
- **工具**：token 生成、对比度检查、组件预览、截图与键盘走查。

关键词是**可执行**。写在文档里但没人能检查的规则，最多叫“建议”；能变成变量、组件、检查器、发布流程的规则，才叫系统。

### 1.3 它不是什么

**它不是一份配色表。** 配色表只回答“用什么颜色”，设计系统还要回答“什么时候用、为什么用、不能用什么、深色模式怎么办、对比度不够怎么办”。

**它不是一个组件库。** 组件库解决“有没有按钮”，设计系统还要解决“按钮该有几个层级、危险操作用什么、加载时能不能重复点、键盘焦点在哪、移动端命中区多大”。

**它不是 Figma 文件。** Figma 可以是设计端的入口，但如果 token、组件、代码、文档各自维护，Figma 只会变成第四份真相。

**它不是“统一视觉”的同义词。** 真正要统一的是**语义和行为**，不是每个像素。一个品牌可以有 Archive 的纸感，也可以有 Console 的仪表感；它们可以共享同一套字号、间距、焦点和交互语法。

**它不是一个一次性的项目。** 项目有终点，系统没有。只要产品还在迭代，系统就要有人维护、有人负责、有人决定“这个需求该不该进系统”。

### 1.4 设计系统真正服务的对象

设计系统的用户不只是设计师。它至少服务五类人：

- **设计师**：不用每次从空白画布开始，知道哪些能改、哪些不能改；
- **工程师**：拿到的是契约和 token，不是一张需要猜的图；
- **产品经理**：知道一个需求会牵动哪些组件、哪些平台、多少迁移成本；
- **内容/运营**：知道文案长度、语气、错误提示怎么写；
- **AI 代理**：知道边界、文件名、检查命令，不会每次都“自由发挥”。

所以设计系统不是“设计团队的内部资产”，而是**产品组织的基础设施**。它的成功标准不是“文件很漂亮”，而是“别人愿不愿意用、用完是否更快、更稳”。

## 二、为什么需要，以及什么时候不需要

### 2.1 它带来的真实收益

**第一，减少重复决策。** 一个按钮用什么圆角、什么字号、什么间距，如果每个页面都重新决定，团队会在无数小问题上消耗注意力。系统把这些决定提前做掉，让人把精力留给真正重要的产品问题。

**第二，让一致性可维护。** 一致性不是“看起来差不多”，而是同一个语义在所有地方行为一致。搜索框在网站是 4px 圆角、在 App 是 12px、在游戏里不能键盘操作——这不是“风格差异”，是用户要重新学习。

**第三，把可访问性变成默认值。** 对比度、焦点、触控目标、文字缩放，如果靠每个开发者自觉，迟早会漏。系统把这些做成 token、组件状态和检查器，让“做对”比“做错”更容易。

**第四，降低协作成本。** 设计稿和代码之间最大的摩擦不是“像素差 1px”，而是“这个名字到底指什么”。当 `--color-danger` 和 `--color-warning` 有明确语义，讨论会从“这个红一点”变成“这是错误还是警告”。

**第五，支持多产品和多平台。** 第二个产品不必重新发明按钮；Web、游戏、App 可以共享同一套语义，只是投影不同。这是设计系统最有价值、也最容易被低估的部分。

**第六，让品牌变得可识别。** 用户未必说得出“你的圆角是 8px”，但会感觉到“这几个产品像一家人”。系统把这种“像一家人”的感觉，从偶然变成可复制。

### 2.2 它的成本

设计系统不是免费的。它至少要消耗：

- **前期梳理成本**：盘点现有颜色、字体、组件、例外；
- **持续维护成本**：有人回答使用问题、评审贡献、发版本；
- **迁移成本**：老产品要改变量、改组件、重新走查；
- **治理成本**：开会、写决策、拒绝不合理需求；
- **机会成本**：这些时间本来可以用来做新功能。

所以问题不是“设计系统好不好”，而是“**我们是否重复到值得为它付出这些成本**”。

### 2.3 什么时候不该做

以下情况，我建议先别做“完整设计系统”：

- **只有一个产品、一个设计师、一个工程师，而且短期不扩**：先把界面做对，比建系统更重要；
- **产品还在找方向，界面每天推倒重来**：这时候需要的是快速原型，不是稳定约束；
- **视觉 novelty 就是产品本身**：每个页面都要不一样，系统会变成束缚；
- **没有明确 owner**：没人维护的系统，三个月后一定变成“过时的第四份文档”；
- **组织不愿意改老代码**：系统只能服务新页面，老页面永远例外，最后系统变成“新项目的装饰”。

如果属于这些情况，可以做更轻的东西：一份**模式库**、一套**颜色/字号变量**、一个**组件清单**。先解决最痛的一两个重复，不要一上来就建“大而全”。

### 2.4 一个判断公式

我常用一个很粗的判断：

> **重复次数 × 不一致的代价 × 可标准化的程度 > 建设与维护成本**

- 重复次数：同一个按钮、表单、空状态出现多少次？
- 不一致的代价：用户会不会困惑？品牌会不会受损？无障碍会不会出问题？
- 可标准化的程度：这件事能不能用 token/组件/流程表达？
- 建设与维护成本：谁来做？做多久？老产品怎么迁移？

四个数都成立，才值得做。只有一个“看起来很专业”，不值得。

## 三、设计系统的五个核心物件

### 3.1 原则：先决定“什么更重要”

原则不是口号。好的原则能用来**裁决争论**。

“简洁、现代、用户至上”不是原则，因为任何团队都可以这么说，遇到具体问题时也帮不上忙。

好的原则通常长这样：

- **先语义，后色值**：业务代码只能引用语义 token，不能写 `#3FB8AB`；
- **可访问性是闸门**：对比度、焦点、触控目标不达标，功能不算完成；
- **产品可变，语法不变**：风格卡可以换色板、材质、光源，但不能换信息位置和交互语法；
- **先收编，再统一**：不推翻既有合理差异，先把语义对齐，再替换取值；
- **没有真实消费者，不算交付**：组件、介质包、规范，都要在真实产品里用过。

原则不需要多，5–8 条足够。每一条都应该能回答：“当 A 和 B 冲突时，我们选谁？”

### 3.2 Token：把决策变成有名字的值

Token 是设计系统里最容易被误解的东西。很多人以为 token 就是“把颜色存成变量”，其实更重要的是**命名**。

一个颜色值本身没有意义：

```css
#3FB8AB
```

它可能是品牌色、行动色、成功色、链接色。不同语义在深色模式下可能完全不同。Token 做的是给这个值一个**稳定的语义名字**：

```css
--color-action-primary: #3FB8AB;
--color-feedback-success: #7BD389;
--color-focus-ring: #8AB4F8;
```

这样，产品代码不需要知道“今天品牌色是哪个绿”，只需要知道“这是主行动”。换品牌、换主题、换深浅色，只改映射，不改业务代码。

#### 三层 token

一个比较稳健的结构是三层：

| 层 | 作用 | 例子 |
| --- | --- | --- |
| **ref（原始值）** | 记录调色板、字号、间距等原始刻度 | `ref.color.teal.500`、`ref.space.16` |
| **sys（通用语义）** | 跨产品共享的角色 | `sys.color.action.primary`、`sys.type.ui.body` |
| **product（产品/风格卡）** | 某个产品的具体映射 | `product.archive.color.bg`、`product.console.color.scanline` |

- **ref** 回答“有哪些值可用”；
- **sys** 回答“这个值在界面里扮演什么角色”；
- **product** 回答“这个产品用哪套风格”。

三层不是强制教条，但它能防止两个常见问题：

1. 业务代码直接引用原始色，换主题时到处改；
2. 每个产品都复制一份完整 token，最后五套系统互相漂移。

#### 命名原则

- **按角色命名，不按颜色命名**：`color.danger` 比 `color.red` 好，因为危险不一定是红色；
- **按用途命名，不按外观命名**：`text.secondary` 比 `text.gray` 好；
- **避免“万能词”**：`color.primary` 太模糊，不如 `action.primary`、`text.primary`；
- **保持层级短**：`sys.color.action.primary` 比 `sys.color.button.background.primary.default` 更容易记；
- **一个语义只对应一个 token**：不要让 `--teal` 和 `--action` 同时存在，否则迟早分叉。

#### 常见 token 类型

- 颜色：背景、表面、文字、线、行动、状态、焦点、材质；
- 字体：字号、行高、字重、字距、字体族；
- 间距：4/8/12/16/24/32 这类刻度；
- 尺寸：控件高度、触控目标、图标大小；
- 圆角：控件 4px、面板 8px；
- 描边：1.5px 控件、2px 焦点；
- 阴影/ elevation；
- 动效：时长、曲线；
- 透明度/遮罩；
- 断点/栅格；
- z-index（谨慎，通常用层级语义而不是数字）。

#### 不要做“token 动物园”

不是每个像素都值得 token 化。判断标准是：

- 这个值会不会在多个地方重复？
- 它会不会随主题/产品/平台变化？
- 它有没有语义，而不只是“这里刚好 7px”？

如果三个答案都是“否”，就让它留在组件内部。Token 太多会让系统变得比硬编码更难用。

#### 深色模式不是“反相”

深色模式不是把 `#FFFFFF` 变成 `#000000`。它需要重新做语义映射：

- 背景层级：base / surface / raised / sunken；
- 文字层级：primary / secondary / muted / inverse；
- 线：subtle / strong；
- 状态色：在深色背景上重新测对比度；
- 焦点：必须独立于强调色，不能“品牌绿=焦点绿”。

如果一个系统只有一套暗色 token，那么它还没有真正的“双模式”；它只是“暗色皮肤”。

### 3.3 组件：契约先于实现

组件不是“一个圆角矩形 + 一段 CSS”。组件是**一组关于行为的承诺**。

一个按钮至少要考虑：

- **层级**：primary / secondary / ghost / danger；
- **尺寸**：sm / md / lg；
- **状态**：default / hover / focus-visible / active / disabled / loading；
- **行为**：点击、键盘 Enter/Space、加载时禁止重复提交、危险操作二次确认；
- **可访问性**：可访问名称、焦点可见、对比度、触控目标；
- **内容**：文案长度、图标位置、图标-only 的 aria-label；
- **跨端**：Web、App、游戏里分别怎么表现。

这些加在一起，才叫“按钮组件”。如果只做了视觉，没有状态和行为，它只是一个“按钮样式”。

#### 组件契约的五段式

一个可维护的契约通常包含：

1. **解剖**：由哪些部分组成（容器、图标、文字、辅助文本）；
2. **变体与尺寸**：哪些合法组合，哪些禁止；
3. **状态与行为**：hover、focus、disabled、loading、error、selected；
4. **键盘与无障碍**：Tab 顺序、Enter/Space、ARIA、焦点管理；
5. **Do / Don't 与 token 清单**：什么时候用、什么时候不用、用了哪些 token。

这份契约不需要写得像法律，但必须能让一个没参与设计的人，做出**行为一致**的实现。

#### 三个常见组件

**按钮**：一个界面通常只应该有一个主行动。主按钮太多，等于没有主行动。危险操作不要用主按钮的视觉，除非你希望用户误点。

**表单字段**：标签必须始终可见，placeholder 不能当标签；错误信息要和字段关联；输入类型、自动填充、键盘类型要正确；只读和禁用是两种不同状态。

**面板/卡片**：静态面板不是控件；整卡可点时，内部不要再嵌套按钮；可交互卡片要有清晰的焦点和 hover；不要把“卡片”当成万能容器。

#### 不要先造组件库

很多设计系统失败，是因为第一步就做“全组件库”：按钮、输入框、下拉、表格、弹窗、标签、步骤条、树、日历……做了三十个，结果只有三个被真实产品使用。

更稳的顺序是：

1. 先有真实页面和真实需求；
2. 找出重复次数最多的 3–5 个组件；
3. 只做这些，并在两个真实产品里用；
4. 用出问题，再扩展。

组件库不是展品，是工具。工具的价值在使用次数，不在数量。

### 3.4 模式：组件是积木，模式是说明书

组件回答“这个零件怎么用”，模式回答“这类任务怎么做”。

例如“搜索”不是一个输入框，而是一整套模式：

- 入口：顶部搜索、快捷键、空状态引导；
- 打开：弹窗/全屏页/内联；
- 焦点：打开后焦点进输入框，关闭后回到触发点；
- 键盘：上下选择、Enter 跳转、Esc 关闭；
- 结果：加载、空结果、错误、分组、高亮；
- 历史：最近搜索、清空；
- 移动端：全屏、键盘避让、取消按钮；
- 可访问性：结果数量播报、焦点不丢、屏幕阅读器能读出“第几条”。

模式文档不需要很长，但要包含：**适用场景、不适用场景、流程、状态、内容规则、无障碍、示例、反例**。

没有模式，组件会被用成“乐高散一地”：每个页面都能拼，但每个页面都拼得不一样。

### 3.5 风格卡：统一语法，不统一皮肤

“设计系统”最容易被误解成“所有产品长一样”。真正健康的做法通常是：

- **共享语法**：字号、间距、圆角、焦点、信息层级、交互行为；
- **产品风格卡**：色板、材质、光源、装饰母题、图像处理。

风格卡不是主题。主题通常只换颜色；风格卡可以换一整套视觉语言，但不能换“按钮在哪里、焦点怎么走、错误怎么提示”。

一个风格卡至少应该登记：

- ID 和名称；
- 所属产品/纪元；
- 色板；
- 材质/光源/装饰参数；
- 源文件；
- 投影到各平台的产物；
- 对账方式（怎么保证源和投影一致）。

风格卡的价值在于：**让第二个产品不必重新发明一套设计系统，也不必假装自己和第一个产品一模一样。**

### 3.6 资产：字体、图标、图片、声音

资产是设计系统里最容易被忽略、也最容易出法律问题的部分。

- **字体**：授权范围、可嵌入、CJK 支持、回退字体、可变字体、加载性能；
- **图标**：网格、描边、光学对齐、命名、可访问名称、图标不是唯一语义；
- **插画/图片**：风格、比例、版权、AI 生成来源；
- **动效/声音**：时长、曲线、减少动态、音量、触发条件。

资产要有登记：来源、授权、可商用范围、修改记录。AI 生成资产还要标注模型/来源/人工修改程度。否则系统越成功，法务风险越大。

---

## 四、架构：一套源，多种投影

### 4.1 五层模型

一个跨介质的设计系统，通常可以分成五层：

1. **品牌核心**：我们是谁、相信什么、和谁说话；
2. **语法层**：颜色、字体、间距、圆角、动效、图标规则；
3. **组件与模式层**：按钮、表单、面板，以及搜索、登录、空状态；
4. **介质层**：Web、游戏、App、打印、实体；
5. **资产层**：字体、图标、插画、图片、声音。

上层决定“为什么”，中层决定“怎么组合”，下层决定“在某个平台怎么落地”。越往下，越具体；越往上，越稳定。

### 4.2 单一事实来源

“单一事实来源”不是“所有东西放一个文件”，而是：

> **同一个决策，只有一个权威出处；其他都是生成物或投影。**

例如：

- 颜色决策在 `tokens/core/sys.tokens.json`；
- Web 的 CSS 变量由它生成；
- Godot 的 theme 由它生成；
- App 的 JSON 由它生成；
- 文档里的色值由它生成。

生成物可以提交到仓库，但**不能手改**。CI 用 `--check` 比较“源生成的”和“仓库里的”，不一致就失败。

这听起来很工程，但它解决的是一个很设计的问题：**你永远不知道文档里的色号和代码里的色号哪个是真的。**

### 4.3 一条典型的 token 流水线

```text
设计决策
  ↓
tokens/*.json（源）
  ↓
schema 校验 / 别名解析 / 对比度检查
  ↓
生成 Web CSS / Godot JSON / App JSON / 文档
  ↓
产品消费（变量、组件、主题）
  ↓
产品侧检查（无裸值、对比度、焦点、Tab 走查）
  ↓
版本发布 / 变更日志 / 弃用
```

这条流水线最重要的是**闭环**：源变了，投影要变；投影变了，检查要能发现；检查失败了，不能靠“这次先这样”混过去。

### 4.4 多介质不是复制粘贴

- **Web**：CSS 变量 + 组件类 + 主题样式；
- **游戏**：Theme/资源 + 场景皮肤 + 运行时参数；
- **App**：平台无关 JSON + Swift/Kotlin 常量或运行时解析；
- **打印**：CMYK/专色、出血、字体嵌入、纸张；
- **实体**：材质、工艺、包装、印刷/注塑/金属处理。

每个介质都有自己的约束。设计系统不应该假装“一个 CSS 文件走天下”，而应该提供**同一语义在不同介质的投影规则**。

### 4.5 版本与稳定性

Token 和组件都应该有稳定性分级：

- **experimental**：可能改，别大规模用；
- **stable**：可以依赖，改动要遵循弃用窗口；
- **deprecated**：还能用，但会在某个版本移除；
- **removed**：已移除，文档保留迁移说明。

版本号建议遵循 SemVer：

- **major**：破坏性变更（删 token、改组件 API、改语义）；
- **minor**：新增能力（新组件、新 token、新变体）；
- **patch**：修复（对比度、bug、文档）。

产品要能 pin 版本。没有 pin，设计系统一升级，所有产品同时炸，这是最现实的治理风险。

## 五、从零开始：一条不容易翻车的路径

### 5.1 第 0 步：先盘点，不要先画

在动手之前，先回答：

- 现在有几个产品、几套视觉定义？
- 颜色、字体、间距、圆角分别有多少个值？
- 哪些组件重复出现？哪些只出现一次？
- 哪些地方已经出现无障碍问题（对比度、焦点、触控）？
- 谁会被这套系统影响？谁必须参与评审？
- 哪些老代码不能动？哪些可以逐步迁移？

盘点的目的不是“画一张大图”，而是找到**最痛的一两个重复**。如果盘点完发现没有重复，那就不该做系统。

### 5.2 第 1 步：定范围和原则

不要一上来做“全公司设计系统”。先定：

- **一个试点产品**，最好是你有权限改、且有真实用户的；
- **一个平台**，先 Web 或先游戏，不要同时开五个；
- **3–5 个组件**，选重复最多、最容易出错的；
- **5–8 条原则**，能裁决冲突；
- **一个 owner**，能对最终决定负责。

原则要写成“选 A 不选 B”的句子，而不是形容词。

### 5.3 第 2 步：做最小 token 地基

第一版 token 不需要上千个。通常 50–150 个就够：

- 一套背景/表面/文字/线；
- 一组行动/状态/焦点；
- 5–7 级字阶；
- 4–6 个间距；
- 2–3 个圆角；
- 1–2 个阴影；
- 2–3 个动效时长。

先做**能覆盖 80% 页面**的最小集。剩下的等真实需求出现再加。

第一版就要做对比度检查，不要等“以后优化”。焦点色要和强调色分开；触控目标要有下限；深色模式如果要支持，一开始就按语义映射，不要事后反相。

### 5.4 第 3 步：选一个真实页面迁移

不要先做“设计系统官网”，也不要先做“组件大全”。选一个真实页面，把它的颜色、字号、间距、圆角、焦点迁移到 token。

迁移时遵守：

- **不改变信息结构**，先只换取值；
- **一次只改一类**（先颜色，再字号，再间距）；
- **每改一类，跑一次检查/截图**；
- **老变量保留别名**，给迁移留时间；
- **发现视觉差异，先记录，不要偷偷改**。

这一步的目标不是“页面变漂亮”，而是证明“token 能覆盖真实页面，而且不破坏它”。

### 5.5 第 4 步：做 3–5 个组件，并在两个地方用

选组件时看两个指标：重复次数、出错代价。

- 按钮：几乎每个页面都有，状态多，最容易出现“主行动太多”；
- 表单字段：错误/帮助/只读/禁用，最容易出现无障碍问题；
- 面板/卡片：布局基础，容易滥用；
- 弹窗：焦点陷阱、Esc、滚动锁定，行为复杂；
- 导航：跨页面一致性要求高。

每个组件先写契约，再做实现，再在真实页面用。**一个消费者不算验证，两个消费者才算。**

### 5.6 第 5 步：把检查接进流程

设计系统最怕“写完就过期”。至少要有：

- token 结构/别名/字阶检查；
- 对比度/焦点分离检查；
- 产品侧裸值检查；
- 生成物一致性检查；
- 组件契约检查；
- 组件使用审计；
- 截图 + 键盘 Tab 走查。

检查不一定要多，但必须**自动、可复跑、失败会拦**。靠人记的规范，最后都会变成“这次先这样”。

### 5.7 第 6 步：发布、文档、治理

第一版发布不需要大张旗鼓，但要有：

- 版本号和变更日志；
- 迁移指南；
- 组件/ token 文档；
- 贡献和提问入口；
- 例外登记；
- 一个能拍板的人。

文档不要复制实现细节，要回答“什么时候用、为什么、不能用什么、怎么迁移”。最好的文档是**能直接运行/预览的示例**，不是一大段形容词。

### 5.8 一个 30 天最小计划

如果你今天就要开始，可以这样排：

- **第 1 周**：盘点 + 定原则 + 选试点 + 定 3 个组件；
- **第 2 周**：最小 token + 对比度/焦点检查 + 生成 CSS；
- **第 3 周**：迁移一个真实页面 + 做 3 个组件 + 两个消费者；
- **第 4 周**：文档 + 截图/Tab 走查 + 版本发布 + 复盘。

不要在这 30 天里做：全组件库、全平台、设计系统官网、完美迁移、定制工具。

## 六、治理：让系统能活下去

### 6.1 治理不是官僚

很多人一听“治理”就想到审批、委员会、流程。好的治理恰恰相反：**它让正确的做法更容易，让错误的做法更早被发现。**

治理要回答四个问题：

1. 谁可以改什么？
2. 一个新需求怎么进系统？
3. 出现例外怎么办？
4. 版本怎么发、怎么弃用？

如果这四个问题没有答案，系统就会变成“谁都能改，谁都不负责”。

### 6.2 角色

不需要很大的团队，但需要明确的责任：

- **设计主控/系统 owner**：对语义、组件契约、视觉一致性有技术否决权；不是“画得最好的人”，而是“最能把关的人”；
- **产品负责人**：决定产品优先级，接受迁移成本；
- **工程师**：实现、性能、可访问性、跨端；
- **无障碍/内容专家**：在关键组件和模式上评审；
- **用户**：真实使用反馈，不是“内部觉得好用”。

一个人可以兼多个角色，但**最终拍板的人只能有一个**。委员会适合收集意见，不适合做最终决定。

### 6.3 决策类型：单向门与双向门

- **单向门**：改了就很难回头，比如 token 命名体系、组件 API、品牌核心色。要慢，要评审，要写决策记录。
- **双向门**：可以快速试错，比如某个页面的布局、临时样式、实验性组件。要快，要允许回滚。

把双向门当单向门，团队会被流程拖死；把单向门当双向门，系统会在半年后无法维护。

### 6.4 贡献流程

一个可运行的贡献流程通常长这样：

1. **提案**：解决什么问题？影响哪些产品？有没有现有模式可复用？
2. **评审**：设计主控 + 工程 + 无障碍；看契约、token、迁移成本；
3. **试点**：在至少一个真实产品用；记录问题；
4. **发布**：版本、变更日志、迁移指南；
5. **观察**：使用量、问题、是否需要弃用。

不是每个改动都要走完整流程。小修小补可以快；新增组件、改语义、删 token 必须慢。

### 6.5 例外与设计债

例外不可怕，静默才可怕。

每个例外至少记录：

- 违反了什么规则；
- 为什么必须例外；
- 谁负责；
- 什么时候到期；
- 怎么收口。

例外要有到期日，到期不处理就阻塞下一次设计评审。否则“临时例外”会变成永久债务。

设计债也一样：不是“以后再说”，而是有清单、有优先级、有 owner。设计债和代码债一样，会复利。

### 6.6 文档与决策记录

设计系统最容易过期的不是代码，是文档。

文档至少分三类：

- **规范**：必须遵守的规则（token、组件契约、无障碍）；
- **指南**：怎么用、什么时候用、反例；
- **决策记录**：为什么这么定、当时放弃了什么。

决策记录特别重要。一年后有人问“为什么焦点不用品牌绿”，如果只有结论没有原因，讨论会重新开始；如果有记录，可以直接回答“因为焦点和强调必须分离，避免状态混淆”。

## 七、无障碍：不是最后一步

### 7.1 为什么设计系统必须管无障碍

无障碍不是“给少数人用的附加功能”。它是**界面在更多条件下仍然可用**：

- 键盘用户；
- 屏幕阅读器用户；
- 低视力/色觉差异用户；
- 运动障碍用户；
- 在强光下看手机的人；
- 用 200% 字号的人；
- 临时受伤、环境嘈杂、网络很差的人。

设计系统如果只做“正常状态”，每个产品都要重新补无障碍，最后一定补不齐。

### 7.2 几条硬底线

- **文字对比度**：普通文字至少 4.5:1，大字号至少 3:1；
- **UI 对比度**：控件边界、焦点、图标至少 3:1；
- **焦点可见**：键盘焦点必须有清晰的 outline，不能只靠颜色变化；
- **焦点独立**：焦点色不要复用品牌强调色，否则“选中/聚焦/强调”会混淆；
- **触控目标**：至少 44×44（iOS pt）/ 48×48（Android dp），视觉可以更小，命中区不能；
- **文字缩放**：200% 不裁切、不重叠；
- **减少动态**：尊重系统设置，动画不是唯一状态信号；
- **语义**：按钮是 button，链接是 link，标题有层级，表单有 label；
- **错误**：错误信息与字段关联，能被屏幕阅读器读出；
- **不要只靠颜色**：状态要有文字/图标/形状辅助。

这些不是“设计系统独有的规则”，但设计系统是把它们**变成默认值**的最佳位置。

### 7.3 怎么测

- **键盘**：只用 Tab/Shift+Tab/Enter/Space/Esc，能否完成主任务？
- **屏幕阅读器**：VoiceOver/TalkBack/NVDA，能否读出名称、角色、状态、错误？
- **缩放**：200%/400%，是否重叠、裁切、丢内容？
- **对比度**：自动检查 + 人工看关键页面；
- **减少动态**：打开系统设置，动画是否还能传达状态？
- **真机**：至少一台 iOS + 一台 Android；Web 至少一个桌面 + 一个移动尺寸。

设计系统要把这些写进组件契约，而不是等产品上线前“补无障碍”。

## 八、多产品、多品牌：统一语法，不统一皮肤

### 8.1 一致的层次

多产品设计系统最容易走两个极端：

- **完全统一**：所有产品长一样，品牌失去个性；
- **完全放开**：每个产品一套，系统名存实亡。

更好的中间态是：

| 层级 | 是否统一 |
| --- | --- |
| 语义（什么是危险、什么是主行动） | 统一 |
| 交互语法（焦点、键盘、错误提示） | 统一 |
| 字号/间距/圆角/触控 | 统一或有限变化 |
| 色板/材质/光源/装饰 | 产品风格卡 |
| 图像/插画/声音 | 产品风格卡 + 资产规范 |

### 8.2 品牌架构

如果有母品牌和子品牌，需要明确：

- 母品牌提供什么背书？（信任、品质、价值观）
- 子品牌可以改什么？（色板、语气、图形）
- 哪些资产必须共用？（标志、字体、法务信息）
- 哪些不能共用？（避免子品牌互相污染）

设计系统不必解决品牌命名，但必须能表达“共享核心 + 产品差异”。

### 8.3 风格卡登记

风格卡要有登记表：

- ID；
- 产品；
- 模式（Archive/Console/…）；
- 色板；
- 材质/光源参数；
- 源文件；
- 各平台投影；
- 对账检查器。

没有登记，风格卡会变成“某个设计师电脑里的 JSON”；没有对账，源和投影会分叉。

## 九、常见失败模式

### 9.1 先造库，后找用户

做了 30 个组件，只有 3 个被用。正确顺序是“真实需求 → 最小组件 → 两个消费者 → 扩展”。

### 9.2 Token 命名按值，不按语义

`--blue-500` 在品牌换成橙色后毫无意义；`--action-primary` 才能活下来。

### 9.3 把系统当警察

“你不能用这个颜色”“你必须用那个组件”——如果系统只带来限制，不带来速度，团队会绕过它。好的系统应该让正确做法**更省事**。

### 9.4 没有 owner

设计系统是产品，不是项目。没有 owner，就没有人回答“这个需求该不该进系统”“这个例外什么时候收口”。

### 9.5 文档和代码分家

文档写 6px 圆角，代码是 8px；文档写 `--teal`，代码是 `#3FB8AB`。最后没人知道该信谁。生成物 + 检查器是解药。

### 9.6 大爆炸迁移

一次改完所有页面，风险极高。更好的方式是：先新页面，再老页面；先颜色，再字号；先一个产品，再第二个产品。

### 9.7 无障碍最后补

上线前才发现对比度不够、焦点不可见、触控太小，改动成本最高。把无障碍写进 token 和组件契约，一开始就做对。

### 9.8 追工具，不追问题

Figma、Storybook、Tokens Studio、Style Dictionary 都是工具。工具不解决“谁决策、谁维护、怎么迁移”。先有问题，再选工具。

### 9.9 过度设计

一上来做五层架构、十个平台、全组件库、设计系统官网。最后没有真实消费者，系统变成“展示品”。

### 9.10 没有度量

不知道有没有人用、有没有减少重复、有没有减少 bug，就无法判断系统是否值得继续投入。

---

## 十、怎么判断它有没有用

设计系统不是“做完就算成功”。可以看几类指标：

### 10.1 采用度

- 有多少产品/页面使用了 token/组件？
- 新页面从设计到上线，有多少比例直接用系统组件？
- 组件实例数、token 引用数是否在增长？

### 10.2 一致性

- 产品侧还有多少裸色值/裸尺寸？
- 同一个语义是否还有多个实现？
- 焦点、错误、禁用状态是否一致？

### 10.3 质量

- 对比度/焦点/Tab 走查缺陷数；
- 无障碍问题复发率；
- 视觉回归/截图差异；
- 线上 UI bug 数量。

### 10.4 效率

- 新页面搭建时间；
- 设计到开发的 handoff 时间；
- 组件复用率；
- 迁移成本。

### 10.5 健康度

- 文档是否过期（链接/生成物检查）；
- 贡献/提问/例外数量；
- 版本发布节奏；
- 有多少“临时例外”到期未收口。

不要只看“组件数量”和“文档页数”。那是产出，不是效果。

## 十一、AI 时代的设计系统

AI 让设计系统变得更重要，而不是更不重要。

原因很简单：AI 可以在一分钟内生成十个页面、二十个按钮变体、五十种文案。如果没有 token、契约、检查器，它也会在一分钟内制造五十种不一致。

AI 适合做：

- 盘点现有颜色/组件/重复；
- 生成 token 映射、迁移 codemod；
- 起草组件契约、文档、变更日志；
- 跑截图对比、Tab 走查、对比度检查；
- 把设计决策转成检查规则。

AI 不适合替代：

- 品牌判断；
- 真实用户研究；
- 无障碍的人工测试；
- 最终责任；
- 对“什么该进系统”的政治/资源判断。

和 AI 协作时，最重要的不是“提示词写得多漂亮”，而是**给它可执行的边界**：

- 单一事实来源（token JSON）；
- 组件契约；
- 禁止裸值；
- 检查命令；
- 示例/反例；
- 变更日志和版本规则；
- 明确的文件组织。

这也是为什么设计系统文档要写给 AI 看：不是让 AI “自由创作”，而是让它知道**什么不能做**。

---

## 十二、一个最小启动清单

如果你今天要开始，先不要问“我们要不要做设计系统”，先问“我们能不能在两周内做出一个真实页面能用的最小系统”。

最小清单：

- [ ] 1 个试点产品；
- [ ] 1 个 owner；
- [ ] 5–8 条能裁决冲突的原则；
- [ ] 50–150 个 token；
- [ ] 1 套对比度/焦点检查；
- [ ] 3 个组件契约；
- [ ] 2 个真实消费者；
- [ ] 1 份使用文档 + 反例；
- [ ] 1 个版本号和变更日志；
- [ ] 1 次截图 + Tab 走查。

如果这些都能做到，再谈第二个产品、第二个平台、组件库扩展、设计工具集成。

## 十三、一个实践案例：LRDS

最后用我们自己的工作做个简短案例，说明这些概念怎么落地。

LRDS 是 LiveRefu 的设计系统，服务网站、Godot 游戏、未来的 App，以及更远的打印/实体。它现在的状态（截至 2026-10-21）大致是：

- **229 个 token**：ref 68 / sys 99 / product 62；
- **4 张风格卡**：未来档案、未来残片、LiveFab、明日频道；
- **3 个组件契约**：button / form-field / panel；
- **2 个 Web 产品接入**：网站、LiveFab；
- **1 个 Godot 产品接入**：未来残片；
- **1 个 App kit 起步**：平台无关 `app/tokens.json`，但还没有真实 App 消费者；
- **1 个 HUB**：一页式可视化总览，支持系统/亮色/暗色；
- **多道闸门**：token 结构、对比度、裸值、生成物、风格卡、组件契约、使用审计、HUB 对账；
- **版本**：v0.2.0 已发布，v0.1.0 补记，v0.3 还在进行。

它做对的几件事：

1. **先收编，再统一**：没有推翻网站/游戏原有视觉，先把语义对齐，再换取值；
2. **单一事实来源**：JSON 生成 CSS/Godot/App，生成物有 `--check`；
3. **真实试点**：网站和游戏先接，不是先造库；
4. **焦点独立**：把“焦点=品牌绿”改成独立蓝，这是可访问性上的真实修复；
5. **风格卡**：四张卡共享语法，但保留产品差异；
6. **契约 + 检查**：组件不是画完就算，有状态、键盘、token、使用审计；
7. **HUB**：让人能一页看完，不用翻十几个文档。

它还没做好的：

- 没有真实 App 消费者，App kit 只是“可接入”；
- Form Field 只有网站搜索框一个消费者；
- 打印/实体还只是路线；
- Archive 亮色模式还没有产品级落地；
- 组件库还很小，但这是有意的——没有需求就不扩。

这个案例想说明的不是“LRDS 很完整”，而是：**设计系统可以从小处开始，但每个小处都要有真实消费者、可执行规则和诚实的边界。**

## 十四、术语表

**Token**：给设计决策起的、可复用的名字，例如 `sys.color.action.primary`。

**Semantic token**：按角色命名的 token，不按具体色值命名。

**Component contract**：组件的解剖、变体、状态、键盘、无障碍、token 清单和使用边界。

**Pattern**：完成一类任务的组合配方，例如搜索、登录、空状态。

**Style card**：产品的视觉皮肤，包含色板、材质、光源、装饰，但不改变交互语法。

**Theme / mode**：主题是品牌/产品风格；模式是深色/浅色/高对比等显示条件。

**Design debt**：为了短期交付而留下的设计/实现不一致，需要登记和收口。

**Governance**：谁决策、怎么贡献、怎么版本化、怎么弃用。

**Adoption**：真实产品/页面使用设计系统的程度。

**Single source of truth**：同一个决策只有一个权威出处，其他是生成物/投影。

**Generated artifact**：由源生成的 CSS/JSON/文档，不应手改。

**Deprecation**：有计划地停止某个 token/组件，给迁移窗口。

**A11y（Accessibility）**：让更多人在更多条件下能使用产品，不只是“残疾人专用”。

## 十五、结语

设计系统最难的部分，从来不是“把按钮画好看”。

难的是：

- 在多个产品之间找到“该统一什么、该放开什么”；
- 让规则可执行，而不是停留在文档；
- 让系统有 owner、有版本、有迁移、有例外；
- 在速度和一致性之间做取舍；
- 在 AI 能无限生成界面的时代，仍然知道什么值得保留。

如果要用一句话总结：

> **设计系统是把“我们反复做的判断”变成“大家可以依赖的语言”，然后让这门语言持续演化。**

它不需要一开始就很大。一个真实页面、三个组件、五十个 token、一条检查、一个 owner，就可以开始。

但它需要诚实：哪些做了、哪些没做、哪些只是“可接入”、哪些还没有真实消费者。一个诚实的系统，比一个看起来完整、实际没人用的系统，有价值得多。
