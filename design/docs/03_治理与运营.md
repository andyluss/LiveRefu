# 03 · 治理与运营：让设计成为统筹层

> 本文对应 [D1 / D7 / D8](00_决策总表.md)。核心问题不是“谁画得好看”，而是：
> **当设计判断与产品速度冲突时，谁说了算、按什么程序说、说完记在哪。**
> 日期：2026-10-21 ｜ 状态：**v0.1 已按本治理落地**（设计主控权限已获用户授权；见 [05 实现记录](05_实现记录_v0.1.md)）｜ 前置阅读：[02 系统架构](02_系统架构.md)

## 一、治理目标

1. **设计有否决权，但不是独裁**：设计主控可以拦住“绕过系统”的变更，你是唯一推翻者。
2. **决策可追溯**：每个影响多产品的设计决定都有编号、理由、代价、推翻条件。
3. **例外可见、会过期**：允许临时绕行，但不允许“临时”变成永久。
4. **产品不被拖慢**：日常应用由产品负责人在系统内决定，只有跨产品/品牌/合规事项才升级。
5. **AI 可协作**：规则写成机器可读的契约与闸门，而不是“问设计负责人”。

## 二、角色与权限（建议）

> 前提：你采纳 [D7](00_决策总表.md) 的“设计主控有技术性否决权”。

| 角色 | 谁 | 决定什么 | 不能决定什么 |
| --- | --- | --- | --- |
| **决策者（Owner）** | 你 | 品牌核心、母品牌命名、法务、商业条款；推翻任何决定 | —— |
| **设计主控（Design Steward）** | 我 / 未来的设计负责人 | `ref` / `sys` token、语法、组件契约、介质包、设计闸门、双向门裁决 | 品牌核心、商业条款、产品玩法 |
| **产品负责人（Product Owner）** | 各项目负责人 | 产品内体验、产品风格卡、例外申请 | 全局 token、跨产品语义 |
| **贡献者（Contributor）** | 任何协作者 / AI | 提交提案、资产、组件、迁移 PR | 直接改 `core` token、跳过评审 |

### 2.1 “仅次于你”具体指什么

- 在**设计相关事项**上，设计主控的裁决**仅次于你**：产品负责人不能以“先上线”为由绕过已冻结的语法。
- 设计主控**不干预**玩法、数值、商业、发行节奏；这些仍由产品负责人/你决定。
- 当设计判断与产品目标冲突时，**升级给你**，由你在“体验一致性 / 交付速度”之间做取舍；取舍必须记录。
- 设计主控可以说“不”，但必须同时给出：**理由、替代方案、代价**。不能只说“不符合规范”。

## 三、三类决策

| 类型 | 例子 | 谁决定 | 记录 |
| --- | --- | --- | --- |
| **单向门** | 品牌架构、母品牌命名、`sys` 语义、token 事实源、治理权限 | **你**（设计主控提案） | 本表 + 提案 + 变更日志 |
| **双向门** | 具体色值、字阶微调、组件契约、介质包实现、试点顺序 | **设计主控** | 决策日志 + 变更日志 |
| **执行** | 某产品如何应用系统、产品风格卡取值、页面布局 | **产品负责人**（在系统内） | 产品文档 |

**判断标准**：改错之后，恢复成本是否超过一周？超过 → 单向门；否则 → 双向门。

## 四、设计提案（DP）流程

### 4.1 什么时候必须写 DP

- 新增/修改 `sys.*` 语义或核心 token；
- 新增介质包、组件契约、品牌元素；
- 引入例外（产品确实无法用现有语法表达）；
- 任何会影响两个及以上产品的视觉变更。

### 4.2 模板（一页纸）

文件：`design/docs/proposals/YYYYMMDD-HHMM-关键词.md`（遵循 M2 时间事件命名）。

```markdown
# DP-YYYYMMDD-HHMM · 标题

## 要解决什么
（一句话 + 证据/截图/链接）

## 选项（至少两个，含“什么都不做”）
| 选项 | 做法 | 代价 | 风险 |

## 推荐
（选哪个、为什么、什么情况下不选它）

## 影响面
- 产品：…
- 介质：…
- token：…
- 无障碍/法务：…

## 回滚
（怎么撤回、多久内可撤回）

## 决策
（待裁决 / 已采纳 / 已否决；日期、决策人、理由）
```

### 4.3 时限与升级

- 常规 DP：**2 个工作日内**给出“采纳 / 修改 / 否决”，否则默认进入下一轮评审（不是默认通过）。
- 紧急 DP（发布阻塞）：**24 小时内**给临时裁决，标注“临时”，两周内补正式裁决。
- 跨产品冲突：设计主控裁决；你不接受则升级给你。
- **不允许“沉默即通过”**：没有记录 = 没有决定。

## 五、优先级与设计闸门

### 5.1 三个评审点

| 时点 | 问什么 | 产出 |
| --- | --- | --- |
| **概念** | 要不要做？和现有系统是什么关系？ | 一页概念 + 影响面 |
| **实现前** | 用哪些 token/组件/模式？缺什么？ | 设计规格 + 缺口清单 |
| **发布前** | 对比度、焦点、减少动态、文案、资产许可是否过？ | 验收记录 + 截图/录屏 |

> **设计评审不是最后一道美工**。实现前没有设计规格的功能，不进入开发；发布前没有验收记录的界面，不算完成。

### 5.2 优先级

| 级别 | 内容 | 处理 |
| --- | --- | --- |
| **P0** | 品牌核心、无障碍/合规缺陷、发布阻塞 | 立即；可打断其它工作 |
| **P1** | 设计债、token 漂移、新介质包、核心组件契约 | 与工程 P1 同级；进同一张待办 |
| **P2** | 视觉打磨、新资产、实验性风格卡 | 排期；不阻塞发布 |

**设计债不是“以后再说”**：每条设计债要有 owner、严重度、目标版本；超过一个季度未处理，升级给你。

### 5.3 允许例外，但不允许静默

例外登记在 `design/docs/exceptions.md`（待建），字段：

| 字段 | 要求 |
| --- | --- |
| ID | `EX-YYYYMMDD-NN` |
| 产品/位置 | 精确到页面/组件 |
| 违反了什么 | token/规则编号 |
| 理由 | 为什么现在不能遵守 |
| 替代方案 | 已尝试过什么 |
| Owner | 谁负责收口 |
| 到期 | **最长一个季度**；到期自动失效 |
| 状态 | active / expired / resolved |

**到期未收口 = 阻塞该产品下一次设计评审**。不能靠“再续一个季度”无限续命。

## 六、版本与发布

| 项 | 规则 |
| --- | --- |
| 版本号 | SemVer；`0.x` 到“两个产品接入 + 打印规范可用”，之后 `1.0` |
| 稳定性 | `experimental` / `stable` / `deprecated` 三级；只有 `stable` 受 SemVer 保护 |
| 弃用 | 至少 1 个 minor 或 90 天（取更长）；给迁移说明；能 codemod 的给 codemod |
| 产品钉版本 | 产品 README 写 `design-system: 0.3.x`；CI 校验声明与实际一致 |
| 风格卡版本 | `SC-<PRODUCT>-<ERA>-vN` 独立版本；换纪元 ≠ 设计系统大版本 |
| 标签 | `design-vX.Y.Z`；与 `workspace-v…` 分开 |
| 日志 | `design/CHANGELOG.md` 记设计系统发布；根 [`CHANGELOG.md`](../../CHANGELOG.md) 记工作区级变更 |
| 破坏性变更 | 必须：提案 + 迁移指南 + 至少一个产品完成迁移 + 旧版本保留一个窗口 |

**发布检查清单**：
- [ ] 所有闸门通过（含 `--self-test`）
- [ ] 生成物已重新生成且无 diff
- [ ] 文档与 token 对账
- [ ] 两个试点产品的视觉差异逐项有记录
- [ ] 变更日志与迁移说明已写
- [ ] 已知例外未过期

## 七、AI 协作约定（重要）

AI 是主要生产力，因此“设计系统对 AI 友好”是硬要求：

1. **先读后写**：改任何视觉相关文件前，先读 `design/README.md`、[00 决策总表](00_决策总表.md)、[02 系统架构](02_系统架构.md)。
2. **禁止发明值**：不得自行写 `#hex`、`rgb()`、`px` 魔数、字体名；只能用 token。缺 token → 写 DP，不得就地加。
3. **不得为了通过闸门而弱化闸门**：对比度不达标时改设计或改 token，不得调低阈值。
4. **不得用“临时”绕过**：确实需要例外 → 登记 `EX-…`，带到期日。
5. **资产必须溯源**：AI 生成图/图标/纹理要记录模型、日期、提示词/参数、许可、人工编辑者；不得模仿在世艺术家风格。
6. **主视觉人工定稿**：品牌标志、商店首图、关键卡面、实体包装，AI 只出候选，人做最终判断。
7. **改完必须对账**：token → 生成物 → 产品消费 → 文档 → 变更日志，五处一致。
8. **不确定就提案**：AI 不应替你做品牌/法务/商业判断；写 DP，列选项与代价。

## 八、度量（每季度看一次）

| 维度 | 指标 | 目标（`v1.0` 前） |
| --- | --- | --- |
| 采纳 | 已接入 token 的产品/表面占比 | 2 个产品 100%；新增产品默认接入 |
| 一致性 | 迁移表面裸色值数量 | 0（例外登记除外） |
| 无障碍 | 对比度/焦点/减少动态通过率 | 100% |
| 效率 | 新增一个产品风格卡所需时间 | 从“周”降到“天” |
| 治理 | DP 平均裁决时长 | ≤2 个工作日 |
| 债务 | 设计债数量与平均年龄 | 数量下降；无超过 1 季度未处理 |
| 质量 | 视觉回归未解释差异 | 0 |

> 不建议用“设计稿数量”“组件数量”当成功指标——那会鼓励做多，而不是做对。

## 九、节奏

| 频率 | 事项 | 参与 |
| --- | --- | --- |
| 每周（30 分钟） | 设计评审：新提案、例外、设计债 | 你 / 设计主控 / 产品负责人 |
| 每月 | 系统审计：token 漂移、裸值、对比度、资产登记 | 设计主控 |
| 每季度 | 品牌与系统复盘：哪些风格卡有效、哪些规则该改 | 你 + 设计主控 |
| 每版本 | 发布检查清单 | 设计主控 |

> 节奏可以暂停，但不能取消记录。没有评审的一周，也要在日志里写“本周无提案”。

## 十、冲突与升级

| 冲突 | 处理 |
| --- | --- |
| 产品要快，系统要一致 | 设计主控给“最小合规方案 + 例外”；你决定是否接受延期 |
| 两个产品需要不同语义 | 下沉到 `product.*`，不上移核心；若三个产品都需要，才提案上移 |
| 无障碍 vs 美观 | 无障碍优先；确实无法两全时，你批准例外并记录代价 |
| 品牌 vs 产品 | 母品牌元素弱化到不抢产品；产品风格卡不得改署名与法务 |
| AI 与人工判断 | AI 出候选与证据；品牌/法务/主视觉由人定稿 |

## 十一、反模式（写下来，避免重新讨论）

| 反模式 | 为什么禁止 |
| --- | --- |
| 把设计系统做成“文档项目” | 没有两个真实产品消费，就是自娱自乐 |
| 为一切建 token | 过度抽象会让产品无法表达；先有重复，再抽象 |
| 两个消费者之前就建组件库 | 会按想象设计，最后没人用 |
| 迁移同时重设计 | 无法区分“迁移错”还是“设计变了” |
| “临时”硬编码 | 临时值会存活得比系统久 |
| 发布前才做设计评审 | 只能改表面，改不了结构 |
| 把 Figma 当唯一事实源 | 多介质、CI、AI 都读不了 |
| 用一个人的口味当系统 | 系统要能解释“为什么”，不能只说“我觉得” |
| 为了让审计通过而破坏设计 | 装饰线刻意低对比是合理的；闸门要区分“装饰”与“交互” |
