## 四、逐条说明

### D1 · 设计系统的定位

**建议：A. 治理系统**——它管“品牌核心、语法、组件契约、介质适配、资产、评审与版本”，不是一张配色表。

| 备选 | 为什么不全选它 | 代价 |
| --- | --- | --- |
| B. 品牌资产库（logo/色/字体） | 管不住组件与介质，产品仍会各写各的 | 一年后回到四套 token |
| C. 纯 token 规范 | 管得住代码，管不住标志、语气、包装、评审 | 实体产品无法落地 |
| **A. 治理系统（推荐）** | 前期要写流程、建闸门，见效比“换皮”慢 | 需要你授予 D7 的权限 |

**代价**：设计从“出图”变成“定规则 + 评审 + 守闸门”，前期有一段看不见成果的投入。
**推翻条件**：若两个试点证明流程成本高于收益，降级为“token + 品牌资产库”，保留闸门。

### D2 · 品牌架构

**建议：B. 母品牌背书 + 产品子品牌**（endorsed brand）。

```
LiveRefu（母品牌 / 出品方）
├── 未来档案       网站 / 知识库
├── 未来残片       主线游戏
├── 明日频道       陪伴应用
├── LiveFab        内部平台
└── Refu Supply    实体产品线（工作名，非最终名）
```

- **母品牌固定**：字标/徽记、署名格式（“LiveRefu 出品” / “A LiveRefu project”）、版权行、联名规则、法务标记。
- **产品可变**：产品名、风格卡、强调色、材质、语气细节。
- **系统内部代号**：`LRDS`（LiveRefu Design System），只用于版本与文件名；**公开母品牌名不现在定**，等首个公开里程碑后再定，避免过早承诺。
- **中文名（暂定）**：**青橙设计**——青/橙是复古未来常用色；只作暂定中文名，不替代公开母品牌名；代码/资产名仍为 `LRDS`。

| 备选 | 为什么不选 | 代价 |
| --- | --- | --- |
| A. 单一品牌（所有产品同一视觉） | 会把“复古未来”压成一种风格，与已裁决的“纪元风格卡”冲突 | 游戏/应用/实体互相拖累 |
| C. 多品牌独立（house of brands） | 每个产品重新建立认知，复利消失 | 长期获客成本最高 |
| **B. 母品牌背书（推荐）** | 需要设计一套“弱但可识别”的母品牌元素 | 前期要定署名与标志规则 |

**代价**：母品牌元素必须“弱到不抢产品”，又要“强到能被记住”，这需要真正的设计判断。
**推翻条件**：若母品牌名最终改变，`LRDS` 与产品子品牌不受影响；标志与署名模块可单独替换。

### D3 · 系统模型：五层 + 三层 token

**建议：A. 五层模型**：

| 层 | 内容 | 可变性 |
| --- | --- | --- |
| **L0 品牌核心** | 定位、承诺、语气、标志、署名、法务 | 极少变（单向门） |
| **L1 语法层** | 语义角色、字阶、间距、形状、动效、图标、网格、无障碍下限 | 稳定（版本化） |
| **L2 组件与模式** | 组件解剖、状态、交互契约、页面模式 | 按需增长 |
| **L3 介质适配** | Web / Godot / App / Print / Physical 的落地包 | 每介质独立演进 |
| **L4 资产库** | 标志、图标、插画、摄影、3D、纹理、模板 | 持续积累 |

**三层 token**：

| 层 | 例子 | 谁可以改 |
| --- | --- | --- |
| `ref.*` 原始值 | `ref.color.ink.950 = #0B0F14`、`ref.space.4 = 4px` | 设计主控（低频） |
| `sys.*` 通用角色 | `sys.color.bg.base`、`sys.color.action.primary`、`sys.color.focus` | 设计主控（中频） |
| `product.*` 产品语义 | `future-debris.color.power`、`tomorrows-channel.color.phosphor` | 产品负责人 + 设计主控 |

> **关键规则**：`power` / `residue` 这类玩法语义**不进核心层**；它们映射到 `sys.color.action.primary` / `sys.color.feedback.danger`。这样新产品不必继承游戏的词，也不会把“电力”误当品牌色。

**双字阶**：UI 用 5 级（游戏/应用够用）；长文/印刷用 7 级编辑字阶。两者共享基准与对比度规则，避免把长文硬塞进 5 级。

**代价**：比“一套 CSS 变量”复杂；需要生成器与文档。
**推翻条件**：若产品数长期不超过 3 个，可把 L2/L3 合并，但 `ref/sys/product` 三层建议保留。

### D4 · 单一事实来源

**建议：A. JSON token 为源，生成各端产物，CI 对账**。

```
design/tokens/core/{ref,sys}.json + design/tokens/products/*.json
        │  build_tokens.ts（解析别名、校验 schema）
        ▼
design/tokens/dist/
  ├── web/future-archive.css  → 网站
  ├── web/livefab.css         → LiveFab 门户
  ├── godot/tokens.json       → 《未来残片》主题生成器
  └── docs/tokens.md          → 自动生成的 token 参考
  （print/* 计划 v0.3）
        │
        ▼
产品消费 + CI：schema / 对比度 / 无裸色值 / 生成物无 diff / 文档对账
```

- **格式**：DTCG 风格的 JSON（`$value` / `$type` / 别名 `{ref.color.neutral.0}`），不绑定某个商业工具。
- **Figma 可选**：Figma 是设计面，不是事实源；变量导出为 JSON，反向不同步。
- **生成物提交**：便于产品直接消费、可审计、不要求 Godot CI 装 Node；CI 重新生成并 `git diff --exit-code`。
- **打印不自动“算”专色**：sRGB→CMYK 只是近似；实体必须打样，专色用人工维护的 `print/spot-colors.json`（含 Delta E 容差）。

| 备选 | 为什么不选 | 代价 |
| --- | --- | --- |
| B. Figma 当源 | 多介质、CI、AI 读写都弱；订阅/导出限制 | 工具锁定，实体更难 |
| C. CSS / Tailwind config 当源 | 游戏与印刷读不了 | 又回到多套定义 |
| **A. JSON 为源（推荐）** | 要维护生成器 | 一次性工程投入，长期最省 |

**代价**：生成器本身要自检；否则“生成错了”比“手写错了”更隐蔽。
**推翻条件**：若 DTCG 标准发生破坏性变化，保留自有 schema 的兼容层，不追标准。

### D5 · 视觉基调

**建议：C. 双模：Archive（档案纸）+ Console（仪表盘）**，共享同一套语法。

| 模式 | 用于 | 气质 | 底色 | 文字 |
| --- | --- | --- | --- | --- |
| **Archive** | 网站长文、知识库、印刷、实体包装、品牌书 | 档案纸、油墨、登记章、编辑感 | 暖白纸 | 近黑墨 |
| **Console** | 游戏、应用、LiveFab、仪表/控制界面 | 仪表盘、荧光、扫描线、技术档案 | 深空蓝黑 | 奶油白 |

**共享的“母品牌语法”**（两模都不变）：
- 网格与登记标记（registration marks）、文件编号/档案号、页脚元数据；
- 字体角色：**Sans 负责阅读，Mono 负责元数据与数字，Serif 可选用于编辑/印刷**；
- 4 基数间距、4/8 圆角、1.5px 交互描边、24px/1.5 图标；
- 语义色角色固定：`action`（青）、`info`（冷蓝）、`success`（绿）、`warning`（琥珀）、`danger`（放射橙红）、`focus`（独立亮蓝，**不得复用 action**）；
- 动效：120 / 220 / 420ms，标准/强调两条曲线；必须响应减少动态效果。

**产品风格卡**只换：强调色相、材质隐喻、图像处理、装饰母题、UI 外壳、字体族（字阶不变）。
- 未来残片：原子纪元 = 镀铬 + 搪瓷 + 塑料；Console 模式。
- 明日频道：磁带/收音机 = 暖棕 + 米色 + 琥珀；Console 模式（暖色变体）。
- 未来档案：Archive 为主、Console 为辅（可切换/跟随系统）。
- LiveFab：Console，低装饰、功能优先。
- 实体：Archive/Print，CMF 与纸张决定质感。

| 备选 | 为什么不选 | 代价 |
| --- | --- | --- |
| A. 纯 Console（暗色仪表） | 长文阅读、印刷、实体都吃亏；容易变成“赛博朋克”单一风格 | 网站与实体要另起一套 |
| B. 纯 Archive（纸感） | 游戏/应用的“仪表感”与夜间使用体验弱 | 游戏要另起一套 |
| **C. 双模（推荐）** | 前期要设计两套表面规则 | 一次投入，覆盖全部介质 |

**代价**：双模容易慢慢分叉；必须靠同一套 token 与视觉回归闸门守住。
**推翻条件**：若两个试点证明双模维护成本过高，保留 Archive 为品牌/印刷、Console 为产品界面，但共享 token 不变。

### D6 · 介质优先级

**建议：A. `v0.1` 做 Web + Godot；打印/实体先架构、后实现；App 次之。**

| 阶段 | 介质 | 理由 |
| --- | --- | --- |
| `v0.1` | **Web + Godot** | 两个最成熟的产品，正好覆盖“阅读”与“游戏”两种极端；能验证双模 |
| `v0.2` | **App（iOS/Android）** | 触控、安全区、平台规范与 Web 差异大；等语法稳定后再做 |
| `v0.3` | **Print** | 需要纸张、专色、打样、条码/法务；不是写代码能解决的 |
| `v0.4` | **Physical** | 需要 CMF、模具/打样、供应链、合规；先做包装与周边，再做工业设计 |

**但架构现在就要预留**：打印字阶、CMYK/专色、出血/裁切线、CMF token、材质与工艺、包装结构、条形码/合规位。否则会做成“数字专用系统”，实体阶段推倒重来。

**代价**：实体产品若很快上马，`v0.3/v0.4` 需要提前；但提前做没有打样能力也会空转。
**推翻条件**：若实体产品有明确上市时间，倒排 `v0.3`，并把打印/CMF 提前到 `v0.2`。

### D7 · 治理权限

**建议：A. 设计主控（Design Steward）拥有“技术性否决权”，你是唯一推翻者。**

| 角色 | 权力 | 不拥有 |
| --- | --- | --- |
| **决策者（你）** | 最终裁决；推翻任何决定；品牌核心与法务 | —— |
| **设计主控**（我/未来的设计负责人） | 拥有 token、语法、组件契约；可拦截“绕过 token / 破坏无障碍 / 无设计评审”的变更；批准双向门；维护决策日志 | 不能改品牌核心、不能改商业条款、不能替代产品负责人 |
| **产品负责人** | 在系统内决定产品体验；提出风格卡与例外申请 | 不能私自定义全局 token |
| **贡献者** | 提交设计提案（DP）、资产、组件 | 不能直接改 `core` token |

**三个评审点**：概念（要不要做）、实现前（怎么做）、发布前（做成什么样）。**设计评审不是最后一道美工，而是进入实现的前置条件。**

**例外机制**：允许例外，但必须登记 `owner / 理由 / 到期日`，**最长一个季度**；到期自动失效，不能静默续期。

**设计债**：与工程债同级（P1），进同一张待办；不允许“先上线，设计以后补”成为默认路径。

**代价**：会增加一次评审与一点流程摩擦；需要我敢于说“不”，也需要你接受偶尔的减速。
**推翻条件**：若你发现设计主控的判断拖慢关键发布，可把否决权降为“必须书面说明的反对权”，你保留裁决。

### D8 · 版本与稳定性

**建议：A. SemVer + 稳定性分级 + 弃用窗口 + 产品钉版本。**

- **版本**：`0.x` 直到“两个产品接入 + 打印规范可用”；之后 `1.0`。设计系统版本独立于产品版本。
- **稳定性分级**：`experimental`（可破坏）/ `stable`（遵守 SemVer）/ `deprecated`（只修安全与可访问性）。
- **弃用窗口**：至少 **1 个 minor 版本或 90 天**（取更长者）；必须给迁移说明；能 codemod 的给 codemod。
- **产品钉版本**：每个产品 README 声明 `design-system: 0.3.x`；CI 检查声明与实际消费一致。
- **风格卡独立版本**：`SC-ATOMIC-v1.2.0`；换纪元不等于设计系统大版本。
- **标签**：`design-vX.Y.Z`（与 `workspace-v…` 分开）；[`design/CHANGELOG.md`](../CHANGELOG.md) 记设计系统发布，根日志记工作区级变更。

**代价**：版本与迁移文档要持续维护；小团队容易偷懒。
**推翻条件**：若产品数量少、升级由你一人控制，可简化为“只维护 `latest` + 迁移备注”，但 `ref/sys` 的破坏性变更仍要记录。

### D9 · 资产与法务

**建议：A. 开源字体 + 自有图标 + 源文件登记 + AI 资产溯源。**

- **字体**：选 2+1 个开源许可家族（例如 Source Han Sans / Source Han Serif + IBM Plex Mono；最终以许可证核验为准）。Web 用子集自托管，游戏按许可嵌入，印刷买/确认商用条款。**品牌与印刷不得只依赖系统字体。**
- **图标**：自有几何图标集（24px、1.5px 描边、单色）；可从 OFL/ISC 图标集起步，但必须登记来源与修改。
- **资产源文件**：PSD/AI/Blend 等二进制**默认不进主仓库**；用 Git LFS 或外部对象存储 + `assets/manifest.json`（路径、哈希、许可、作者、版本）。仓库只提交 SVG/PNG/GLB 等可复算导出物与生成脚本。
- **AI 资产**：每条记录模型、日期、提示词/参数、许可、人工编辑者；**不得模仿在世艺术家风格**；主视觉、商店首图、品牌标志必须人工定稿。
- **实体**：Pantone/专色授权、商标检索、材料合规（如 CE / CPSIA / 食品接触）、模特与音乐授权；建 `references/legal-register.md`。

**代价**：前期要建登记表；资产管线比“把文件丢进仓库”慢一点。
**推翻条件**：若团队规模扩大、需要设计源文件强版本化，改用 Git LFS 全量托管，但仍保留 manifest 与许可字段。

### D10 · 首版范围与试点

**建议：A. 地基 + 两个试点；不做全家桶、不做换标。**

**`v0.1` 必须交付**：
1. `tokens/core/{ref,sys}.json` + 一个产品风格卡样例（未来残片·原子纪元）；
2. `build_tokens.ts` + 生成 CSS、Godot tokens、token 文档；
3. 四道闸门：schema、对比度/层级、无裸色值、生成物无 diff；
4. **网站试点**：用生成 token 替换 `theme.css` 的颜色定义，**不重做视觉**；
5. **游戏试点**：用生成 token 替换 `tokens.json` 的重复定义，保持主题资源与现有截图一致；
6. 迁移说明、回滚方案、变更日志；每个检查器带 `--self-test`。

**`v0.1` 明确不做**：全组件库、所有产品换肤、Figma 库、实体打样、母品牌正式命名、网站/游戏重设计。

**Definition of Done**：两个产品真实消费生成 token；迁移表面 **0 个裸色值**；对比度与无障碍全绿；视觉差异逐项有记录（预期内）；文档与生成物对账；根日志与设计日志都有条目。

**代价**：首版看起来“只是把颜色搬了个家”，不会立刻变漂亮；但这是后面所有复用的地基。
**推翻条件**：若试点迁移必须改产品布局才能套 token，说明 token 抽象错了——停下来改模型，不硬推。
