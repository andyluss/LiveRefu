# 01 · 现状盘点：四套视觉定义，已经分叉

> 目的：用证据回答“为什么现在必须做设计系统”，而不是凭感觉。
> 方法：读取各产品现有主题/皮肤/文档，逐项对照**同名语义**的取值与规则。
> 日期：2026-10-21 ｜ 状态：**盘点快照**（不追求穷尽，只列会阻碍长期维护的差异）。

## 三、七个真问题

### 1. 焦点色与强调色混用（可用性缺陷，不只是不一致）

《未来残片》的契约明确写过：**焦点指示是可用性基础设施，不能复用语义色**——借用 `--accent` 会与“单一焦点强调”打架，借用 `--power` 会被误读为状态。这条教训来自真实实现反馈（见 [04 视觉语言 §2.2](../../projects/mainline/future-debris/docs/04_视觉语言与设计token.md)）。

但《未来档案》与 LiveFab 的 `--focus` 都**直接等于** `--teal-bright` / 强调色。键盘用户看到的高亮，与“可点击/被选中”的强调是同一个颜色。**这是新系统必须统一修掉的第一个缺陷。**

### 2. `--line` 与 `--line-strong` 的分工没有被普遍遵守

《未来残片》把“装饰分隔线”（可低对比）与“交互控件边框”（≥3:1）分成两个 token，并用闸门守；《未来档案》与 LiveFab 虽有同名 token，但大量控件仍用 `1px solid var(--line)`。这不是审美问题，而是 WCAG 1.4.11 的合规问题，且**同一类缺陷在既有项目已经栽过两次**（见 [04 §十](../../projects/mainline/future-debris/docs/04_视觉语言与设计token.md)）。

### 3. 字号与间距没有共同尺度

- 游戏：固定 **5 级字号**（28/20/16/14/32），间距 **4/8/12/16/24/32**，圆角 **4/8**，描边 **1.5px**。
- 网站：正文 `16px`，标题用 `clamp()` 与 `rem` 自由取值；间距多为 `1rem/1.5rem/2.5rem`；圆角 `6px`；描边 `1px`。
- LiveFab：又一套 `16px/1.7` 与 `0.74–1.3rem` 的局部取值。

结果：**同一个“面板标题”在不同产品里既可能是 20px/600，也可能是 1.02rem/600，还可能是 1.3rem/600。** 跨产品拼页面时无法预测。

### 4. 产品专属语义被写进了“全局语法”

《未来残片》的 `--power`（电力）与 `--residue`（残渣）是**玩法语义**，不是品牌语义。它们被放在语法层，导致：
- 换一个产品（没有电力/残渣）时，这两个 token 无处安放；
- 新产品的“危险/成功”语义要么复用游戏词，要么另起一套。

**新系统要把“行动/成功/警告/危险/信息”留在核心层，把 `power`/`residue` 下沉为产品风格卡里的映射。**

### 5. 没有母品牌，只有四个产品名

- 网站：未来档案（曾名“明日档案”）；
- 游戏：未来残片（代号 `future-debris`，正式中文名待定）；
- 应用：明日频道；
- 平台：LiveFab；工作区：LiveRefu。

目前没有统一的字标、徽记、署名方式、版权行、联名规则；也没有“这是 LiveRefu 的出品”这类背书结构。**实体产品一旦出现，第一件事就是“印什么标”，现在答不出来。**

### 6. 字体策略只解决了“屏幕上能看”，没解决“跨介质能印”

现有做法是**运行时加载系统 CJK 字体、仓库不塞字体二进制**（网站与游戏一致）。这在网页/游戏里是合理取舍，但带来三个长期问题：
- 不同平台（macOS / Windows / Linux / Android）字形与字重不一致；
- 打印/实体无法依赖“用户机器上有什么字体”；
- 没有字体授权登记，未来商用、嵌入、再分发时说不清。

### 7. 资产没有登记，无法复用也无法追责

工作区已有大量视觉资产：`doc/refu-game-001/美术/`（99 PNG / 80 SVG / 47 PDF）、`future-debris/docs/style-samples/`、网站画廊 99 件、各产品截图与预告片。但**没有一张总表**说明：源文件在哪、谁做的、什么许可、哪个版本、能否商用、对应哪个 token/风格卡。

> 这七个问题里，**1、2 是合规缺陷，3、4 是架构缺陷，5、6、7 是长期维护缺陷**。设计系统要同时解决，而不是只做一套好看的颜色。

## 四、必须保留的六个好做法

不要因为“统一”把已经验证过的东西丢掉：

1. **语义 token 优先**：脚本/样式只引用语义名，不引用颜色名（《未来残片》已做到）。
2. **对比度闸门 + 层级亮度顺序**：只查对比度会漏掉“颜色达标但主次分不清”的退化。
3. **检查器自检（`--self-test`）**：负向用例必须断言**错误类型**，不能只断言“有错”。
4. **文档 ↔ 机器可读副本对账**：两份定义不允许静默分叉（`check_tokens.py`）。
5. **可关闭的装饰层与减少动态效果**：CRT/扫描线不得成为无障碍负担。
6. **卡面信息位置契约**：位置固定、风格可变——这是“学一次语法，享受多种风格”的具体样本。

## 五、对设计系统的直接要求

| 盘点结论 | 设计要求 |
| --- | --- |
| 四套取值、同一语义 | 先定义**语义角色**，再让每个产品做**风格卡映射**；不强行统一取值 |
| 焦点色被误用 | 核心层单列 `focus`，禁止产品覆盖为强调色；闸门检查色相/对比 |
| 字号/间距自由发挥 | 冻结尺度阶梯；产品只能选级，不能自造 |
| 产品语义混入核心 | 三层 token：`ref`（原始值）/ `sys`（通用角色）/ `product`（产品语义） |
| 无母品牌 | 先定**品牌架构**与**署名规则**，标志可后做；不阻塞 token |
| 字体/资产无法追责 | 建立**字体授权登记**与**资产登记表**；源文件与导出分离 |
| 没有实体经验 | 打印/实体在架构里预留 `print` / `physical` 介质包，`v0.1` 不实现 |

## 六、盘点边界

- 本盘点**没有**逐页审计网站与游戏的每一个控件；它只对照“主题定义层”，足以支撑架构决策。
- `indie/` 下的独立项目默认豁免根规则，**不纳入**首版迁移范围；未来若愿意接入，按外部消费者处理。
- 本盘点不评价美术质量，只评价**可维护性与一致性**。
