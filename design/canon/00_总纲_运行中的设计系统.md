# 00 · 总纲：运行中的设计系统

> 纲领第一篇 ｜ 2026-10-28 ｜ 上位理念：[清澄](../philosophy/09_清澄_透明作为方法.md)

## 一、设计系统不是文档站

设计系统是一套**持续运行的决定机制**：

```text
源（ref/sys/product）
  → 契约（组件承诺）
  → 风格卡（主题差异）
  → 闸门（对比度/角色/生成物）
  → 投影（CSS/JSON/截图/报告）
  → 反馈（采用、弃用、评审）
```

只画组件、只写规范、只维护 Figma，都不等于系统在运行。

## 二、四件事必须同时成立

| 维度 | 问题 | 失败表现 |
| --- | --- | --- |
| 语义 | 这个值扮演什么角色？ | 业务写裸色、颜色名承载业务 |
| 结构 | 它属于哪一层？ | 原始值和语义值混在一起 |
| 表达 | 换主题后还读得懂吗？ | 对比度差、层级消失、焦点不可见 |
| 治理 | 谁批准变更、怎么回滚？ | 版本失控、弃用无窗口、没有 owner |

## 三、五层模型

沿用 [`../docs/02_系统架构.md`](../docs/02_系统架构.md)：

```text
L0 品牌核心
L1 语法层（语义角色 / 尺度 / 无障碍）
L2 组件与模式（契约）
L3 介质适配（Web / Godot / App / Print / Physical）
L4 资产库（标志/图标/插画/纹理）
```

本纲领主要约束 **L1–L2**；L0/L3/L4 由对应规则与介质包负责。

## 四、设计系统的四个“不”

1. **不把风格当语法**：颜色、材质、装饰可以换；信息位置、字阶、间距、焦点不能换。
2. **不把 token 当越多越好**：token 是维护责任，不是 KPI；每个新增都要有消费者或明确保留期。
3. **不把组件库当目标**：先有契约，再有实现；没有真实消费者的组件不进核心。
4. **不把无障碍当发布后补丁**：不达标 = 未完成。

## 五、判断一个新需求该不该进系统

按顺序问：

1. 是否跨两个以上产品/介质重复？
2. 出错代价是否足够高（可访问性、品牌、交付）？
3. 能否用现有语义表达，而不新增角色？
4. 是否有 owner、版本、弃用与验收方式？

四个都过，才进入 L1/L2；否则留在产品层。

## 六、代价必须可见

每张风格卡、每个新增 token、每次弃用，都要能回答：

- 谁受益？
- 谁维护？
- 什么会坏？
- 怎么退出？

这就是“清澄”在设计系统里的具体形态：**不是把内部全部暴露，而是让关键代价可查、可退。**
