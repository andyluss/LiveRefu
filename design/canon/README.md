# 设计系统纲领 · Canon

> **定位**：LiveRefu 设计系统（LRDS）的**纲领层**，回答“为什么这样分层、什么该放在哪里、什么不该做”。
> **不是**：项目流水账、实现记录、组件清单或临时提案。那些留在 [`../docs/`](../docs/) 与各项目 `docs/`。
> **状态**：v1.0 草案 ｜ 2026-10-28 ｜ 维护者：设计主控 ｜ 最终裁决：用户

## 一、权威顺序

发生冲突时，按以下顺序：

1. **用户明确指令**
2. [`../rules/`](../rules/README.md) 的 MUST 规则（可执行、可校验）
3. **本纲领**（解释原则、结构与取舍）
4. [`../docs/`](../docs/) 的决策/实现记录
5. [`../philosophy/`](../philosophy/README.md) 的理念（约束提问方式，不直接规定 token）

纲领不替代规则；它解释规则背后的判断，并提供跨规则的整体结构。

## 三、三条不可妥协

1. **先语义，后取值**：业务只消费 `sys` / `product` / `component`，不消费 `ref` 色值。
2. **单一事实来源**：同一条设计值只在一个层里定义一次；其余是别名或生成物。
3. **可访问性是闸门**：对比度、焦点、缩放、减少动态不达标，不发布。

## 四、一句话

> **一套语法，多种介质；一个系统，多张风格卡；每个未来都要展示代价。**
