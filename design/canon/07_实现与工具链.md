# 07 · 实现与工具链

> 纲领第八篇 ｜ 关联：LiveDSO [`../../lab/livedso/`](../../lab/livedso/)、[R-009](../rules/R-009-generated-artifacts.md)

## 一、源与生成物

```text
手写源： tokens/*.json + components/*.md + canonical docs
生成物： CSS / JSON / 报告 / 截图 / 索引
```

- 不手改生成物；
- 生成器必须可复算；
- 生成物进入版本控制，便于 diff；
- 生成失败即发布失败。

## 二、LiveDSO 的定位

LiveDSO 是设计系统的**本地操作台**：

- 读取 DTCG 风格 vault；
- 解析别名、检查角色/契约/对比度；
- 投影 CSS、生成报告；
- 扫描采用、快照、CI；
- 本地优先，不接云/账号。

它不替代设计判断，只把判断变成可运行检查。

## 三、一次变更的完整链路

```text
改 ref
  → 改 sys 角色（如需要）
  → product 覆盖（如风格卡）
  → 组件契约
  → 生成 CSS/JSON
  → token/对比度/风格卡/截图闸门
  → 文档与版本
```

## 四、当前实现需要收敛的点

1. scale token 目前可能散落在厂商前缀下，应归并到 `ref`；
2. 50 角色应优先落 `sys.role`，风格卡只做 `product` 稀疏覆盖；
3. `theme.<card>` 全量副本应删除，只保留迁移别名；
4. 组件 token 应归 `component`，不混在角色里；
5. 审计要同时看 token 数、角色覆盖率与视觉回归。

## 五、工程约束

- 零运行时依赖优先；
- 本地可运行优先；
- 生成/检查可脚本化；
- 失败退出码明确；
- 不把审计变成“为了绿而弱化阈值”。

## 六、最低交付

一个设计变更至少要带：

1. token diff；
2. 受影响角色/组件；
3. 生成物；
4. 闸门结果；
5. 截图或可复现 URL；
6. 回滚方式。
