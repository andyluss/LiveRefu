## 一、复杂性不是敌人

复杂性常被当成一句坏话：

- “这个系统太复杂了。”
- “界面要简单。”
- “把流程删到三步。”

但复杂不等于混乱。一座太空城、一个塔防 Sim、一个多人协作项目，本来就有大量真实关系：资源、权限、时间、维护、故障、人的判断。**把这些关系删掉，不会让系统变简单，只会让系统变得更不诚实。**

真正的问题是：

> **复杂性放在了哪里？由谁承担？是否可见？是否可退？**

所以本文区分三种东西：

| 概念 | 含义 | 设计问题 |
| --- | --- | --- |
| **简单** | 关系少、目标单一 | 是否删掉了必要的代价？ |
| **复杂** | 关系多、相互影响 | 复杂放在系统/界面/组织/时间哪一层？ |
| **混乱** | 关系不可见、不可预测 | 谁在承担不可见的复杂性？ |

设计不是消灭复杂，而是**分配复杂**：该由系统吸收的，不要推给人；该被人判断的，不要假装自动化；该暴露的，不要藏在默认值里。

## 二、复杂性的六个来源

| 类型 | 表现 | 设计的杠杆 |
| --- | --- | --- |
| **结构复杂性** | 模块多、依赖多、边界不清 | 模块化、接口、分层、契约 |
| **认知复杂性** | 选项多、规则多、记忆负担重 | 渐进披露、默认值、分组、空间化 |
| **组织复杂性** | 角色多、权限多、责任不清 | 权限表、交接、决策记录、RACI |
| **时间复杂性** | 版本多、状态多、历史长 | 时间线、版本化、回放、迁移 |
| **技术债复杂性** | 补丁叠补丁、例外越来越多 | 可测试、可替换、偿还计划 |
| **意义复杂性** | 价值冲突、叙事矛盾、没有唯一答案 | 多世界、场景、参与、保留退路 |

### 2.1 复杂 vs 错综复杂

- **complicated（错综但可拆）**：像钟表，拆开能理解，专家能预测；
- **complex（复杂适应）**：像城市，参与者互相影响，只能探测、适应、观察。

塔防的数值是 complicated；一座城的夜班是 complex。

设计思维对两者的策略不同：

```text
complicated：分析 → 拆解 → 优化 → 标准化
complex：探测 → 感知 → 响应 → 再探测
```

## 三、五种设计策略

不要问“怎么把它变简单”，先问“这种复杂应该由谁吸收”。

| 策略 | 做什么 | 代价 | 适用 |
| --- | --- | --- | --- |
| **移除** | 删掉不必要的关系/步骤 | 可能删掉必要的代价 | 目标明确、冗余明显 |
| **吸收** | 系统替人处理复杂 | 黑箱、自动化错误 | 高频、规则稳定 |
| **排序** | 把复杂拆成先后顺序 | 延迟、等待 | 新手/首次使用 |
| **暴露** | 把复杂展示出来，让人判断 | 认知负担、训练成本 | 高风险/需要判断 |
| **委托** | 把复杂交给专家/社区/工具 | 权力集中、依赖 | 专业领域/罕见情况 |

### 3.1 一个判断顺序

```text
1 这是必要复杂，还是历史遗留？
2 如果必要：谁最有能力承担？系统、专家、还是当事人？
3 如果交给系统：出错时谁发现、谁修复、谁负责？
4 如果交给人：他有没有时间、信息、权限与退路？
5 如果交给组织：边界、交接、维护是否可见？
```

## 四、设计思维的管理循环

复杂性不能靠一次“简化”解决；它需要持续管理。

### 4.1 Frame：先定义问题

- 这是 complicated 还是 complex？
- 谁被复杂性伤害？谁从复杂性获益？
- 这是“用户不会用”，还是“系统把代价推给了用户”？

### 4.2 Map：把关系画出来

- 系统图、依赖图、权限图、时间线；
- 标出：谁输入、谁决定、谁维护、谁承担、谁退出；
- 用 [13 白盒化方法](13_白盒化方法_把系统翻过来.md) 选择分辨率。

### 4.3 Probe：用小原型探测

- 不要在复杂系统上一次做大改；
- 做可逆的小实验：一个默认值、一个提示、一个队列、一个权限；
- 观察：错误率、等待、绕路、求助、放弃。

### 4.4 Decide：把决定与代价一起记录

- 选了哪种策略？放弃了什么？
- 谁批准？谁维护？何时复审？
- 用什么信号判断“复杂度又长回来了”？

### 4.5 Institutionalize：让管理成为制度

- 复杂性预算；
- 变更评审；
- 维护窗口；
- 事故复盘；
- 定期删功能，而不只是加功能。

## 五、复杂性放在哪里

| 位置 | 适合放什么 | 风险 |
| --- | --- | --- |
| **系统内部** | 稳定规则、计算、重试、兼容 | 黑箱、自动化错误 |
| **界面** | 选择、预览、解释、比较 | 认知过载 |
| **组织** | 权限、审批、交接、维护 | 推诿、流程僵化 |
| **时间** | 分阶段、版本、迁移、回放 | 延迟、历史包袱 |
| **空间** | 分区、层级、导航、地图 | 遮挡、迷路 |
| **关系/叙事** | 多世界、角色、场景 | 相对主义、逃避判断 |

> 复杂性不会消失，只会换一个位置。**设计的工作，是选择它换到哪里，以及谁看得见。**

## 六、复杂性的设计工具箱

| 工具 | 作用 | 例子 |
| --- | --- | --- |
| **渐进披露** | 先给主线，细节按需展开 | 高级设置、专家模式 |
| **默认值** | 替多数人吸收复杂 | 推荐配置、安全默认 |
| **分组/分块** | 降低同时处理的元素 | 4±1 组、步骤条 |
| **空间化** | 用位置承载关系 | 地图、分层、仪表盘 |
| **契约/接口** | 把复杂关进边界 | API、schema、插件 |
| **可观测性** | 让复杂可被看见 | 日志、状态灯、回放 |
| **可逆性** | 降低错误代价 | 撤销、预览、灰度 |
| **冗余/缓冲** | 吸收波动 | 备用电池、队列、余量 |
| **删除** | 去掉不必要的关系 | 删功能、删选项、删流程 |

## 七、复杂性的度量

不要只用“看起来简单”判断。可以观察：

- 首次成功时间；
- 完成任务所需步骤/切换；
- 错误率与恢复时间；
- 求助/支持负担；
- 变更一个规则要动几处；
- 事故影响半径；
- 维护 backlog；
- 新人上手时间；
- 用户绕路/自建工具的比例。

> 指标也会制造复杂性。**不要用一张复杂仪表盘管理复杂性。**

## 八、复杂性与稀缺性

复杂性和稀缺性是一对：

- 复杂性消耗稀缺的注意力、时间、维护力；
- 稀缺又制造复杂性：缺人、缺时间、缺备件，于是出现例外、补丁、绕路；
- 复杂性会隐藏稀缺：把代价推给不可见的人/未来。

所以管理复杂性，必须同时问：

```text
这项复杂消耗了谁的稀缺资源？
这项稀缺又被谁的复杂掩盖了？
```

详见 [15 稀缺性](15_稀缺性_设计在不够的时候.md)。

## 九、LiveBay 的具体例子

| 对象 | 复杂性 | 设计处理 |
| --- | --- | --- |
| 塔防 Sim | 塔/敌/波/故障/经济 | 数据驱动 + 读模型 + 回放 |
| 生存模式 | 电/氧/救援/封舱/撤离 | 独立 LabGame + HUD + 自动测试 |
| 自由模式 | 覆盖/标签/候选/导入导出 | 独立页面 + capability + 候选 diff |
| 项目文档 | 世界/玩法/工程/验证 | 分层目录 + BOX 地图 + 索引 |
| BOX-PROJECT | 6 层/34 节点 | 3D 堆栈 + 维度开关 + 检查器 |
| BOX-GAME | 空间/时间/经济/威胁 | 2.5D 画布 + 波次/矩阵/塔卡 |

一个反例：把所有信息都塞进一个“总览页”，看起来全面，实际上把复杂性推给了读者的工作记忆。

## 十、反模式

| 反模式 | 表现 | 后果 |
| --- | --- | --- |
| **简化表演** | 删到只剩一个按钮，代价藏到后台 | 用户失去判断 |
| **复杂崇拜** | 参数越多越显得专业 | 只有专家能用 |
| **自动化黑箱** | 系统替人做决定，但不解释/不可撤销 | 错误无法定位 |
| **流程堆积** | 用审批吸收复杂性 | 延迟、推诿 |
| **仪表盘倾倒** | 所有指标都上屏 | 信息过载 |
| **把复杂推给用户** | “你自己配置” | 弱者承担更多 |
| **只加不删** | 每次迭代都加功能 | 复杂性债务 |

## 十一、检查表

1. 这是 necessary complexity 还是 legacy complexity？
2. 复杂现在放在哪一层？谁承担？
3. 如果交给系统，出错时谁发现、谁修复？
4. 如果交给人，他有时间/信息/权限/退路吗？
5. 有没有可逆的小实验，而不是一次大改？
6. 变更一个规则要动几处？有没有契约？
7. 新人/外部人能否在 10 分钟内理解主线？
8. 有没有定期删功能/删选项？
9. 复杂性消耗了谁的稀缺资源？
10. 有没有把复杂性藏进“默认值/自动化/流程”？

## 十二、结论

复杂性不是设计的失败，**未被分配、未被看见、未被承担的复杂性**才是。

> 好的设计不是让系统看起来简单，
> 而是让复杂出现在该出现的地方，并由有能力承担的人/系统承担。

一句话：

> **把复杂放在正确的位置，而不是把复杂藏起来。**
