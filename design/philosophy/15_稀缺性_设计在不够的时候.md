## 一、稀缺不是“少”

稀缺不是简单的数量少，而是：

> **需求 > 可用供给，且不能同时满足所有重要目标。**

因此稀缺至少有三层：

| 层 | 例子 | 设计问题 |
| --- | --- | --- |
| **绝对稀缺** | 氧气、电力、时间、预算 | 怎么分配？谁先？ |
| **相对稀缺** | 注意力、信任、耐心、合法性 | 怎么降低需求？ |
| **制造稀缺** | 限时、限量、邀请码、焦虑 | 谁获益？是否诚实？ |

设计不能消灭所有稀缺；但设计可以决定：

- 稀缺由谁承担；
- 稀缺是否可见；
- 稀缺是否可被讨论；
- 有没有缓冲、替代、退出；
- 谁有权分配。

## 二、八种稀缺

| 类型 | 表现 | 设计杠杆 |
| --- | --- | --- |
| **物质** | 材料、备件、空间 | 循环、维修、替代、共用 |
| **能源** | 电力、燃料、热 | 预算、储能、削峰、降级 |
| **注意力** | 信息过载、通知、选择 | 默认、分层、静默、节奏 |
| **时间** | 交付、等待、恢复 | 排队、截止、缓冲、异步 |
| **信任** | 可信度、声誉、合法性 | 来源、审计、透明、可退出 |
| **维护** | 人、知识、备件、预算 | 维修权、文档、冗余、培训 |
| **协调** | 会议、审批、对齐 | 契约、权限、异步、小团队 |
| **选择权** | 可选方案、退路、余量 | 保留选项、可逆决策、退出 |

### 2.1 稀缺会伪装成别的问题

- “用户不活跃”可能是注意力稀缺；
- “团队执行力差”可能是协调/维护稀缺；
- “设计不够高级”可能是时间/信任稀缺；
- “内容不够多”可能是维护/合法性稀缺；
- “系统太复杂”可能是认知/时间稀缺。

**先诊断稀缺类型，再谈设计。**

## 三、设计如何对待稀缺

| 策略 | 做什么 | 代价 | 适用 |
| --- | --- | --- | --- |
| **降低需求** | 少要一点、少一步、少一个选择 | 可能牺牲能力 | 注意力/时间稀缺 |
| **增加供给** | 扩容、复用、自动化 | 成本、维护 | 物质/能源稀缺 |
| **缓冲** | 储备、队列、余量 | 占用资源 | 波动/峰值 |
| **共享** | 公共资源、池化、互助 | 治理成本 | 物质/维护稀缺 |
| **排序** | 优先级、配额、分阶段 | 排除、等待 | 绝对稀缺 |
| **替代** | 换材料/路径/方案 | 质量/习惯 | 供应链/能源 |
| **降级** | 优雅退化、保核心 | 体验损失 | 故障/峰值 |
| **退出** | 导出、迁移、拒绝 | 商业/锁定 | 信任/选择权稀缺 |

### 3.1 优先顺序

```text
1 先诚实承认稀缺：缺什么、缺多少、谁承担？
2 再降低需求：哪些不是必须同时满足？
3 再做缓冲/共享：能不能不让人直接互相抢？
4 最后才做配额/排序：并公开规则与申诉。
```

不要一上来就做“限时/限量/抢购”，那通常是把稀缺变成焦虑。

## 四、设计思维的管理循环

### 4.1 Frame：把稀缺说清楚

- 是绝对稀缺，还是相对/制造稀缺？
- 谁定义“不够”？
- 谁承担等待/排除/风险？
- 如果不解决，最坏会发生什么？

### 4.2 Map：画稀缺流

- 资源从哪里来、经过谁、到哪里去；
- 峰值/谷值/储备；
- 谁有优先权、谁没有；
- 哪些稀缺被隐藏/外部化。

### 4.3 Prototype：小规模试用分配规则

- 一个配额、一个队列、一个预约；
- 一个降级模式、一个备用方案；
- 观察：等待、绕路、冲突、放弃、公平感。

### 4.4 Decide：规则与代价一起拍板

- 谁分配？依据是什么？
- 例外谁批？多久复审？
- 失败时怎么降级/补偿/退出？

### 4.5 Institutionalize：把稀缺管理变成制度

- 预算/配额；
- 储备/维护；
- 公开的优先级；
- 定期复审；
- 申诉/退出通道。

## 五、稀缺的设计模式

| 模式 | 说明 | 适合 |
| --- | --- | --- |
| **预算** | 给一段时间/团队/舱段固定额度 | 能源、注意力、时间 |
| **配额** | 每人/每单位固定份额 | 物质、服务 |
| **队列** | 先来后到/优先级 | 时间、审批 |
| **预约** | 提前锁定资源 | 注意力、设备 |
| **渐进分配** | 先给最小可用，再按表现/需要追加 | 预算、内容 |
| **储备/缓冲** | 留余量应对波动 | 能源、维护、时间 |
| **优雅降级** | 不够时保核心、关非核心 | 故障、峰值 |
| **共享池** | 公共资源池 + 治理规则 | 备件、知识、空间 |
| **可逆承诺** | 先小后大，保留退出 | 选择权稀缺 |
| **维护窗口** | 把维护当成一等公民 | 维护稀缺 |

## 六、稀缺的伦理

稀缺不是中立的。每个分配规则都在回答：

- **谁决定**：算法、议会、市场、专家、社区？
- **谁承担**：外环、夜班、弱者、未来的人？
- **谁被排除**：没有记录的人、不会申诉的人？
- **谁维护**：谁修、谁备件、谁培训？
- **谁获益**：稀缺被谁变成了权力/利润？

### 6.1 四种危险

1. **稀缺剧场**：制造紧迫感，让人来不及判断；
2. **稀缺转移**：把成本推给不可见的人；
3. **稀缺自然化**：把人为分配说成“自然规律”；
4. **稀缺羞耻**：让不够的人觉得是自己的错。

> 设计不能假装稀缺不存在；也不能利用稀缺操控人。

## 七、LiveBay 的具体例子

| 对象 | 稀缺 | 设计 |
| --- | --- | --- |
| 低功率夜班 | 电力、氧气、救援时间 | 功率分配、备用电池、封舱、撤离、氧气只扣评级 |
| 塔防 | 供能、塔位、时间 | 建造/升级/出售、波次准备、故障处置 |
| 自由模式 | 开发时间、注意力 | 独立页面、模板、候选 diff、自动测试 |
| 项目 | 人力、验证、内容厚度 | 范围纪律、P0/P1、verify、真人试玩 |
| Solarpunk 城市 | 太阳能、材料、维护 | 太阳公约、循环额度、维修权、公共所有 |
| BOX 页面 | 屏幕空间、认知 | 维度开关、分层、检查器、默认折叠 |

低功率夜班不是“多一个蓝条”，而是把**能源稀缺**变成可被分配、可被讨论、可失败的设计材料。

## 八、稀缺的度量

- 等待时间与分布（不是平均值）；
- 峰值/谷值/储备余量；
- 排除率/放弃率；
- 绕路/黑市/自建工具；
- 维护 backlog 与恢复时间；
- 注意力成本（通知/切换）；
- 决策延迟；
- 申诉/例外比例；
- 谁承担最多稀缺（分层看）。

> 平均值会隐藏稀缺。**看分布，尤其看最弱的人。**

## 九、反模式

| 反模式 | 表现 | 后果 |
| --- | --- | --- |
| **稀缺剧场** | 限时、限量、倒计时 | 焦虑、冲动、信任损耗 |
| **无限增长** | 用更多内容/功能解决稀缺 | 维护崩溃 |
| **隐性配额** | 规则不公开，靠关系 | 不公平、黑市 |
| **平均主义** | 所有人平均分，忽略需求差异 | 最需要的人不够 |
| **只加缓冲** | 不改变需求，只加储备 | 成本/空间崩溃 |
| **降级即抛弃** | 一坏就全关 | 失去核心 |
| **没有退出** | 不能导出/迁移 | 锁定 |
| **把稀缺当美德** | “穷是创意之源” | 美化剥夺 |

## 十、检查表

1. 这是绝对、相对，还是制造稀缺？
2. 谁定义“不够”？谁获益？
3. 谁承担等待/排除/风险？
4. 能不能先降低需求，而不是先加供给？
5. 有没有缓冲/共享/替代？
6. 分配规则是否公开、可申诉、可复审？
7. 不够时如何优雅降级？保什么？
8. 维护者/备件/知识在哪里？
9. 有没有退出/导出/迁移？
10. 最弱的人是否承担了最多稀缺？

## 十一、结论

稀缺不是设计的借口，也不是营销的工具。它是**设计材料**：

> 设计不能消灭稀缺，但可以让稀缺被看见、被分配、被讨论、被承担，并保留退路。

一句话：

> **在不够的时候，设计最重要的不是“挤更多”，而是“谁先、谁后、谁承担、谁可以走”。**
