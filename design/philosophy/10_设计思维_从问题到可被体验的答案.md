## 一、设计思维不是“想得美一点”

设计思维（design thinking）最容易被误解成一种态度：多贴便签、多画草图、多说“以用户为中心”。这些只是表面动作。它真正处理的是一个更困难的问题：

> **当问题本身没有被定义清楚时，我们如何做出一个可以被体验、被检验、被修改的答案？**

工程问题通常可以写成约束：在给定负载、预算、材料和时限下，让系统稳定运行。设计问题往往连“成功是什么”都还在争夺：

- 这个产品到底在帮谁？
- 用户说的“想要更快”，真正想摆脱的是什么？
- 一个功能让流程更顺，却让谁失去了判断权？
- 这个未来看起来很美，但谁承担维护代价？
- 我们是在解决一个问题，还是在把一个问题包装成可售卖的商品？

设计思维不是绕开约束，而是在约束尚未定型时，先通过观察、 framing、原型和反馈，把“要解决什么”变成一个可以被共同讨论的对象。

## 二、它从哪些传统里长出来

设计思维不是凭空出现的。它至少吸收了四条传统：

1. **建筑设计中的“做中学”**：图纸、模型、现场之间反复往返，问题在制作中显形。
2. **人因工程与参与式设计**：从“替用户设计”转向“和用户一起设计”，关注真实工作现场，而不是实验室里的抽象用户。
3. **IDEO 与 d.school 的方法化**：把观察、访谈、头脑风暴、快速原型、用户测试整理成可教学的流程。
4. **设计委员会的 Double Diamond**：把过程分成 Discover / Define / Develop / Deliver 两次发散与收敛。

这套方法在 2000—2010 年代被企业、咨询公司、公共部门大量采用，也被批评为“工作坊剧场”：便签很热闹，权力关系没有改变，最后仍然由最有权的人拍板。

青橙保留它的方法，但不保留它的神话。设计思维不是“设计师比其他人更懂人”，而是一种**把判断暴露出来、把答案做成可体验对象**的工作方式。

## 三、五个动作，不是五个阶段

常见的五阶段是 Empathize、Define、Ideate、Prototype、Test。把它当成线性流水线会失去意义；更准确地说，它是五个反复发生的动作。

| 动作 | 要回答的问题 | 常见产物 | 失败方式 |
| --- | --- | --- | --- |
| 观察 / 共情 | 人们实际在做什么，而不是说想要什么？ | 访谈、现场观察、旅程图、异常记录 | 把“用户画像”写成刻板印象 |
| 定义 / 重新框定 | 真正要解决的是哪一个问题？ | 问题陈述、How might we、边界条件 | 把方案伪装成问题 |
| 发散 | 还有哪些没有被考虑的可能？ | 概念草图、类比、极端方案 | 只收集“安全的好点子” |
| 原型 | 最快能让人体验到什么？ | 纸面原型、可点击稿、角色扮演、规则原型 | 原型太精致，导致没人敢否定 |
| 测试 | 它在真实情境里如何失败？ | 使用记录、访谈、对照、失败清单 | 只测试“能不能用”，不测试“谁被排除” |

### 双钻：两次发散，两次收敛

```text
问题空间                         答案空间
Discover  →  Define      Develop  →  Deliver
  发散        收敛          发散        收敛
```

双钻最重要的不是四个英文词，而是两个判断：

- **Define 决定了后面所有工作的上限**。问题定义错了，后面越高效越危险。
- **Deliver 不是终点**。真实使用会改变问题，下一轮 Discover 必须重新开始。

## 四、六条原则

### 1. 以真实的人为起点，而不是以“用户”为抽象

“用户”是一个统计单位，人会累、会怀疑、会照顾别人、会拒绝、会被排除。设计思维要求进入具体场景：谁在什么时候、用什么身体、承担什么风险、被谁看着使用。

在 LRDS 里，这意味着：不只问“这个界面是否易用”，还要问“谁没有时间学它”“谁不信任它”“谁能退出”。

### 2. 先重新框定问题

好的设计经常不是给旧问题一个更好的答案，而是发现旧问题问错了。

- 旧问题：怎样让用户更快地完成设置？
- 重新框定：为什么用户需要理解这么多设置？哪些判断可以由系统承担，哪些必须留给人？

### 3. 用制作思考，而不是只用语言争论

原型是一种认识工具。它让隐形的假设变成可以被看见、被使用、被反驳的东西。原型的 fidelity 不是越高越好，而是**刚好足以暴露关键风险**。

- 纸面原型暴露信息结构；
- 可点击原型暴露流程；
- 规则原型暴露激励与失败；
- 角色扮演暴露权力关系；
- 服务蓝图暴露后台劳动。

### 4. 发散与收敛分开

发散时不要急着证明自己正确；收敛时不要用“感觉”替代判据。青橙的收敛判据至少包括：真实状态是否可见、谁承担代价、是否可退出、是否保留人的判断。

### 5. 迭代，但不把迭代当免责

“先上线再迭代”经常被用来逃避责任。迭代的前提是：有可观察的反馈、有明确的停止条件、有对受影响者的说明。没有这些，迭代只是把风险延后。

### 6. 让设计成为共同作者，而不是设计师的独角戏

设计思维不是设计师的专利。工程师、产品、运营、领域专家、受影响者都应该参与问题定义。差别不在于谁画图，而在于谁能提出“这个方向不对”。

## 五、方法工具箱

| 方法 | 何时用 | 产出 | 注意 |
| --- | --- | --- | --- |
| 深度访谈 | 问题定义前 | 真实语言、矛盾、例外 | 不要按问卷念；追问“上一次是什么时候” |
| 现场观察 | 访谈之外 | 工作流、变通、隐性知识 | 人们说的和做的不一样 |
| 旅程图 | 跨触点问题 | 情绪、等待、断点、后台 | 不要只画“顺利路径” |
| 服务蓝图 | 涉及后台/多人 | 前台—后台—支撑系统 | 把劳动和维护放回图里 |
| How might we | 定义之后 | 可发散的问题句 | 不要暗含唯一答案 |
| 类比 | 卡住时 | 跨领域结构 | 类比要说明哪里可迁移、哪里不可 |
| 纸面/可点击原型 | 早期 | 信息结构与流程 | 允许粗糙，鼓励否定 |
| 可用性测试 | 中期 | 任务失败点 | 不只测效率，也测理解与退路 |
| 日记研究 | 长周期 | 真实使用变化 | 适合生活类、陪伴类产品 |
| 参与式工作坊 | 多利益方 | 共同问题定义 | 必须说明谁有决定权 |

## 六、设计思维与设计系统不是一回事

设计系统回答：

- 颜色、字号、间距、组件怎么统一；
- 什么状态用什么组件；
- 代码与设计如何对账；
- 可访问性如何验收。

设计思维回答：

- 为什么做这个产品；
- 它为谁改变什么关系；
- 哪些问题不应该被解决；
- 什么代价必须被展示。

设计系统让设计**可复制**；设计思维让设计**值得复制**。一个有设计系统但没有设计思维的团队，会非常高效地生产错误的东西。

## 七、对设计思维的四种批评

1. **工作坊化**：把方法变成便签仪式，问题定义仍由老板决定。
2. **去政治化**：只谈用户体验，不谈谁拥有系统、谁承担外部性。
3. **救世主化**：设计师带着“为你好”的姿态进入社区，忽略当地知识。
4. **指标化**：把同理心、创意、实验变成 KPI，最后优化的是表演。

青橙的修正是：

- 先做**清澄**：来源、代价、权限、退路可见；
- 再做**多世界**：不假定只有一种好未来；
- 保留**可参与**：受影响者不是素材，而是共同作者；
- 保留**边界**：有些问题不该用“更顺的体验”解决。

## 八、一个简化的青橙设计流程

```text
1. 进入现场：谁在做什么？谁不在场？
2. 写清代价：谁受益、谁维护、谁承担风险？
3. 重新框定：这是不是一个被产品化的问题？
4. 做三个不同未来的原型：保守 / 参与式 / 退出式
5. 让受影响者试用，记录失败与排除
6. 收敛：可感、可参与、可退出、代价可见
7. 交付：设计系统落地 + 维护与退出说明
```

注意：这不是七步流水线。第 2 步可能推翻第 1 步，第 5 步可能回到第 3 步。设计思维的价值不在于步骤整齐，而在于**允许问题在过程中改变**。

## 九、评审清单

- [ ] 问题陈述里有没有“谁”？
- [ ] 我们访谈的是真实场景，还是我们的想象用户？
- [ ] 这个方案让谁更轻松，让谁更累？
- [ ] 有没有一个“不设计”的选项？
- [ ] 原型暴露了哪个关键假设？
- [ ] 失败时会发生什么，谁能退出？
- [ ] 这个答案是否只是把旧权力关系包得更漂亮？
- [ ] 如果规模扩大十倍，维护代价由谁承担？

## 十、结语

设计思维不是“让一切变得更好”的魔法。它更像一种纪律：

> **在被要求立刻给答案之前，先坚持把问题看清楚；在把问题看清楚之后，仍然愿意做一个可以被体验、被反驳、被修改的答案。**

这和青橙的“清澄”是同一条路：不是把世界解释得更漂亮，而是让世界的关系变得可见，让人仍然有位置。
