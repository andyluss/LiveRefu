## 一、青橙与清澄

“青橙”是颜色：青与橙并置，冷系统里保留暖生命。

“清澄”是同音词，也是青橙的**核心中的核心**：

> **清**，是可见、可读、可核对；**澄**，是让杂质沉淀，留下可理解的结构。

青橙可以换风格卡、换时代、换介质；清澄不能换。它不是第十个原则，而是**判断所有原则的那条原则**。

一个界面可以是青色与橙色，却仍然是浑的；一个系统可以没有任何颜色，却可以是清澄的。清澄不是视觉配方，是**信息与权力的透明度**。

## 二、清澄不是什么

### 1. 不是“全部曝光”

清澄不是把所有数据、所有人的操作、所有内部讨论都摊在界面上。那是数据倾倒，不是透明。

清澄要回答的是：

- 哪些信息影响判断，必须可见？
- 哪些信息属于私密，必须被保护？
- 哪些信息可以按需展开，而不是默认淹没？
- 谁知道它存在、谁有权查看、谁有权修改？

> **透明不是“没有墙”，而是“墙在哪里、为什么在那里，所有人都知道”。**

### 2. 不是“极简白色”

留白、细线、无装饰，可能让界面看起来“干净”，但把来源、代价、维护者藏起来，仍然是不清澄。

清澄允许复杂，甚至允许“脏”——只要脏是可见的、可解释的、可处理的。旧纸、盐雾、维修痕迹不是杂质；**把维修痕迹擦掉，才是杂质**。

### 3. 不是“开源”的同义词

开源代码可以伴随不透明的治理、资金、路线图与维护；闭源系统也可以在合同内提供清晰的来源、责任与退出条款。

开源是清澄的**重要手段**：它让代码可审计、可 fork、可退出。但“仓库公开”不等于“权力透明”。清澄还要问：

- 谁决定路线图？
- 谁付钱维护？
- 谁有权合并/否决？
- 出问题时谁负责？
- 不开放的部分是什么，为什么？

### 4. 不是“把复杂性删掉”

清澄不是把系统简化到只剩一个按钮。那是把判断外包给产品。

清澄是**把复杂性放在正确的位置**：默认界面安静，关键状态可见，细节可展开，代价可追溯。

## 三、清澄的七种可见

### 1. 来源可见（Provenance）

每个事实、资产、数据、建议，都应该能回答：

- 从哪里来？
- 谁做的/谁记录的？
- 什么时候？
- 经过谁的手？
- 能不能追溯到原始文件？

没有来源的“权威”，只是噪音。

### 2. 代价可见（Cost）

每个未来、每个自动化、每个“免费”，都要显示：

- 谁承担成本？
- 谁维护？
- 什么会坏？
- 坏了谁修？
- 不修会怎样？

清澄不是悲观，而是**不把账单藏在最后一页**。

### 3. 维护可见（Maintenance）

维护不是后台杂务，是系统的一部分。

- 谁在修？
- 修得多频繁？
- 备件/知识/工具在哪里？
- 维护者走了怎么办？

一个不显示维护者的系统，会把维护变成隐形劳动；隐形劳动最终会变成系统性脆弱。

### 4. 权限可见（Power）

- 谁能看？
- 谁能改？
- 谁能删？
- 谁能导出？
- 谁能否决？
- 谁不能被看见？

权限不清，透明就会变成监控：**对一部分人透明，对另一部分人黑箱**。

### 5. 不确定性可见（Uncertainty）

- 哪些是事实？
- 哪些是推测？
- 哪些是模型生成的？
- 置信度多少？
- 什么情况下会错？

清澄不是“永远正确”，而是**错误发生时，能被看见、被定位、被修正**。

### 6. 退路可见（Exit）

- 数据能不能导出？
- 格式是不是可读？
- 服务停了还能不能用？
- 迁移成本是多少？
- 有没有“离开”按钮，而不是只有“注销”？

没有退路的透明，是玻璃房；有退路的透明，才是家。

### 7. 资金与治理可见（Governance）

- 谁付钱？
- 钱花在哪？
- 谁拥有？
- 谁决定？
- 冲突怎么解决？

这是开源项目最容易被忽略的一种清澄：**代码公开，但生计与权力不公开**。

## 四、清澄与可感/可参与/可退出

清澄不是另起一套，而是把已有原则收束成一条底线：

| 已有原则 | 清澄之后 |
| --- | --- |
| **可感** | 现象必须指向真实状态；不是装饰性的“透明感” |
| **可参与** | 参与的前提是看得见规则、代价与权限 |
| **可退出** | 退出的前提是知道数据在哪、能带走什么 |
| **多世界** | 每个世界都要展示自己的代价，而不是只换皮肤 |
| **诚实代价** | 代价可见，就是清澄的最低要求 |

所以，清澄不是“更高级的理念”，而是**这些理念的共同前提**：如果连来源、代价、权限都看不见，可感只是氛围，可参与只是按钮，可退出只是口号。

## 五、清澄的界面语法

### 1. 先给判断，再给细节

- 默认界面：状态、风险、下一步；
- 展开后：来源、历史、依赖、原始数据；
- 不把 40 个指标平铺，也不把关键信息藏进三级菜单。

### 2. 用颜色表示状态，不用颜色制造神秘

- 青/橙可以标识冷暖、正常/警示、系统/生命；
- 但颜色不能是唯一信息通道；
- 不用低对比“氛围色”吞掉正文；
- 不用渐变/发光把错误包装成“高级感”。

### 3. 错误必须可定位

- 错误说清：发生了什么、影响谁、怎么修、谁负责；
- 不只给“出错了”；
- 不只给一个红色感叹号；
- 不把错误日志只留给开发者。

### 4. 空白必须诚实

- 空状态说清“为什么空、下一步是什么”；
- 加载状态说清“在等什么”；
- 不确定状态说清“还不知道什么”；
- 不用 skeleton 动画掩盖长时间失败。

### 5. 默认保护，主动公开

- 私密是默认，公开是动作；
- 公开前显示“将公开什么、谁能看到”；
- 不把“公开”做成一个不起眼的开关；
- 不把用户数据拿去训练，除非明确、可拒绝、可撤回。

## 六、清澄与开源

青橙的“可退出”天然靠近开源，但清澄要求比“开源许可证”更多：

| 层次 | 清澄问法 |
| --- | --- |
| **代码** | 能读、能构建、能 fork 吗？ |
| **许可** | 能商用/修改/再分发吗？边界清楚吗？ |
| **治理** | 谁决定路线图？谁能合并？ |
| **资金** | 谁付钱？维护者的生计是什么？ |
| **数据** | 训练数据/用户数据/资产来源清楚吗？ |
| **退出** | 格式开放吗？服务停了还能用吗？ |

**开源不是清澄的充分条件，但是最可验证的起点之一。**

反过来，如果一个项目说“我们开源”，却说不清谁维护、谁付钱、谁决定，它仍然是不清澄的。清澄不是许可证标签，是**权力与成本的可见性**。

## 七、三个产品的清澄

### LiveDSO（设计系统操作台）

- token 的来源、别名、分层可见；
- 每个警告说清“哪个 token、哪个契约、什么后果”；
- 不自动“修复”用户的系统；
- 开源核心 + 商业服务，边界写清。

### LiveLand（世界/时代创作工具）

- 每条 canon 有来源、置信度、依赖、冲突；
- 每个时代显示技术、维护者、代价；
- 不把 AI 生成的内容伪装成 canon；
- 资产有许可与来源，公开页只显示 public。

### LiveFile（个人档案 OS）

- 每个条目有 sidecar：来源、许可、保留、public；
- 备份/恢复/继承状态可见；
- 不静默上传、不静默训练；
- 原始文件不动，导出可带走。

> 三个项目的共同点不是“复古配色”，而是：**用户能看见系统在做什么，以及为什么。**

## 八、清澄的反模式

- **透明剧场**：仪表盘很多，但没有一个能支持决定；
- **数据倾倒**：把原始日志/全部字段丢给用户，叫“透明”；
- **隐私泄漏**：以“公开”为名暴露弱者；
- **开源洗白**：代码公开，治理/资金/数据不公开；
- **极简伪装**：留白很漂亮，来源/代价/维护全消失；
- **确定性崇拜**：不给置信度、不给错误边界、不给“不知道”。

## 九、清澄评审：七个问题

1. **来源**：这个结论/资产/建议从哪来？能追到原始文件吗？
2. **代价**：谁付钱、谁维护、什么会坏？
3. **权限**：谁能看、谁能改、谁能否决？
4. **不确定**：哪些是事实、哪些是推测、错在哪里？
5. **退路**：数据能带走吗？服务停了还能用吗？
6. **边界**：什么故意不公开？为什么？
7. **治理**：谁决定？谁负责？谁不能被看见？

> 七个问题不必每次全答；但**不能假装问题不存在**。

## 十、结论：青橙是颜色，清澄是水

青橙是一组颜色，清澄是颜色下面的水。

水可以是青的、橙的、透明的、浑浊的；清澄不是水的颜色，是**你能不能看见水底**。

> **清澄不是把水搅浑后再给你一个过滤器；是先让水静下来，让你看见底。**

青橙设计可以有很多未来；清澄要求每个未来都敢让人看见：谁在受益、谁在承担、谁在维护、谁可以离开。

这就是核心中的核心。
