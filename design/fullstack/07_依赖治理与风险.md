# 07 · 依赖治理与风险

> 青橙全栈 · 技术框架提案 ｜ 状态：提案 / 未实现 ｜ 日期：2026-10-26 13:24

## 一、依赖分层

| 层 | 例子 | 规则 |
| --- | --- | --- |
| **T0 平台** | Node/Bun、Web API、SQLite、OS | 不重写；薄 adapter |
| **T1 核心** | TypeScript、esbuild、密码哈希、validator | 少量、pin、可替换、写预算 |
| **T2 适配** | Postgres、OAuth、S3、邮件 | 可选、不进核心 |
| **T3 应用** | 业务 SDK/库 | 应用自选；框架不担保 |

## 二、核心依赖准入

一个依赖进入核心，必须回答：

1. 平台原语为什么不够？
2. 它解决的是“契约/胶水”还是“核心能力”？
3. 出问题能否在 1 天内替换/绕过？
4. 许可证是否允许商用/分发？
5. 是否有安全维护/版本记录？
6. 是否会渗透到应用 API？
7. 是否有 raw/escape 出口？

**预算**：第一版运行时核心依赖 ≤5；超过要用户批准。

## 三、版本与升级

- 所有依赖 **精确 pin**（lockfile + package.json 范围）；
- 升级走 `qc update`：先跑测试/示例/dogfood；
- 破坏性升级给 codemod/迁移说明；
- 安全更新优先；不允许“永远不升”；
- 框架自身 SemVer；核心契约破坏性变更走 major。

## 四、供应链与安全

- 只从官方 registry/固定源安装；
- 检查 lockfile diff；
- 依赖许可证清单；
- 不引入来源不明的二进制/原生模块；
- 原生模块（SQLite/argon2）优先平台/成熟包，必须有 Node/Bun 兼容测试；
- secrets 不入库；示例用 `.env.example`；
- 发布产物带哈希/来源说明。

## 五、退出测试

每个核心依赖/适配器都要有“退出测试”：

| 依赖 | 退出方式 | 目标 |
| --- | --- | --- |
| SQLite 驱动 | 换 adapter | 页面/动作不改 |
| validator | 换 Standard Schema 实现 | 表单/错误结构不变 |
| 密码哈希 | 换算法 + 重哈希 | 登录流程不变 |
| 构建器 | 替换 build adapter | server entry 不变 |
| runtime | Node ↔ Bun | 应用代码不改 |

**判据**：一天内能换掉，应用不重写。

## 六、主要风险

### 6.1 NIH / 重造轮子

自研 HTTP/SSR/ORM/UI 会带来安全/性能/维护风险。防御：核心只做契约/胶水；平台原语优先；每个自研模块写“为什么”。

### 6.2 安全

auth/CSRF/XSS/上传/依赖漏洞。防御：默认安全、审计、测试、依赖治理、外部评审。

### 6.3 范围蔓延

从 Web 全栈扩到移动/游戏/CLI/云。防御：阶段门槛、真实需求触发、第一版不做列表。

### 6.4 生态/文档

新框架没有社区；用户遇到问题只能读源码。防御：dogfood、错误诊断、配方、AI 友好、示例。

### 6.5 性能

自研 SSR/DB 可能慢。防御：基准、查询计划、缓存、避免每请求重对象。

### 6.6 维护者风险

一个人维护框架 + 产品。防御：核心小、依赖少、自动化、停止条件、可回退到现有框架。

### 6.7 迁移风险

旧项目无法迁移。防御：并行新应用、逐步迁移、不重写、内容/路由映射。

### 6.8 AI 生成代码

AI 可能生成不安全/不一致代码。防御：类型/测试/安全闸门、固定契约、review。

## 七、许可证与资产

- 框架代码许可证待定（建议 MIT/Apache-2.0，用户决策）；
- 依赖许可证清单；
- 设计 token/字体/图标沿用 LRDS 的资产登记；
- 文档/示例的许可证与代码一致。

## 九、治理

- 核心契约变更：D/E 决策记录 + CHANGELOG；
- 依赖变更：lockfile diff + 理由 + 测试；
- 安全事件：登记、修复、复盘；
- 版本发布：SemVer + tag；
- 定期（季度）依赖/风险复核。
