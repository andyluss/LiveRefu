# 01 · 理念与边界

> 青橙全栈 · 技术框架提案 ｜ 状态：提案 / 未实现 ｜ 日期：2026-10-26 13:24

## 一、我们真正想摆脱的是什么

“摆脱对第三方技术的过度依赖”很容易被理解成“什么都自己写”。那不是可控，是自负。

浏览器、HTTP、SQLite、密码学、操作系统，都不该由一个小团队重写。真正要摆脱的是：

- **黑箱**：出了问题只能等上游；
- **锁定**：路由/数据/auth/构建绑死在一个框架的抽象里；
- **不可替换**：换一个运行时或数据库要重写应用；
- **不可审计**：不知道依赖做了什么、传了什么、升级会坏什么；
- **不可退出**：没有 raw handler、raw SQL、adapter 出口。

所以青橙全栈的原则是：

> **拥有应用契约，不拥有整个宇宙；依赖可以换，应用不重写。**

## 二、五条设计原则

### 2.1 契约优先

框架的核心不是“实现”，而是**契约**：

- 一个页面是什么；
- 一个动作的输入/输出/错误是什么；
- 一张表/迁移是什么；
- 一次 session/权限检查是什么；
- 一个 adapter 必须满足什么。

实现可以换（Node/Bun、SQLite/Postgres、HTML/其它 renderer），契约不换。

### 2.2 铺好的路 + 随时下车

默认路径要足够短：

```bash
qc new my-app
cd my-app
qc dev
```

但每一层都要有出口：

- 路由层可以挂 raw handler；
- 数据层可以写 raw SQL；
- UI 层可以输出原生 HTML；
- 构建层可以拿到 server entry；
- adapter 可以替换。

“下车”不是失败，是设计的一部分。

### 2.3 渐进披露

新手只需要知道：

- 文件放哪；
- `page` / `action` / `table` / `auth` 四个词；
- `qc dev` / `qc build` / `qc start`。

高级用户才需要知道：

- 请求生命周期；
- adapter 接口；
- 流式渲染；
- 连接池/事务；
- 部署拓扑。

框架不应该一上来把 30 个概念塞给使用者。

### 2.4 Web 标准优先

- 请求/响应用 `Request` / `Response`；
- HTML 是默认输出；
- 表单是默认真实交互；
- CSS 用标准层叠/变量；
- 不把“必须用某个客户端运行时”作为前提。

这样框架可以老得慢一点，用户也可以带着 HTML/CSS/JS 知识离开。

### 2.5 安全与无障碍是默认值

- 默认转义 HTML；
- 默认 CSRF 保护；
- 默认安全头；
- 默认 session cookie（HttpOnly/SameSite/Secure）；
- 默认密码哈希；
- 默认焦点可见/对比度/键盘；
- 默认错误页不泄露堆栈。

这些不能靠“使用者记得”。

## 三、依赖分层

| 层 | 内容 | 策略 |
| --- | --- | --- |
| **T0 平台** | Node/Bun、Web API、SQLite、OS | 不重写；只做薄 adapter |
| **T1 核心依赖** | TypeScript、构建器、密码哈希、校验器 | 少量、固定版本、可替换、写进依赖预算 |
| **T2 适配器** | Postgres、OAuth/OIDC、对象存储、邮件 | 可选；不进核心；按需安装 |
| **T3 应用依赖** | 业务库、第三方 SDK | 应用自己选；框架不替它担保 |

**核心依赖预算**：第一版运行时依赖不超过 **5 个**（不含 devDependencies），每个都要写“为什么不能用平台原语替代”。

### 3.1 “过度依赖”的判据

不是“用了第三方”，而是：

- 核心抽象被某家框架独占；
- 升级要改应用代码；
- 出问题无法定位/替换；
- 没有 raw/escape 出口；
- 依赖链不可审计；
- 版本不 pin。

只要不满足这些，用成熟原语是理性的。

## 四、目标用户

- 会 TypeScript、HTML/CSS、基本 HTTP 的独立开发者/小工作室；
- 想快速做网站、后台、API、应用服务端，但不想学五套框架；
- 接受“默认约定”，但在需要时能接管；
- AI 代理：需要稳定文件结构、命令、错误信息，而不是“猜魔法”。

## 五、成功标准

第一版不追求“比 Nuxt 强”，而是：

1. **10 分钟内**从空目录到可访问页面；
2. **1 小时内**做出带 auth + CRUD + 迁移的小应用；
3. 核心运行时依赖 ≤5；
4. 换 SQLite→Postgres、Node→Bun 不重写页面/动作；
5. 所有关键路径有错误页/诊断/测试；
6. 一个真实项目（网站或 LiveFab 子集）能 dogfood；
7. 使用者能说出“我知道我的数据/请求/权限在哪”。

## 六、非目标

- 不做通用低代码/无代码；
- 不做“一套代码跑所有端”的幻想；
- 不做新的 UI 设计语言（用 LRDS）；
- 不做云平台/托管服务；
- 不追求零依赖；
- 不替代 Git/CI/部署平台。

## 七、最大的风险

**NIH（Not Invented Here）**：为了“可控”重写太多，最后得到一个更差、更不安全、更没人维护的框架。

防御：

- 核心只写“契约 + 胶水 + 默认值”；
- 每个自研模块必须回答“为什么不用现成原语”；
- 每个依赖必须有替换路径；
- 先 dogfood，再推广；
- 没有真实应用，不扩平台。
