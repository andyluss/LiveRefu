# 青橙全栈（QC Stack）· 技术框架提案

> **状态**：**P4 运维核心已完成（日志/备份/部署模板）/ P5 待做** ｜ 日期：2026-10-26 13:47 ｜ 决策：F1–F12 已按推荐（见 [08](08_决策清单.md)）
> **定位**：青橙设计的技术底座。不是新的设计系统，也不是 Nuxt/Astro 的换皮；是一套**Web 优先、全栈、可替换依赖**的应用框架。
> **一句话**：让一个懂 TypeScript 和基本 Web 的人，不研究 bundler / HTTP / ORM / session / 部署细节，也能做出网站、应用和大部分游戏服务端需求；同时保留“随时接管底层”的出口。

## 一、为什么现在做

现有工作区已经证明了几件事：

- 网站用 **Nuxt 4 + Vue 3 + Bun**，LiveFab 用 **Astro**，两套 Web 框架、两套路由/构建/部署心智；
- 数据层有 **Drizzle + SQLite**，但只在网站里，LiveFab 还没有同构的数据/鉴权底座；
- 每个新项目都要重新决定：路由、渲染、表单、鉴权、session、迁移、错误页、构建、部署；
- 依赖一多，升级/安全/排障就变成“只有某个人懂”的黑箱；
- AI 能快速生成代码，但如果没有统一契约，生成得越快，分叉得越快。

青橙设计已经有理念、token、组件契约、验收闸门；现在缺的是**让这些约束真正运行起来的技术框架**。

## 二、目标与非目标

### 目标

1. **全栈但薄**：路由、渲染、数据、鉴权、表单、任务、构建、部署走一条默认路。
2. **使用者不需要懂底层**：默认配置可用；错误信息能指路；契约由框架守住。
3. **可控依赖**：核心只依赖平台标准与少数固定版本；第三方通过 adapter 接入，可替换。
4. **Web 优先**：先把网站/应用/后台/API 做扎实；移动端、游戏、CLI 后置。
5. **对 AI 友好**：命令、文件结构、错误、文档可预测；不靠“猜框架魔法”。
6. **与青橙设计同源**：UI 直接用 LRDS token/组件；不另造一套视觉语言。

### 非目标

- 不做新的浏览器/操作系统/数据库/编程语言。
- 不做“零代码”或“万能低代码”。
- 不做第二个 Nuxt/Astro；核心不依赖它们。
- 不强迫所有产品用同一套 UI 运行时；共享契约，不共享一切。
- 不在第一版做移动端、游戏引擎、CLI 全家桶。

## 三、核心主张

> **拥有“应用契约”，不拥有“整个宇宙”。**

不重写 HTTP 解析、SQLite、密码学、浏览器；这些用平台/成熟原语。青橙全栈拥有的是：

- 项目结构与应用生命周期；
- 路由/页面/动作/data/auth 的**契约**；
- 默认的渲染、表单、校验、错误、session、迁移、构建、部署；
- 依赖的**准入/替换/升级规则**；
- 开发体验与诊断信息。

这样既不是“从零造轮子”，也不是“把命交给某个框架”。

## 五、框架会提供什么（第一版 Web）

- `qc new`：生成一个可运行的应用骨架；
- `qc dev`：本地开发、热重启、错误页；
- `qc build` / `qc start`：可部署的单进程产物；
- 文件即路由：page / action / api；
- 服务端渲染的 HTML + 可选 islands；
- SQLite 优先的数据层 + 迁移；
- 内置 session/password/OAuth 适配位；
- 表单/校验/错误/CSRF/安全头默认值；
- 与 LRDS 组件/token 的 UI 接入；
- `qc test` / `qc typecheck` / `qc doctor`；
- 依赖治理与“退出测试”。

## 七、与 LRDS / kits 的关系

- **LRDS**：设计系统（token、组件契约、风格卡、HUB、闸门）——负责“长什么样、怎么用”。
- **青橙全栈**：技术框架（路由、数据、auth、构建、部署）——负责“怎么跑起来”。
- **`design/kits/`**：保留；它是**介质接入包**（Web/Godot/App），可服务非全栈项目。全栈 UI 会复用 `kits/web` 的 token/组件，但不会把 kit 变成框架核心。
- 一句话：**kits 是零件，全栈是装配线。**
