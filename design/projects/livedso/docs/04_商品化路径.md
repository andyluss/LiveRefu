# LiveDSO · 商品化路径（未来提案）

> **状态**：提案，**未实施、未排期** ｜ 日期：2026-10-27 ｜ 适用版本：v1.3+
> **原则**：核心仍是本地优先的设计系统操作台；商品化只在项目成熟后增加**可交付成果物**，不改核心定位。
> **关联**：[产品定义](00_产品定义.md) · [路线图](02_路线图.md) · [决策记录](03_决策记录.md) · [许可选项](../../../../docs/software/licenses/08_LiveDSO许可选项.md)

## 一、为什么现在不直接卖

LiveDSO 现在卖的是“能力”，不是“成品”：

- 用户要自己导入 token、跑检查、读报告、决定修什么；
- 独立开发者愿意用，但不一定愿意为“又一个工具”付费；
- 设计系统的价值依附于具体产品；脱离项目的工具很难单独定价。

所以商品化不是加功能，而是把 LiveDSO 的检查能力包装成**别人能直接购买的结果**。

## 二、Hero SKU：设计系统体检包

**名称（暂定）**：Design System Health Report / 设计系统体检包。

| 项 | 内容 |
| --- | --- |
| **买家** | 设计代理机构、20–200 人产品团队、正在做设计系统迁移的团队 |
| **交付物** | 健康分 + 问题清单（对比度/契约/裸值/风格卡）+ 按影响排序的修复计划 + 90 天路线图 + 一页老板摘要 |
| **价格带** | ¥6,800–12,800 / 次；代理机构白标报告 ¥2,000/份（待验证） |
| **交付周期** | 5 个工作日 |
| **为什么能卖** | 买家已经被问题卡住；现有 `check/report` 已覆盖大部分；不需要云端/迁移 |
| **不包含** | 不替客户改代码；不做长期驻场；不承诺“一次修完” |

### 最小扩展（未来再做）

- CLI `audit`：输入 vault，输出 HTML/PDF 体检报告；
- 报告模板：问题分级、修复建议、90 天计划；
- 白标字段：机构名/Logo/联系方式；
- 样本报告：用 LRDS 真实 case 做 1 份公开样张。

**不做**：新的 SaaS、账号系统、计费系统；先卖报告，不卖平台。

## 三、备选方案

| 方案 | 卖什么 | 优点 | 风险 | 建议 |
| --- | --- | --- | --- | --- |
| **A. 体检包（推荐）** | 报告 + 修复计划 | 最快；客单价高；复用现有检查 | 是产品化服务，不是纯软件 | 先做 |
| B. 设计系统 Starter Kit | token + CSS + 组件 + 文档模板 | 数字商品，可规模化 | 通用套件易被压价；适配成本高 | 作为引流/低价品 |
| C. 白标设计系统门户 | 托管 token/契约/文档 | 订阅收入；代理机构需要 | 工程/运维重；竞争激烈 | 体检验证后再做 |
| D. 修复 Sprint | 人天服务 | 客单价更高 | 不可规模化；依赖个人时间 | 体检后的 upsell |

## 四、目标产品案例：设计系统服务于什么

> 以下为**示例产品**，用于说明“设计系统 → 可售软件”的链路，不是路线图承诺。

### 案例 A · 自由职业者的发票/账本 Web App「慢慢记」

- **形态**：本地优先 Web App；发票编辑、客户账本、年度收入摘要、PDF 导出；桌面/移动自适应。
- **用户**：独立设计师、写作者、顾问；每月 5–20 张发票；不想用重型财务软件。
- **核心体验**：打开就是一张“本月待收”清单 → 新建发票 → 预览/导出 → 标记已收；空状态给模板，不要求先配置。
- **价格**：免费 3 张/月；¥68/年不限量；不强制账号。
- **设计系统在其中的角色**：发票表单、错误状态、金额/日期层级、浅色/深色/高对比三套主题；`form-field` 契约保证“错误在哪、怎么修”一致；对比度闸门保证账本数字可读。
- **没有它会怎样**：三套主题变成三个产品；同一个“保存失败”在四个页面四种写法；深色模式金额看不清；每加一个页面就多一套 CSS。
- **LiveDSO 的角色**：token/契约/风格卡/检查；发布前跑健康报告，防止“新页面绕过系统”。

### 案例 B · 家庭能源硬件配套 App「家的能量」

- **形态**：硬件电流传感器 + 手机 App；显示光伏/电池/电网/用电成本与停电预案；家庭共享。
- **用户**：有光伏/储能的城市家庭；关心电费、停电、老人小孩用电安全。
- **核心体验**：首页一眼看到“现在用什么电、多少钱、今晚够不够”；异常时给动作，不只给红色；安装向导必须让非技术用户完成。
- **价格**：硬件一次性 + ¥199/年家庭版（历史/共享/备份）。
- **设计系统在其中的角色**：状态色不能是唯一通道；焦点/触控/大字；安装表单的字段契约；暗色环境下的可读性；家庭共享权限的视觉一致性。
- **没有它会怎样**：红/绿对比度不足；安装失败无法定位；父母看不懂“电网/电池”术语；客服成本随用户数上升。
- **LiveDSO 的角色**：语义 token 把“电网/电池/光伏”映射为稳定角色；audit 报告检查对比度、焦点与契约完整性。

### 案例 C · 老人用药提醒 App「药盒」

- **形态**：大字号、高对比的移动 App；今日用药、确认/跳过、漏服提醒、家属共享、打印用药表。
- **用户**：65+ 老人 + 子女照护者；每天 1–5 种药；对复杂菜单和低对比极不耐受。
- **核心体验**：打开只有“今天要吃什么”；一次确认一个大按钮；漏服时给“现在补/联系家人”，不制造羞耻。
- **价格**：免费基础；¥99/年家庭共享 + 打印/导出。
- **设计系统在其中的角色**：字号/对比度/触控目标/焦点可见是硬闸门；“确认/跳过/稍后”的语义必须全产品一致；减少动效。
- **没有它会怎样**：字号层级混乱；确认与跳过颜色相近；误触造成漏服；无障碍问题变成安全问题。
- **LiveDSO 的角色**：把“安全关键状态”做成契约和检查；报告能指出具体 token/组件，而不是泛泛说“再优化一下”。

## 五、成熟触发条件

只有满足以下条件才进入实施：

- [ ] v0.3 的契约编辑/预览/采用至少有一项稳定；
- [ ] `check/report` 在 3 个真实 vault 上误报可接受；
- [ ] 有 1 个代理机构愿意用真实项目试跑；
- [ ] 能出具一份不暴露客户隐私的样报；
- [ ] 许可/商业服务边界已写清（Apache-2.0 核心 + 商业服务）。

## 六、商业化边界

- 核心代码保持 Apache-2.0；体检报告/白标/咨询是商业服务；
- 客户 vault 不上传；报告在本地生成或客户指定环境生成；
- 不把客户数据用于训练/案例，除非书面同意；
- 报告是技术建议，不替代法律/合规审计。

## 七、成功指标

- 2 周内卖出 1 份体检；
- 报告能直接进入客户下一次迭代计划；
- 1 个代理机构愿意复购/白标；
- 不增加核心维护负担（报告模板可复用）。

> **当前决定：只记录，不实施。** 等 LiveDSO 成熟、有真实客户意向后再启动。
