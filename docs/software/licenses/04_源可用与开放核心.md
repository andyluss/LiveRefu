# 04 · 源可用与开放核心

> **一句话**：源可用是“你能看源码，但不是开源”；开放核心是“核心开源，企业功能收费”；两者都需要诚实边界。

## 一、源可用（Source-available）

常见：

- **BUSL-1.1**：限制生产/竞争使用，约定时间后转开源；
- **Elastic-2.0**：不能提供竞争性托管服务；
- **SSPL-1.0**：提供服务需开源服务栈，争议大；
- **FSL**：限制竞争使用，2 年后转 MIT/Apache；
- **Commons Clause**：禁止“销售”软件功能，附加在宽松许可上。

**它们不是 OSI 开源**：因为限制用途/领域/竞争。宣传时必须写“source-available”，不能写“open source”。

**适合**：

- 你有一个明确的商业服务，需要防止云厂商直接托管；
- 你愿意用“时间锁”换保护；
- 你能接受部分社区/发行版拒绝。

**风险**：

- 社区信任下降；
- 企业采购可能不接受；
- 许可变更历史复杂；
- “开源”品牌受损。

## 二、开放核心（Open Core）

- 核心开源（如 MIT/Apache/AGPL），企业功能/托管/合规/SSO/审计收费；
- 边界要清楚：不能把基础可用性砍掉，逼用户买企业版；
- 开源核心要有真实价值，否则社区不会来；
- 企业版要解决“组织问题”（权限/审计/SLA/合规），不是“把按钮藏起来”。

**适合**：独立开发者/小团队，先建立采用，再卖团队/企业。

## 三、诚实边界

| 说法 | 是否诚实 | 建议 |
| --- | --- | --- |
| “开源，但生产环境要付费” | 通常不是开源 | 说“source-available” |
| “开源核心 + 企业版” | 可以 | 写清哪些功能开源 |
| “免费试用，之后收费” | 可以 | 不是开源，别混用 |
| “AGPL + 商业授权” | 可以（双许可） | 需拥有版权/CLA |
| “MIT 但禁止商用” | 不是 MIT | 用其他许可并明确 |

## 四、对 LiveDSO 的含义

LiveDSO 是本地优先工具，天然适合：

- **核心开源 + 托管/团队/审计收费**；
- 不宜把“本地检查/报告/导出”锁进企业版；
- 若担心云厂商托管，可考虑 AGPL 或“核心 Apache + 托管服务”的组合；
- 若首批用户是独立开发者，**简单、可读、低摩擦**比“最强保护”更重要。
