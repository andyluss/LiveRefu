# 00 · 总论：开源不是一种许可

> **一句话**：开源是一组关于**使用、研究、修改、分发**的自由；许可只是把这组自由写成可执行条款。

## 一、开源定义（OSI 的七条直觉）

1. **自由再分发**：不能禁止别人把软件作为更大作品的一部分分发；
2. **源码可得**：必须提供源代码；
3. **允许衍生作品**：必须允许修改和派生；
4. **完整性**：可以要求修改版用不同名称/版本，但不能禁止修改；
5. **不歧视个人/群体**；
6. **不歧视用途**（不能禁止商业、军事、研究等）；
7. **技术中立**：不能绑定某一种产品/平台。

> “源码可见”不等于开源；BUSL/Elastic/SSPL 等是 **source-available**，不是 OSI 开源。

## 二、许可 vs 商业模型

| 问题 | 许可回答 | 商业模型回答 |
| --- | --- | --- |
| 能不能商用？ | 是/否/条件 | 谁付钱？ |
| 能不能改？ | 是/否/条件 | 谁维护？ |
| 改了要不要开源？ | 看许可 | 谁承担成本？ |
| 能不能提供云服务？ | 看许可 | 如何收费？ |
| 专利/商标？ | 看许可 | 品牌如何授权？ |

**常见错误**：以为“选了 AGPL 就能赚钱”或“选了 MIT 就没法赚钱”。许可只决定权利边界；收入来自服务、托管、支持、市场、企业版等。

## 三、四种产品姿态

1. **最大化采用**：MIT/Apache-2.0；别人容易集成，你的护城河是执行/品牌/服务。
2. **保护共同体**：GPL/AGPL；衍生/网络服务必须回馈；适合基础设施/平台。
3. **开放核心**：核心开源，团队/企业功能专有；需要清晰边界，避免“开源版残疾”。
4. **源可用**：先保护商业，再定时转开源；不是开源，需诚实标注。

## 四、对独立开发者的含义

- 你没有法务团队，**简单、可读、被广泛理解**的许可更重要；
- 你的第一批用户也是独立开发者，他们更在意“能不能用/能不能改/会不会被起诉”；
- 你需要的不是“最强保护”，而是**信任 + 可持续收入**；
- 如果以后要双许可/企业版，**贡献者授权（CLA/DCO）**要提前想清楚。

## 五、青橙视角

青橙的“可参与/可退出”与开源天然接近，但要注意：

- 开源不是“把代码扔出去”；
- 可退出 = 数据/格式/部署可迁移，不等于许可；
- 诚实 = 明确标注“开源/源可用/开放核心”，不玩文字游戏；
- 维护 = 许可之外，还要有治理、文档、支持。
