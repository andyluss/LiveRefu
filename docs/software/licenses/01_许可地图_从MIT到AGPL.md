# 01 · 许可地图：从 MIT 到 AGPL

> **一句话**：先看“你想让别人做什么”，再看“你要求别人回馈什么”，最后看“你能不能接受被云厂商白嫖”。

## 一、宽松许可

### MIT

- 极简：保留版权/许可声明，允许使用/复制/修改/合并/发布/再许可/销售；
- **没有明示专利授权**；没有商标授权；没有担保；
- 适合：库、工具、希望最大化采用的产品。

### Apache-2.0

- 宽松 + **明示专利授权** + 专利诉讼终止条款；
- 需要保留 NOTICE（如有）、变更声明；
- 与 GPLv3 兼容，**与 GPLv2-only 不兼容**（专利/附加限制）；
- 适合：企业采用、需要专利确定性的基础设施。

### BSD-2/3

- 与 MIT 类似；3-clause 多一条“不得用作者名背书”；
- 没有明示专利；适合学术/极简项目。

## 二、弱著佐权

### MPL-2.0

- **文件级** copyleft：修改的 MPL 文件要开源；可与闭源代码组合；
- 明示专利授权；有二级许可兼容机制（GPL/LGPL/AGPL）；
- 适合：希望“改动回馈”，但允许更大作品闭源。

### LGPL-2.1/3

- **库级** copyleft：修改库本身要开源；通过动态链接使用可闭源；
- 适合：库/运行时；比 GPL 更适合商业集成。

## 三、强著佐权

### GPL-2.0 / GPL-3.0

- 分发衍生作品时，必须按 GPL 提供源码/许可；
- **SaaS 通常不触发**（除非分发软件/容器镜像等，需具体分析）；
- GPLv2-only 与 Apache-2.0 不兼容；GPLv3 与 Apache-2.0 兼容；
- 适合：桌面软件、系统工具、希望衍生回馈的社区项目。

### AGPL-3.0

- 在 GPLv3 基础上，**网络交互**也视为触发点：用户通过网络使用修改版，应能获取源码；
- 适合：SaaS/服务端产品，防止“改完只放云上”；
- 代价：部分企业/独立开发者会回避；需要清楚解释“什么时候触发”。

## 四、源可用（不是开源）

| 许可 | 核心限制 | 备注 |
| --- | --- | --- |
| BUSL-1.1 | 限制与“生产使用/竞争服务”相关；到期转开源 | 参数由发布者定，需读全文 |
| Elastic-2.0 | 不能提供竞争性托管/服务 | 不是 OSI 开源 |
| SSPL-1.0 | 提供服务需开源“服务栈” | 争议大，常被发行版拒绝 |
| FSL | 限制竞争使用，2 年后转 MIT/Apache | 由某公司提出，需读具体版本 |
| Commons Clause | 不能“销售”软件功能 | 常附加在 MIT/Apache 上，改变开源性质 |

## 五、兼容性速查

- Apache-2.0 → GPLv3：可以；→ GPLv2-only：不可以；
- MIT/BSD → GPL：可以；
- MPL-2.0 → GPL/LGPL/AGPL：有二级许可机制，通常可以；
- GPLv2-only + Apache-2.0：不可以；
- GPLv3 + AGPLv3：AGPL 更严格，组合需谨慎；
- 源可用许可与开源代码混合：通常不能声称整体开源。

## 六、怎么选（粗线条）

| 目标 | 首选 | 次选 |
| --- | --- | --- |
| 最大采用/库/工具 | MIT | Apache-2.0 |
| 企业采用/专利确定性 | Apache-2.0 | MIT |
| 改动回馈但不强制整个作品 | MPL-2.0 | LGPL |
| 衍生/分发必须开源 | GPL-3.0 | GPL-2.0 |
| 防止云厂商白嫖 | AGPL-3.0 | 源可用 |
| 先商业后开源 | FSL/BUSL | 开放核心 |
