# 08 · LiveDSO 许可选项

> **状态**：许可未定 ｜ **首批用户**：独立开发者 ｜ **不是法律意见**
> 目标：在“被采用”“能收费”“保护托管”“社区信任”之间选一个可持续组合。

## 一、四个方案

### 方案 A：Apache-2.0 核心 + 商业托管/团队版（推荐给独立开发者优先）

- 核心：Apache-2.0（专利授权、企业友好、可闭源集成）；
- 收费：托管、团队协作、审计、私有 registry、支持、培训；
- 优点：采用门槛低；独立开发者/企业都能接受；有专利确定性；
- 风险：云厂商可托管；护城河靠产品/服务/品牌；
- 适合：想先做采用、再卖服务。

### 方案 B：MIT 核心 + 服务

- 核心：MIT（最简单、最容易被独立开发者采用）；
- 收费：托管/服务/企业版；
- 优点：摩擦最低；社区友好；
- 风险：无专利明示；更难阻止闭源 Fork/托管；
- 适合：极简工具、个人品牌强、服务收入为主。

### 方案 C：AGPL-3.0 核心 + 商业授权

- 核心：AGPL（网络使用触发源码义务）；
- 收费：商业授权/托管/企业版；
- 优点：保护托管；防止“改完只放云上”；
- 风险：企业/部分独立开发者回避；需要 CLA/版权才能双许可；
- 适合：托管是主要收入、且你拥有版权/贡献者授权。

### 方案 D：源可用（FSL/BUSL）+ 定时转开源

- 核心：source-available（限制竞争/生产使用，2 年后转 MIT/Apache）；
- 收费：商业许可/托管；
- 优点：保护商业；最终开放；
- 风险：不是 OSI 开源；社区/发行版可能拒绝；信任成本高；
- 适合：有明确商业服务、能承受“非开源”标签。

## 二、对比

| 维度 | A Apache | B MIT | C AGPL | D 源可用 |
| --- | ---: | ---: | ---: | ---: |
| 独立开发者采用 | 高 | 最高 | 中 | 低 |
| 企业采用 | 高 | 高 | 低 | 中 |
| 专利明确 | 是 | 否 | 是 | 看具体 |
| 防云托管 | 弱 | 弱 | 强 | 强 |
| 社区信任 | 高 | 最高 | 中 | 低 |
| 双许可可行性 | 需 CLA | 需 CLA | 天然 | 可 |
| 与“开源”标签 | 是 | 是 | 是 | **否** |

## 三、我的倾向（供决策）

如果首批用户是独立开发者，**A（Apache-2.0 核心 + 商业服务）**最平衡：

- 独立开发者不害怕专利/企业条款；
- 企业以后也容易接受；
- 你保留托管/团队/审计/支持的收入空间；
- 不玩“假开源”。

如果你更在意“防止云厂商直接托管”，选 C；但要做好采用率下降、需要 CLA 的准备。

如果你只想最大化传播、服务收入为主，选 B；但要接受 Fork/托管竞争。

不要把 D 说成“开源”；如果选 D，文案、包元数据、README 都要明确“source-available”。

## 四、无论选哪个，先做

- 版权归属/贡献者授权（CLA/DCO）；
- LICENSE + NOTICE + 文件头；
- 第三方依赖清单/SBOM；
- 商标/品牌政策；
- 安全/隐私说明；
- 律师审阅。

## 五、需要你拍板

1. A / B / C / D？

3. 是否愿意引入 CLA（为了未来双许可）？
4. 是否接受 2 年转开源的源可用方案？
