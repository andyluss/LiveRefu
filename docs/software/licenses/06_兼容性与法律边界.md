# 06 · 兼容性与法律边界

> **一句话**：许可是“版权许可”，不自动解决专利、商标、数据、贡献者权利与出口合规。

## 一、兼容性：最常见的坑

| 组合 | 结论 | 说明 |
| --- | --- | --- |
| Apache-2.0 + GPLv3 | 可以 | Apache 专利条款与 GPLv3 兼容 |
| Apache-2.0 + GPLv2-only | **不可以** | GPLv2 的附加限制与 Apache 冲突 |
| MIT/BSD + GPL | 可以 | 宽松代码可被 GPL 吸收 |
| MPL-2.0 + GPL/LGPL/AGPL | 通常可以 | 有二级许可机制，需按版本 |
| GPLv2-only + GPLv3 | 不可以（除非“or later”） | 版本边界要看清 |
| AGPL + 闭源服务 | 可以商用，但网络使用触发源码义务 | 不是“不能闭源”，是“必须提供源码” |
| 源可用 + 开源 | 通常不能声称整体开源 | 限制条款会传染/冲突 |

**做法**：维护一份 SBOM/第三方清单；对每个依赖记录 SPDX、版本、修改、链接方式；不要凭“大家都这么用”判断。

## 二、专利

- MIT/BSD 没有明示专利许可；Apache-2.0 有；
- 专利诉讼可能触发终止条款（Apache）；
- 你自己的专利要单独考虑：是否授权、是否防御性终止；
- “开源”不等于“专利免费”。

## 三、商标

- 版权许可通常不包含商标；
- 你可以用代码，但不能用项目名/Logo 暗示官方；
- 建立商标政策：允许事实性引用，禁止误导性使用；
- 域名/社交账号也属于品牌资产。

## 四、贡献者权利

- **DCO**：贡献者声明有权提交；简单，适合宽松项目；
- **CLA**：贡献者授权你重新许可/双许可；适合开放核心/双许可；
- 没有 CLA/DCO，你可能无法改变许可或做企业版；
- 记录贡献者、来源、AI 生成内容（如适用）。

## 五、数据与隐私

- 许可不覆盖用户数据；
- 隐私政策、数据处理协议（DPA）、GDPR/CCPA 等单独处理；
- 如果产品处理个人数据，需要明确“谁控制/谁处理/保留/删除”。

## 六、出口/制裁/免责

- 出口管制/制裁名单可能限制分发；
- 免责声明（“AS IS”）不能免除故意/重大过失；
- 企业客户可能要求 indemnity（赔偿）——保险/合同单独处理。
