# 02 · 宽松许可：MIT、Apache-2.0、BSD

> **一句话**：宽松许可把“采用成本”降到最低；你的护城河必须来自产品、服务、品牌或生态，而不是许可。

## 一、共同点

- 允许商用、修改、分发、再许可（保留声明）；
- 通常不要求衍生作品开源；
- 不提供担保；不保证适销/适用；
- 商标通常不授权（许可只覆盖版权，必要时另有专利条款）。

## 二、MIT

**适合**：库、CLI、模板、希望被大量集成的工具。

**要写清**：

- 版权声明 + 许可全文；
- 第三方依赖的许可；
- 如果你有专利，考虑额外专利授权（MIT 本身没有明示专利许可）。

**风险**：

- 别人可以闭源 Fork 并商业竞争；
- 没有专利保护；
- 社区可能期待你长期维护，但许可不产生收入。

## 三、Apache-2.0

**优点**：

- 明示专利授权，企业法务更容易接受；
- 专利诉讼终止条款（你起诉别人专利侵权，专利许可终止）；
- 有 NOTICE/变更声明机制。

**义务**：

- 保留版权/许可/NOTICE；
- 修改文件要显著说明；
- 不得使用项目商标（除非另有商标政策）。

**兼容性**：

- 与 GPLv3 兼容；
- **与 GPLv2-only 不兼容**（附加限制）；
- 与 LGPL/MPL 组合需看具体方向。

**适合**：基础设施、企业采用、希望专利确定性的独立产品。

## 四、BSD-2/3

- 2-clause：保留版权/许可；
- 3-clause：额外禁止用作者/项目名背书；
- 没有明示专利；适合学术/极简。

## 五、对独立开发者的建议

- 如果你要**最大采用**：MIT 或 Apache-2.0；
- 如果你有专利/企业客户：Apache-2.0；
- 如果你只想要极简：MIT；
- 如果你担心云厂商白嫖：不要只靠宽松许可，考虑 AGPL/源可用/服务护城河；
- 如果你计划双许可/企业版：**提前做 CLA/DCO**，否则你没有权利改许可。

## 六、常见误区

- “MIT 就必须免费”：不，MIT 允许商用/收费；只是不能禁止别人也商用。
- “Apache-2.0 可以随便用商标”：不，商标是单独的。
- “宽松许可没有义务”：有，保留声明/NOTICE/变更说明。
- “选了 MIT 就不能有企业版”：可以，但企业版功能/服务要与开源核心边界清楚。
