# 03 · 著佐权：GPL、AGPL、LGPL

> **一句话**：著佐权不是“禁止商用”，而是“你可以商用，但衍生/分发的自由必须继续传下去”。

## 一、GPL：分发触发

- 你分发 GPL 代码的衍生作品时，必须提供对应源码和许可；
- 你可以收费，但必须提供源码；
- **SaaS 通常不触发**（因为没有“分发”软件副本）；但容器镜像、客户端、SDK 可能触发；
- GPLv2-only 与 Apache-2.0 不兼容；GPLv3 与 Apache-2.0 兼容；
- 静态/动态链接、插件、脚本的边界需要法律判断，不要靠直觉。

**适合**：桌面应用、系统工具、希望衍生回馈的社区项目；不适合“希望被闭源产品广泛集成”的库。

## 二、AGPL：网络触发

- 在 GPLv3 基础上增加“网络交互”条款；
- 如果用户通过网络使用修改版，应能获取对应源码；
- 对 SaaS 更保护，但会劝退部分企业/独立开发者；
- 不是“禁止商业化”；你可以收费，但源码义务仍在。

**适合**：服务端/平台型开源产品，尤其是“云厂商可能直接托管”的场景。

**代价**：

- 企业法务可能直接拉黑；
- 独立开发者可能不理解“何时触发”；
- 你需要写清楚“哪些组件是 AGPL、哪些是独立服务”。

## 三、LGPL：库级

- 修改 LGPL 库本身要开源；
- 通过动态链接使用库的程序可以闭源（满足条件）；
- 适合库/运行时；比 GPL 更适合商业集成；
- 静态链接/修改库的边界需要具体分析。

## 四、怎么选

| 场景 | 建议 |
| --- | --- |
| 希望被闭源产品集成 | MIT/Apache-2.0 |
| 希望改动回馈，但允许大作品闭源 | MPL-2.0 |
| 库，允许商业链接 | LGPL |
| 桌面/工具，衍生必须开源 | GPL-3.0 |
| SaaS，防止云白嫖 | AGPL-3.0 |
| 既想开源又想卖企业版 | 双许可/开放核心，需 CLA |

## 五、独立开发者注意

- AGPL 会降低采用率；如果你的首批用户是独立开发者，先问他们是否介意；
- 如果你选 AGPL，**不要**再承诺“随便商用/闭源集成”；
- 如果你选 GPL，SaaS 可能不触发，别以为能防住云厂商；
- 如果你要双许可，必须拥有版权或拿到贡献者授权。

## 六、一句话对比

- GPL：**分发**时回馈；
- AGPL：**网络使用**也回馈；
- LGPL：**改库**回馈，用库可闭源；
- MPL：**改文件**回馈，可组合闭源。
