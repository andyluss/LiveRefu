# 00 · 总论：软件生态是文明的操作系统

> **一句话**：软件生态不是一堆 App，而是一套**把能量、材料、注意力、信任与权力转换成日常行为**的操作系统。

## 一、为什么用“生态”而不是“行业”

“行业”按公司分类：教育、金融、医疗、娱乐。它适合看竞争，不适合看**依赖**。

“生态”问的是：

- 这个产品依赖哪些基础设施？
- 谁为它付钱，谁承担维护？
- 数据、身份、关系、资产被锁在哪一层？
- 出故障时，谁能修、谁承担后果？
- 它让哪些行为变得更容易，哪些变得更难？

软件的真实结构，是一张**有方向的依赖图**：应用依赖框架，框架依赖运行时，运行时依赖操作系统与云，云依赖芯片、网络、电力与土地。每一层都向上提供“承诺”，向下转嫁“成本”。

## 二、五个底层供给

| 供给 | 内容 | 谁控制 | 设计含义 |
| --- | --- | --- | --- |
| **能量/算力** | 芯片、云、推理、存储 | 少数基础设施商 | 延迟、成本、可用性会变成产品体验 |
| **网络** | 协议、带宽、路由、身份 | 运营商/平台/标准组织 | 离线、同步、跨区是产品结构，不是工程细节 |
| **数据** | 数据库、对象存储、日志、模型 | 平台/企业 | 数据重力决定迁移成本 |
| **界面** | OS、浏览器、输入、屏幕 | 平台 | 交互语法受平台约束 |
| **分发** | 应用商店、搜索、社交、开源 | 平台/社区 | 获客成本与规则风险 |

> 软件产品不是“想法 + 代码”，而是“**在这五个供给上，切出一块可被承诺的稳定性**”。

## 三、三种经济

1. **许可证经济**：一次性卖软件/买断。适合工具、库、嵌入式；缺点是收入不连续。
2. **订阅经济**：按月/年租用。适合持续服务、协作、云；缺点是疲劳、流失、必须不断证明价值。
3. **交易经济**：从每笔交易/抽成/服务费中收费。适合市场、支付、垂直 SaaS；缺点是需要规模与信任。

还有第四种常被忽略：**维护经济**。企业为“不出事、能修复、能审计、能交接”付费。它不性感，但更长期；青橙的“维护被看见”正好落在这里。

## 四、四个设计面

软件设计不只是界面：

- **工具面**：用户如何完成动作（编辑器、表单、命令、快捷键）。
- **协议面**：系统之间如何承诺（API、文件格式、权限、同步）。
- **组织面**：谁决定、谁维护、谁承担失败（角色、审计、SLA）。
- **美学面**：用户如何感受与记忆（材料、声音、节奏、语气）。

只做工具面，会得到“好用但脆弱”的产品；只做美学面，会得到“好看但不可维护”的皮肤。青橙的机会在**四个面同时成立**。

## 五、生态位：不要站在“被平台顺手做掉”的位置

一个生态位是否成立，看四个问题：

1. **平台会不会顺手做？** 如果它是平台主路径的附属功能，独立产品很难活。
2. **用户是否愿意为“独立”付费？** 数据主权、离线、可迁移、审计、品牌，都是独立理由。
3. **维护是否可累积？** 每次修复是否变成资产（模板、规则、知识、社区），而不是纯人力。
4. **是否有可退出的信任？** 导出、迁移、自托管、开放格式，反而会提高付费意愿，因为用户不怕被锁。

## 六、复古未来在这里的位置

复古未来不是“给软件加一层旧滤镜”。它关心的是：

- 技术曾经承诺过什么，又没兑现什么；
- 材料、维修、时间、劳动如何被看见；
- 一个系统是“被拥有”，还是“被租用”；
- 未来不是单一的，而是多种世界并存。

这使它对软件生态有一个独特提问：

> **这个产品让未来更像一个可居住的地方，还是更像一个更顺滑的收银台？**

## 七、设计含义 / 机会 / 反模式

**设计含义**：

- 先画依赖图，再画界面；
- 把“离线、导出、迁移、维护”当产品功能，不是文档脚注；
- 用可读的状态替代黑箱的“智能”。

**机会**：

- 本地优先的基础工具；
- 可自托管/可审计的垂直系统；
- 维护/资产/知识的长生命周期产品；
- 把“可退出”做成卖点的服务。

**反模式**：

- 用“生态”当借口做全家桶；
- 用“AI”掩盖没有工作流；
- 用“开源”掩盖没有商业模式；
- 用“复古”掩盖不可用。
