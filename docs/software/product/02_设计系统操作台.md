# 设计系统操作台：从 Token 到可维护的系统

> **一句话**：设计系统不是“一个文档站”，而是一套**持续运行的运维系统**：源、契约、闸门、投影、采用、弃用。
> 方向：产品机会 Top 1 ｜ 状态：v0.1 ｜ 面向：设计系统负责人、设计工程师、20–500 人产品团队、设计代理机构。

## 一、先纠正一个品类错误

大多数“设计系统工具”把自己做成：

- 一个更漂亮的组件文档站；
- 一个 Figma 插件；
- 一个 token 编辑器；
- 一个 Storybook 的托管版。

它们都只覆盖了链条的一段。真正让设计系统失败的不是“文档不好看”，而是：

1. **源不一致**：Figma 一套、代码一套、文档一套；
2. **契约缺失**：组件只有样子，没有状态、键盘、错误处理；
3. **闸门太晚**：对比度、裸值、弃用、跨端差异到发布前才发现；
4. **采用率黑箱**：不知道哪些产品用了旧组件；
5. **维护不可见**：谁负责、何时弃用、迁移到哪，没人知道；
6. **多品牌/多世界失控**：每加一个产品就复制一套 token。

所以正确的品类是：

> **Design System Operations（设计系统运维）**：把设计系统当作一个持续交付的系统来运行，而不是一份静态规范。

## 二、谁痛，痛到什么程度

| 角色 | 当前工作流 | 真实痛点 | 愿意为什么付钱 |
| --- | --- | --- | --- |
| 设计系统负责人 | Figma + Storybook + zeroheight + 脚本 | 无法证明系统在被采用；每次变更像拆弹 | 采用率、审计、迁移、减少返工 |
| 设计工程师 | token JSON + CSS + TS + 多端 | 手写映射、裸值、平台漂移 | 自动生成、CI 闸门、预览 |
| 产品设计师 | Figma 组件库 + 文档 | 不知道代码里到底有什么；状态缺失 | 可信的组件目录、可预览状态 |
| 工程负责人 | 多产品/多端 | 升级成本、技术债、可访问性风险 | 版本、弃用、合规报告 |
| 代理/咨询 | 每个客户一套 | 重复搭建、交付不可复用 | 模板、白标、审计服务 |

**最愿意付费的不是“画图的人”，而是“要对系统一致性负责的人”**：设计系统负责人、平台工程、设计运营、代理机构。

## 三、产品对象：六个核心实体

### 1. Token

不是“颜色变量”，而是有层级、有所有者、有生命周期的设计决策：

```json
{
  "id": "sys.color.action.primary",
  "tier": "sys",
  "type": "color",
  "value": "{ref.color.teal.400}",
  "owner": "design-system",
  "status": "stable",
  "platforms": ["web", "ios", "android"],
  "contrast": { "on": ["bg.base", "bg.surface"], "min": 4.5 },
  "deprecatedBy": null,
  "since": "0.2.0"
}
```

关键字段不是 `value`，而是 **owner / status / platforms / contrast / deprecatedBy / since**。没有这些，token 只是变量。

### 2. Component Contract

组件契约至少包含：

- anatomy（解剖）；
- states（default/hover/active/focus/disabled/error/readonly）；
- keyboard & a11y；
- do/don't；
- cross-platform mapping；
- token references；
- usage（真实消费者）。

契约不是 Markdown 装饰，而是**可被检查的结构**：缺状态、引用不存在 token、没有键盘说明，都应该报错。

### 3. Style Card

风格卡是“世界皮肤”，不是主题变量：

- 色板、材质、光源、装饰母题、字体族、图像处理；
- 必须共享语法：字阶、间距、焦点、信息位置、无障碍下限；
- 与 token 的映射、对比度、预览、版本。

这使产品可以支持多品牌/多纪元，而不复制一套设计系统。

### 4. Projection

同一份源投影到：

- Web CSS variables / Tailwind / CSS-in-JS；
- iOS/Android 常量；
- Godot Theme；
- 文档站；
- Figma variables（可选）；
- 打印/实体规范（未来）。

投影不是“导出一次”，而是**可复算、可对账、可回滚**。

### 5. Gate

闸门是产品的核心差异：

- 对比度（文字/大文本/边框/焦点）；
- 裸值（业务代码不得写色值/字号/圆角）；
- 弃用（deprecated token/组件不得新增使用）；
- 跨端 parity（同一语义在不同端是否存在）；
- 文档新鲜度（生成物是否落后于源）；
- 组件使用（真实消费者、旧版本）；
- 视觉回归（可选，接 Playwright/Chromatic）。

### 6. Adoption

采用率不是“有多少组件”，而是：

- 哪些产品用了哪个版本；
- 哪些页面还在用旧 token/旧组件；
- 升级/迁移的阻塞点；
- 谁负责、截止何时。

## 四、工作流：从改一个 token 到全端生效

```text
导入/编辑源
  → 规范化 & 归属
  → 预览（多主题/多风格卡）
  → 闸门（对比度/裸值/契约/弃用）
  → 生成投影
  → PR / 发布
  → 采用扫描
  → 弃用/迁移
  → 复盘
```

产品要把每一步都做成**可观察、可回滚**：

- 改 token 前：影响面（哪些组件/页面/端）；
- 改 token 后：diff、预览、失败原因；
- 发布：版本、变更日志、迁移指南；
- 采用：谁还没升级、为什么；
- 弃用：替代项、截止、自动提醒。

## 五、MVP：不要先做“平台”

### v0（4–6 周，自己用）

- CLI：导入 W3C DTCG / 现有 JSON；
- 本地 Web：token 树、搜索、编辑、预览；
- 3 个闸门：对比度、裸值、弃用；
- 2 个投影：CSS、JSON；
- 生成一份“系统健康报告”（HTML/Markdown）；
- 不接 Figma、不做协作、不做托管。

### v1（8–12 周，卖给第一个客户）

- 组件契约结构 + 预览；
- 风格卡（至少 3 张）；
- GitHub App / PR 评论；
- 采用扫描（按仓库/产品）；
- 托管 registry（可选，自托管优先）；
- 版本/弃用/迁移向导。

### 暂不做

- Figma 克隆；
- 通用文档站；
- 运行时设计工具；
- 全自动“AI 生成设计系统”；
- 大而全的项目管理。

## 六、差异化：不要和文档站竞争

| 竞品类型 | 它们强在哪 | 你的楔子 |
| --- | --- | --- |
| zeroheight / Supernova | 文档、协作、企业采购 | 代码原生、闸门、可自托管、多世界 |
| Storybook | 组件预览、生态 | 契约/采用/跨端/治理，不是另一个预览器 |
| Style Dictionary | 构建投影 | 可视化、闸门、采用、协作 |
| Figma Variables | 设计端源头 | 代码/多端/CI/审计，不与 Figma 抢画布 |
| 自建脚本 | 完全贴合 | 产品化、可维护、可交接、报告 |

一句话：

> **他们做“展示设计系统”，你做“运行设计系统”。**

## 七、开源与许可

建议 **open core**：

- **核心开源**（MIT/Apache-2.0）：格式、CLI、闸门、基础编辑器、投影；
- **托管/企业收费**：私有 registry、SSO、审计、SLA、团队协作、历史；
- **不锁数据**：完整导出；不用“开源版不能导出”；
- **插件 API**：让团队写自己的检查/投影；
- **商标/品牌**单独保护。

风险：open core 容易“核心太强、付费太弱”。解决方式是**把“组织级信任”做成付费**：权限、审计、合规、托管、支持，而不是把基础功能砍掉。

## 八、商业模式：软件 + 服务

| 收入 | 内容 | 适合阶段 |
| --- | --- | --- |
| **开源赞助** | GitHub Sponsors/基金会 | 0–1 |
| **托管订阅** | 私有 registry、CI、历史、团队 | 1–2 |
| **审计包** | 设计系统健康检查、对比度/裸值/采用报告 | 0–2（最快） |
| **迁移** | 从旧 token/组件/Figma 迁移 | 1–2 |
| **培训/工作坊** | 团队设计系统课 | 1–2 |
| **定制适配** | 内部系统/多端/合规 | 2–3 |
| **企业版** | SSO/审计/SLA/私有部署 | 2–3 |

**定价思路**（仅作区间，不是承诺）：

- 开源核心：免费；
- 小团队托管：$49–199/月；
- 企业：$10k–50k/年起（含支持/审计/私有部署）；
- 审计/迁移：$5k–30k/项目；
- 培训：$2k–10k/场。

**先卖服务，再卖订阅**：第一个客户买的是“帮我把系统理清楚”，不是“再装一个工具”。

## 九、获客：用“健康报告”做钩子

最有效的入口不是广告，而是**免费/低价的系统审计**：

1. 开源 CLI 跑一遍客户的仓库；
2. 生成“设计系统健康报告”：token 漂移、裸值、对比度、弃用、采用率；
3. 报告里给出 3 个可立即修复的问题；
4. 转化到托管/迁移/培训。

内容策略：

- 公开“设计系统事故复盘”；
- 开源报告模板；
- 对比不同规模团队的真实工作流；
- 与设计系统社区/代理机构合作；
- 不做“设计系统之美”的空泛内容。

## 十、用你的工作区先 dogfood

你已经有最好的试验田：

- `design/tokens` 三层 token + 生成器；
- `design/rules` 15 条规则 + 反例/迁移；
- `design/GUIDE` / `HUB` 双入口；
- M1/M2 闸门、对比度、裸值、组件契约；
- 4 张风格卡、Web/Godot/App 投影；
- 青橙 OS 的多世界演示。

第一版可以直接做成 **“LRDS Ops”**：

- 导入 LRDS token；
- 跑现有检查；
- 生成健康报告；
- 用 GUIDE/HUB 作为文档投影；
- 再把流程产品化，卖给第一个外部客户。

## 十一、90 天验证

| 周 | 目标 | 产出 |
| --- | --- | --- |
| 1–2 | 选 1 个真实团队（最好是你自己/朋友） | 现状图、3 个最痛问题、付费意愿 |
| 3–4 | CLI + 3 个闸门 + 报告 | 可运行、能在一个真实仓库跑 |
| 5–6 | token 编辑 + CSS/JSON 投影 | 从源到产物闭环 |
| 7–8 | 组件契约 + 预览 | 1 个真实组件的完整契约 |
| 9–10 | 第一个付费审计 | 报告 + 修复 + 报价 |
| 11–12 | 决定 | 继续/收窄/停止；写复盘 |

**12 个月**：从“审计 + 开源 CLI”到“托管 + 3 个付费团队”，不要先做平台。

## 十二、指标

- 从改 token 到全端生效的时间；
- 每个 PR 的闸门失败率/修复时间；
- 裸值/弃用/漂移数量趋势；
- 组件采用率（按产品/版本）；
- 文档新鲜度（生成物落后天数）；
- 审计→付费转化率；
- 续费率/服务收入占比。

## 十三、风险与停止条件

**风险**：

- 市场比想象小：设计系统团队数量有限；
- 买家分散：设计/工程/平台谁付钱不清楚；
- 竞品从文档/设计工具向下延伸；
- 自建脚本的“足够好”；
- 服务收入占比过高，产品化不足。

**停止条件**：

- 3 个目标团队都不愿为审计付费；
- 每次交付都要大量定制，无法复用；
- 开源 CLI 有人用，但无人愿意为托管/治理付费；
- 12 个月后收入仍 100% 来自一次性服务。

## 十四、结论

设计系统操作台是三个方向里**最接近现金流**的：

- 你的专业最深；
- 客户最具体；
- 审计/迁移/培训可以先收费；
- 开源核心能建立信任；
- 多世界/风格卡是差异化。

但它不是“画一个漂亮后台”。它要求你真正理解：

> **设计系统的价值不在文档，而在“变更被安全地送达所有产品”。**

如果你能把这句话做成产品，你就有机会从一个设计系统项目，长成一套设计基础设施。

## 附：一个更具体的落地切片（LRDS Ops）

### 技术架构（v0）

```text
vault/
  tokens/           # 源 JSON（ref/sys/product）
  contracts/        # 组件契约（YAML/MD + 结构化字段）
  style-cards/      # 风格卡
  projections/      # 生成物（CSS/JSON/Theme）
  checks/           # 自定义规则
  reports/          # 健康报告
  index.sqlite      # 本地索引（可删可重建）
```

- CLI：`lrds check`、`lrds build`、`lrds report`、`lrds diff`；
- 本地 Web：读同一 vault，不依赖云；
- 生成物可提交，`--check` 保证复算一致；
- 规则可执行：对比度、裸值、弃用、契约完整、跨端 parity；
- 报告输出 HTML/Markdown/JSON，可直接进 PR。

### 第一个客户画像

一个 30 人产品团队：

- 4 个产品、2 个品牌、Web + iOS；
- 120 个 token、18 个组件；
- Figma 一套、代码一套、文档一套；
- 每次品牌改色要 3 周，且总有页面漏掉。

**6 周试点**：

1. 导入 token/组件，跑健康报告；
2. 修 3 个高优问题（焦点色、对比度、弃用按钮）；
3. 接 CI，PR 失败即阻断；
4. 生成品牌投影与采用报告；
5. 交付迁移指南 + 培训；
6. 转托管/季度审计。

**报价结构**：审计 $8k + 迁移 $12k + 季度支持 $1.5k/月；托管另计。这个结构比“先卖 $49/月订阅”更符合早期信任建立。

### 产品边界

- 不做“设计工具”，做“设计系统的运行层”；
- 不拥有客户的画布，拥有客户的**规则/契约/投影/报告**；
- 不承诺“全自动”，承诺“可复算、可审计、可回滚”。
