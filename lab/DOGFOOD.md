# 三工具狗粮计划（未来，未排期）

> **状态**：只记录，**未启动、未排期** ｜ 日期：2026-10-27 ｜ 关联：[LiveDSO](../design/projects/livedso/README.md) · [LiveLand](liveland/README.md) · [LiveFile](livefile/README.md)
> **原则**：九个案例是未来的“复杂型狗粮”，不是当前承诺；一次只并行少量，且必须把真实问题回流到三个生产工具。

## 一、为什么要吃自己的狗粮

三个生产工具现在都能做“局部验证”，但还没有经历**完整产品的交付压力**：

- LiveDSO 没有服务过一个真正要上线的软件；
- LiveLand 没有支撑过一本真正要卖的世界包/游戏；
- LiveFile 没有做过一本真正要交给家庭的书。

只有把工具放进“要卖给真实用户”的项目里，才会暴露：

- 哪些检查是误报，哪些问题根本没检查；
- 哪些导出看起来完整、印刷/上架时不能用；
- 哪些字段是给工具看的，哪些是给最终读者看的；
- 哪些功能必须做，哪些只是看起来酷。

## 三、建议波次

### Wave 1：一工具一案例，形成完整闭环

- **D1 慢慢记**（LiveDSO）：最小可售软件；验证 token/契约/主题/报告；
- **D4 橙港 World Pack**（LiveLand）：最小可售世界包；验证 canon/时代/资产/导出；
- **D7 橙港一家人**（LiveFile）：最小可售档案书；验证选择/隐私/来源/印刷。

为什么是这三个：

- 都能在 2–6 周内做出“可给人看/可卖第一份”的版本；
- 都不需要先建平台/供应链；
- 三者共享「橙港」素材与设计语言，可以互相喂：
  - LiveLand 产世界/canon/资产；
  - LiveFile 管原始档案/来源/许可；
  - LiveDSO 做产品网页/报告/风格一致性。

**Wave 1 的目标不是三款都赚钱，而是让三个工具各暴露 3–5 个真实缺口。**

### Wave 2：加深一个案例，再开第二个

- D2/D3（LiveDSO 复杂/安全关键）；
- D5 或 D6（LiveLand 游戏/机构）；
- D8/D9（LiveFile 研究/作品）。

一次最多并行 2 个案例；一个“复杂型”必须配一个“小闭环”，避免所有案例都卡在长周期。

### Wave 3：只做被验证值得做的

- 游戏垂直切片 / 互动展 / 机构版；
- 需要团队、预算、授权与更长周期；
- 进入前必须有 Wave 1/2 的真实付费/使用证据。

## 四、反馈回路

每个案例必须走同一条回路：

```text
选案例 → 用工具做出第一版 → 记录工具缺口 → 修工具/加检查/改导出
      → 用修好的工具重做 → 把案例变成可展示证据 → 再决定下一个案例
```

### 记录格式

| 字段 | 说明 |
| --- | --- |
| 日期 | YYYY-MM-DD |
| 案例 | D1–D9 |
| 工具 | LiveDSO/LiveLand/LiveFile |
| 缺口 | 具体到命令/字段/导出/检查 |
| 严重度 | blocker / major / minor |
| 临时绕法 | 脚本/手工/外部工具 |
| 工具改动 | commit/文档/规则 |
| 案例改动 | 内容/排版/范围 |
| 证据 | 截图/样张/测试/用户反馈 |

### 反模式

- 把狗粮案例做成**定制外包**：只为一个客户改工具，不通用；
- 用**手工脚本**绕过工具缺口，却不记录；
- 为了案例赶工，**删掉检查/来源/许可**；
- 同时开太多复杂案例，工具和产品都半成品；
- 把“案例能跑”当成“工具成熟”。

## 五、进入条件

- 对应生产工具达到该案例所需的最低稳定度；
- 案例有明确买家/价格/交付物，不是“做着玩”；
- 有真实素材/授权（尤其 LiveFile/LiveLand）；
- 能接受“第一版可能不卖，只用于暴露问题”；
- 用户明确选择波次与案例。

## 六、退出/停止条件

- 连续 2 个案例都只暴露同类问题，且工具无改进 → 停；
- 案例需要定制到无法复用 → 降级为服务，不写回工具；
- 工具改动开始伤害其他案例 → 回滚/拆分；
- 12 个月内没有任何案例产生付费/真实使用 → 重新评估商品化。
