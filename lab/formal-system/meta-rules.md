# 元规则（Meta-Rules）—— 工作区组织与治理的"规则之规则"（实验稿）

> 定位：这是 [`lab/formal-system`](README.md) 的一项实验——把"**工作区元规则**"显式化、可追踪，
> **先在本实验基地试**，成熟后再回流主项目（对应基地 README 的初衷：先小范围验证更形式化的协作路径）。
> 对照：工作区既有"规则"文档在 [`tech/`](../../tech/)（书写/链接、Git 提交、形式化验证）。

## 一、为什么需要元规则

普通规则回答"某类产物怎么写/怎么命名"；元规则回答更上层的问题：

1. **我们如何决定并组织规则**（避免规则散落、互相打架、无人复核）；
2. **如何让结构一眼可懂**（结构是给人看的，目标不是"存进去"而是"读得懂"）。

> 一句话：普通规则约束产物，元规则约束"我们怎么收敛出一个好结构并保持它可读"。

## 二、元规则清单（规则总表）

每条元规则一个 `id`，编号递增、可追踪；状态 `已定 / 建议 / 待定`，新增/变更在此表登记。

| id | 法则 | 一句话 | 状态 |
| --- | --- | --- | --- |
| M0 | 规则的组织方式 | 每条规则成文、按域编号、可追踪 | 已定(本文档) |
| M1 | 文件组织方式 | **关注点优先，类型其次**（concern-first, type-secondary） | **已定(实验期)** |
| M2 | 命名与深度 | 路径/文件名沿用"关注点→子关注点→产物类型"，固定类型词表 | 待定 |
| M3 | 元规则自身的演进 | 新规则先"建议"，讨论/实测达标后才升"已定" | 已定(本节) |

## 三、每条元规则的结构（便于人核对、机器可检查）

一条元规则尽量含下面几项，缺的标"——"：

1. **id / 标题**：唯一编号 + 一句话。
2. **目标**：为什么要这条（服务"人快速理解"）。
3. **决策**：结论（二选一/折中）。
4. **判定标准**：怎么判断"该放哪"（可操作）。
5. **权衡**：被放弃的另一方案及其代价。
6. **自检问题**：一句反问。
7. **可验证**：若可，给出检查命令（如脚本）。

## 四、M1 · 文件组织方式（已定 · 实验期）

> 状态：**已定（实验期）**；2026-09-09 经讨论确定采纳"关注点优先，类型其次"，本期仅**固化为规则+判据**，不改现有结构。

### 4.1 问题：按"类型"组织 vs 按"模块/关注点"组织？

关键认识：**这不是非此即彼，而是轴序问题**——"类型"与"关注点"两条轴都存在，真正要选的是
**哪条是主轴（顶层/第一刀）**。

### 4.2 决策：**关注点优先，类型其次**

> 顶层按"关注点/领域/项目"切分（第一刀让人知道"这工作区是关于什么的"）；
> 每个关注点内部用一套**固定、可预期**的"类型词表"组织（README / docs / data / code / test / plans / tool）。

**主轴选关注点**（对"快速理解"）：
- 人找东西的第一问是"**这是什么**"（知识库？项目？实验？），而非"这是什么类型"。
- 关注点是**语义边界**，天然聚合归属：`明日频道` 的文档、代码、数据都在它的目录下，
  不会被拆进三个全局 `docs/code/data` 桶里散开。
- 顶层关注点**少而稳定**（约 5–8 个），一眼扫完、可记忆。

**从轴仍要类型**（避免"纯模块化"）：进入某个关注点后仍要区分"规范/数据/代码/测试/计划"，
统一类型词表让"进了任何目录都长一样"，认知负担最低；少数跨关注点类型（根 README、`tools/`、`tech/`）各归其位。

### 4.3 对比表

| 维度 | 按类型为主轴（全局 docs/code/data） | 按关注点为主轴（concern-first）★ |
| --- | --- | --- |
| 理解速度 | 需读完文件名才知归属 | 看目录名即知"这是什么" |
| 归属聚合 | 一个项目的产物被拆散 | 一个项目/领域的东西聚在一起 |
| 随规模 | 每桶线性膨胀、难排序 | 关注点拆分后仍稳 |
| 内部一致性 | 靠全局类型词表 | 靠"关注点内固定类型词表"保证一致 |
| 代价 | 跨项目归属难以一眼看出 | 需先定义"哪些算关注点"（顶层保持小） |

### 4.4 判定标准（放一个新文件时依次问）

1. 它服务**哪个关注点/领域/项目**？ → 顶层目录（第一刀）。
2. 它是**哪种产物**（README/规范/数据/代码/测试/计划/工具/研究）？ → 关注点内类型子目录。
3. 它**跨关注点**吗（全局约定→`tech/`；通用可复用工具→`tools/`；通用说明→顶层 `README.md`）。

### 4.5 自检问题

> **"一个刚接手的人想知道 X，能否只靠 1 次目录点击 + 一眼看清固定的子结构就定位到 X？"**

### 4.6 对本工作区的对照（2026-09-09）

- 顶层已是**关注点优先**：`doc/`(知识库) `projects/`(项目) `studio/`(角色) `lab/`(实验) `tech/`(约定) `tools/`(工具) → ✅ 符合本决策，保持。
- 项目内 `projects/<project>/`：`docs/<角色>/`、`data/`、`game/`、`art/`、`plans/`、`references/`、`assets/` → 关注点(项目)→类型/角色 → ✅ 基本符合。
- 实验区 `lab/formal-system/`：`tools/` `viz/` `methods/` `specs/` `prototypes/` `notes/` → 关注点(实验)→类型 → ✅ 符合。
