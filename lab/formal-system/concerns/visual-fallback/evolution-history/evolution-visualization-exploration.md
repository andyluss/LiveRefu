# 演进历史 / 时间序可视化 · 探讨

> 所属子关注点：[`evolution-history/`](README.md)。定位：把"**随时间变化的事实**"渲染成可视面，用**视觉直觉**
> 兜底感知"哪里变了、何时变、为何变、是否健康"。本文只探讨、给方向，**暂不实现脚本**。
> 与 "文档健康仪表盘 / 一致性热力图"（看**当前状态**）互补——本子关注点看**时间轴上的演变**。

---

## 一、为什么值得做

形式化（编译器/契约/测试）判"当前是否正确"；但**"这套东西是怎么一路走到今天的"**也是重要的可读性/健康度事实：

- Git 提交历史、CHANGELOG、元规则演进史、文档修订史……都是**已经存在、机器可读**的演化证据。
- 把这些**摊到时间轴上**，人能一眼看出：**某段时间是不是在"高频返工/长尾拖延"、某规则是不是被多次推翻、某文档是不是长期没动（僵尸）**——这些很难靠读文字获得，却是"这个工作区健不健康"的强信号。
- 正贴合本实验"可视验证面"的人机兜底思路：**把"演化健康度"从"去感受"变成"去看"**。

## 二、什么是"演进/时间序"事实（数据源）

| 数据源 | 事实 | 本机可得性 |
| --- | --- | --- |
| **Git 提交历史** | commit 时间/作者/文件/消息；文件逐版本变化；作者与文件同改关系 | ✅ `git log`/`git log --name-status` |
| **CHANGELOG** | 里程碑时间线 / 版本轨迹 / `Added|Changed|Fixed` 计数趋势 | ✅ 项目/实验 `CHANGELOG.md` |
| **元规则演进史** | 每条规则的 `draft→…→retired` 状态轨迹 + 每一次"版本/日期/状态/依据" | ✅ `meta-rules/M*-*.md` 演进历史表 |
| **文档历史 / 质量** | 相对链接、`【待定】/【已定】`、复核账本、文件 mtime/commit 的演变 | ✅ `visual_health.py`、`review-ledger.json`、mtime |
| **里程碑计划 vs 实际** | 计划时间线 vs 实际提交/完成 | ⚠️ `plans/milestones/`（部分） |

> 再次强调（防"好看但没用"）：只锚定**可验证事实**（时间戳、状态、版本号、提交哈希），
> 不做"这个变更好不好"的主观打分。

## 三、可视化手法工具箱（同一批"时间序"数据可用的画法）

| 手法 | 画什么 | 暴露什么异常 | 适合对象 |
| --- | --- | --- | --- |
| **时间线 / 泳道（timeline / swimlane）** | 一段段事件/区间沿时间轴排布（多泳道=多作者/多规则/多主题） | 重叠、断层、长尾、频发区 | Git 提交、CHANGELOG 里程碑、文档变更 |
| **提交图 / 分支图（graph）** | commit + 父子边 + 分支合流 | 提交是否集中在少数人、是否长期不合并 | Git |
| **趋势曲线（line / area）** | 某计数随时间的曲线（提交数、待定数、违规数） | 突增/骤降/尖峰（返工、大量待定）、长期低迷 | 提交密度、待定/已定、复核违规 |
| **热力图 / 密度（heatmap）** | 时间(横) × 维度(纵) 的格子着色 | 高频时间段/人/类型 | 作者×时间、规则状态×版本 |
| **变更视图（diff / sparkline）** | 单文件逐版本大小/改动量 | 文件突变、反复重写 | Git、文档 |
| **状态机轨迹（state-flow）** | 某实体沿时间的状态迁移（`v1→v2→v3`） | 异常迁移、反复回退、卡死在某状态 | 元规则演进史、需求/里程碑状态 |
| **共变网络（co-change）** | 常一起变动的文件聚成节点、连边 | 脆弱的耦合（改了 A 必改 B） | Git `--name-only` 同 commit |
| **版本谱系 / 时间胶囊** | 某主题/卡池的内容随时间阵容变化 | 内容是否随版本"长青"还是"替换" | 知识库/内容池 |

> 每张图都应能回答一个问题："这里在动、还是死了？"若图答不出，就不画。

## 四、按对象逐一展开

### 4.1 Git 提交历史
- **数据**：`git log --format='%h|%cI|%an|%s'`、`git log --name-status`。
- **可画**：
  - 提交次数趋势（按天/周）——看**节奏**（M1 是否密集、M2 是否长尾）。
  - 作者 × 时间的泳道——看**是否集中在少数人/角色**（呼应"虚拟工作室"是否真的分工）。
  - 提交图——看**分支/合流**健康度。
  - 共变网络——看**哪些文件总要一起改**（如 schema 与检查脚本）。
- **暴露的异常**：冲刺期集中后骤停；某个文件 30 天内被反复改（返工）；一次超大提交（全脏）把约定打乱。
- **MVP 成本**：低（`git log` 已是结构化数据）。

### 4.2 CHANGELOG / 日志
- **数据**：`CHANGELOG.md` 的 `## [版本] · 日期` 标题 + `Added/Changed/Fixed` 列表。
- **可画**：版本时间线（每版本一个区间）+ `Added/Changed/Fixed` 计数趋势（面积图）。
- **暴露的异常**：某版本堆积大量"Changed"（大改）却无"Fixed"；版本间隔突然拉长（停滞）；长期只有 Added 没有收敛。
- **MVP 成本**：低（解析 md 标题/列表即可，`consistency_heatmap.py`/`visual_health.py` 已示范 md 解析）。

### 4.3 元规则演进历史（本基地最有代表性的"演化"对象）
- **数据**：每条规则 `M*-*.md` 的「演进历史」表（版本/日期/状态/变更/依据），已由
  [`rule_evolution_check.py`](../../meta-rules/evolution/rule_evolution_check.py) 校验过。
- **可画**：
  - **状态机轨迹**：每条规则沿时间轴画 `proposed→experimental→accepted→…` 的阶梯（y=状态，x=日期）——一眼看出"谁在反复回退、谁卡在 proposed、谁已退役"。
  - **跨规则泳道**：把 M0-M3（及未来 M4…）的状态并列，看整个元规则集的"演进节奏"。
- **暴露的异常**：某规则 `accepted→in-review→accepted→in-review` 反复震荡（没想清楚）；某 proposta 多年未定稿（僵尸提案）；同一天多条规则同时"升/降"（可能是批量拍板而非深思）。
- **MVP 成本**：中（需解析演进历史表；规则本身已在演进，正好用 M3 状态机做"状态阶梯"）。

### 4.4 文档历史 / 质量演化
- **数据**：`visual_health.py` 的复用（链接互链、`【待定】`数、`review-ledger.json`、文件 mtime）。
- **可画**：
  - `【待定】/【已定】` 随时间曲线——看**问题收敛**还是**累积**。
  - 复核覆盖率复核随时间——看**人工复核推进**。
  - 某主题/文档的互链度随时间——看**知识库是否在连接**（回应"doc/ 孤立法高"）。
- **暴露的异常**：待定只涨不降（烂尾）；某主题从不被链接（孤立）；文档 6 个月没人动（僵尸）。
- **MVP 成本**：中（需要给 `visual_health.py` 加"记录快照→时间对比"能力，即**快照存档**）。

### 4.5 里程碑计划 vs 实际
- **数据**：`plans/milestones/`、`plans/progress/`。
- **可画**：甘特/燃尽——计划时间线 vs 实际完成曲线。
- **暴露的异常**：计划压点、实际长期落后；里程碑"名义达成"但无实质提交（靠文字自述 vs 机器提交）。
- **MVP 成本**：中高（计划数据结构化程度较低，需人工对齐）。

## 五、优先级 / MVP 建议

从"数据已是结构化、最能暴露本工作区真实问题"的角度排序：

1. **元规则演进史 · 状态机轨迹**（§4.3）——**最贴合本基地**，规则状态已在检查里被机器化，但"怎么看它在动/卡住"还没有可视面。
2. **Git 提交趋势 + 提交图**（§4.1）——数据最现成（`git log`），能立刻回答"这个工作区的开发节奏/分工健康吗"。
3. **CHANGELOG 时间线**（§4.2）——低成本的"版本轨迹 + 变更类型趋势"。
4. **文档质量演化**（§4.4）——需引入"快照存档"机制（每次跑 `visual_health` 存一份 JSON 时间点，才能画趋势），成本略高但价值大（从"当前健康"升级为"演化健康"）。
5. **里程碑 vs 实际**（§4.5）——数据结构化度低，靠后。

> **建议首个 MVP**：先做 **§4.3（元规则演进状态阶梯）** 做一个**最小的静态/半交互图**（如用 SVG/`visualize`），
> 因为它的数据源（演进历史表）已经结构良好、且能直接印证 M3 状态机是否真的被用起来。

## 六、与"可视验证面"主题的关系

- 形式化（编译器/契约/测试）管"当前正确"；本子关注点管"**演化健康**"，是同一"人机兜底"逻辑在时间轴上的延伸。
- 若能做出"**提交趋势 + 规则状态阶梯**"，就能对"这个基地到底在不在按 M1/M2/M3 迭代"给出**可看的证据**，而非靠自述。
- 这正呼应：[`../../meta-rules/M3-rule-evolution.md`](../../meta-rules/M3-rule-evolution.md) 的"每条约规则都值得被挑战/应被记录"——**记录下来的演化轨迹理应被看到**。

## 七、边界与注意

1. **只锚定可验证事实**（时间戳/状态/版本/提交哈希），不做主观评分。
2. **别做成"好看的假象"**：每张图先问"它暴露了哪种"不健康"或"哪一种变化"？答不出就不画。
3. **快照存档是关键**：要画"趋势"，前提是**每次跑检查都存一份带时间戳的 JSON**（引入 `snapshots/` 或 `viz/history/`），
   否则只有"当前状态"没有"随时间"。这是 §4.4 的成本来源。
4. **别替代人**：可视化是**提示异常**，最终是否"有问题"由人确认，并可登记到复核账本（呼应第③层）。
