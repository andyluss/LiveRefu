# M0 · 规则的组织方式（已定）

**一句话**：每条规则**成文**、按"域"归类、**编号可追踪**，变更记演进历史。

## 一、目标

避免规则散落（聊天/脑内）、互相打架、无人复核。任何一条可依赖的规则都应能被**引用**、被**追踪**。

## 二、主选（决策）

- 规则**成文**为 Markdown，不只在会话或口头约定里。
- 按"域"归类：
  - 工作区**具体规则** → [`../../../tech/`](../../../tech/README.md)（docs-convention / git-convention / formalization / hooks-readme）；
  - **元规则**（本目录）→ `lab/formal-system/meta-rules/`；
  - **项目规则** → `projects/<项目>/`（如 `docs/`、[`../README.md`](../README.md)）。
- 每条规则一个**唯一 id**，变更写入其"演进历史"表（见 [M3](M3-rule-evolution.md)）。

**权衡**：成文要花一点时间，但换来"可引用、可核对、可演进"，且 AI/人都能依据同一条规则行事。

## 三、备选（被放弃的选项）

| 备选 | 描述 | 为何不为主选 | 代价 |
| --- | --- | --- | --- |
| A0.1 约定即规则 | 只靠口头/默契约定 | 无追踪、易失忆、无法核对 | 失控与返工 |
| A0.2 单一大总文档 | 所有规则塞进一个文件 | 难以查找、演进、单独引用 | 越长越难维护 |
| A0.3 只用机器强制（脚本） | 一切都做成能跑的检查 | **覆盖不到**文档/结构类约定 | 留下不被约束的部分 |

## 四、判定标准

一条新规则"被落地" = 有一份可引用的文档 + 一个唯一 id + 一句"为什么"（目标/依据）。

## 五、自检问题

> "我能否从这份清单（[`README.md`](README.md)）快速找到并引用某条规则？"
