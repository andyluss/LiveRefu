# 形式化协作实验基地 · formal-system

> 实验目标：探索用**更形式化、可机器验证的系统与语言**与 AI 协作（替代"模拟人类组织/角色"的松耦合模式），回答"AI 产出能否被编译器/证明器/模型检验器**独立验证**"。
> 背景：工作区主项目已用"虚拟工作室 + 角色"模式完成 M1，但该模式**验证缺位**（见 [`tech/formalization.md`](../../tech/formalization.md)）——本基地用于**小范围实验更形式化的路径**，成熟后再回流主项目。

## 一、为何形式化取代"组织模拟"

| | 角色工作室（现状） | 形式化系统（本实验） |
| --- | --- | --- |
| 人/角色边界 | 叙事约定（"主程序做 X"） | 机器可检查的声明（类型/契约/证明） |
| 验证 | 靠 agent 自述 + 少量检查 | 编译器/证明器/模型检验器自动验证 |
| 确定性 | 角色越多越不确定 | 越形式化越可判定 |
| 需求 | 散落文档 | 结构化规格（可机械追踪） |

**核心**：形式化不是"写更多规范"，而是把**约定变成机器可判定的约束**——AI 产出任何不被验证的东西都进不了门。

## 二、形式化方法与系统 · 分层推荐

按"验证强度"分层，从实用到强形式化。每层给**这个实验最值得试的代表**。

### 层 A · 类型化语言（静态可验证，最易上手）
> 让编译器替你验证类型/数据流/内存安全。

| 语言 | 特点 | 适合 | 本机 |
| --- | --- | --- | --- |
| **Rust** | 所有权+借用，编译期保证内存/并发安全；强类型+枚举+模式匹配 | 系统/引擎/数据管线；AI 产出代码的可验证底座 | ✅ 已装 |
| **TypeScript** | 结构化类型+可组合；生态大 | Web/数据层；类型即契约 | ⚠️ 需装 |
| **OCaml** | ML 家族，不可变默认，强类型推断；形式化传统（与 Coq 同源） | 代数/规则引擎；偏向"可证明"风格 | ⚠️ 需装 |
| **Lean（函数式+证明）** | 一等公民可编程证明 | 最前沿；证明算法性质 | 重 |

🅿️ **建议起步**：**Rust**（本机已有，编译器验证最"硬"，且能立刻验 AI 产出）。用一个小的数据/规则处理模块试。

### 层 B · 规格与模型检验（验证"设计/算法正确"）
> 在写代码前，用形式化规格描述系统，用模型检验器验证性质。

| 系统 | 特点 | 适合 |
| --- | --- | --- |
| **TLA+ / PlusCal** | 行为规格 + 模型检验，验证并发/系统的**不变式与活性**；业界（AWS）已验证 | 状态机/并发/协议的逻辑正确性 |
| **Alloy** | 轻量关系逻辑，用 SAT 找**反例**；建模+快查 | 数据模型/不变式，快速发现反例 |
| **Event-B / Z** | 经典形式化规格，细化证明 | 高安全关键系统 |

🅿️ **建议起步**：**Alloy**（最轻量、面向数据/模型、能快速找出反例——很适合验证"数据契约/业务规则"）；**TLA+** 用于有状态/并发部分。

### 层 C · 契约式设计 & 配置契约（验证"接口/数据"）
> 用契约（前置/后置/不变式）与强类型配置，让 AI 协作的接口/配置可机器校验。

| 系统 | 特点 | 适合 |
| --- | --- | --- |
| **Design by Contract**（契约式设计）| 前置/后置/不变式，运行时或编译期断言 | 模块接口契约（比纯类型更强）|
| **CUE** | 声明式配置语言：强类型 + 校验 + 合并 + 作为契约 | **配置/数据契约**（比 JSON Schema 强，AI 协作友好）|
| **Protobuf / Avro / XSD** | 携带 schema 的序列化，自动校验 | 数据交换 |

🅿️ **建议起步**：把主项目现有的 JSON Schema 契约升级为 **CUE**（本实验试：确定性配置、合并、校验——非常契合"AI 生成配置需要验证"）。

### 层 D · 属性测试 & 形式化验证（验证"行为可真/证明性质"）
> 用数学证明或属性测试收敛到"正确性"。

| 系统 | 特点 | 适合 |
| --- | --- | --- |
| **Property-based testing**（QuickCheck/Hypothesis）| 随机生成输入验证属性 | 函数/模块的行为正确性，成本低 |
| **Coq / Isabelle / Lean** | 定理证明器，可证明算法/协议性质 | 最严格，但成本高 |

🅿️ **建议起步**：**Property-based testing**（在语言侧，如 Rust `proptest`/`quickcheck`）——用属性而非样例测，覆盖面大增，且机械化。

### 层 E · 可重复构建（验证"环境/构建确定"）
> Nix——声明式、可重复、确定性的构建，消除"在我机器上能跑"。

| 系统 | 特点 |
| --- | --- |
| **Nix / NixOS** | 纯函数式包管理+构建，输入完全确定 → 环境可验证、可复现 |

🅿️ **建议**：实验阶段可选；若 AI 产出跨机器要可复现，用 Nix 锁定构建（本机未装，需评估）。

## 三、推荐组合（本实验的第一步 MVP）

结合本机现状（Rust 已装）与"快速可验证 AI 协作"目标，建议 MVP：

> **Rust（类型化底座）+ CUE（配置/数据契约）+ Property-based testing（行为验证）**
> 可选叠加：**Alloy**（先验数据/规则模型）、**TLA+**（有状态部分）。

**为什么这个组合**：
1. **Rust** 编译器是当前最硬的"AI 产出验证器"——AI 写的代码，`cargo build`/`clippy`/`rustc` 直接判定，无需信任 AI 自述；
2. **CUE** 让"AI 生成配置/数据"这类高频动作可机器校验（比 JSON Schema 表达力强，且天然支持合并/约束）；
3. **Property test** 把"行为正确性"从"样例/自述"提升为"属性被随机验证"；
4. 三者都是**机械可判定**，都可接入 pre-commit/CI——真正把 AI 隔离在"未验证不进"的门后。

- [`visual-fallback/`](concerns/visual-fallback/)：**子关注点** · 可视化兜底（文档健康 / 一致性热力图 / 复核账本 的工具+输出）。

- [`methods/`](methods/)：类型 · 深入研究某方法（待写）。
- [`specs/`](specs/)：类型 · 用 Alloy/CUE 写的形式化规格样例（待写）。
