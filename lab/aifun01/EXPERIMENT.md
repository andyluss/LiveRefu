## 一、研究问题

1. 显式的 `Context/Task/Proposal/Result` 是否让人更容易发现 AI 的方向漂移？
2. 把 adopt/execute 放在人类边界，是否减少“AI 顺手扩大范围”？
3. 不可变 journal 是否让决策更容易复述和审计？
4. 惰性生产是否减少“核心未成立就批量生成内容”的浪费？

## 二、实验单元

一次实验 = 一个**真实的小任务**（30–90 分钟）：

- 有明确目标；
- 有至少一条非目标；
- 有可观察的验收；
- 允许 AI propose，不允许 AI adopt；
- 由人执行最终决定与效果。

例如：

- 给未来残片写 3 个不同的 10 分钟试玩方案；
- 给 Refu 的一个机制做 2 个规则原型；
- 给某个 Life 应用做 3 个信息层级方案。

## 三、变量与指标

| 变量 | 记录 |
| --- | --- |
| Context 完整度 | 一句话/支柱/非目标/验收是否齐全 |
| AI 提案数 | 方向数、每个方向的代价与风险 |
| AI 越界 | 是否提出非目标内的事、是否自行扩范围 |
| 人干预 | Blocked 次数、改范围次数、否决次数 |
| 决策可追溯 | 每条 decision 是否有 rationale、proposalHash |
| 效果控制 | 是否有未批准的执行 |
| 体验证据 | 是否发生了真人试玩/使用 |
| 时间 | 提案、评审、试玩、返工 |

## 四、Phase 0：结构模拟（已完成）

用确定性 `propose` 代替真实 AI，验证：

- 缺非目标/验收 → Blocked；
- AI 提案不携带待执行效果；
- 触碰非目标 → 被拒绝；
- 决策必须有人的理由；
- fold 不可变追加；
- 执行效果必须有人类批准。

```bash

npm run demo
```

## 五、Phase 1：真实 AI 任务（待做）

### 步骤

1. 人选一个真实小任务，写 `Context` 与 `Task`；
2. AI 只输出 `Proposal`（方向、代价、风险、不确定项）；
3. 人用 `accepts` 的规则审查，记录是否触碰非目标；
4. 人写 decision + rationale；
5. 人批准并执行一个最小效果（试玩/原型/文档）；
6. 记录结果，决定下一轮。

### 成功判据

- AI 没有在缺失关键信息时自行补全；
- 没有发生未批准的范围扩张；
- 每条决定可追溯到 proposal + rationale；
- 至少一次真实体验证据；
- 人能在 5 分钟内复述“为什么做/不做什么”。

### 失败/停止判据

- AI 仍然通过“更多内容”绕过核心验证；
- 人无法在不读长文的情况下做决定；
- 模型复杂到比任务本身更贵；
- 连续两轮没有产生新的体验证据。

## 六、下一步
