# 函数式协作：把 AI 当纯函数，把人当运行时

> **AI 参考 · 非决定** ｜ 日期：2026-11-02
> 对应的人类意图：[`../README.md`](../README.md)（人类手写设计源）
> 用途：给“人与 AI 如何分工、如何防止主题漂移”提供一个更接近本质的结构模型。
> 可信度：本文是设计类比与工程建议，不是学术论文；类比有边界，见第九节。

## 一、问题的本质：不是 AI 不听话，而是副作用没有边界

上一篇文章《人类控制权》讲的是“人如何拿回方向盘”。这一篇想再往下问一层：

> 为什么人一旦把方向盘交出去，项目就很容易被 AI 带着走？

一个更精确的回答是：

**因为大多数 AI 协作，把“纯变换”和“有副作用的决定”混在了一起。**

- AI 读上下文、生成方案、写代码、改文档、提交、扩展范围；
- 人也读、也改、也点头；
- 聊天记录同时充当需求、设计、决策、状态和记忆；
- 没有明确的输入类型，没有明确的输出类型，没有明确的副作用边界。

在这种结构里，AI 每一次“帮你往前推一点”，都可能悄悄改变项目的状态。它不是恶意，它只是**在一个没有类型、没有边界、没有事务的系统里做局部最优**。

函数式编程给的启发不是“用 Haskell 写游戏”，而是：

> **把计算和副作用分开；把状态变成不可变的值；把决定留在边界上。**

这正好可以重新定义人机协作。

## 二、一个更准确的人机模型

### 2.1 AI 是纯函数

理想情况下，AI 应该是一个纯函数：

```text
proposal = ai(context, task)
```

给定相同的：

- 意图（intent）
- 非目标（non-goals）
- 约束（constraints）
- 已知证据（evidence）
- 任务（task）

AI 应该给出一个**可解释的候选输出**，而不是顺手改变项目状态。

纯函数不意味着 AI 每次输出逐字节相同（模型有随机性），而是意味着：

- 输出可以追溯到输入；
- 输出不偷偷依赖“上次聊天里的一句话”；
- 输出不自动修改源文件、不自动扩大范围、不自动做决定；
- 同一个任务可以用不同的 `seed / context version` 重现和比较。

### 2.2 人是运行时

人不是“审稿人”，人是这个系统的：

- **类型定义者**：定义什么叫“这个项目”、什么叫“好”；
- **运行时**：决定什么时候执行、执行哪一个；
- **效果处理器（effect handler）**：把提案变成真实的决定、代码、发布、试玩；
- **最终解释器**：把“玩家体验”解释成是否继续。

可以把人写成：

```text
decision = human(proposal, experience, responsibility)
```

AI 负责把 `context` 变成 `proposal`；人负责把 `proposal` 变成 `decision` 和真实世界的 `effect`。

### 2.3 想法是不可变值

人的原始想法不是草稿纸，而是**不可变值**：

```text
idea_v1 = "..."
idea_v2 = derive(idea_v1, new_thought)   // 新值，不覆盖旧值
```

AI 可以：

- 读取 `idea_v1`；
- 在 `ideas/AI/` 生成 `proposal`；
- 生成 `idea_v2` 的候选。

AI 不可以：

- 直接改写 `idea_v1`；
- 把“它理解的版本”写回源；
- 删除旧判断来让新方案显得一致。

这对应函数式编程的**不可变性**：不是不能演进，而是演进产生新值，旧值保留，历史可追溯。

## 三、把 FP 概念翻译成协作规则

| FP 概念 | 人机协作含义 | 反模式 |
| --- | --- | --- |
| **纯函数** | AI 从显式上下文生成候选，不偷改状态 | 聊天记录就是需求；AI 顺手改范围 |
| **不可变值** | 人的想法、旧决策、历史证据只追加不覆盖 | 为了让新方案自洽而改写旧文档 |
| **显式类型** | 任务有目标、非目标、约束、验收、权限 | “帮我优化一下”这种无类型输入 |
| **纯核心 / 副作用外壳** | 分析、提案、原型是核心；提交、发布、决定是外壳 | 一个 agent 从思考到发布全包 |
| **组合** | 小任务组合：调研 → 提案 → 原型 → 试玩 | 一个巨型 agent “把游戏做完” |
| **惰性求值** | 按需生成，不提前生产 100 张卡 | 核心 10 分钟没成立就批量生成内容 |
| **错误即值** | 返回 `Blocked` / `NeedHuman` / `Conflict`，不猜 | 遇到歧义就自行补全 |
| **幂等** | 重跑任务不重复破坏、不重复扣成本 | 每次重试都新增一套系统 |
| **可组合证据** | 测试、试玩、调研是可拼接的证据 | “测试全绿”替代“好玩” |
| **属性测试** | 用不变量检查提案：是否违背主题、非目标、范围 | 只看单点输出是否“看起来不错” |
| **固定点** | 收敛到稳定意图，不追逐最新输出 | 每轮都换方向，永远在重构 |

## 四、参考架构：纯核心 + 效果边界

### 4.1 类型

```text
Context = {
  intent:        String,       // 一句话
  pillars:       [String],     // 最多 3
  non_goals:     [String],     // 明确不做
  constraints:   [Constraint], // 时间/预算/平台/团队
  evidence:      [Evidence],   // 测试/试玩/调研
  version:       String
}

Task = {
  goal:          String,
  non_goals:     [String],
  scope:         [Path],       // 允许改哪里
  authority:     ReadOnly | Propose | Implement,
  stop_if:       [Trigger],
  acceptance:    [Check]
}

Proposal = {
  options:       [Option],
  assumptions:   [String],
  evidence:      [Evidence],
  risks:         [Risk],
  effects:       [Effect],     // 需要人批准的执行
  open_questions:[String]
}

Result = Ok(Proposal) | Blocked(Reason) | Conflict(Intent, Proposal)
```

关键不在字段多，而在：

- **`authority` 显式**：AI 是只读、提案，还是可以改代码；
- **`scope` 显式**：允许改哪里，不允许改哪里；
- **`effects` 显式**：哪些动作需要人批准；
- **`Result` 显式**：不能完成时返回原因，不许静默猜。

### 4.2 纯核心

```text
ai : (Context, Task) -> Result<Proposal>
```

纯核心负责：

- 把模糊问题拆成 2–3 个方向；
- 给出每个方向的代价与反方；
- 做调研、对比、原型设计；
- 生成可验证的假设；
- 指出与 `intent / non_goals` 的冲突。

它不负责：

- 决定哪个方向；
- 改人的 `ideas/`；
- 改项目范围；
- 提交/发布；
- 宣布“这个好玩”。

### 4.3 效果外壳

```text
humanRun : Proposal -> IO<Decision>
Decision = Keep | Cut | Explore | Adopt
```

只有人能执行这些效果：

- `Adopt`：把提案升级为项目方向；
- `Cut`：删掉一个系统/内容；
- `Publish`：对外发布；
- `Spend`：投入更多时间/钱；
- `Playtest`：把真实玩家拉进来；
- `Kill`：停止项目。

AI 可以准备 `Plan<Effect>`，但 `runEffect` 必须经过人。

这就是 **IO Monad / Effect System** 在协作层的意思：不是禁止副作用，而是**把副作用放在边界上，显式标记、显式批准**。

## 五、五个具体的协作函数

### 5.1 `clarify`

```text
clarify : (Context, Task) -> Either<Question, Task'>
```

当任务缺少关键信息时，AI 不猜，返回问题：

- 这是主题问题还是实现问题？
- 这个功能服务于哪一个支柱？
- 这次允许扩大范围吗？
- 哪个决定必须由人拍板？

### 5.2 `diverge`

```text
diverge : Task -> [Option]
```

至少给三个方向，并且每个方向带：

- 核心体验；
- 代价；
- 最可能失败的地方；
- 什么证据会支持/推翻它。

### 5.3 `critique`

```text
critique : Proposal -> [Risk]
```

AI 必须能扮演反方：

- 这个方案如何违背最初意图？
- 如果玩家不买单，最可能的原因是什么？
- 如果范围翻倍，哪里先崩？
- 这个方案是不是在解决一个不存在的问题？

### 5.4 `prototype`

```text
prototype : Option -> Prototype
```

原型是**最小可体验物**，不是完整实现：

- 纸面流程；
- 一局 10 分钟的核心循环；
- 一个机制的规则原型；
- 一个可试玩场景。

### 5.5 `observe`

```text
observe : Prototype, Player -> Evidence
```

这一步只能由人真实执行/解释：

- 玩家在哪停顿；
- 他误解了什么；
- 他第一次犹豫/兴奋是什么时候；
- 他是否想再来一局。

AI 可以记录、整理、对比；不能替玩家“感觉”。

## 六、惰性求值：不要在验证前生产内容

函数式语言默认惰性求值：表达式只在需要时计算。

协作也应该如此：

```text
-- 不要
generate 120 cards
generate 6 maps
generate 40 chapters
then ask "is it fun?"

-- 应该
build 10-minute core
playtest
if core works:
    generate content under constraints
else:
    change core, not content volume
```

这就是为什么“AI 生成了很多内容”不是进展，而是**急切求值**：

- 它把未来的可能性提前固化；
- 它用内容量掩盖核心体验未成立；
- 它提高了删除成本。

**核心体验是惰性求值的边界；边界没成立，不要 force。**

## 七、游戏：核心是纯的，体验是效果的

游戏设计可以分成两层：

### 纯核心：规则、状态、数值、内容数据

这些适合 AI 大量参与：

- 卡牌数据、关卡配置、数值表；
- 规则解释器、测试、平衡模拟；
- 内容和变体的生成；
- 文档整理与对账。

### 效果层：玩家体验、审美、主题判断

这些必须由人主导：

- 这个主题是否值得做；
- 这个核心 10 分钟是否让人想继续；
- 这张卡/这个界面是否“对味”；
- 这个世界的语气是否可信；
- 这个代价是否被玩家感知到。

把游戏写成函数式结构，不是把“好玩”形式化，而是承认：

> **“好玩”不是纯函数；它是在真实玩家身上执行的效果。**

所以正确的顺序是：

```text
人定义 intent + core experience
AI 生成 rules / content / variants
人执行 playtest
人把体验解释成 decision
AI 根据 decision 再生成下一批候选
```

## 八、放到两个项目上

### 未来残片

AI 可以继续做：

- 卡池变体、关卡配置、平衡模拟、数据对账；
- 商店页素材整理、文档索引、测试。

人必须抓住：

- “电力 ↔ 残渣”的核心张力；
- 10 张签名卡与 30 分钟核心体验；
- 真人试玩后的继续/收缩；
- 生成卡是否真的服务于主题。

反模式：**先生成 108 张卡，再问“好不好玩”**。这是典型 eager evaluation。

### Refu 001

AI 可以继续做：

- 三族规则实现、卡表对账、地图数据、试玩工具；
- 设计文档的结构化整理。

人必须抓住：

- 哪一个美术方向；
- 哪一个阵营体验必须被玩家感受到；
- 三族/6 图/20+ 卡的优先级；
- 故事与卡面是否服务于游戏，而不是替代游戏。

反模式：**继续写 100 万字设定，来回避“只有 1 张地图可玩”**。这是把 effect 当成了 pure core。

## 九、这个类比的边界

函数式编程是类比，不是教条。

- 人不是纯函数：人有身体、情绪、审美、责任和情境；
- AI 也不是严格纯函数：模型有随机性、训练偏差、上下文限制；
- “好玩”不能被类型系统完全捕获；
- 有些创意来自偶然、混乱、非理性，不该被过度形式化。

所以不要走到另一个极端：

> 把协作变成一套僵死的类型系统，让人也变成执行器。

正确的用法是：

- **用纯函数约束 AI 的可预测部分**；
- **用效果边界保护人的判断与真实体验**；
- **用不可变历史保留“当时为什么这样想”**；
- **用类型/契约减少“它到底在做什么”的歧义**；
- **给意外、直觉和推翻留空间**。

## 十、一句话总结

> **AI 是纯函数：给它明确的上下文和任务，它返回候选、证据与风险。**
> **人是运行时：决定执行哪个候选，承担副作用，解释真实体验，并对结果负责。**

再压缩一点：

```text
ai       : Context -> Task -> Proposal
human    : Proposal -> Experience -> Decision
project  : fold(Decision, initialIntent)
```

项目不是“AI 输出之和”，而是**人的意图经过一系列有意识决定后的折叠**。

只要这条折叠线上的 `Decision` 仍然由人给出，AI 就无法把项目带走。

## 十一、最小落地清单

- [ ] 给项目写一个 `Context`：一句话、三支柱、三非目标、停止条件；
- [ ] 给 AI 任务加 `authority` 与 `stop_if`；
- [ ] 要求 AI 返回 `Proposal`，而不是直接改范围；
- [ ] 把“提交/发布/改方向/加内容”列为需要人批准的 `Effect`；
- [ ] 每次只做一个 `clarify → diverge → critique → prototype → observe` 的小循环；
- [ ] 在核心体验成立前，不批量生成内容；
- [ ] 把人的真实试玩记录写进 `Evidence`，不要用测试替代；
- [ ] 保留旧想法与旧决定，只追加新版本。
