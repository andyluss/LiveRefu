# ideas · 我的想法与设计源

> **这是人类手写的设计源，不是 AI 的提案箱。**
> 这里放原始想法、判断、审美偏好、非目标与未解决问题。AI 的职责是理解、追问、实现和验证，不是替你定义项目。

## 一、角色约定

| 谁 | 负责 |
| --- | --- |
| **我（人类）** | 主题、核心体验、审美方向、范围、优先级、最终验收与是否继续 |
| **AI** | 阅读与复述意图、提问、调研、实现、做原型、跑验证、准备证据、指出风险 |

默认关系：

> **人定方向，AI 扩可能性；人做决定，AI 提供依据。**

AI 可以不同意、可以提出更好的方案，但不能把“建议”变成“默认”，更不能因为实现起来更顺就改写原始想法。

## 二、`ideas/` 是什么

适合放：

- 一个突然想到的题材、机制、画面或情绪；
- 为什么这个想法值得做、它和别的项目有什么不同；
- 目标玩家、目标体验、希望玩家记住的瞬间；
- 明确不要的东西：非目标、反例、不能接受的代价；
- 审美参考、语气、参考作品；
- 还没想清楚的问题、矛盾、可以推翻的假设；
- 对已有项目的方向性修正。

不适合放：

- AI 生成的项目计划、代码说明、验收记录；
- 已经进入项目的实现细节（放项目 `docs/`）；
- 为了“看起来完整”而补出来的设定；
- AI 自己发散出来、但人没有明确采纳的新方向。

> 如果 AI 想探索一个想法，应该去 `lab/` 或临时原型，不默认写进 `ideas/`。

## 三、AI 读取规则

涉及**主题、玩法、体验、审美、范围、优先级**的任务，AI 开始前必须：

1. 读本文件；
2. 读与任务相关的 idea 文件；
3. 用一句话复述它理解的**意图**；
4. 列出它看到的**非目标 / 边界**；
5. 标出它不确定的地方，向人提问，而不是自行补全；
6. 再开始实现或提方案。

如果任务和 `ideas/` 冲突，AI 应停下来说明冲突，由人裁决。不得静默选择“实现更方便”的那一边。

## 四、AI 的行为边界

### 可以做

- 把模糊想法拆成可实现的选项；
- 给出 2–3 种方案、代价与推荐，但标明“建议”；
- 做小原型验证手感、性能、内容成本；
- 用测试、试玩、数据反驳一个想法；
- 在项目文档里记录“实现裁决”，但不改写原始想法；
- 提醒“这个新功能已经偏离最初意图”。

### 不可以做

- 未经明确要求，新增或改写 `ideas/` 里的内容；
- 把 AI 生成的世界观、卡牌、剧情、美术方向塞进人的想法；
- 因为“这样更完整”而扩大范围；
- 把“测试通过 / 代码跑通”当成“设计成立”；
- 用项目文档替代人的设计判断；
- 在人没有拍板前，把建议写成决定。

## 五、想法怎么写

一个想法一个文件或一个目录；不要求完整，允许粗糙、矛盾、待定。

建议文件名：

```text
YYYYMMDD-短标题.md
```

建议开头：

```markdown
# 标题

> 状态：种子 / 探索中 / 候选 / 已采纳 ｜ 日期：YYYY-MM-DD
> 一句话：

## 我为什么想做

## 我想让玩家/用户感受到什么

## 核心机制或体验

## 明确不要什么

## 还没想清楚

## 参考与语气
```

不是模板考试。只要能让 AI 分清“这是人的意图”与“这是 AI 的补全”，就够了。

## 六、从想法到项目

```text
种子 → 探索 → 候选 → 人拍板 → 项目
```

- **种子**：一句话、一个画面、一个机制，允许不完整；
- **探索**：AI 可以调研、做小原型、提出反方，但不改原想法；
- **候选**：人明确说“这个方向值得继续”；
- **人拍板**：人才可以把它变成项目目标、范围与验收；
- **项目**：进入 `games/`、`products/` 或 `lab/`，实现文档写在那里。

只有人能推进状态。AI 不能自行把“种子”升级成“项目”。

## 七、AI 每次工作的最小动作

```text
我读到的意图：
我理解的非目标：
我不确定、需要你回答的：
我建议的选项（附代价）：
我这次不会做的事：
```

如果这五项写不出来，说明还没有理解想法，不应直接开始实现。

## 九、给你的备注

这份 README 是 AI 起草的**协作约定**，你可以直接改。

尤其是：

- “AI 默认只读”是否要放宽；
- 想法的状态词是否合适；
- 是否允许 AI 在 `ideas/` 里追加“AI 回应”；
- 哪些项目类型必须先经过 `ideas/`。

你改过之后，以你的版本为准；AI 不应把自己的措辞当成不可改的规则。
