# R05 · 变更日志记录约定（已定 · 现行）

**一句话**：**每次（非琐碎）变更都须写入变更日志**（工作区根 `CHANGELOG.md` 或项目/实验各自的 `CHANGELOG.md`）；**琐碎改动豁免**。

> 状态：`accepted.active` ｜ 版本：v4 ｜ 最后更新：2026-10-27
> 本文是变更日志的**唯一规则与格式规格**；原 [`tech/changelog-convention.md`](../tech/changelog-convention.md) 已整合进本文，仅保留指针。

## 一、目标与适用范围

让工作区“改了什么、为什么、影响谁”有一份**面向人**的可追溯记录，与 `git log`（机器历史）互补。

适用于工作区根、`projects/`、`lab/`、`design/` 等所有**被跟踪的 `CHANGELOG.md`**。`indie/` 独立仓库按各自约定执行。

## 二、规则条款（必须）

1. **必写**：每次**非琐碎**变更写入变更日志——工作区根 [`CHANGELOG.md`](../CHANGELOG.md)；项目/实验写入各自根 `CHANGELOG.md`。
2. **格式**：遵循 **Keep a Changelog** 类目（`Added/Changed/Deprecated/Removed/Fixed/Security`）+ **SemVer** 版本 + **东八区、精确到分的时间**（版本头 `## [x.y.z] - YYYY-MM-DD HH:MM`）。时间精度/来源/格式见 [R06](R06-time.md)。
3. **粒度**：一条对应一个**逻辑变更**，与 git 提交粒度对齐；**面向人**，写清“改了什么、为什么、影响谁”。
4. **不替代提交记录**：变更日志是审阅版摘要，`git log` 是机器历史，两者互补。
5. **改规则时**：既写变更日志条目，又在**被改规则文件的「演进历史」**追加一行（见 [M3](meta/M3-rule-evolution.md)）。
6. **豁免（琐碎）**：同时满足①不改变对外/可观察语义；②不新增/删除/改动需追踪的产物；③纯文字（错别字、标点、格式、空白、措辞、相对链接深度）——可免写条目。

> 反之：只要触及**内容 / 结构 / 约定 / 产物**之一，就必须记录。

## 三、文件与位置

- **工作区根**：`CHANGELOG.md`（工作区级变更）。
- **项目/实验根**：各自根目录的 `CHANGELOG.md`（如 `projects/tomorrows-channel/CHANGELOG.md`、`lab/formal-system/CHANGELOG.md`）。
- 变更日志是普通 Markdown：内部链接必须按 [R03](R03-link-validation.md) 写正确深度，不享受链接校验豁免。

## 四、结构模板

自上而下，**最新版本在最上**、时间倒序；未发布改动集中在 `[未发布]`。

```markdown
# 变更日志

> （可选）一句话说明本仓库/项目是什么、日志遵循什么约定。

## [未发布]

## [1.2.0] - 2026-09-09 10:11
### 新增
- …

### 变更
- …

### 移除
- …

### 修复
- …
```

规则：

- 版本头：`## [<版本>] - <YYYY-MM-DD HH:MM>`，**东八区、精确到分**；只到日期的旧形态会被检查器拒绝。
- 进行中的改动放 `## [未发布]`；发布时新增版本段，不删除/覆盖旧版本。
- 每个语义小节为 `### <类目>`；无变化的类目不写。
- 类目可用中文或英文，但同一文件保持一致；正文列表用 `- `。

## 五、标准类目

| 类目 | 英文 | 说明 |
| --- | --- | --- |
| 新增 | Added | 新功能/新特性 |
| 变更 | Changed | 对既有内容的改动 |
| 弃用 | Deprecated | 即将移除、暂仍可用 |
| 移除 | Removed | 移除/删除的内容 |
| 修复 | Fixed | 修复 bug/失效链接 |
| 安全 | Security | 安全/漏洞相关 |

## 六、条目撰写

1. **一条一个逻辑变更**：避免把无关改动塞进同一条。
2. **面向读者**：写清“改了什么、为什么、影响谁、影响面多大”，不要只复述文件路径。
3. **跨目录/跨模块大改动**：可拆多条；必要时用二级列表/补充节，但不要用补充节替代标准类目。
4. **多件不相关改动**：分条目，不强行合并。
5. **关联文档**：规则/规范改动加 `见 [rules/…]` 或对应 README 链接。
6. **撤销/回滚**：用“变更/移除”记录，并注明原提交号/原版本。
7. **草稿/待定**：标 `【待定】`，结论定稿后并入正式条目。
8. **琐碎豁免**：判据见 §二.6。

## 七、版本号（SemVer）

- `MAJOR.MINOR.PATCH`；预发布/元数据按 SemVer 追加（如 `1.2.0-beta.1`）。
- `MAJOR`：不兼容变更；`MINOR`：向后兼容新增；`PATCH`：向后兼容修复。
- 头部可加 `v` 前缀，但全库保持一致；本仓库示例不带 `v`。

## 八、发布流程（时间 ↔ 标签）

版本头时间**必须等于该版本 tag 指向提交的作者时间**（本地格式 `%Y-%m-%d %H:%M`）。检查器会拒绝不一致。

- **标签命名**：`<前缀>-v<版本>`（根 `workspace-v`，项目如 `livefab-v`、`mainline-v`、`livedso-v`）。
- **正常流程**：
  1. 取本次提交时间，写进版本头；
  2. 以该时间为作者时间提交：`GIT_AUTHOR_DATE='YYYY-MM-DD HH:MM' git commit …`；
  3. 提交后**立刻打标签**：`git tag <前缀>-v<版本>`；
  4. 推送提交与 tag。
- **最新版本可暂缺 tag**：tag 必须指向已存在提交；更早版本必须有 tag 且时间一致。
- **旧版本缺 tag**：补 tag 到该版本最后一个提交，并让版本头时间等于该提交作者时间；**不要折叠/删除旧版本**。

## 九、哪些变更写进根日志（硬约定）

| 写进根 `CHANGELOG.md` | 写进项目 `CHANGELOG.md` |
| --- | --- |
| 工作区级：`rules/`、`tech/`、`docs/`、`tools/`、根配置、跨项目约定 | 单个项目的代码、文档、素材、验收、裁决 |
| 跨项目格局变化（立项/暂停/改名、结构调整） | 该项目的里程碑、阶段、机制裁决 |
| 影响多个项目的工具链（如 pre-commit） | — |

**边界倾向**：拿不准时写项目日志——写窄了以后能往上提，写宽了会污染根日志。

**把关**：`check_changelog --assert-workspace-level` 检查根日志是否只有工作区级条目；它只看路径引用，是启发式，不能证明一条目真的属于工作区级。

## 十、版本段 append-only（硬规则）

> 2026-10-27 新增。起因：LiveDSO 为绕开“旧版本没有 tag”的校验，把 `0.2.0` / `0.3.0` 折叠进 baseline，导致旧日志消失。正确做法是补 tag。

1. 已发布的 `## [x.y.z]` 版本段**不可删除、改名、折叠或合并**；只允许修正链接、格式、错别字。
2. 新版本只能**新增**一个版本段；`[未发布]` 只放尚未发布内容，不能替代历史版本。
3. 旧版本缺 tag 时：补 tag 到该版本最后一个提交，并让时间对齐；不折叠、不改写历史。
4. **当前 A 策略不允许“归档拆分”**：主日志必须保留全部版本段。若未来改 B 策略，必须给检查器增加显式归档参数，并保留归档与 tag 对应关系。
5. 任何“baseline”只能作为新版本继承能力的摘要，不能删除被继承的旧版本段。

**机器闸门**：`tools/check_changelog.ts` 默认对比 `HEAD` 与当前文件；旧文件有、当前文件没有的版本号直接失败；新文件不适用。失败时补 tag，不要折叠。

**发布顺序**：

```bash
# 1. 写版本段（时间取本次提交作者时间）
# 2. 提交
git commit -m "release: vX.Y.Z"
# 3. 立刻打 tag（不要隔天补）
git tag <project>-vX.Y.Z
# 4. 推送提交与 tag
git push origin main
git push origin <project>-vX.Y.Z
```

## 十一、机器校验与能力边界

- [`tools/check_changelog.ts`](../tools/check_changelog.ts)：版本头格式、时间倒序、标准类目、空版本、未来时间、旧版本段消失、版本头↔tag。
- [`tools/check_links.ts`](../tools/check_links.ts)：日志内相对链接。
- pre-commit / CI 对所有被跟踪 `CHANGELOG.md` 执行。
- **能力边界**：根日志“子项目专属”检查只看路径引用，是启发式；不能替代人审。

## 十二、备选（被放弃）

| 备选 | 为何不为主选 | 代价 |
| --- | --- | --- |
| 不写变更日志 | 无面向人的变更脉络 | 回溯成本高 |
| 只靠 `git log` | 机器历史，非审阅摘要 | 读不出“为什么” |
| 全量都写（含错别字） | 噪声大 | 维护负担 |
| 为过校验折叠旧版本 | 删除历史、校验失真 | 不可追溯；禁止 |

## 十三、自检

> “这次改动如果别人下周来看，变更日志能告诉他发生了什么吗？”
>
> “旧版本段还在吗？tag 与版本头对得上吗？”
