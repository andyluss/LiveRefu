# M3 · 元规则自身演进（已定 · 已落地）

**一句话**：每条规则是一个**活的合约**，带**多状态 + 子状态**的生命周期、**允许的迁移**、**版本化演进历史**与
**鼓励演进**的立场；并由 [`evolution/`](evolution/README.md) 子关注点的**形式化检查**校验其演进状态是否合法。

## 一、目标

在两极之间取得平衡：既不要"拍脑袋一次定死"（缺验证、难回退），也不要"永远不定/悄悄偏离"（无法判别可依赖、
共同记忆流失）。让元规则**可演进、可回退、可追踪、可被检查**。

## 二、主选（决策）：多状态生命周期

### 2.1 主状态（primary）

| 状态 | 含义 |
| --- | --- |
| `draft` 草案 | 只有想法，尚未成文 |
| `proposed` 建议 | 已成文，待讨论 / 试行 |
| `experimental` 试用 | 在本基地**试行**（实验期） |
| `accepted` 已定 | **采纳**，作为判据 |
| `in-review` 复核中 | 被挑战，重新审议 |
| `superseded` 被取代 | 被新规则/新版本取代 |
| `deprecated` 废弃 | 不再推荐，保留历史 |
| `retired` 退役 | 从清单移出，留档 |

### 2.2 子状态（sub-state，挂在主状态后，如 `accepted.active`）

| 主状态 | 允许的子状态 |
| --- | --- |
| `proposed` | `draft`(初稿) · `discussion`(讨论中) · `trial`(试行中) |
| `experimental` | `trial`(试点) · `validated`(已初验) |
| `accepted` | `active`(现行) · `applied`(已落地-有检查/工具) · `lapsed`(暂搁置) |
| `in-review` | `challenged`(被质疑) · `superseding`(待被取代) |

### 2.3 允许的迁移（`from → to`，其余迁移视为非法）

```
draft        → proposed, experimental, retired
proposed     → experimental, accepted, retired
experimental → accepted, in-review, retired
accepted     → in-review, superseded, deprecated, retired
in-review    → accepted, superseded, deprecated, retired
superseded   → deprecated, retired
deprecated   → retired
retired      → (终态)
```

> 回退（如 `accepted → in-review`）也**受允许**（因为被挑战就是要回审议），但要登记理由。

### 2.4 每个规则文件须声明

- 标题行给**当前状态**（如 `（已定 · 实验期）`）。
- **演进历史**表含**状态列**：`| 版本 | 日期 | 状态 | 变更 | 依据 |`，每一行记录一次"状态/内容变更"。
- 相邻两行的状态迁移**必须**属于上述允许集合。

## 三、鼓励演进（立场）

- **规则是"活的合约"，不是定死的教条**：它值得在"被绕过/被质疑/被重估"时被重新审视。
- **请求修改、重估或取代一条规则 = 健康的正反馈**，不是挑衅——它说明这条规则正被使用、被检验。
- **当你想违反一条规则时，先问**："我应该改规则，还是改我做的东西？"若是前者，走"提出变更"路径，而不是绕过它。
- **永远优先"提出并记录变更"，而不是"悄悄偏离"**——偏离不记录 = 共同记忆流失。
- **回退与取代同样值得记录**；历史表**只增不改**，保留完整决策轨迹，方便任何后来者看清"为何这样、何时变的"。

## 四、备选（被放弃的选项）

| 备选 | 描述 | 为何不为主选 | 代价 |
| --- | --- | --- | --- |
| A3.1 一次定死 | 讨论后立即定案、不再记录 | 缺验证土壤、难回退 | 出错只能推倒重来 |
| A3.2 无状态（都当临时） | 规则一律不标状态 | 无法区分"可依赖/实验性" | 人人各自解读 |
| A3.3 只有历史无状态 | 只记账不标状态 | 无法判定当前是否生效 | 需额外推断 |
| A3.4 纯单状态（建议/已定） | 二态足够 | 覆盖不了"复核/被取代/废弃/退役"等场景 | 缺中途与终态语义 |
| A3.5 随意迁移 | 任何状态可跳任意状态 | 无法判定迁移是否合理 | 状态失去意义 |

## 五、判定标准 / 可验证

- 一条规则的状态迁移应遵循 §2.3；演进历史表须有**状态列**且迁移合法。
- **形式化检查**：[`evolution/rule_evolution_check.ts`](evolution/rule_evolution_check.ts)（属 [`evolution/`](evolution/README.md) 子关注点）
  扫描 `M*-*.md`（元规则，`rules/meta/`）与 `R*-*.md`（具体规则，`rules/`），校验：状态合法（主+子）、历史非空、日期递增、相邻迁移合法。用 `--self-test` 自检。

## 六、自检问题

> "我能从这条规则的演进历史看出它的**状态轨迹**（为何从建议→已定→被复核…）、依据是什么吗？"
