# 形式化验证（formalization）——现状、边界与演进

> 仓库级技术文档。记录本工作区用**形式化手段**（可机器验证的契约/校验/测试）管理需求与工作复杂度的**现状与边界**，以及后续演进路线。
> 背景：工作区以"虚拟工作室 + 角色（AI agent）"模式开发《明日频道》（Godot 4.7.x 氛围陪伴应用）。该模式擅长**生成内容**，但若不引入独立的形式化验证层，**角色越多、确定性越低**——无法保证某 agent 的产出在任何机器上、任何时刻都成立。

## 一、为何需要形式化验证

角色驱动的开发组织方式（主策划/主程序/主美术…各司其职）本身没有问题，但存在一个结构性弱点：

> **"生成"与"验证"被耦合在同一个"角色心智"里——每个 agent 既是作者又是质检，缺乏独立的、机器的、可重复的验证层。**

形式化工具（编译器、schema 校验、类型检查、测试）正是那个"独立验证层"。它把**约定变成机器可检查的声明**，从而在提交/合入前拦下错误，而不是依赖 agent 自述"我验证过了"。

### 已遇到的实际问题（驱动本机制）
- **软契约靠人自觉**：`event_bus` 信号契约（参数/emit/订阅）、配置表字段与 token 引用，只靠文档/注释约定，无机器验证。改名一个信号，全链路静默断裂。
- **角色边界是叙事非约束**：`git add -A` 让"主程序只改程序、数值只改数据"在工程层面形同虚设（本项目曾多次发生多 agent 混提交）。
- **需求非结构化**：需求散落在 GDD/各角色文档/meetings/issues 的【待定】里，无机器可读清单——"需求是否被满足"无从自动验证。
- **复杂度不可测算**：M1/M2 有多少表/模块/事件/未知量，没有可测算的形式；issues/ 是文本分类，无法自动追踪"风险是否已关闭"。

## 二、已落地的形式化验证层（现状，2026-09）

按"能验证的强度"分层次，现已落地 **层次 1 + 层次 3（务实版）**：

### 层次 1：数据契约 → schema 校验（✅ 已落地）
- **工具**：`tools/check_data.py`（纯标准库，无外部依赖，与 `check_links.py` 一致）。
- **校验内容**：`data/tables/*.json` 是否符合 `data/schema/*.schema.json` 契约——必填字段 / type（integer/string/number/boolean/object/array）/ enum / min / max / 嵌套 `copyright`。
- **接入**：pre-commit 钩子（暂存涉及 `data/` 表时）+ CI（`python3 tools/check_data.py`）。
- **即时价值**：校验器首次运行即发现并修复一个真实契约缺陷——`content_card.schema.json` 顶层 `type: object`（单卡）但卡池数据是数组（与 `channel` 的 `type: array` 不一致），已改为 `array`+`items`。
- **实测**：能正确拦截 4 类非法数据（超上限 / 低于下限 / 类型错 / 负值），exit 1。

### 层次 3：Godot 工程加载检查（✅ 已落地，务实版）
- **工具**：CI 里 `godot --headless --path game --quit-after 5`（`HOME=/tmp/gdhome` 处理沙箱 user://）。
- **验证内容**：Godot **真正加载工程**（主场景 + autoload 链编译）并执行内建自检 `_verify_closed_loop()`——暴露脚本编译错误 / 资源加载错误 / 行为回归。
- **接入**：CI 的第三步（与链接/数据并行），本地 pre-commit 不跑 Godot（重、慢）。

### 其它已存在的形式化
- **pre-commit/CI 链接校验**：`tools/check_links.py` + `tools/hooks/pre-commit`（md 相对链接）。
- **数据驱动**：配置表（`data/schema|tables`）+ `config_loader` 读 JSON——内容/数值/文案零硬编码，天然可据 schema 校验。

## 三、GDScript 的边界（实测，诚实记录）

**GDScript 是弱类型语言，其静态检查能力远弱于 TypeScript/Java。** 实测三种命令行方式：

| 方式 | 结果 |
| --- | --- |
| `godot --check-only --script <file>` | ❌ **误报**——单独检查一个脚本时无法解析全局 `class_name`（如 `ChannelSkin`）与 autoload 单例（`event_bus`），把正常的跨文件引用当"未声明"。11 个健康脚本全被误报。 |
| `godot --headless --import` | ⚠️ 不拦截语法/类型错误（只注册类，import 后即 quit，不触发真实编译）。 |
| `godot --headless --path game --quit-after N` | ✅ 最可靠——验证**主场景+autoload 链**编译，并暴露运行期错误。但**不扫描未被挂载的独立脚本**（`scripts/` 下未进 autoload/场景链的 .gd 不会编译）。 |

**结论**：
- Godot 能给的**可靠静态验证有限**——真正靠谱的是**运行时加载 + 测试**。
- 因此 **"全工程 GDScript 静态类型检查"在 Godot 上不可行**，不要用 `--check-only` 逐个 script 当门禁（会误报）。
- CI 定位为"**运行时加载 + 内建自检**"，而非虚假宣称"静态类型安全"。

## 四、形式化验证的适用边界（哪些能/不能机器验证）

| 类别 | 能机器验证？ | 手段 |
| --- | --- | --- |
| 数据契约（必填/type/enum/范围） | ✅ | `check_data.py`（schema 校验）|
| 主场景+autoload 链编译/加载 | ✅ | Godot 运行时加载 + 自检 |
| 行为正确性/回归 | ✅（需测试）| GUT / Godot 测试（层次 4）|
| 模块接口（信号名/参数/emit/订阅） | 🟡 部分 | 集中契约 + 静态扫描（层次 2，较难）|
| 需求完整性（需求→测试关联） | 🟡 部分 | 结构化需求模型（层次 5，重）|
| GDScript 全工程类型安全性 | ❌ | 弱类型语言，静态检查不可靠 |
| 设计/手感（"温暖、可久处"）| ❌ | 只能靠人评审（无法形式化）|

**核心原则**：形式化只能覆盖**可判定的工程/数值/契约/行为**部分；创意与手感无法形式化。应优先把**"已有但未机器化的约定"变成工具**（schema 校验、测试），而非引入重形式化框架。

## 五、演进路线（优先级）

1. **层次 4：GUT / Godot 自动化测试（M2 前做，最实质）**
   - 把 `_verify_closed_loop()` 自检正式化为可重复跑的集成/单元测试（GUT 或 Godot `--script` 测试）。
   - 价值：复杂度一到三频道，无回归测试会很痛；把"靠记忆/人肉验证"变成机械回归验证。**这是"管理工作复杂度"最实质的手段。**
2. **层次 2：接口契约静态扫描（模块多了再做，避免早期过度设计）**
   - 事件契约（信号/参数/emit/订阅）搞单一权威源 + 扫描 GDScript 检查一致性。
3. **层次 5：结构化需求模型（产品形态稳定后再做，谨慎）**
   - 需求/验收提炼成机器可读清单，绑定测试，"需求被满足 ≈ 测试 green"。
   - 注意：MVP 阶段不建议（成本高 + 手感无法形式化）。
