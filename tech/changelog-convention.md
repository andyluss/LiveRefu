# 变更日志约定（CHANGELOG Convention）

> 工作区级规范：**每次（非琐碎）变更都须写入变更日志**（规则见 [`../rules/R05-changelog.md`](../rules/R05-changelog.md)）。
> 本文定义变更日志的**格式规格**，供根 `CHANGELOG.md` 及各项目/实验的 `CHANGELOG.md` 共同遵循。
> 本文件是变更日志书写的**格式规格 / 技术详解**（规则权威在 [`rules/R05-changelog.md`](../rules/R05-changelog.md)）；根 [`README.md`](../README.md) 仅保留入口。

## 一、基准规格（业界惯例）

本规格参考业界最常见的三套约定，取长补短：

| 约定 | 用途 | 链接 |
| --- | --- | --- |
| **Keep a Changelog** | 「为人类」记事：按语义分组、按日期可追溯，是目标格式的主体 | [keepachangelog.com/zh-CN/1.1.0](https://keepachangelog.com/zh-CN/1.1.0/) |
| **SemVer** | 版本号语义化（`MAJOR.MINOR.PATCH`），表达兼容性影响 | [semver.org](https://semver.org/) |
| **Common Changelog**（可选） | 更严格、更利于机器校验的补充约束 | [common-changelog.org](https://common-changelog.org) |

> 原则：变更日志是一份**面向人的审阅版摘要**（按语义分组、说明"改了什么/为什么/影响谁"），与机器侧的 `git log / git diff` 互补，但**不以日志替代提交记录**。

## 二、文件与位置

- **工作区根**：`CHANGELOG.md`（本工作区根级变更）。
- **项目/实验根**：各自根目录的 `CHANGELOG.md`（如 `projects/tomorrows-channel/CHANGELOG.md`、`lab/formal-system/CHANGELOG.md`），遵循同一格式；「每年/每项目一条」各自管理。
- 变更日志文件**不参与**相对链接深度校验的豁免——它本身也是普通 Markdown，内部链接须按 [`docs-convention.md`](docs-convention.md) 书写正确深度。

## 三、结构（模板）

自上而下，**最新版本在最上**、时间倒序；未正式发布的改动集中在 `[未发布]`（Unreleased）。

```markdown
# 变更日志

> （可选）一句话说明本仓库/项目是什么、日志遵循什么约定。

## [未发布]

## [1.2.0] - 2026-09-09 10:11
### 新增
- …

### 变更
- …

### 移除
- …

### 修复
- …
```

### 标题格式

- 版本条目头：`## [<版本>] - <YYYY-MM-DD HH:MM>`，**东八区、精确到分**（见 [R06](../rules/R06-time.md)）。
  ⚠️ **只到日期的旧形态会被 [`tools/check_changelog.ts`](../tools/check_changelog.ts) 直接拒绝**（自测用例即"缺时分…旧格式必须被拒"）——本文件此前的写法就是错的，2026-10-08 修正。
- 进行中的改动放 `## [未发布]`；发布时把 `[未发布]` 的条目并入对应版本号并补上**日期时间**。
- 每个语义小节为 `### <类目>`；**无变化的类目不写**（省略空头）。
- 类目名建议用**英文**（`Added/Changed/Deprecated/Removed/Fixed/Security`，Keep a Changelog 标准），正文列表项可用中文描述。

## 四、标准类目（Keep a Changelog 七个）

| 类目 | 英文 | 说明 | 典型示例 |
| --- | --- | --- | --- |
| 新增 | Added | 新功能/新特性 | 新增某目录、新增某工具 |
| 变更 | Changed | 对既有内容的改动 | 调整目录结构、改写某规范 |
| 弃用 | Deprecated | 即将移除、暂仍可用 | 标记某写法将被弃用 |
| 移除 | Removed | 移除/删除的内容 | 删除某文件/模块 |
| 修复 | Fixed | 修复的 bug/失效链接 | 修复失效相对链接 |
| 安全 | Security | 安全/漏洞相关 | 收紧某安全约定 |

> 列表项统一用 `- `；每条尽量**一条代表一个逻辑变更**（与 git 提交粒度一致）。

## 五、条目撰写（可胜任复杂情形）

1. **一条一个逻辑变更**：避免把无关改动塞进同一条；与提交粒度对齐。
2. **面向读者**：写清"改了什么、为什么、影响谁、影响面多大"，而非复述文件路径/代码。
3. **跨目录/跨模块大改动**：可拆多条，各归最贴切类目；或用二级 `- ` 分组、子标题保持可读。
4. **多件不相关改动**：分条目，不强行合并；单版本条目过长时可加**补充节**（如 `### 已知问题`、`### 后续待办`，属信息性、非标准类目）。
5. **关联文档**：涉及规则/规范改动时，条目尾部加 `见 [rules/…]` 或对应目录 README 链接，便于追溯。
6. **撤销/回滚**：用 `### 变更` 或 `### 移除` 记录，并注明对应的原提交号 / 原版本。
7. **琐碎改动豁免**：改错别字、纯格式（空白/缩进）、不改语义的措辞润色等**琐碎改动**可不写条目（判据见 [`../rules/R05-changelog.md`](../rules/R05-changelog.md)）。
8. **草稿/待定**：未决事项标 `【待定】`，结论定稿后并入正式条目（延续工作区文档惯例）。

## 六、版本号（SemVer）

- 版本号 `MAJOR.MINOR.PATCH`；有预发布/元数据时按 SemVer 追加（如 `1.2.0-beta.1`）。
- **升位规则**：
  - `MAJOR`：不兼容变更（破坏既有接口/目录/约定）。
  - `MINOR`：向后兼容的新增功能。
  - `PATCH`：向后兼容的修复。
- 头部可加 `v` 前缀，但**全库保持一致**；本仓库示例不带 `v`。
- 发布时用 `## [<新版本>] - <东八区日期 时间>` 合并发布。

## 七、示例

```markdown
## [未发布]

## [2.0.0] - 2026-09-09 10:11
### 新增
- 新增根规则目录 `rules/`，集中收口工作区具体规则（初始为 R01–R04 占位）。

### 变更
- 根 README 增加 `rules/`、`indie/`、`lab/` 目录说明与导览行。
- 改写「约定豁免」说明，显式列出被豁免规则（R01–R04）。

### 修复
- 修正根 README 中 `lab/` 的入口链接（指向其 README）。
```

## 八、流程

- **起草**：以本次 `git log` / `git diff` 为线索，但改写成**面向人的叙述**并归类，避免机械拷贝提交信息。
- **落盘**：非琐碎改动在提交所属的版本条目（或 `[未发布]`）下补记；完成一个逻辑改动即更新。
- **发布**：把 `[未发布]` 改写为 `## [<新版本>] - <日期 时间>`，按 SemVer 定版本号。
- **校验**：变更日志链接仍受 `tools/check_links.ts`（pre-commit + CI）校验；改动不满足一致性时会被流程提醒。

## 九、版本头时间 ↔ 标签（机器校验）

变更日志的**版本头时间不是自由填写**——它必须等于**该版本 tag 指向提交的作者时间**（本地格式 `%Y-%m-%d %H:%M`）。
这条把"文档"与"git 历史"钉在一起：**版本头与标签对不上，检查器会直接拒绝提交**。

- **标签命名**：`<前缀>-v<版本>`（根为 `workspace-v`，各项目如 `livefab-v`、`mainline-v`、`future-debris-v`）。
- **谁来查**：[`tools/check_changelog.ts`](../tools/check_changelog.ts)，接入 pre-commit 与 CI；时间规则见 [R06](../rules/R06-time.md)。
- **正常流程**（不按这个顺序会被卡住）：
  1. 取本次提交时间，写进版本头：`date '+%Y-%m-%d %H:%M'`；
  2. **以该时间为作者时间提交**：`GIT_AUTHOR_DATE='YYYY-MM-DD HH:MM' git commit …`；
  3. 提交后**立刻打标签**：`git tag <前缀>-v<版本>`。
- **为什么允许"最新版本暂时没有标签"**：标签必须指向一个**已存在**的提交，而版本头是"本次提交要引入的版本"——提交前它必然还没有标签。
  因此检查器**只要求更早的版本都有标签且时间一致**；最新版本可暂缺（提交后立刻打即可）。
  此前"缺标签一律判失败"会让**每一次版本提交都被前钩拦下**，而本文当时并未写明流程（无章可循）。
- **注意取的是作者时间**（`git log --format=%ad`），不是提交时间（`%cd`）。

## 十、哪些变更写进**根**日志（本条为硬约定）

> 2026-10-05 新增。起因：本工作区早期把**各项目的进展也写进根日志**，
> 结果根日志里混着大量 `projects/future-debris`、`projects/mainline` 之类的内容；
> 同一件事在根日志与本项目日志两处出现，两边都可能过期。已把那批条目迁入各自项目日志。

**判定标准**：

| 写进**根** `CHANGELOG.md` | 写进**项目** `projects/<x>/CHANGELOG.md`（或 `lab/`、`indie/`、`studioNNN/`）|
| --- | --- |
| 工作区级：`rules/`、`tech/`、`doc/`、`tools/`、根配置、跨项目约定 | 单个项目的代码、文档、素材、验收、裁决 |
| **跨项目**的格局变化（如某项目立项/暂停/改名、工作区结构调整） | 该项目的里程碑、S 阶段、机制裁决 |
| 影响多个项目的工具链（如 pre-commit 钩子） | — |

**边界上的倾向**：拿不准时写**项目**日志——写窄了以后能往上提，写宽了会污染根日志。

**把关**：[`tools/check_changelog.ts`](../tools/check_changelog.ts) 带 `--assert-workspace-level` 时，
会检查根日志里是否有"只写某一个子项目"的条目；pre-commit 对根日志默认开启。

> ⚠️ **这条把关的能力边界**（必须说清，否则会被当成万无一失）：
> 它只看**路径引用**，是启发式。实测在迁移前那版根日志上抓到 **22/33** 条、
> 在迁移后的根日志上**零误报**——**能挡住大多数，但不能证明一条目真的属于工作区级**。
> 认定不了的靠人审。
