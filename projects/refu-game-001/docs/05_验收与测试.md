## 一、为什么要有无头验收

卡片塔防最容易出的错不是"画不出来"，而是"算错了还看不出来"：能量给多了、钩子没触发、
对空规则漏判、羁绊永远不可达、挑战卡偷偷改了卡表数值。这些错误在画面上都长得像"手感问题"。
所以本工程把 `core/` 做成**不依赖渲染**的纯逻辑，用固定种子驱动整局，把"必须成立的性质"写成 19 条用例。

## 三、19 条用例在守什么

| 场景 | 用例 | 守的规则（文档依据） |

| 数据装载 | B = 158 | 数值/04 第三节：WAV-ANV-A 合计威胁值 = B_ref |
| 数据装载 | 推荐卡组合法 | doc 05：20 张、同名 ≤2、≥2 个不同标签 |
| 自动通关 | 守住 6 波 | doc 04：胜利 = 守住全部波次 |
| 自动通关 | 漏怪 ≤ 3 | doc 21：第 1 章目标胜率 90%+ |
| 自动通关 | 触发羁绊 ≥1 | doc 02 组合法则四：羁绊是"卡片融合感"的主要来源 |
| 自动通关 | 评级 ≥ A | doc 04 第五节：评级三维 |
| 空手必败 | 基地归零判负 | doc 04：基地生命归零 = 失败 |
| 确定性 | 同种子同结果 | 工程要求：验收可复跑（不是文档要求） |
| 挑战卡 | 难度分/掉落系数 | 数值/05 第四节：`1 + 0.05 × 难度分` |
| 挑战卡 | 加压后敌人生命 ×1.3 | doc 13：CHL-01 只改环境参数，不改卡表数值 |

| 白名单 | 单入口图不可挂双流 | doc 19 第三节 + doc 13 CHL-04 |
| 白名单 | 教学关不开放挑战卡 | doc 06 第四节 |

## 五、验收的四道闸门（建议接入 CI）

```bash
cd projects/refu-game-001
python3 tools/verify_data.py                     # 1) 数据表 ↔ 策划文档
python3 tools/extract_map_data.py --check        # 2) 地图数据 ↔ 地图出图
python3 tools/sync_assets.py --check             # 3) 工程资源 ↔ 美术出图
cd game && ./run.sh check                         # 4) 文件预算 + 战斗逻辑 19 项
```

四条都是**非零退出即失败**，且不需要网络、不需要显示器（`--headless`）。
`./run.sh check` 内部先跑 `tools/check_file_size.py`（每个 .gd 的代码行预算，
见 [06_文件预算与拆分约定](06_文件预算与拆分约定.md)），超预算直接 FAIL，不进入用例阶段。

### 重构后的额外验证（2026-09-16 文件拆分）

把 23 个文件拆成 128 个时，除了上面四道闸门，还做了两件更严格的核对：

1. **数值不变**：验收场景一的数字与拆分前逐字一致（漏怪 1、基地 19/20、用时 215s、评级 S 0.87）——
   期间发现自动玩家的调用顺序被拆分改动，导致用时分 204s，已回退到原顺序；
2. **像素不变**（由 `view/` 拆分负责方执行）：用 `git HEAD` 的原始绘制代码与拆分后代码，
   在相同参数下各截一次图逐字节比对，`level_select` / 战斗布防期 / 战斗 50s 实战三组 **SHA256 完全相同**。

## 六、尚未覆盖 / 已知缺口

- **没有单元测试框架**：所有断言写在 `tools/sim/sim_suites*.gd` 里，用例多了之后建议引入 GUT/gdUnit；
- **未覆盖 UI 交互**（点选、放置、弹窗）的自动化——只用 `AutoPlayer` 覆盖了逻辑层的放置 API；
  界面行为目前靠截图人工核对；
- **未覆盖多地图/多波次卡组**（M1 只有 1 张地图、1 套波次），M2 铺开时用例需要参数化；
- **未做长时间稳定性测试**（周长长局的 20+ 波、内存增长）。
