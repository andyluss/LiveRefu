### 2.4 性能与无障碍（`tools/verify-perf.ts`）

**为什么不用 Lighthouse**：验收口径只要 LCP / CLS 两个**浏览器原生指标**，
引入 Lighthouse 及其一大串依赖只为拿两个数，性价比不合理。

**关键细节 —— 性能测量必须限速。** 本机 localhost 回环下 LCP 只有 60–100ms，
那个数字**不能用来判断「< 2.5s」目标是否达成**（等于没测）。脚本模拟
**4× CPU 降速 + 1.6 Mbps / 150ms RTT**（"桌面宽带"口径的偏保守近似）：

```
✓ 首页        LCP 324ms  CLS 0.0003
✓ Wiki 文章   LCP 280ms  CLS 0
✓ 画廊专辑    LCP 292ms  CLS 0
✓ 博客列表    LCP 292ms  CLS 0
```

> **诚实说明**：无头 Chrome + 本机服务端的**绝对值**与真机、真实网络有差异，
> 因此这个结果说明的是「**距离 2.5s 阈值有近一个数量级的余量**」，
> 而不是"在任意网络下 LCP 就是 280ms"。CLS 为 0 是可确认的（无重排）。

**无障碍**：9 项**页面上下文可判定**的检查 × 4 个页面全部通过——
img 有 alt、恰好一个 h1、标题不跳级、按钮/链接有可访问名称、`<html lang>`、
存在 `<main>` 地标、id 不重复、无正数 tabindex。

**并且做了负向自检**（`--selftest`）：注入故意违规的 DOM，确认检查器**真的会报错**：

```
✓ 捕获 img-alt          → ["x.png"]
✓ 捕获 h1-single        → ["h1 数量 = 2"]
✓ 捕获 button-name      → ["<button></button>"]
✓ 捕获 dup-id           → ["dup"]
✓ 捕获 positive-tabindex → ["DIV[tabindex=3]"]
5/5 项违规被捕获
```

> 理由：**一个永远返回"通过"的检查器比没有检查器更糟**——它给人虚假的安全感。
> 这个自检证明检查逻辑是活的。

**本项不声称的范围**：这不是完整 WCAG 审计（对比度、屏幕阅读器实读、
动态内容播报等未覆盖）。

### 2.5 颜色对比度（`tools/verify-contrast.ts`）

对比度是**唯一可以纯计算判定**的无障碍维度（WCAG 公式是确定的），
所以它应该被机器守住，而不是靠肉眼。审计结果——**查出并修掉了一个真实缺陷**：

| 问题 | 原值 | 实测对比度 | 处理 |
| --- | --- | --- | --- |
| `--text-faint` 用于页脚、面包屑、侧栏标签 | `#6b7889` | 在 `bg-elev-2` 上仅 **3.57:1**（AA 需 4.5） | 提亮至 `#808d9f`，最低 **4.76:1** |
| 交互控件边框 | `--line` `#24303f` | **1.43:1**（1.4.11 需 3:1） | 新增 `--line-strong` `#66727f`，最低 **3.27:1** |

**两处刻意的判断**（都不只是"改到通过"）：

1. **`--line` 保留不动，只给交互控件换 `--line-strong`。** 1px 装饰性分隔线
   不受 WCAG 1.4.11 约束；把它们也调亮会让整个界面变得又脏又吵，
   是"为了通过审计而破坏设计"。
2. **提亮 `--text-faint` 后立刻检查层级没被压平。** 只查对比度会漏掉一种退化：
   颜色达标了，但和相邻层级挤在一起，用户分不出主次。所以审计里加了
   **亮度顺序断言**（`bg < bg-elev < bg-elev-2`、`text-faint < text-dim < text`、
   `line < line-strong`）以及 `text-faint` 与 `text-dim` 的**最小亮度比 1.15**
   （当前 1.45）。将来改 token 若把层级压平，会直接失败而不是靠肉眼发现。

同时补了**全局 `:focus-visible` 焦点轮廓**（`--focus` 对三种背景均 ≥3:1）——
早先只有搜索框和灯箱有焦点样式，侧栏与画廊图格等键盘可达元素没有。

**最终**：27 个前景/背景组合全部达 WCAG AA（普通文字 18 组 ≥4.5:1、
大字 2 组 ≥3:1、非文字 UI 7 组 ≥3:1），最低一组 3.27:1。

## 三、M1 的技术决定（实现期拍的板）

### 3.1 搜索：客户端 FTS，不引入搜索服务（落实 D9）

Nuxt Content 3 的 `useSearchCollection` 在**浏览器本地**加载集合并建 FTS 索引。好处是不需要
Meilisearch / Typesense 这类外部服务，与 D5「零外部服务」取向一致。

- **首次真正检索时才 `init()`**（`immediate: false`），避免每个页面都下载索引；
- 输入 **250ms 去抖**，不逐字建索引；
- 中文分词受 SQLite FTS5 限制（按字切分），实测短词命中良好；长词组召回一般，
  按 [05](05_实施路线图与验收.md) §七 R5 的预案，M2 视情况评估 Orama/外部分词。

**集成注意（实测）**：搜索被放在 `SearchDialog.vue` 内部，其触发按钮同时充当页头的搜索入口——
无需额外的 provide/inject 或全局状态，组件自身就是入口 + 弹层。

### 3.2 画廊素材：只读暴露，不复制（落实 D2）

素材位于 `doc/refu-game-001/美术/`，在 Nuxt 工程之外。按「`doc/` 是唯一内容权威」：

- **不复制**进 `public/`，**不修改**源文件；
- 新增 Nitro 路由 [`server/routes/media/[...].get.ts`](../server/routes/media/[...].get.ts)，
  把 `/media/**` **只读**映射到 `doc/`，带 MIME 推断与 7 天缓存；
- **目录穿越防护**：解析后必须仍在 `doc/` 内，越界返回 403。实测：
  `/media/../../etc/passwd` → 404；`/media/%2e%2e%2f...` → **403**。

### 3.3 画廊条目：一条 md 一个作品

[`tools/sync-gallery.ts`](../tools/sync-gallery.ts) 扫描素材生成 `content/gallery/*.md`。
选 md 而非 JSON 的理由：条目同样是**可版本化、可人工补充 `credit`/`era`/`note` 的文本**，
且复用 Nuxt Content 的 schema 校验。`credit` 是**必填**字段（沿用工作区既有版权约定）。

### 3.4 七纪时间轴：不是装饰，而是入口

每个纪都挂到**该纪代表篇目的正文**（如「原子与太空纪」→ 主卷 08 原子篇），
篇号↔篇目对应关系直接取自论文集总论 §2.1 原表的「对应篇目」列。
数据见 [`app/assets/eras.ts`](../app/assets/eras.ts)，附原作者的重要限定：
**分期的是「想象的技术」，不是真实历史。**

## 四、M1 踩到的坑

### 4.1 服务端查询必须用 `@nuxt/content/server` 的版本

`/rss.xml` 与 `/sitemap.xml` 初次实现用了客户端的 `queryCollection('blog')`，**两个端点都 500**：

```
TypeError: undefined is not an object (evaluating 'event.node.req')
    at getRequestHeaders → fetchContent → fetchQuery → all
```

**根因**：客户端版 `queryCollection(collection)` **不接收 event**；在 Nitro 路由里，
内容层需要从请求上下文取信息（headers/路径），拿不到就崩。

**修正**：
```ts
import { queryCollection } from '@nuxt/content/server'
const posts = await queryCollection(event, 'blog').all()   // ← 显式传入 event
```

> 这是个**容易反复踩**的坑：同名函数、同样的链式 API，只在**是否传 event** 上有区别，
> 类型错误在构建期不一定暴露（本次是运行时 500）。已写入本文档备查。

### 4.2 画廊标题重复（数据层面的坑，非代码错误）

地图动态的文件名是 `MAP-ANV-02_双路并行_动画.png`，去掉前缀后只剩「双路并行 · 动画」——
**四张图标题完全相同**，在画廊里无法区分。

**修正**：从「地图」专辑的文件名建立 `地图 ID → 中文名` 映射，用作地图动态标题的限定词。
现在标题是「双闸峡谷 · 双路并行 · 动画」等，全站 **0 个重复标题**。

（这类问题不会让构建失败，只会让页面看起来"对但没用"——所以需要**实际看渲染结果**。）

### 2.6 OG 分享图（M3 补齐）

M1 的未完成项里挂着"OG 图自动生成"，当时的顾虑是"要引入 `@nuxtjs/seo`/`nuxt-og-image` 依赖"。
**最后没有引入任何依赖**：`sharp` 本来就是 `@nuxt/image` 的传递依赖、且已在构建产物里
（`.output/server/node_modules/sharp`），用它把一段 SVG 渲成 PNG 只要几十行。

- 渲染器 [`server/utils/og-render.ts`](../server/utils/og-render.ts)（放 `server/utils/` 由 Nitro 自动导入）；
- 端点 [`server/routes/og.png.get.ts`](../server/routes/og.png.get.ts)：`/og.png?title=…&eyebrow=…&badge=…`，
  1200×630，带 `max-age=86400` 强缓存；**参数截断 + 固定尺寸**以免变成任人调用的图片处理代理；
- 元信息 [`app/composables/useStructuredData.ts`](../app/composables/useStructuredData.ts) 重写为
  `useShareMeta()`，一次挂上 OG/Twitter 卡片、canonical、RSS 自动发现与 JSON-LD，
  **并顺手修掉了一处早先的错误**：原来把站点域名硬编码成 `https://retro-futurism.example`，
  换域名或本地预览时 canonical/og:url 就是错的；现改为从 `NUXT_PUBLIC_SITE_URL`
  或请求头推导（`og:image` 仍保证是绝对地址，因为社交平台不解析相对路径）。

**这里有三个"看才看得出来"的排版 bug**，正是它们促成了
[`tools/verify-og.ts`](../tools/verify-og.ts) 的像素级断言：

| bug | 现象 | 根因 |
| --- | --- | --- |
| 标题从右边溢出 | 66px 下行宽 ≈1122px > 可用 1040px | 折行把每行"单位数"**写死**，**没按字号算**（正确算法是 `可用宽度 ÷ 字号`） |
| 眉标与标题叠在一起 | 两行文字视觉上粘连 | 眉标基线 208 / 标题首行 250，间距不足 |
| 断言带误报（两次） | 检查器说"重叠"，其实只是字形下沉部 | 用"固定 y 带里有没有像素"近似，被「卷」「带」的撇与字号变化骗过 |

最终判据改成**量两块文字的墨迹真实边界、断言净空 ≥12px**（实测 35px）——
而不是猜一个 y 区间。验收 8/8：

```
✓ 端点可用 · ✓ 尺寸 1200×630 · ✓ 标题区有文字像素（防字体缺失致空白）
✓ 右侧不溢出 · ✓ 眉标与标题有净空 35px · ✓ 标题不压底部线
✓ 超长标题不溢出 · ✓ 带强缓存头
```

> **上线前提**：目标机需有 CJK 字体（精简容器常常没有，中文会渲染成空白）。
> "标题区有文字像素"这一项就是为这个风险设的——**字体缺失会失败，而不是悄悄发一张空白图**。
> 部署检查见 [08 §八·补](08_部署与备份.md)。
