## 三、第 1 件待办：M2 第一阶段——**需要你或维护者去申请**（非代码问题）

决策 [D4](00_决策记录.md) 已批准"先 Giscus"（你此前答复"按推荐项来"）。
代码、组件、验收脚本、降级逻辑**全部就绪并已验证**（三种情形 3/3 通过）。

只差**去 GitHub 申请四个值**（约 5 分钟）：

1. 建一个**公开**仓库；
2. 该仓库 Settings → General → Features，勾选 **Discussions**；
3. 到 [giscus.app](https://giscus.app) 把 **giscus App** 安装到该仓库；
4. 在 giscus.app 填仓库名并选分类（建议 `Announcements`），拿到 `repo-id` 与 `category-id`；
5. 填进环境变量（详见 [`.env.example`](../.env.example) 与 [07 §2.1](07_实现记录_M2.md)）：

```bash
NUXT_PUBLIC_GISCUS_REPO=owner/repo
NUXT_PUBLIC_GISCUS_REPO_ID=R_kgDOxxxx
NUXT_PUBLIC_GISCUS_CATEGORY=Announcements
NUXT_PUBLIC_GISCUS_CATEGORY_ID=DIC_kwDOxxxx
```

填好后站点即启用讨论区。**填之前站点完全可用**：讨论区会降级成一份配置说明，不影响任何其他页面。

> **验收的边界**：`bun run verify` 里的 `giscus` 套件用**占位** `repoId`/`categoryId`
> 验证"降级、注入、参数正确"这三条路径，**它证明不了真实 GitHub 仓库与 Discussions 的端到端可用性**——
> 那需要真实凭证（脚本自己也在输出里这么声明）。填上真实值后请手工点开一次讨论区确认能加载、能发言。

> ⚠️ **一个仍需你判断的风险**：Giscus 依赖 GitHub，**境内网络可达性存疑**。
> 若读者主要在中国大陆，应直接走 [D4](00_决策记录.md) 的第二阶段（站内自建论坛，
> 表结构与存储方案已按 [D5](04_数据存储与同步方案.md) 的 Bundle A 备好，约 1.5–2 周）。

## 四、第 2 件待办：M3 部署——**需要一台目标机**（非代码问题）

部署产物已就绪并做完静态校验：[`deploy/`](../deploy/)（Caddyfile / systemd 单元 / Litestream 配置），
[08 §五](08_部署与备份.md) 备好了 **10 条 smoke test 命令**。

**已排除"用本地容器自己验"这条路**（实测依据）：
本机 OrbStack + Docker 可用，但 **Docker Hub 不可达、容器内无任何外网**——
装不了 Bun、装不了 CJK 字体，**造不出可验证的 Linux 环境**。

拿到目标机后照 [08 §三](08_部署与备份.md) 走即可，两个易错点已写进文档：
- **构建与运行都必须用 Bun**（产物含 `bun:sqlite`，用 Node 跑会 `ERR_UNSUPPORTED_ESM_URL_SCHEME`）；
- **必须配 `NUXT_PUBLIC_SITE_URL`**（否则 RSS/sitemap/og:image 的绝对地址只能靠反代头推导，易错）；
- **必须装 CJK 字体**（否则 `/og.png` 中文渲成空白，`verify-og` 会失败而非悄悄发空白图）。

## 五、交接检查清单

```bash
cd projects/website
export PATH="/opt/homebrew/bin:$PATH"     # 本机 Bun 在 /opt/homebrew/bin

bun install
bun run sync:all        # doc/ → content/wiki + content/gallery（幂等）
bun run build           # 含产物完整性校验
bun run verify          # ★ 13 个套件一条命令全跑（自带临时实例与清理）
bun start               # 起生产服务（必须用 bun）
```

`bun run verify` 预期输出：

```
通过 13 · 失败 0 · 跳过 0 · 合计 ~30s
```

> 若本机没有 Chrome，需要浏览器的 3 个套件会被标为 **SKIP**——
> 脚本会明确提示"**被跳过的套件未被验证，不要当成通过**"。
> CI 无头环境可显式 `bun run verify --skip=search,perf-a11y,giscus`。

## 六、接手时最该知道的六件事（都是实测踩出来的）

1. **`doc/` 是唯一内容权威**，站点构建期单向转换，**不改源文件一个字节**（[D2](00_决策记录.md)）。
   改内容改 `doc/`，然后 `bun run sync:all`。
2. **产物必须用 Bun 运行**，不能用 Node（[02 §3.2](02_技术栈与选型.md)）。
3. **服务端查内容必须用 `@nuxt/content/server` 的 `queryCollection(event, name)`**；
   客户端版不接收 event，在 Nitro 路由里会运行时 500（构建期不报错）（[06 §4.1](06_实现记录_M1.md)）。
4. **Giscus 挂载点 id 不能用随机数**（SSR/CSR 不一致会导致脚本静默不注入）（[07 §6.1](07_实现记录_M2.md)）。
5. **`verify-giscus` 只能证明"注入路径与参数正确"**，用占位 `repoId` 走通；
   **不能证明真实 GitHub 仓库与 Discussions 的端到端可用性**——那需要真实凭证（脚本里也这么写着）。
6. **验收必须用真浏览器（CDP）的三项**：搜索（客户端 FTS）、Giscus（客户端注入）、性能指标。
   curl 只能证明"页面返回 200"。
