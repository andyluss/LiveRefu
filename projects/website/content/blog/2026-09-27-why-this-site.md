工作区里已经躺着一套相当完整的复古未来主义论文集：主卷 00—20 共 21 篇，加上蒸汽/柴油/原子/生物/赛博五卷朋克专题，再算上七个附录卷，**129 篇、约 14 万字汉字**。

它们一直以 Markdown 形式存在，用 git 管着，读起来也没问题。那为什么还要做一个网站？

因为**读**和**用**是两件事。

## 一、Markdown 做不到的三件事

### 1. 交叉引用点不动

这是最要命的一条。论文集的写作习惯是在正文里写「（见 16 末日篇）」「（见主卷 08、16）」——人类读得懂，但它是**纯文本**。

要把它变成可点击的链接，需要知道「16」对应哪一篇。而篇号到篇名到 URL 的映射，只存在于文件名里：

```
16_末日篇_被取消的未来_复古末日与废墟乡愁.md
```

于是我们写了**内容适配层**（`tools/sync-content.ts`），在构建期扫描全部正文，把 `（见 16 末日篇）` 改写成 `（见 [16 末日篇](/wiki/main/16-apocalypse)）`。

实测结果：**331 处交叉引用被改写，命中率 97.1%**。

剩下的 2.9% 是**故意不改**的，理由值得单独说：

- `（见 1.1）`、`（见 2.3）` —— 指向**文内小节**，不是篇目。如果强行解析，会被当成「主卷第 1 篇」，生成一个**错误的链接**。宁可不做链接，也不做错链接。
- `（见第三节）`、`（见下）` —— 篇内指代，本来就不该跨页跳转。

### 2. 没有元数据的结构化表达

源文档的篇首是这样的：

```markdown
# 磁带篇：磁带未来主义——模拟接口的暖未来

> 关键词：磁带未来主义；CRT 终端；模拟—数字过渡；操作员未来；界面考古；暖未来
>
> 摘要：本篇考古一种"被 1980 年代想象出来的近未来"…
```

信息全在，只是**不是机器可读的 frontmatter**。适配层把它解析成标题、标签、摘要——于是「按标签检索」「生成 SEO 描述」这些事才有了数据基础。

### 3. 没有检索入口

`grep` 是给作者用的，不是给读者用的。

## 二、一个刻意的架构决定：不改 doc/

面对「源文档不适合直接上网」这个事实，有三条路：

| 方案 | 代价 |
| --- | --- |
| 手工把 265 个 md 改成带 frontmatter 和绝对链接的站源文件 | 破坏 `doc/` 独立性；源文一更新就漂移 |
| 直接把 `doc/` 复制进 `content/`，靠运行时解析 | 交叉引用依然点不动，Wiki 退化成静态阅读器 |
| **写一个构建期单向转换层**（采用） | 多一个脚本和一张映射表要维护 |

选第三条的核心理由是**单一权威**：

> `doc/` 是内容的唯一权威。站点是它的呈现层，不改写它一个字节。

转换是**幂等**的——`doc/` 更新后重跑 `bun run sync:content` 就好。而如果哪天觉得这个网站不要了，`doc/` 完全无损。

## 三、副产品：反向链接

改写交叉引用时，我们顺手收集了反向关系。于是每一篇的页脚都能显示「**被引用于（N）**」——谁在引用我。

这是纯文件式知识库真正优于传统 CMS 的地方：**引用关系本来就在文本里**，只是之前没人去读。目前 26 篇被引用。

## 四、所以这个站是什么

它不是「把论文贴上网」。

它是把一套已经写好的知识体系，**补上它作为文本时缺失的那几个维度**：可点击的引用网络、可检索的全文、机器可读的元数据。

正文一个字没改。
