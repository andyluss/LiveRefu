# 08 · 规则卡系统（S3）

> 用途：说明**规则卡**是什么、为什么它是纪元差异的载体、以及它怎么落地。
> 日期：2026-09-30 ｜ 上游：[mainline 03 玩法与经济循环](../../docs/03_玩法与经济循环.md)（"规则卡系统必须在原子纪元就做对，否则纪元 2 只能换皮"）

## 一、它解决什么问题

**纪元之间的差异如果只靠美术与卡池，玩家会读成换皮 DLC，复购率就是 0。**
规则卡是"同一套引擎、不同玩法"的最小机制：**换一张表就换玩法**。

因此它的设计目标不是"能表达很多花样"，而是**两件事**：

1. **新纪元的差异主要写在数据里**（`rules.json`），而不是散落在 `core/` 的 `if era == ...`；
2. **规则的种类少而硬**，否则每个纪元都会变成一堆互不兼容的特例（那是拼贴，不是风格卡）。

## 二、模型：钩子 × 条件 × 效果（三者正交）

```
        ┌─ trigger（何时检查）─┐   ┌─ condition（什么条件）─┐   ┌─ effect（做什么）─┐
规则卡 = │ run_start            │ × │ always                  │ → │ gain_power        │
        │ turn_start           │   │ residue_total_at_least  │   │ reduce_residue    │
        │ before_placement     │   │ residue_total_at_most   │   │ reduce_cost       │
        │ before_combat        │   │ slot_residue_at_least   │   │ add_damage        │
        │ wave_cleared         │   │                         │   │ sub_damage        │
        └──────────────────────┘   └─────────────────────────┘   │ clean_on_turn     │
                                                                  └───────────────────┘
```

**三者正交的好处**：加一个新触发点只改 `TRIGGERS` + 一个 `fire()` 调用；加一个新条件只改 `RuleConditions`；加一个新效果只改 `RuleEffects`。**不必为每条规则写代码。**

### 两类用法（分开很重要）

| 类型 | 例子 | 为什么不混用 |
| --- | --- | --- |
| **动作型**（`fire`） | 开局加电力、回合开始清残渣、清波奖励 | 会改状态，**每个钩子点只能触发一次** |
| **查询型**（`damage_delta` / `cost_delta` / `placement_residue`） | 交战 ±伤害、出牌减费 | 伤害与费用被多处读取（UI、自动玩家、结算）；若各处各自触发一次，同一回合会被结算多次 |

## 三、原子纪元 T1 四张规则卡

| id | 名称 | 触发 | 条件 | 效果 |
| --- | --- | --- | --- | --- |
| `RULE-ATOMIC-001` | 链式反应 | before_combat | 残渣总量 ≥ 12 | 输出 **+6** |
| `RULE-ATOMIC-002` | 公开听证 | before_combat | 残渣总量 ≥ 30 | 输出 **−4** |
| `RULE-ATOMIC-003` | 一次冷却 | turn_start | 无条件 | 清最脏格 **1** 点残渣 |
| `RULE-ATOMIC-004` | 郊区样板 | wave_cleared | 残渣总量 ≤ 6 | 电力 **+5** |

**这四张的组合就是原子纪元的性格**：污染能当燃料（001），但污染一旦成为公共议题就要付代价（002）；
同时给出两条"洁净有奖"的路（003/004）。**玩家看到的不是四个 buff，而是同一个政治问题在四种立场下的处理方式。**

## 四、钩子顺序（**顺序就是规则**）

```
turn_start → 供电 → 出牌（before_placement）→ 场地维护（排污）
           → before_combat → 交战 → 波次结算 → wave_cleared
```

两条容易搞错、已固定的口径：

1. **交战用的是"场地维护之前"的残渣**。否则"本回合新增的排污"会立刻参与减益——等于双重惩罚，且与玩家界面看到的不一致（`TurnLoop` 里显式传入 `residue_before_upkeep`）。
2. **出牌费用只有一个计算入口** [`CardCost.of`](../game/scripts/core/systems/card_cost.gd)。费用被三处读取（UI 显示 / 自动玩家判断 / 实际扣费），各算一次就会出现"看到 2、扣掉 3"——每处单看都对，合起来错。

## 五、未实现的条件/效果**不得静默成立**

`RuleConditions.holds` 对未知条件是**返回 false**（整条规则不生效），而不是当作"无条件"。
理由：字段名打错时，若默认成立就会变成一条"总是触发"的规则，**只会让数值悄悄失真**，不会有任何报错。

## 六、S3 实测（标定过程）

实验条件：3 套牌 × 4 种子 × 4 势力，节制/贪心两档。

| 配置 | 节制档（存活 / 均剩血 / 残渣 / 评分） | 贪心档 |
| --- | --- | --- |
| 无规则 | 2/4 · 2.0/20 · 8 · 0.356 | 0/4 · 0 · **167** · 0.137 |
| **有规则** | 2/4 · **4.0/20** · 8 · **0.400** | 0/4 · 0 · 162 · 0.128 |

**三条结论**：

1. **规则卡确实起作用**：均剩血 2.0 → 4.0、评分 0.356 → 0.400（同样的卡池与种子）。
2. **"管不管污染"仍然是最强的区分**：节制档残渣 8 vs 贪心档 162–167，分差约 3 倍。
3. **电力不是瓶颈，"出牌机会"也不是**——对照实验发现：每回合多主动抽 2 张牌，出牌数几乎不变（6→6）。
   真正的约束是 `SLOT_CAP`（自动玩家的塔位上限）与"输出 vs 波次配额"。**S2 的 F1（电力闲置）因此被改判**：
   它的根因不是"电力没处花"，而是**自动玩家的自我约束**；人为增加出牌机会不会改善局面。

### 一个"不公平比较"的教训

模拟原先按 `min(8, pool.size())` 组牌，**小卡池的阵营只拿到 5–6 张就"满编"**，
于是各阵营被比较的**不是同一个条件**，报告里的差异混着"卡池大小"这个无关变量。
修正为**窗口长度固定 8**（小卡池绕回重复取）后，各阵营才在同一条件下可比。

## 七、配额曲线的标定

依据"自动玩家能力"反推，而不是凭感觉：

| 项 | 值 |
| --- | --- |
| 能力（6 塔位 × 后期战力约 9） | 约 **54**，扣残渣惩罚后约 **40** 输出/回合 |
| 曲线（`40 + 15×i`，8 波 × 4 回合 = 32 回合） | 总配额 740 ｜ **均需 23.1** ｜ 末波需 **36.2** |
| 结论 | 有压力但不绝望；**S3 之后应由关卡表覆盖**（现在仍是公式默认值） |
