## D1 · 项目命名 → **推荐 `retro-futurism-site` / 《明日档案》**

- **推荐**：目录 `projects/retro-futurism-site`，站名《明日档案》（英文 Retro-futurism Archive）。
- **理由**：「未来的考古学」是论文集的纲领母题，「档案」与之同构；中文好记、英文 slug 干净。
- **备选**：《明日频道》（⚠️ 与既有游戏项目《明日频道》撞名）、`refu-archive`《复古未来档案》（稳但少味道）。
- **代价**：改名成本低，随时可换（影响目录名与文档内引用）。

## D2 · 内容权威与仓库关系 → **推荐：`doc/` 为唯一权威，单向转换**

- **推荐**：`doc/` 保持**人写友好**的原始形态（**不动一个字节**）；站点侧由 `tools/sync-content.ts` **构建期单向转换**出规范 frontmatter 与可点击交叉链接。
- **理由（基于实测）**：源文档**无 YAML frontmatter**（篇首用 `> 关键词：` / `> 摘要：` 引用块），且**交叉引用是纯文本**（`（见 16 末日篇）` 点不动）。直接贴上网会得到一个"能滚动的文本"，而不是 Wiki。
- **代价**：多一个转换脚本 + 一张「篇号 ↔ slug」映射表要维护；漏项会导致链接降级为纯文本（**降级不报错**，但构建期出告警清单）。
- **备选（不推荐）**：① 手工给 265 个 md 加 frontmatter 与绝对链接 → 破坏 `doc/` 独立性，源更新即漂移；② 直接把 `doc/` 复制进 `content/` 靠运行时解析 → 交叉引用依然点不动，Wiki 退化为静态阅读器。

## D3 · 技术栈与版本 → **推荐 Bun 1.4 + Nuxt 4 + Vue 3.5 + Nuxt Content + TS**

用户已指定 **Web + Bun + Vue + Nuxt** 这条主线，因此本项只裁**具体版本与配套**：

| 层 | 推荐 | 版本（已核验 npm） |
| --- | --- | --- |
| 运行时 / 包管理 | **Bun**（已装 1.4.0，位于 `/opt/homebrew/bin/bun`） | 1.4.0 |
| 框架 | **Nuxt 4**（稳定版） | 4.5.2 |
| UI 库 | **Vue 3** | 3.5.43 |
| 内容 | **Nuxt Content**（SQL 存储 + 内置全文检索） | 3.16.1 |
| 样式 | **Nuxt UI 4 + Tailwind CSS 4** | 4.11.2 / 4.3.3 |
| 图片 | **@nuxt/image** | 2.1.0 |
| 灯箱 | **PhotoSwipe 5** | 5.4.4 |
| SEO | **@nuxtjs/seo** | 5.3.16 |
| 语言 | TypeScript | — |

- **理由**：Nuxt 4 是当前稳定线；Nuxt Content 一套同时满足博客与 Wiki，并自带 SQL 全文检索，避免额外引入搜索服务。
- **代价**：Nuxt 4 采用 `app/` 目录结构，与网上大量 Nuxt 3 教程不一致；社区资料需注意版本。
- **风险**：**Bun 与 Nuxt/Nitro 的兼容性是本项目最大技术风险**，M0 **首日**验证；若原生模块（如 better-sqlite3、sharp）在 Bun 下不可用，回退方案见 [02](02_技术栈与选型.md) 风险段（Node 跑构建 + Bun 跑包管理，或换 `bun:sqlite` / 内置 IPX）。

## D4 · 论坛形态 → **推荐：两段式（M2 先 Giscus，M3/M4 再自建）**

| 路径 | 工作量 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. Giscus**（GitHub Discussions） | **半天** | 零运维、零反垃圾、免账号体系 | 外观受限（iframe，主题化难）、**国内网络可达性存疑**、数据在 GitHub 不在自己手里 |
| **B. 外挂 Discourse** | 2–4 天 | 功能完整、成熟 | 需**单独**跑一套 Docker + Postgres + Redis，对小站偏重；与主站账号未打通 |
| **C. 站内自建**（Nuxt + 数据库） | 1.5–2 周 | 外观完全可控（对复古未来主题**很重要**）、数据自有、账号统一 | 要自己做鉴权/反垃圾/分页/权限 |

**推荐**：**先 A 后 C**。M1 上线时用 Giscus 提供"能评论"的即时价值（半小时接完），同时 D5 的数据库选型**按自建论坛的需求来选**（不浪费）；等讨论量起来（比如月新增主题 > 50）再切 C。

- **理由**：论坛功能深度不是本站卖点，**视觉一致性**才是；但一上来就花 2 周做论坛会拖垮 M1。两段式让 M1 快速上线、又保留 C 的升级路径。
- **代价**：未来做一次数据迁移或共存；Giscus 期间的数据导出受限（GitHub Discussions 可导出）。**若你的读者主要在境内**，A 的可达性风险可能迫使直接走 C —— 请特别确认这一点。
- **决策点**：请明确「**Giscus 是否可接受**」；若不可接受，则 M2 直接做 C。

## D5 · 数据存储与同步 → **见 [04 数据存储与同步方案](04_数据存储与同步方案.md) §E**

这是本次最重的一项，已单列专题分析：[04 数据存储与同步方案](04_数据存储与同步方案.md)——给出四套**内部自洽的 bundle**（全自托管 SQLite / 云 Postgres + 对象存储 / PocketBase 单二进制 / libSQL 嵌入式副本），按 8 个维度打分，并给出**主推荐**与**次推荐**。

> **一句话预告**：若追求"低运维 + 数据自持 + 与 Bun 天然契合"，倾向 **全自托管 SQLite 系**；若更看重"多人协作编辑后台 + 实时能力 + 少写后端代码"，倾向 **PocketBase 单二进制**。具体取舍与代价见 04。

## D6 · 部署形态 → **推荐：单机自托管（Bun + 反向代理）**

- **推荐**：一台小 VPS，`bun run build` 后由 Bun/Nitro 直接跑，前置 Caddy/Nginx 做 TLS 与静态缓存；数据落本地磁盘 + 定时备份。
- **理由**：与 D5 的"数据自持"取向一致；成本可控（$5–10/月）；无厂商锁定。
- **代价**：要自己管 TLS 续期、备份、升级；单点故障（无冗余）。
- **备选**：Serverless/边缘平台（Cloudflare Pages + D1 + R2）—— 更省运维，但**锁定加深**、且与"自托管论坛/账号"取向冲突。

## D7 · 账号与鉴权 → **推荐：自建邮箱+密码 + 会话 Cookie**

- **推荐**：`nuxt-auth-utils`（0.5.30）做会话与 Cookie；密码用 argon2/bcrypt 哈希；先只做邮箱密码，不做 OAuth。
- **理由**：自建论坛（D4 路径 C）本来就需要本地账号；OAuth（GitHub/Google）在境内可用性不稳定，且引入第三方依赖。
- **代价**：要自己实现注册校验、找回密码（可先只做管理员重置）、邮箱验证（可后置）。
- **备选**：更好用的 **Better Auth**（1.7.6），功能更全（含 2FA、组织、插件），但与 Nuxt 的集成样板比 `nuxt-auth-utils` 多。**若确定走自建论坛且看重长期功能，建议 Better Auth**。

## D8 · 视觉基调 → **推荐：「可关闭的 CRT」+ 原子时代配色**

- **推荐**：扫描线/暗角/轻微色散作为**可关闭**的装饰层；配色取原子时代青绿+奶油黄、镀铬银、深空蓝；字标题几何无衬线/等宽，正文易读中文字体（**运行时加载系统 CJK，不塞字体二进制**，沿用 [`refu-game-001`](../../refu-game-001/README.md) 既有做法）。
- **理由**：CRT 质感是复古未来的招牌语汇，但**全屏闪烁与低对比度会劝退读者**；做成可关闭既保留风格又不牺牲可读性。正文对比度须过 WCAG AA。
- **代价**：比"纯暗色科技风"实现成本高；需要一次正经的设计 token 梳理。
- **亮点**：把「**七纪时间轴**」（神话→古典→近代→机器→原子/太空→信息→千禧，取自论文集分期）做成**全局导航组件**，画廊按年代筛选与 Wiki 按纪读史共用同一心智模型。

## D9 · 搜索实现 → **推荐：Nuxt Content 内置 SQL 全文检索**

- **推荐**：构建期建索引，`queryCollection().search()` 直接查，零外部服务。
- **理由**：零运维、零成本、与内容同库；对 91+53 篇的量级完全够用。
- **代价**：SQLite FTS5 对中文默认**按字切分**，短词命中尚可、长词组召回一般；论坛帖子检索需另做（后置）。
- **备选**：`@orama/orama`（纯 JS、中文分词更可控，但需自己建索引管线）；Meilisearch/Typesense（体验最好，但要多跑一个服务）。

## D10 · 内容同步方式 → **推荐：构建期转换 + git，非运行时读取**

- **推荐**：`doc/` 以 **git 子模块或同仓库路径**引入；内容变更 → 触发构建（可 webhook 自动化）→ 生成静态/增量产物。
- **理由**：与 D2 一致；构建期可做**链接校验、交叉引用改写、index 生成**，把错误挡在上线前。文章量级（百余篇）不需要运行时 CMS。
- **代价**：非技术编辑者改内容需**经过 git**（或后续接 Nuxt Studio 类可视化编辑）；每次改文需重新构建（分钟级）。
- **备选**：运行时从数据库/GitHub API 拉取内容——更"实时"，但失去构建期校验，且引入网络依赖。

## M0 实测对决策的反馈

M0 实施（2026-09-27）验证了 D2、D3，并**发现三条 D3/D5/D6 未预见的具体约束**，已落进代码：

| 发现 | 影响哪项决策 | 处理 |

| **产物必须用 Bun 运行**：Bun 下构建时 Nuxt 选 Bun 运行时预设，产物含 `bun:sqlite` 导入 | D3 / D6 | 构建与运行统一用 Bun（`bun start`）；已写入 README §五 |

| **`@nuxt/content` 按构建运行时的 `process.versions.bun` 选 SQLite 连接器** | D3 / D5 | 与第 1 条同源：构建/运行同运行时即可自洽；否则产物会引用当前运行时不可用的连接器 |

**不需要额外依赖或服务**（这也顺带消除了 M0 原计划里"验证 better-sqlite3 是否可用"的必要性）。

**对 D2 的确认**：内容适配层实测**改写 331 处交叉引用、命中率 97.1%**，10 处刻意保留
