## 一、这份文档能保证什么、不能保证什么

**必须先把这条说清楚**，否则容易把"跑过校验脚本"误当成"部署验证过"。

| | 内容 |
| --- | --- |
| ✅ **已验证**（本机） | 应用构建与启动（`bun run build` → `bun start`）；迁移器**幂等**可重复执行；存储健康检查 7/7（含外键真的会拦截非法引用）；备份→校验→恢复演练 9/9（含**损坏备份会被拒绝**的反向证明）；部署配置静态校验 |
| ❌ **未验证** | Caddy / systemd / Litestream 在**真实服务器**上能否运行——三者都需要对应运行环境，本机（macOS，无这些程序）无法验证。**必须在目标机做 §五 的 smoke test。** |

## 二、部署形态（D6：单机自托管）

```
                    ┌─────────────────────────────────────┐
  用户 ──HTTPS──▶  │ Caddy（自动 TLS，反代 + 静态媒体）    │
                    └───────────────┬─────────────────────┘
                                    │ 127.0.0.1:3000
                    ┌───────────────▼─────────────────────┐
                    │ Bun 进程（Nuxt/Nitro 产物）          │
                    │  ├ /wiki /blog /gallery /search …    │
                    │  ├ /api/health/storage ← 运维用      │
                    │  └ /media/** → 只读映射 doc/         │
                    └───────────────┬─────────────────────┘
                                    │ bun:sqlite（WAL）
                    ┌───────────────▼─────────────────────┐
                    │ /var/lib/retro/app.db               │
                    │  └ Litestream 持续复制 → R2/B2       │
                    └─────────────────────────────────────┘
```

**零外部服务**：没有 Postgres、没有 Redis、没有搜索服务（搜索在浏览器本地做）。
这就是 D5 选 Bundle A 的兑现——一台机器、一个二进制依赖（Bun）、一个数据文件。

## 三、部署步骤

### 3.1 准备（一次性）

```bash
# 目标机：Linux x86_64 或 arm64
curl -fsSL https://bun.sh/install | bash          # 装 Bun
sudo useradd -r -s /usr/sbin/nologin retro
sudo mkdir -p /srv/retro-futurism /var/lib/retro /var/backups/retro
sudo chown -R retro:retro /var/lib/retro /var/backups/retro
sudo apt install -y caddy                          # 或按官方源
```

### 3.2 拉代码与构建

```bash
cd /srv/retro-futurism
git clone <repo> LiveRefu && cd LiveRefu/projects/retro-futurism-site
bun install
bun run sync:all      # doc/ → content/wiki + content/gallery（生成物已入库，此步用于确认无漂移）
bun run build         # 含产物校验；srvx 条件导出缺失会自动补齐（见 02 §3.2）
```

> ⚠️ **构建与运行必须都用 Bun**。Bun 下构建会选 Bun 运行时预设，产物里含
> `import { Database } from 'bun:sqlite'`；用 `node` 跑会直接
> `ERR_UNSUPPORTED_ESM_URL_SCHEME: 'bun:'` 起不来。见 [02 §3.2](02_技术栈与选型.md)。

### 3.3 数据库初始化与迁移

```bash
export DATABASE_PATH=/var/lib/retro/app.db
bun run db:migrate        # **幂等**：已应用的迁移会跳过，可每次部署无脑跑
```

迁移记录存在 `_migrations` 表里。迁移 SQL 在 `server/db/migrations/`，**必须入库**——
它是 schema 的唯一真相（数据库文件本身不进版本库）。

### 3.4 配置站点根地址（**必做**）

```bash
NUXT_PUBLIC_SITE_URL=https://你的域名
```

**这一项不做会静默出错**：RSS 的 `<link>`、sitemap 的 `<loc>`、页面的 `og:image` 与
`canonical` 都必须是**绝对地址**（订阅器与社交平台不解析相对路径），
而它们都要知道站点根。

留空时会退化为**从请求头推导**（读 `x-forwarded-proto`/`x-forwarded-host`/`host`）——
在 Caddy 反代后面通常也对，但**反代漏传 `X-Forwarded-*` 时会拼出错误域名**。
所以生产环境建议显式配置。

> 这个位置真出过问题：`rss.xml.ts` / `sitemap.xml.ts` / `useStructuredData.ts`
> 三处**各自把域名硬编码**成 `https://retro-futurism.example`。
> 部署到真实域名后三处产出的地址**全是错的，而且没有任何报错**——
> 只有别人订阅或抓取时才会发现。现已统一到 `resolveSiteUrl(event)`，
> 并加了 `bun run tools/verify-urls.ts` 专门守这条（见 §七）。

### 3.5 配置 Giscus（可选，D4 第一阶段）


```bash
# 见 docs/07_实现记录_M2.md §2.1 的四步申请流程
NUXT_PUBLIC_GISCUS_REPO=owner/repo
NUXT_PUBLIC_GISCUS_REPO_ID=R_kgDOxxxx
NUXT_PUBLIC_GISCUS_CATEGORY=Announcements
NUXT_PUBLIC_GISCUS_CATEGORY_ID=DIC_kwDOxxxx
```

留空不影响站点可用性——讨论区会降级为配置说明。

### 3.6 起服务与反代

```bash
sudo cp deploy/retro-futurism.service /etc/systemd/system/
sudo cp deploy/Caddyfile /etc/caddy/Caddyfile      # 改掉域名与路径
sudo systemctl daemon-reload
sudo systemctl enable --now retro-futurism
sudo systemctl reload caddy
```

## 四、备份（两条腿走路）

| 机制 | 位置 | 作用 | RPO |
| --- | --- | --- | --- |
| **Litestream** | [`deploy/litestream.yml`](../deploy/litestream.yml) | 持续把 WAL 复制到 R2/B2，应对"机器突然没了" | ~10 秒 |
| **校验快照** | [`tools/backup-db.ts`](../tools/backup-db.ts) | 产出**经校验**的时点快照，用于恢复演练 | 按 cron 频率 |

两条腿的分工很重要：Litestream 保证**能恢复到很近的时间点**，
自带脚本保证**备份真的能用**（每次备份都会打开产物、跑 `integrity_check`、对比行数，
验证不通过就改名 `.bad` 并以非零码退出）。

```bash
# 每日 03:30 打一份经校验的快照，保留 14 份
30 3 * * * cd /srv/retro-futurism/LiveRefu/projects/retro-futurism-site && \
  DATABASE_PATH=/var/lib/retro/app.db /usr/local/bin/bun run tools/backup-db.ts \
  --out=/var/backups/retro --keep=14 >> /var/log/retro-backup.log 2>&1
```

> **立场**：**未经验证的备份等于没有备份。** 所以 `backup-db.ts` 每次都会验证自己刚产出的东西，
> 而不是"拷完就完事"。

## 五、目标机 smoke test 清单（**部署后必须逐条跑**）

这些是本机**无法**验证、必须在目标机上确认的：

```bash
# 1) 服务起来了
systemctl status retro-futurism --no-pager

# 2) 应用健康（HTTP 200 + JSON ok:true）
curl -fsS http://127.0.0.1:3000/api/health/storage | tee /dev/stderr | grep -q '"ok": true'

# 3) 存储健康检查 7/7
curl -s http://127.0.0.1:3000/api/health/storage | grep -o '"summary": "[^"]*"'

# 4) 对外 HTTPS 与证书
curl -fsSI https://<域名>/ | head -3

# 5) 关键页面可达（应全部 200）
for p in / /wiki /wiki/main/00-general-introduction /blog /gallery /forum /rss.xml /sitemap.xml; do
  printf '%s %s\n' "$(curl -s -o /dev/null -w '%{http_code}' https://<域名>$p)" "$p"
done

# 6) 媒体只读路由 + 目录穿越防护
curl -s -o /dev/null -w '%{http_code}\n' "https://<域名>/media/refu-game-001/美术/全量出图/卡面/ANV-M01_齿轮帮·维修工.svg"   # 期望 200
curl -s -o /dev/null -w '%{http_code}\n' "https://<域名>/media/%2e%2e%2f%2e%2e%2fetc%2fpasswd"                          # 期望 403

# 7) 反代直送媒体的缓存头
curl -sI "https://<域名>/media/..." | grep -i cache-control

# 8) 迁移幂等（再跑一次不应有变更）
DATABASE_PATH=/var/lib/retro/app.db bun run db:migrate

# 9) 备份真的能产出并自校验
DATABASE_PATH=/var/lib/retro/app.db bun run tools/backup-db.ts --out=/var/backups/retro

# 10) Litestream 正在复制
systemctl status litestream --no-pager
litestream snapshots -config /etc/litestream.yml /var/lib/retro/app.db
```

## 六、恢复演练（**每季度一次，必须做**）

[04 §4.2](04_数据存储与同步方案.md) 定下的口径：**备份不验证等于没有备份**。

```bash
# 方式 A：从校验快照恢复（最常用）
cp /var/backups/retro/app-<时间戳>.db /tmp/restore-test.db
bun run tools/backup-db.ts --verify=/tmp/restore-test.db      # 先确认这份备份可用

# 方式 B：从 Litestream 副本恢复（机器整个没了的情况）
litestream restore -config /etc/litestream.yml -o /tmp/restore-test.db \
  s3://retro-backups/app.db

# 两种方式之后：用真实数据验证恢复出来的库
DATABASE_PATH=/tmp/restore-test.db bun run --cwd . start &   # 或直接起一个临时实例
curl -s http://127.0.0.1:3000/api/health/storage | grep -o '"summary": "[^"]*"'
```

**演练记录表**（每季度填一行，这是"备份真的能恢复"的唯一证据）：

| 日期 | 方式 | 备份时点 | 恢复耗时 | 健康检查 | 行数是否一致 | 备注 |
| --- | --- | --- | --- | --- | --- | --- |
| 待填 | A/B | | | /7 | | |

> **目标**：恢复耗时 < 30 分钟（[04 §4.2](04_数据存储与同步方案.md) 定的口径）。

## 七、本机已做的自动化验收

`bun run tools/verify-backup.ts` —— 一条完整闭环演练（在临时目录，不碰真实数据）：

```
✓ 迁移建库        迁移器执行成功
✓ 造数据          users=1 boards=1 threads=1 posts=2
✓ 备份并自校验    备份脚本退出码 0（内部已校验）
✓ 产出备份文件    app-2026-09-27_08-31-24.db
✓ 备份行数一致    源 users=1/posts=2 → 备份 users=1/posts=2
✓ 独立校验通过    --verify 退出码 0
✓ 拒绝损坏的备份   退出码 1（已拒绝）        ← 这一步证明校验器不是空跑
✓ 恢复后可查询    联表读回 2 层（第一层/第二层）
✓ 恢复库完整性    integrity_check = ok
9/9 项通过
```

`bun run tools/verify-deploy.ts` —— 部署配置**静态**校验（括号配对、root 路径为绝对路径、
systemd 用 bun 而非 node、数据库目录在 `ReadWritePaths` 内等）。
**它不能替代 §五。**

`bun run tools/verify-urls.ts` —— 断言 RSS / sitemap / og:image / canonical 四处都是
**绝对地址**、**站点根一致**、且**不含任何硬编码域名**。编排器会用
`NUXT_PUBLIC_SITE_URL=https://site-root.example` 这种**明显非默认**的值启动实例，
所以代码里一旦残留硬编码就会立刻失败。
（**已做反向验证**：临时把硬编码塞回 `rss.xml.ts`，该检查确实报错并指出了不一致的源头。）

## 八·补、OG 图的 CJK 字体前提（上线必查）

`/og.png` 用 sharp 把 SVG 渲成 PNG，文字靠系统字体渲染。macOS 上开箱可用，
但**精简的 Linux 容器常常一个 CJK 字体都没有**，此时中文会渲染成空白或方块。

```bash
# 目标机上确认存在任一 CJK 字体
fc-list :lang=zh | head -5

# 若没有（Debian/Ubuntu 系）
sudo apt install -y fonts-noto-cjk
```

装好字体后，`bun run tools/verify-og.ts` 的「标题区有文字像素」一项会通过——
**这一项就是为这个风险设的**：字体缺失时它会失败，而不是悄悄发出一张空白图。
