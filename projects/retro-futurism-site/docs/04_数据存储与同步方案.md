## 〇、先问四个问题（不要把四类数据混成一个决策）

多数"选数据库"的讨论之所以吵不清，是因为把性质完全不同的数据混为一谈。本站有四类数据，**它们的正确答案几乎是被各自主导因素唯一确定的**：

| # | 数据 | 特征 | 主导因素 | 结论 |
| --- | --- | --- | --- | --- |
| ① | **内容**（Wiki / 博客） | 读多写极少、作者就是我们、需版本历史、需构建期校验 | 与 Nuxt 的整合度 | **文件式（Markdown）+ Nuxt Content 的 SQL 索引**——由 [02](02_技术栈与选型.md) 已定，**不是决策点** |
| ② | **社区数据**（账号/主题/楼层/会话） | 关系型、写多、需事务、需权限 | 运维成本 vs 开发速度 | ⬅ **这才是 D5 真正要裁的** |
| ③ | **媒体**（图片/视频/PDF） | 大二进制、一次写多次读、需 CDN | 体量与成本 | **本地磁盘起步**，增长后上 S3 兼容对象存储 |
| ④ | **同步** | — | 场景不同策略不同 | 拆成 5 个独立子问题（§四） |

> **一句话**：①③④ 基本已被技术栈与内容形态决定；**真正开放的选择只有 ②**。下文 §一、§二聚焦 ② 与 ③，§三 给出四套自洽 bundle，§四 拆解"同步"。

## 一、社区数据（决策主体）

### 1.1 候选方案

| 方案 | 是什么 | 运维 | 成本 | 与 Nuxt/Bun 的契合 | 主要代价 |
| --- | --- | --- | --- | --- | --- |
| **SQLite 自托管**（better-sqlite3 / bun:sqlite）+ Drizzle | 单文件数据库，随应用进程 | **无**（零外部服务） | **¥0** | ✅ Bun 内置 [bun:sqlite](https://bun.sh/docs/runtime/sqlite)；Drizzle 有 [Bun 官方指南](https://bun.sh/guides/ecosystem/drizzle) | 需自建鉴权；单机写入（小站无感） |
| **Turso**（云 libSQL + 嵌入式副本） | 把 SQLite 放到边缘，本地留只读副本 | 低 | 有[新开发者档](https://turso.tech/blog/turso-cloud-debuts-the-new-developer-plan)，小站免费额度够 | ✅ `@libsql/client` 0.18.0 | 云依赖；副本同步语义需理解 |
| **PostgreSQL 自托管** | 经典关系库 | **高**（要管服务、连接池、升级） | VPS 成本 | ✅ 适配良好 | 小站**过重**：为一个论坛多养一个服务 |
| **Supabase**（托管 Postgres） | 数据库 + 认证 + 存储 + 实时 | 低 | 免费档 → $25/月 | ✅ 但引入完整 SDK | 功能远超所需；**自托管 Supabase 很重** |
| **Neon / Xata**（Serverless PG） | 托管 Postgres，按用量计费 | 低 | 小站近免费 | ✅ | 冷启动延迟；云依赖 |
| **PocketBase** | **单二进制** Go 后端：SQLite + 认证 + 实时 + 文件存储 + 管理 UI | **最低**（一个文件） | **¥0** | 🟡 非 Nuxt 原生，需走 REST/SDK | 引入**第二套数据层**（双写/双源）；管理 UI 风格与主题无关；逻辑用 JS 钩子写 |
| **D1**（Cloudflare） | 边缘 SQLite | 无 | 极低 | ⚠️ **须走 Workers 绑定** | 本地开发需 `wrangler`/`nuxt-hub`，社区有[绑定缺失](https://github.com/nuxt-hub/core/issues/331)、[本地 dev 不可用](https://github.com/nuxt-hub/core/issues/741)的报告 → **与"单机自托管"（D6）冲突** |
| **Directus / Strapi / Payload** | 完整 headless CMS | 中–高 | VPS | 🟡 独立服务 | 面向"内容管理后台"，**不是论坛后端**；对本站是错配 |

### 1.2 关键判断

1. **本站的社区规模不支持重型基础设施。** 目标读者是复古未来主义爱好者——**小众而长尾**。为一个可能只有几百注册用户的论坛常驻一套 Postgres + Redis，是明显的过度设计。
2. **内容已经用 SQLite 了。** Nuxt Content 3 的内部后端就是 SQLite（构建期建库）。再引入一个重型数据库，等于**在一个 SQLite 项目里维护两种数据库文化**。
3. **SQLite 在"读多写少 + 单机 + 中小规模"上是正确答案**，这不是妥协——它避免了网络往返，论坛这种"读主题列表 + 读楼层"的负载表现很好。
4. **D1 与已选的部署形态冲突**，除非愿意把整个部署推向 Cloudflare Workers（那就该重开 D6）。
5. **PocketBase 是唯一真正有竞争力的替代**：它把"认证 + 实时 + 文件存储 + 管理后台"一次性解决，能省掉 1.5–2 周的自建工作量。**代价是引入第二套数据源与第二套心智模型。**

## 二、媒体存储

| 阶段 | 方案 | 触发条件 |
| --- | --- | --- |
| **起步**（推荐） | **本地磁盘** + `@nuxt/image` IPX 自托管处理 | 当前：99 PNG / 80 SVG / 47 PDF，量级在**几百 MB** |
| **增长** | **S3 兼容对象存储**：Cloudflare R2（出网免费是决定性优势）/ Backblaze B2 / MinIO 自托管 | 媒体 > 2–3 GB，或需多实例共享 |
| **视频** | 起步直接用原生 `<video>` 播 92 秒演示录像；**不自建转码** | 若未来有长视频/多清晰度，再评估 Cloudflare Stream / Bunny Stream |

> **关键取舍**：R2 的**出网流量免费**对"图片画廊"这种高流量场景是压倒性优势——画廊是本站的流量大户。但**首版不必上**：本地磁盘 + Caddy 静态缓存足够，且不引入任何云依赖。**把对象存储作为"增长时再开"的开关**，而非首版前提。

**图片处理的位置**：`@nuxt/image` + IPX 默认依赖 **sharp（原生模块）**——这正是 [02 §3.2](02_技术栈与选型.md) 要验证的 V2 风险点。若 sharp 在 Bun 下有问题，回退方案：构建期预生成多尺寸（用 Node 跑一次），运行时不依赖原生模块。

## 三、四套自洽的 Bundle 对比

> 每套都是**内部一致、可直接落地**的组合，不是"某一层的选项罗列"。评分 1–5，5 最好。

### Bundle A · 全自托管 SQLite（**推荐**）

```
内容   Markdown in doc/ → 构建期转换 → Nuxt Content（SQLite 索引）
社区   SQLite（bun:sqlite 经 Drizzle）同一 VPS
媒体   本地磁盘 + @nuxt/image(IPX)
备份   Litestream 持续复制到对象存储（或定时 .backup + rsync）
部署   单机 Bun/Nitro + Caddy（对应 D6）
```

| 维度 | 分 | 说明 |
| --- | :--: | --- |
| 上手成本 | 4 | 无基础设施要搭；自建鉴权/论坛是主要工作量（约 1.5–2 周） |
| 运维负担 | **5** | 零外部服务；备份靠 Litestream 自动化（[Litestream 工作原理](https://litestream.io/how-it-works/)） |
| 成本 | **5** | 仅 VPS（约 $5–10/月），无按量费用 |
| 可扩展性 | 3 | 单机写入上限；论坛过万用户需迁 Postgres（**有明确迁移路径**，见下） |
| 数据自持 | **5** | 数据是一个文件，随时 `scp` 走 |
| 离线/同步 | 3 | 天然支持（本地文件），但**不做客户端离线**（§四.3） |
| 中文生态 | 4 | SQLite 中文资料极多；Drizzle 中文资料中等 |
| 锁定风险 | **5** | 零锁定 |

**为什么推荐它**：本站是一个**内容主权项目**（内容已在 git 里），数据也放在自己手里与之同构；运维负担与成本都最低；且与已定的 Nuxt Content（本身就是 SQLite）**技术文化一致**。

**要求认下的代价**：① 自建鉴权与论坛逻辑（1.5–2 周，且安全细节要自己把关）；② 单机——**服务器挂了站点就挂**（用备份 + 快速重建缓解，不是高可用）。

**迁移路径（重要）**：Drizzle 抽象了方言，`app.db` 从 SQLite 迁到 Postgres 主要是**换驱动 + 跑迁移 + 改少量 SQL 方言差异**，不是重写。所以 Bundle A 不是"死路"，而是"**先简单，需要时再长大**"。

### Bundle B · PocketBase 单二进制

```
内容   同 A
社区   PocketBase（SQLite + 认证 + 实时 + 文件存储 + 管理 UI）
媒体   PocketBase 文件存储
部署   单机：PocketBase + Nuxt 两个进程
```

| 维度 | 分 | 说明 |
| --- | :--: | --- |
| 上手成本 | **5** | 认证/实时/文件/后台**开箱即用**，省 1.5–2 周 |
| 运维负担 | 4 | 单二进制、零依赖，但要**管两个进程**并做反代路由 |
| 成本 | 5 | 同 A |
| 可扩展性 | 3 | 同 A（同为 SQLite） |
| 数据自持 | 4 | 数据仍是 SQLite 文件，但**经 PocketBase 的 schema 抽象** |
| 离线/同步 | 4 | 自带实时订阅，省掉自建 WebSocket |
| 中文生态 | 3 | 中文资料较少 |
| 锁定风险 | 3 | 逻辑写在 PocketBase 的 JS 钩子里，迁移需重写这部分 |

**什么情况下该选它**：**如果你想最快看到"能注册、能发帖、能实时看到新回复"**，且不介意多一个进程与一套 schema 抽象。它把本项目最耗时、最容易出错的部分（认证）直接解决了。

**为什么不是主推荐**：引入**第二套数据源与心智模型**（内容在 Nuxt Content、社区在 PocketBase），主题一致性仍要自己保证（管理 UI 不进前台，所以问题不大），且钩子逻辑的迁移成本让"以后再换"变贵。

### Bundle C · 云 Postgres + 对象存储（规模化取向）

```
内容   同 A（Nuxt Content 构建期）
社区   Supabase / Neon 托管 Postgres + Drizzle
媒体   Cloudflare R2
部署   无状态应用 + 托管数据库（可上 Serverless/容器）
```

| 维度 | 分 | 说明 |
| --- | :--: | --- |
| 上手成本 | 3 | 三处云配置 + SDK 接入 |
| 运维负担 | 4 | 数据库托管了，但**多了三个云依赖与三处账单/密钥** |
| 成本 | 3 | 免费档够用，增长后 $25/月起（Supabase） |
| 可扩展性 | **5** | 明确最好 |
| 数据自持 | 2 | 数据在别人库里；导出可行但非日常 |
| 离线/同步 | 4 | Supabase 自带实时；Neon 需自建 |
| 中文生态 | 4 | Supabase 中文资料充足 |
| 锁定风险 | 2 | 越用越深 |

**什么情况下该选它**：**如果你预期这站会长得很大**（数十万用户、多实例、需要高可用），或**你不想自己管服务器与备份**，愿意用钱换运维。

**为什么不是主推荐**：与当前规模（小站长尾）和 [D6 单机自托管](00_决策记录.md) 的取向都不一致；把三处云依赖引入一个尚未验证读者规模的项目，是**为想象出来的负载付费**。

### Bundle D · libSQL 嵌入式副本（边缘取向）

```
内容   同 A
社区   Turso（云 libSQL）+ 本地嵌入式副本，@libsql/client + Drizzle
媒体   R2
部署   单机或边缘，读走本地副本（零网络往返）
```

| 维度 | 分 | 说明 |
| --- | :--: | --- |
| 上手成本 | 3 | 要理解副本同步语义 |
| 运维负担 | 4 | 比 A 多一个云依赖，比 C 少 |
| 成本 | 4 | [新开发者档](https://turso.tech/blog/turso-cloud-debuts-the-new-developer-plan)，小站近免费 |
| 可扩展性 | 4 | 读扩展好；写仍集中 |
| 数据自持 | 3 | 主库在云，可随时 dump |
| 离线/同步 | **5** | **"同步"是它的原生能力**——本地副本即离线可读 |
| 中文生态 | 2 | 中文资料最少 |
| 锁定风险 | 3 | libSQL 是 SQLite 分支，退出需 dump+迁回 |

**什么情况下该选它**：**如果你确实需要"多机部署 + 读就近 + 主库托管"**，又舍不得离开 SQLite。它是 A 与 C 之间的甜点。

**为什么不是主推荐**：**当前只有一个部署实例**，嵌入式副本的主要收益（跨机读就近）现在用不上；多引入一个云依赖与一套同步心智，收益要等规模上来才兑现。

### 3.1 评分汇总

| 维度（权重） | A 自托管 SQLite | B PocketBase | C 云 Postgres | D libSQL 副本 |
| --- | :--: | :--: | :--: | :--: |
| 上手成本（2） | 4 | **5** | 3 | 3 |
| 运维负担（3） | **5** | 4 | 4 | 4 |
| 成本（3） | **5** | 5 | 3 | 4 |
| 可扩展性（1） | 3 | 3 | **5** | 4 |
| 数据自持（2） | **5** | 4 | 2 | 3 |
| 离线/同步（1） | 3 | 4 | 4 | **5** |
| 中文生态（1） | 4 | 3 | 4 | 2 |
| 锁定风险（2） | **5** | 3 | 2 | 3 |
| **加权总分**（权重合计 15） | **4.53** | 4.07 | 3.20 | 3.53 |

> 权重按本站实际（小众长尾、单人维护、内容主权）设定：**运维负担/成本/数据自持各占 3 或 2，可扩展性与同步只占 1**——因为当前规模下后两者不是瓶颈。

### 3.2 结论

- **主推荐：Bundle A（全自托管 SQLite + Drizzle + Litestream + 本地磁盘）**
  在"低运维、零成本、数据自持、零锁定"上全面领先，且与已定的 Nuxt Content 技术文化一致。**需认下的代价：自建鉴权/论坛约 1.5–2 周，且单机无冗余。**

- **次推荐：Bundle B（PocketBase）**
  如果你**更看重开发速度**、希望立刻拥有认证 + 实时 + 文件存储 + 管理后台，选它。**需认下的代价：第二套数据源与 schema 抽象，迁移成本更高。**

- **A 与 B 的抉择点就一句话**：
  > **你愿意花 1.5–2 周自己写认证与论坛（A，换来零锁定与单一数据源），还是愿意引入第二个服务换时间（B，换来更快的功能闭环）？**

- **C / D 仅在"预期规模显著增长"或"不愿自管服务器"时才值得**；两者都把数据自持度降到 2–3。

### 3.3 一个务实的折中（若难以取舍）

**先 A，但把数据访问层写薄**：用 Drizzle + 一个 `server/utils/db.ts` 门面，**所有查询走这层**。这样：

- 若日后想要 PocketBase 的实时/后台能力 → 把门面实现换成 PocketBase SDK，**页面代码基本不动**；
- 若日后要上 Postgres → 换 Drizzle 方言，**迁移成本可控**；
- 首版仍是零外部依赖的自托管 SQLite。

**这是推荐的落地姿态**：选 A，但**不让 A 变成锁定**。

## 四、"同步"要拆成五个独立问题

"数据同步"是一个含糊的词。对本站而言它是五个不同的问题，**不要用一套机制解决**：

| # | 同步场景 | 方向 | 推荐方案 | 首版 |
| --- | --- | --- | --- | --- |
| 1 | **内容同步**：`doc/` → 站点 | 单向、构建期 | **git + 构建期转换**（[D2/D10](00_决策记录.md)） | ✅ |
| 2 | **数据备份**：数据库 → 异地 | 单向、持续 | **Litestream** 持续复制到 R2/B2；或 `sqlite3 .backup` + rsync 定时 | ✅ |
| 3 | **客户端离线**：服务端 → 浏览器离线可读 | 单向、缓存 | **首版不做**（见下） | ❌ |
| 4 | **多实例同步**：多台服务器共享数据 | 双向 | **首版不需要**（单实例）；需要时走 Bundle D 或 Postgres | ❌ |
| 5 | **实时推送**：新帖子 → 在线用户 | 推送 | **首版用轮询/手动刷新**；需要时 Nitro WebSocket / PocketBase 实时 | ❌ |

### 4.1 为什么首版不做客户端离线（避免过度设计）

| 候选 | 为何现在不做 |
| --- | --- |
| `@vite-pwa/nuxt` + Workbox | 收益（移动端离线读）**尚未被验证有需求**；引入 SW 会带来缓存失效这一整类难调 bug |
| RxDB / TinyBase（本地优先） | 为"多端协同编辑"设计，本站是**读多写极少**，用不上 |
| ElectricSQL / PowerSync | 需 Postgres + 同步服务，与 Bundle A 取向冲突 |
| Yjs / CRDT | 面向**多人实时协同编辑**——本站作者就是自己，用 git 更好 |

> **判断**：本地优先架构解决的是"多端并发写"问题。本站**没有这个问题**——内容是单作者 git，社区数据是低频写入。上本地优先是**为解决不存在的问题引入真实复杂度**。
> **保留路径**：Nuxt 服务端渲染 + 合理缓存头已能覆盖"网络差"的场景；真要做离线，M4 用 `@vite-pwa/nuxt` 缓存正文即可，不必重构数据层。

### 4.2 备份的具体口径（Bundle A 下）

| 项 | 做法 | 验证 |
| --- | --- | --- |
| 数据库 | Litestream 持续复制到 R2/B2（[目录复制指南](https://litestream.io/guides/directory/)） | 定期**实际恢复**一次到临时目录并比对行数（备份不验证等于没有备份） |
| 媒体 | `rsync`/`rclone` 到对象存储，按周 | 抽查文件可下载 |
| 内容 | 已在 git（含远端） | 无需额外动作 |
| 恢复演练 | **每季度一次**：从备份在新目录起一个实例 | 记录耗时（目标 < 30 分钟） |

## 五、成本估算（小站口径：< 10k 月访、媒体 < 5 GB）

| 项 | Bundle A | Bundle B | Bundle C | Bundle D |
| --- | --- | --- | --- | --- |
| 计算 | VPS $5–10/月 | VPS $5–10/月 | $0–20/月 | $5–10/月 |
| 数据库 | ¥0 | ¥0 | $0–25/月 | $0–10/月 |
| 媒体 | 含在 VPS 盘内 | 含在 VPS 盘内 | R2 ~$0.5/月 | R2 ~$0.5/月 |
| 备份 | R2/B2 ~$0.5/月 | 同 A | 同 C | 同 C |
| **合计** | **≈ $6–11/月** | **≈ $6–11/月** | **≈ $1–46/月** | **≈ $6–21/月** |

> 结论：**A 与 B 成本几乎相同且最低**；C 的区间跨度最大（取决于是否上 Supabase 付费档）。

## 六、风险与运维

| # | 风险 | 对策 |
| --- | --- | --- |
| S1 | **SQLite 单机故障 = 站点停摆** | Litestream 备份 + 记录**恢复演练**步骤；接受"非高可用" |

## 七、推荐摘要（给决策者）

> **推荐 Bundle A：全自托管 SQLite。**
>
> - **内容**：Markdown 在 `doc/`（git）→ 构建期转换 → Nuxt Content 索引；
> - **社区**：同一个 VPS 上的 SQLite（经 Drizzle，bun:sqlite 驱动）；
> - **媒体**：本地磁盘起步，> 2–3 GB 时切 R2；
> - **备份**：Litestream 持续复制到 R2/B2 + 季度恢复演练；
> - **同步**：只做"内容同步（git 构建期）"与"数据备份"两件；**客户端离线、多实例、实时推送首版全不做**。
>
> **你要认下的代价**：自建鉴权与论坛约 **1.5–2 周**（含安全细节），且**单机无冗余**。
>
> **若"1.5–2 周"不可接受** → 选 **Bundle B（PocketBase）**：多一个进程，但认证/实时/文件/后台开箱即用。
>
> **无论选 A 还是 B，都建议加一道薄数据访问层**（`server/utils/db.ts` 门面），让今天的简单选择**不变成明天的锁定**。
