## 二、内容信源与单一权威原则

> **原则**：`doc/` 是内容的**唯一权威信源**；站点仓库不复制、不改写正文。

这带来一个必须先解决的现实问题（已实测确认）：

| 现状 | 实测结果 | 影响 |
| --- | --- | --- |
| **无 YAML frontmatter** | 主卷 21 篇全部**无** `---` 元数据块；`---` 只是正文分隔线 | 标题、关键词、摘要、卷属、序号需**从文件名与"关键词/摘要"引用块解析**，不能直接当 frontmatter 读 |
| **篇首元信息用引用块** | 形如 `> 关键词：…；…` 与 `> 摘要：…` | 可解析为 `tags` / `description`，**是好事**：元数据已在正文里 |
| **交叉引用是纯文本** | 形如 `（见 16 末日篇）`、`（见本卷 03）`、`（见主卷 12 谱系篇）` | **不是链接、点不动**。要变成可点击的双向链接，必须写转换器 |
| **目录级归属靠路径** | `doc/punks/atompunk/01_定义与谱系.md` | 卷属 / 篇序 / slug 可由路径推导 |
| **文件名即标题** | `14_磁带篇_磁带未来主义_模拟接口的暖未来.md` | 编号 + 篇名 + 副题需按 `_` 切分 |

### 2.1 结论：需要一个「内容适配层」，而不是手工改 doc/

**推荐做法**：写一个**构建期转换脚本** `tools/sync-content.ts`，把 `doc/` 单向同步成站点内容目录：

```
doc/retro-futurism/14_磁带篇_磁带未来主义_模拟接口的暖未来.md
        ↓ tools/sync-content.ts（构建期，幂等，不改源文件）
projects/retro-futurism-site/content/wiki/main/14-tape-futurism.md
   （生成 frontmatter：title / subtitle / volume / order / slug / tags / description）
   （重写交叉引用：（见 16 末日篇） → Markdown 链接，指向 /wiki/main/16-apocalypse）
```

**收益**：
1. `doc/` 保持**人写友好**的原始形态，不动一个字节；
2. 站点侧拿到规范 frontmatter 与**可点击交叉链接**（这是 Wiki 的核心价值）；
3. 转换幂等、可重复跑，`doc/` 更新后 `git pull` + 重新构建即可；
4. 交叉引用改写规则可单测（`（见 NN 篇名）` / `（见本卷 NN）` / `（见主卷 NN 篇名）` 三类），**映射表可校验**。

**代价**：多一个脚本与一张「篇号 ↔ slug」映射表要维护；映射表漏项会导致链接降级为纯文本（**降级不报错**，但写入构建告警）。

> **备选（不推荐）**：手工把 265 个 md 改成带 frontmatter 与绝对链接的站源文件 —— 破坏 `doc/` 的独立性，且源文更新后立刻漂移。**备选二**：直接把 `doc/` 整个软链/复制进 `content/`，靠运行时解析 —— 交叉引用依然点不动，Wiki 退化成静态阅读器。

## 三、内容模型（schema 草案）

采用 **Nuxt Content** 的 `content.config.ts` 集合定义（详见 [02 技术栈](02_技术栈与选型.md)）。四类集合：

### 3.1 `wiki` 集合（论文/词条）

| 字段 | 类型 | 来源 | 说明 |
| --- | --- | --- | --- |
| `title` | string | 文件名主段 | 篇名 |
| `subtitle` | string? | 文件名副段 | 副题 |
| `volume` | enum | 路径 | `main` / `punks` / `appendix` |
| `series` | string? | 路径 | 朋克卷名（`atompunk` 等） |
| `order` | number | 文件名前缀 | 排序键（00→20） |
| `slug` | string | 映射表 | URL 段 |
| `tags` | string[] | 篇首「关键词：」 | 检索/关联 |
| `description` | string | 篇首「摘要：」 | SEO/卡片 |
| `body` | markdown | 正文 | 交叉引用已改写 |

### 3.2 `blog` 集合（编辑部写作）

```yaml
title:        # 标题
description:  # 摘要
date:         # 东八区日期
tags: []      # 标签
cover:        # 封面图
draft: false  # 草稿开关
author:       # 作者
```

> 博客是**新写作**，与 `doc/` 无关，**手写 frontmatter**（这是 Nuxt Content 的原生用法）。

### 3.3 `gallery` 集合（多媒体）

```yaml
title:        # 作品名
album:        # 专辑
media:        # image | video | svg
src:          # 资源路径（@nuxt/image 处理）
thumb:        # 缩略图
date:         # 年代（用于"按年代筛选"）—— 复古未来站的核心筛选维度
tags: []      # 如 卡面/地图/单位/风格图
credit:       # 版权与出处（强制字段，沿用工作区既有约定）
```

### 3.4 `forum` 集合（关系型，**不走 Nuxt Content**）

论坛是**写多读多**的关系数据（账号、主题、楼层、权限），不适合文件式内容集合。
其数据模型与存储方案**独立决策**，见 [04 数据存储与同步方案](04_数据存储与同步方案.md)。表结构草案：

```
users      (id, name, email, password_hash, role, created_at)
boards     (id, slug, name, description, order)
threads    (id, board_id, author_id, title, slug, pinned, locked, reply_count, created_at, updated_at)
posts      (id, thread_id, author_id, body, created_at, updated_at)
sessions   (id, user_id, expires_at)
```

## 四、导航与检索设计

### 4.1 三种进入路径（对应三类读者）

| 路径 | 入口 | 设计要点 |
| --- | --- | --- |
| **视觉驱动** | 首页画廊九宫格 → 专辑 → 灯箱 | 大图优先、无需登录、键盘左右切换 |
| **知识驱动** | Wiki 侧栏树 → 单篇 → 文内交叉链接 → 关联篇 | 侧栏常驻、面包屑、右侧本篇目录（TOC） |
| **检索驱动** | 全局搜索框（⌘K） → 结果分栏 | 跨集合检索、结果高亮、直达锚点 |

### 4.2 Wiki 侧栏结构（由内容自动生成）

```
主卷 · 未来的考古
├── 理论地基        00 总论 · 01 理论篇
├── 未来的考古      02 远古 · 03 古典 · 04 近代 · 05 奠基 · 06 机器
│                   07 战间 · 08 原子 · 09 太空 · 10 红旗 · 11 中国
├── 回收的未来      12 谱系 · 13 蒸汽 · 14 磁带 · 15 赛博 · 16 末日
├── 当代乡愁与多元  17 蒸汽波 · 18 千禧 · 19 多元
└── 收束            20 结语与附录
朋克五卷            atompunk · biopunk · cyberpunk · dieselpunk · steampunk
附录卷              千禧 · 原子 · 太阳 · 柴油 · 生物 · 蒸汽 · 赛博
```

> **四段分组不写死**：分组依据取自论文集 README 的「卷内结构（四段）」表，落到 `content/wiki/_sections.yml`（或 `content.config.ts` 常量），**新增篇目时改一处**。

### 4.3 搜索方案

- **首选**：Nuxt Content 内置 SQL 全文检索（`queryCollection().search()`），构建期建索引，**零外部依赖**；
- 覆盖范围：Wiki 正文 + 博客 + 画廊元数据；论坛检索**后置**（或走数据库 `LIKE`/FTS5）；
- 中文分词：SQLite FTS5 对中文默认按字切分，**短词命中可接受**；若效果不佳，M2 再评估接外部分词或改用 `@orama/orama`。

### 4.4 双向链接（Wiki 的灵魂）

交叉引用改写后，可反向生成「**本篇被谁引用**」区块：

```
转换期：扫描全部 (见 NN 篇名) → 建 refs 索引 { 目标篇号 → [来源篇号] }
渲染期：单篇页脚显示「被引用于：12 谱系篇、16 末日篇」
```

这是纯文件式知识库**真正优于**传统 CMS 的地方，也是本项目 Wiki 与「把 md 贴上网」的分水岭。**工作量约 1 天**，建议进 M1。

## 五、URL 与 SEO 约定

- **URL 一律英文 slug，页内标题中文**：`/wiki/main/14-tape-futurism`（不与中文路径纠缠，避免百分号编码）；
- `@nuxtjs/seo` 统一生成 `sitemap.xml` / `robots.txt` / OG 图 / canonical；
- 每篇 Wiki 生成 `BlogPosting`/`Article` JSON-LD 结构化数据；
- 旧合订本 PDF 提供 `/download/` 直链（保留 `content-type: application/pdf`）。

## 六、视觉方向（供 02 与美术细化）

复古未来主义的界面语言（**不写死具体年代，保留后续拼贴**）：

| 元素 | 手法 | 注意 |
| --- | --- | --- |
| CRT 质感 | 扫描线、暗角、轻微色散、荧光余晖 | **可关闭**（无障碍/护眼），首屏不做全屏闪烁 |
| 颜色 | 原子时代青绿/奶油黄 + 镀铬银 + 深空蓝 | 正文对比度须过 WCAG AA |
| 字体 | 标题用几何无衬线/等宽，正文用易读中文字体 | 中文字体**运行时加载系统 CJK**（沿用 `refu-game-001` 既有做法，仓库不塞字体二进制） |
| 动效 | 缓慢呼吸、机械拨杆、翻页感 | 尊重 `prefers-reduced-motion` |
| 年代筛选 | 画廊/文章按 七纪（神话→千禧）筛选 | 复用论文集的「七纪分期」，**让导航本身传达知识体系** |

> **亮点建议**：把「七纪时间轴」做成**全局可用的导航组件**——用户在画廊按年代筛选，与在 Wiki 按纪读史是同一个心智模型。这是本站区别于普通"暗色科技风"站的记忆点。
