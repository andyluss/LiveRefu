# 开发计划会意见：M1 / M2 数值投入（数值策划 A）

> 数值策划 A · 2026-09-08 12:02 · 会议：《明日频道》M1/M2 数值投入计划会 · 类型：例会对齐（非正式产出，见 [`plans/README`](../../plans/README.md)）
> 输入：GDD v0.2（§7 / §11）、主程序回执 [`04_response-gdd`](../../docs/lead-programmer/04_response-gdd.md) §4.3、自有框架 [`01_`](../../docs/systems-designer-a/01_numerics-framework.md) 与 [`04_response-gdd`](../../docs/systems-designer-a/04_response-gdd.md)。
> 原则：M1 只交"能跑起来的最小初值"，**不投产完整经济曲线**；完整解锁/碎片曲线随 M3 垂直切片一并对齐（既有 `02_` §五 开放问题约定）。

## 1. 一句话立场（投入量 & 冻结时点）

> **M1 数值策划 A 投入 ≈ 1.5–2 人日**（表结构 schema + 3 项最小初值 + 一份取整/口径说明）；**冻结点 = M1 程序开工前（M1 入口闸门）**，只冻结「番茄参数（meta）+ 聚焦反馈初值 + 内容卡数值字段契约」三件事。完整解锁/碎片经济曲线**不在 M1 冻结**，推迟到 **M3 垂直切片前**（与 `02_` 既有"首版数值冻结建议随 M3 同步"对齐）。
> M2 仅约 **0.5–1 人日**：随 3 频道滤镜/内容量回填稀有度配比、频道表、收藏字段，**只小改不新增经济系统**，无独立冻结点（沿用 M1 已冻 schema，仅更新 tables 值）。

> 一句话逻辑：**M1 的"数值"本质是"参数"，不是"曲线"**——先让 25+5 番茄、1 次正反馈、收藏 1 卡能跑通，曲线留给内容量与皮肤清单回填后再建，避免在未验证手感前锁死一套经济。

---

## 2. M1 需要交付的数值表（最小集）

M1 单频道（磁带暖未来）闭环，按主程序 §4.3 的**阻塞项**反推，数值侧只需要 3 项最小产出：

| # | 产出 | 形式 | 说明 | 给程序 schema 时点 |
| --- | --- | --- | --- | --- |
| 1 | **番茄参数 + 聚焦反馈初值**（`data/tables/meta.json`） | JSON 表 | 唯一"硬驱动"M1 的表：`pomodoro_work=25`、`pomodoro_break=5`、`focus_min=5`、`focus_max=120`、`fragment_base_per_tomato`（聚焦反馈初值，见下） | **M1 入口**（主程序加载器接入前） |
| 2 | **聚焦反馈初值契约**（并入 `meta` + 说明列） | 非独立表 | M1 只需"完成一段专注给 1 次正反馈"的**初值**，不做递减倍率表（递减/保底曲线 M3 前） | **M1 入口** |
| 3 | **内容卡数值字段契约**（并入主程序内容卡 schema） | schema 契约（非表） | 只给字段命名/取值约定：`rarity`（enum: `common/rare/cult`）、`collect_frag`（首次收藏初值）、**版权字段为程序强制**（数值侧只提供数值位，不给表） | **M1 入口** |

**明确不做的（防范围蔓延）**：频道解锁时间线、碎片递减倍率序列、图鉴稀有度配比、皮肤定价、今日信号激励、图鉴进度里程碑——**全部推迟到 M3**。

> 关于「收藏 1 卡」：它不是一张数值表，而是**内容卡 schema 上的数值字段**（`rarity`/`collect_frag`）。M1 收藏动作验的是"字段可写、图鉴可存"，故抽成契约给主程序并入内容卡 schema，数值侧不另立 `collection` 表（避免与主程序内容池 schema 两份真源冲突）。

> 「频道表 / 混音轨列表」：M1 只跑 1 个频道（`tape_warm`）+ 2–3 轨，其字段契约（`channel_id`/`mix_track`）由**主程序在内容池/配置表加载器里一并落地**；数值侧不单列频道表，只在 `01_` 框架下给出字段命名约定即可。

## 3. 数据驱动方案：先定哪张表结构 & 对齐点

`data/schema`（表长什么样）与 `data/tables`（实际数值）分离，落地方式如下：

**先定哪张表结构 → 先定 `meta` 表。**

| 顺序 | 表 | 为何先做 | 备注 |
| --- | --- | --- | --- |
| 1 | **`meta.json`**（`data/schema/meta.schema.json`） | 唯一**无依赖**表：不依赖内容量收口、不依赖皮肤清单，可**立即冻结**；且是主程序加载器最小可跑的最小单元 | M1 入口交付 |
| 2 | **内容卡数值字段契约** | 并入主程序已排 P0 的内容卡 schema（含版权必填）；数值侧只给 `rarity`/`collect_frag` 字段槽 | M1 入口交付 |
| 3 | 频道 / 混音轨字段契约 | 主程序在加载器落地；数值侧给命名约定（`snake_case`、单位） | M1 入口交付 |
| 4 | 完整解锁/碎片/稀有度曲线 | 需内容量 + 皮肤清单回填后建模 | **M3 前**交付 |

**与主程序的对齐点**（`game/README` 与 `01_` 已约定，落实到 schema）：

1. **字段规范**：`snake_case`、一律带 `type`/`unit`/`min`/`max`/`required` 元数据（便于主程序 Godot 加载 + 自校验 + 供 UI 取值），中文说明放 `$comment`/注释列；**禁止魔法数**，常数全进 `meta`。
2. **格式**：JSON 作为 **schema 权威格式**（带嵌套/枚举/范围，能表达 `fragment_mult_seq` 数组与 `rarity` 枚举）；`.csv` 仅留给纯行式表（如进度/频道），**以主程序加载器拍板为准**，数值侧保持"人读版 Markdown + 机器版 JSON/CSV 同步"。
3. **单位与上限**：时间一律秒（meta 内以 min 存、程序层换算），货币=非负整数（`min:0`），`focus_max=120` 等上限写进 schema 让主程序在编辑期就拦截非法值。
4. **合规闸门**：内容卡 schema 含**强制版权字段**（source/license/license_url/status），数值侧并入 `rarity`/`collect_frag` 时**不动**该字段结构，只提供数值位槽（版权判定责任在主策划，程序侧做工程闸门，数值侧不做）。

## 4. 对其它角色的依赖（需先对齐什么）

| 角色 | M1 需先对齐 | 冲突/阻塞 |
| --- | --- | --- |
| **主程序** | ①②数据加载器（读 schema + 自校验，读取路径落在 `game/data/` 引用 `../../data/tables/`）；②内容卡 schema 里的**数值字段插槽**（在版权字段之外给 `rarity`/`collect_frag` 位置）；③取整/跨日口径（`floor` vs `round`、本地日零点清零当日档位）——M1 只需定取整规则，跨日口径 M3 前定即可 | ①阻塞（加载器是数据驱动底座）；②阻塞；③不阻塞 M1 |
| **UI 设计美术 A** | 数字**字段最大位数**（供等宽数字/防溢出，GDD §8.6）：建议给 UI 一套"上限位宽"——时长 `MAX:120:00`（6 字符）、碎片金额 ≤4 位、图鉴计数 ≤3 位、片段时间 ≤4 位。M1 计时器仅需 `mm:ss`（`25:00` 5 位）。 | 不阻塞（M1 计时只需秒/分显示） |
| **主策划 / 内容管线** | M1 不阻塞；但**内容量收口**（每频道 50/12/15）与**稀有度标注**（哪些引言=典藏）需在 **M3 前**回填，否则图鉴条目总量与 `rarity` 配比无法实装 | M3 前回填 |
| **UI 设计美术 A / 主美术** | 皮肤清单 → 回填皮肤定价（60/120/40/20 为初值） | M2 后回填 |

> 一句话：**M1 的依赖几乎全落在主程序一侧**（加载器 + schema 插槽 + 取整规则），这是数值侧能交付的前提；UI 只需先接住"最大位数"一个契约即可开工。
