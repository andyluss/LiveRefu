# 01 · 实现裁决记录

> 用途：把"实现时做的取舍"与"为什么"留在代码旁边（设计层的决策在 [`mainline/docs/`](../../mainline/docs/00_决策总表.md)）。
> 规则：**每条裁决写清 决定 / 理由 / 代价 / 推翻条件**；被推翻的不删除，标注指向新裁决。
> 建立于 S1 · 2026-09-30

## 一、S1（工程地基，2026-09-30）

### D1 · 引擎与渲染后端 → **Godot 4.7 stable + GL Compatibility**

- **决定**：与工作区既有工程同引擎同渲染后端。
- **理由**：验证管线（无头跑完整局 + 表与文档对账 + 字节级截图对照）已建在 Godot 上；无授权费与抽成。
- **代价**：3D 与高端渲染弱于 Unreal、生态小于 Unity——本项目形态不依赖这些。
- **推翻条件**：S5 垂直切片若在目标平台达不到性能与表现要求，则重估并记账迁移成本。
- **上游依据**：[`mainline 05 §六`](../../mainline/docs/05_美术与技术方向.md)（Q7 裁决）。

### D2 · 核心逻辑不依赖渲染 → **强制**

- **决定**：`scripts/core/` 不得引用任何场景、贴图或 `Node2D`；无头环境必须能驱动完整逻辑。
- **理由**：这是**后续所有自动化验收的地基**；一旦破坏，"AI 高效改玩法"和"无头验收"同时失效。
- **代价**：多一层门面（状态 / 只读查询 / 生命周期命令），文件数增加。
- **推翻条件**：无。这条属于项目红线。

### D3 · 数据契约写成数据 → **`schema.json` + 校验器执行**

- **决定**：字段规范（类型 / 命名 / 枚举 / 范围 / 条目数下限）写在 `game/data/schema.json`，校验器只执行它。
- **理由**：加纪元＝加表 + 声明，不需改校验器代码；契约改动会出现在 `git diff`，自然触发变更日志。
- **代价**：契约与文档需要双向同步（[03 数据契约](03_数据契约.md) 的表格）。
- **推翻条件**：若契约表达力不足（如需要条件依赖、跨表约束），再引入正式 schema 工具；**跨表引用完整性校验已列为 S2 待办**。

### D4 · 检查器必须自证 → **两个检查器各带 `--self-test`**

- **决定**：`check_data.py` 带 8 个负向用例，`check_file_size.py` 带 3 个；`./run.sh check` 先跑自检再跑校验。
- **理由**：**一个永远返回"通过"的检查器比没有检查器更糟**；自检把"检查器失效"变成会失败的门槛。
- **代价**：每次改动校验逻辑要同步维护负向用例。
- **推翻条件**：无。

### D5 · 分辨率取横屏 1280×720 → **占位，非定稿**

- **决定**：`project.godot` 的设计分辨率先按 PC 横屏写。
- **理由**：Q5（平台）尚未裁决；先给一个能跑的值，且改它只动一个文件。
- **代价**：若最终选移动端竖屏，界面布局要重做（但 S1 没有任何真实界面，成本近零）。
- **推翻条件**：Q5 裁决后立即改写，并在本表追加记录。

### D6 · 工作区根用"上溯找 `.git`"定位 → **不用数 `..` 层数**

- **决定**：`run.sh` 通过向上查找 `.git` 确定工作区根，再把 `HOME` 指到 `<root>/.godot-home`。
- **理由**：本环境里含 `..` 的写路径会被文件沙箱拒绝，而错误信息只有一行 `mkdir: ... Operation not permitted`，极易误判为权限问题；层数写错也难自查。
- **代价**：多几行 shell 逻辑（可读性略降）。
- **推翻条件**：若将来 `run.sh` 被移出工作区（不再有 `.git` 祖先），改用显式环境变量。

### D7 · 视觉拆成"语法层 + 风格卡"→ **两层，语义 token 优先**

- **决定**：颜色/字号/间距/圆角/动效/图标/卡面信息位置 = **语法层（永不变）**；色板取值、材质、光源、装饰母题、图像处理 = **风格卡（每纪元替换）**。脚本与素材只引用**语义名**（`--power` / `--residue`），不引用颜色名。
- **理由**：玩家学一次语法即可跨纪元；这是"加法成本递减"（[`mainline 03` C3](../../mainline/docs/03_玩法与经济循环.md)）在美术侧的技术前提；也避免"纪元 2 被读成换皮"。
- **代价**：前期要投入一段"看不见成果"的语法层工作；风格卡设计仍需真正美术判断，AI 只能加速。
- **推翻条件**：若 S3 的"同版式换风格卡"实验证明语法层约束过死（例如某纪元确实需要不同的信息布局），则放宽为"位置可微调、层级不变"，并记账。
- **落地**：[04 视觉语言与设计token](04_视觉语言与设计token.md)（13 个 token + 卡面版式规范）。

### D8 · 对比度与层级由机器守（第三道闸门）→ **`check_contrast.py`**

- **决定**：token 的**唯一权威写在 `docs/04`**，`tools/check_contrast.py` 从中解析并断言：文字 ≥4.5:1、交互与语义色 ≥3:1（各 × 三种背景），以及**层级亮度顺序**（背景 / 文字 / 描边三组必须严格递增）。
- **理由**：对比度是唯一可纯计算判定的无障碍维度；层级顺序检查用来抓"颜色达标但与相邻层级挤在一起、用户分不出主次"——**只查对比度会漏掉这种退化**。
- **代价**：改色要走闸门；装饰性分隔线（`--line`）需要显式豁免，否则会被"顺手调亮"。
- **推翻条件**：无（无障碍不放松）。**注意**：它证明不了完整 WCAG 合规，只覆盖可计算的那部分。
- **实测收获（本条最有价值的部分）**：闸门第一次运行就抓出两个真缺陷——`--text-faint` 对 `--bg-elev-1` 仅 **4.43:1**，`--line-strong` 对 `--bg-elev-2` 仅 **2.82:1**（后者与既有项目当年栽的坑完全相同），修复后才达标。

### D9 · 美术产能路线 → **分件分路线，不整体外包**

- **决定**：语法层 / 风格卡 / UI 外壳 **自画（A）**；卡面与立绘 **AI 出量（C）+ 关键件外包精修（B）**；音效纹理用素材包但**必须重混（D）**；图标手写 SVG（成本极低且天然一致）。
- **理由**：纪元契约 v2 要 200–300 张卡，**边际成本必须低到"多 100 张不心疼"**；而识别度来自语法层与风格卡，不能外购。
- **代价**：需要维护统一提示词与后期管线；关键件外包仍需现金与沟通成本。
- **推翻条件**：若 AI 出量在 S4 仍无法通过"10 秒辨识 + 30 秒氛围"两个测试，则改为小卡池（先 60–80 张）并上调单价或延后发售。
- **产能信息（2026-09-30 收到）**：AI 出量 + 自画语法层 + 外包精修关键件；现金**万元级人民币以内**；工时**波动很大、无法估**。
- **由产能信息推出的 D10**：**卡量改为阶梯，不设一次性门槛**——见 [06 产能预算与卡量阶梯](06_产能预算与卡量阶梯.md)（T1 12 张 / T2 40–60 张 / T3 120–150 张 / T4 200–300 张），并优先做四个便宜的体量杠杆（规则卡 / 难度阶梯 / 每日种子 / 未来残片）。

### D10 · 卡量做阶梯而不是一次性门槛 → **T1→T4，S5 只到 T2**

- **决定**：S4 验证用 12 张（T1）；**S5 的公开 Demo 用 40–60 张（T2）**；首发线 120–150 张（T3）；契约 v2 的 200–300 张（T4）为"有余力"目标。
- **理由**：现金不是瓶颈、**工时才是**；而工时不可估。把 200–300 张压在 S5 会让任何一次工时下滑直接推倒交付，且契约 v2 的本来目的并不要求一次性完成。
- **代价（接受）**：发布时若停在 T3，$19.99 的支撑更依赖"规则与平衡的质量"而非卡量；需要在商店页与 Demo 里把差异化讲清。
- **推翻条件**：若 T3 的实测（好评率 <80% 且差评集中在"内容少"）证明 $19.99 需要更多卡量，则回到 T4 并延后发售。
- **依据**：M3 结论"内容量决定差评下限、不决定销量上限"+《杀戮尖塔 2》反例（**堆卡量买不到好评**）。

### D11 · 波次用"敌方配额"抽象，不逐帧模拟敌人（S2）

- **决定**：每波是一个**敌方战力配额**，需在限定回合内打完；未打完则按缺口扣基地生命并计一次漏怪。
- **理由**：S2 要验证的是**资源循环**能否成立；敌人寻路与走位属手感与表现，S3 之后再细化。抽象成配额**更利于断言与平衡**。
- **代价（接受）**：暂时无法评估"防线被突破的观感"，也没有单位移动与射程概念。
- **推翻条件**：S3 引入关卡表与规则卡后，若配额模型无法承载关卡差异（如多入口、护送），改为简化敌人实体。

### D12 · 残渣必须可被清除（S2 实测得出的规则，不是初始设计）

- **决定**：`CardPlayer.clean`——**花电力清理某一格残渣**（每点 1 电力）。
- **理由**：实测发现**没有解除手段的"排污"是纯陷阱**——残渣堆到 155、降级区 38，把自身战力压垮，
  四个阵营 0/6 存活。此时理性玩家的最优解是"什么都不做"，机制看着有张力、实际是死结。
- **代价（接受）**：多一个资源出口（电力不再只能用于出牌）。
- **推翻条件**：若 S3 的规则卡提供了其它解除路径（搬运/封存/降解），可下调清理效率或让它成为某阵营专属。
- **教训（写进 [07](07_S2发现记录.md)）**：**每引入一项"代价"，必须同时给出至少一条"解除/缓解"路径。**

### D13 · 自动玩家是"两档策略"，不是 AI（S2）

- **决定**：`AutoPlayer` 提供**节制**（先清理、且拒绝压垮某格的放置）与**贪心**（只买不卖不清）两档；
  `./run.sh sim` 同时报告两档。
- **理由**：真实玩家会不会玩得好，无法用单一策略代表；而**两档的差距就是"决策有没有意义"的度量**。
  实测节制档平均分约为贪心档 **2–3 倍**、残渣低一个数量级——张力成立的证据。
- **代价（接受）**：模拟结果依赖策略实现质量；策略本身也成了需要维护的代码。
- **推翻条件**：若后续加入规则卡后两档差距收窄到无意义，说明决策空间消失，需回到玩法层重估。

### D14 · 闸门守不变量，报告露事实（S2）

- **决定**：玩法验收**只断言不变量**（终止性、原子性、确定性、单调性、引用完整性）；
  **胜负与数值是标定问题，降级为打印的报告值**。
- **理由**：把"必须赢"写成断言会产生两种坏结果——要么为变绿而偷偷调数（掩盖问题），
  要么让闸门长期为红（人被训练成忽略它）。两者都比"没有这条断言"更糟。
- **代价（接受）**：闸门无法自动发现"游戏不可赢"；需要人定期看 `./run.sh sim` 的报告。
- **推翻条件**：无（这条是方法论层面的约定）。

### D15 · token 的单一来源与对账（S3 落地主题时确立）

- **决定**：**权威在 `docs/04`（给人读）**，引擎侧的机器可读投影是 [`game/data/tokens.json`](04_视觉语言与设计token.md)；
  两者由 [`tools/check_tokens.py`](../tools/check_tokens.py) **强制逐项一致**（颜色名与值双向、字号 5 级且值相同）。
- **理由**：色值与字号一旦有两份定义就会分叉，而分叉的表现是"文档说达标、界面颜色不同"——
  **在代码里看不出来，只看文档也看不出来**。
- **代价（接受）**：改一个颜色要动两处；改一处忘另一处会被闸门拦下（这正是目的）。
- **推翻条件**：无。

### D16 · 背景底色用显式样式覆盖，不用 theme_type_variation（S3 实测）

- **决定**：场景根面板的 `panel` 样式用 `add_theme_stylebox_override` 显式套用 `RootBackground` 的取值。
- **理由**：实测**变体在渲染时不生效**——主题里取值正确（断言通过），渲染仍走 `PanelContainer` 默认样式，
  **静默回落且无报错**。
- **代价（接受）**：场景装配要经过 [`Shell`](../game/scripts/view/theme/shell.gd) 这个共用壳，不能随手 `new()` 一个 PanelContainer。
- **推翻条件**：若将来确认是 Godot 版本问题且已修复，可改回变体；**但保留像素断言作为兜底**。
- **配套**：**PNG 也是闸门**——`./run.sh shot` 在写文件前断言渲染底色等于 `--bg-base`。

### D17 · 主界面就是"token 预览"（S3）

- **决定**：S3 的主界面不画玩法，只呈现语法层（5 级文字样例 + 全部语义色 + 控件三态），并作为人工验收的固定靶子。
- **理由**：在此之前**所有验证都是数值断言，没人确认过"看起来对不对"**。截图一出来就发现了三个真问题（见 [07](07_S2发现记录.md) 补记）。
- **代价（接受）**：多维护一个预览界面与一个截图工具。
- **推翻条件**：S4 开始做真实表现层时，预览可收进"开发工具"入口。

### D18 · 规则卡 = 钩子 × 条件 × 效果（三者正交）（S3）

- **决定**：规则卡由数据表描述（`rules.json`），引擎提供少量**触发点**、**条件种类**、**效果种类**；三者正交组合。
- **理由**：**纪元差异必须写在数据里**，否则每个纪元都会变成 `core/` 里一堆互不兼容的 `if`（那是拼贴，不是风格卡）。
  加触发点只改一处、加条件只改 `RuleConditions`、加效果只改 `RuleEffects`——**不必为每条规则写代码**。
- **代价（接受）**：表达力受限（不能写任意逻辑）。这是**故意的**：表达力换一致性。
- **推翻条件**：若某个纪元的核心机制无法用现有三种效果表达，**先考虑加"效果种类"**；只有在加种类也无法表达时才引入脚本化规则。

### D19 · 规则分"动作型"与"查询型"（S3）

- **决定**：动作型（`fire`）在钩子点改状态且**每钩子点只触发一次**；查询型（`damage_delta` / `cost_delta` / `placement_residue`）**只回答修正值**，由调用方统一套用。
- **理由**：伤害与费用被多处读取（UI 显示 / 自动玩家判断 / 实际扣费）。若各处各自触发"动作型"效果，同一回合会被结算多次。
- **代价（接受）**：调用方要记得传口径（例如交战必须传"场地维护前"的残渣）。
- **推翻条件**：无。

### D20 · 未实现的条件/效果一律不生效，不静默兜底（S3）

- **决定**：`RuleConditions.holds` 遇到未知条件返回 **false**（整条规则不生效）。
- **理由**：字段名打错时若默认成立，就会变成一条"总是触发"的规则——**只会让数值悄悄失真，不会有任何报错**（与 S2 的 F3 同一类失败模式）。
- **代价（接受）**：规则写错时表现为"没反应"，需要看 `events` 日志排查。
- **推翻条件**：无。

### D21 · 关卡表是"配额 + 规则集"的权威（S3）

- **决定**：每关的**逐波配额**（`quotas`，长度必须等于 `waves`）与**生效规则集**（`rule_set`）都写在关卡表里；
  关卡没给满配额时用可推导公式兜底（允许只精调前几波，避免手抄数字互相不一致）。
- **理由**：教学关与终章关不该共用一条曲线；`rule_set` 是**"纪元差异配置化"**的落点——
  同一套引擎，改数据即改玩法。运行期与数据闸门**都**校验（含数组字段的跨表引用）。
- **代价（接受）**：改难度要动数据表；配额条数与波数不一致会被拦下。
- **推翻条件**：若出现"同一关需要多套难度"的需求，再加难度分层字段而不是复制关卡。

### D22 · `SLOT_CAP` 改为物理塔位数（并如实记录"改了没效果"）（S3）

- **决定**：自动玩家的塔位上限从 6 改为 `BoardSystem.MAX_SLOTS`（8）。
- **理由**：6 是"留转向余地"的自我约束，会人为压低能力。
- ****实测结果：数字完全没变**。这证明真正的约束是**残渣**（放第 7 张就超 `RESIDUE_PER_TURN_OK`），
  而不是塔位数。**这类"排除了一个假设"的负结果同样要记账**，否则下次还会有人去调它。
- **推翻条件**：若残渣经济放宽（更多清理手段 / 规则卡），塔位数会重新成为约束，届时需重测。

### D23 · 清完最后一波必须显式收尾，不能靠"下标自然越界"（S3）

- **决定**：`TurnLoop` 在"清空且已是最后一波"时置 `battle.finished = true`，`is_active()` 据此结束。
- **理由**：实测 bug——`advance()` 在最后一波返回 false，波数下标**永远出不去**，
  战斗空转到回合上限，**评分被系统性低估（0.889 → 0.739）且没有任何报错**。
- **代价（接受）**：多一个终局标志位（与"基地被打爆"共同构成两种终局）。
- **推翻条件**：无。**配套**：新增 H3 断言与 K 组"逐关扫描"（每关必须能终止、必须给出确定终局）。

### D24 · 规则获取：三种来源累加、永不删除（S3）

- **决定**：`era_default`（纪元默认）+ `level_grant`（关卡授予）+ `unlock`（局内解锁）三者**累加**；
  未知来源**一律不生效**。
- **理由**：规则卡是"玩家对纪元的理解在增长"。每关重置会让玩家只在打一串互不相关的谜题，
  而不是在经营一条线。未知来源不生效与 D20 同源——**不静默兜底**。
- **代价（接受）**：规则总数必须受控（后期规则会互相放大），因此**解锁规则要逐条评审**。
- **推翻条件**：若玩家反馈"规则太多记不住"，改为**纪元内可选 2–3 条**（像挑战卡那样自选），而不是删除已解锁的。

### D25 · 势力机制落在"同一个数字上算出不同结果"（S3）

- **决定**：四种 `residuePosture` 各自给一个**只围绕残渣主轴**的机制（`cleans` / `avoids` / `moves` / `feeds`）。
- **理由**：若四势力只有卡池与描述差异，玩家会读成**换皮**。机制必须能被玩家感觉到，
  因此断言针对的是"同一张卡在不同势力下结果不同"，而不是描述文本。
- **代价（接受）**：机制少而硬，表达力有限；`moves` 目前偏弱（见下）。
- **已知不平衡（如实记录）**：按势力扫描时 `moves` 在 LV-08 被打爆（C 级）。
  但 **T1 卡池分配不均**（某些势力只分到 4 张卡）会污染这个结论。
  生成器已改为**按势力轮转**；`moves` 是否仍需加强，要等卡池均衡后重测。
- **推翻条件**：卡池均衡后若 `moves` 仍显著弱于其它三者，给它一个不依赖"回收"的正面机制。

### D26 · 拆文件时不得用"按注释文字替换"来搬函数（S3 的教训）

- **决定**：把函数从一个文件搬到另一个文件时，**用整段剪切而不是字符串替换**；
  搬完必须跑一次编译（`./run.sh s2`）。
- **理由**：本轮我用"按文档注释做字符串替换"搬函数，两次误伤实现文件——
  ① 替换 `move_target` → `MoveRouting.target` 时**改掉了整个函数体**（缩进错乱）；
  ② 拆分时把 `turn_start_clean` / `might_bonus` **复制**进了新文件而没从原文件删除，
  两个文件各有一份残留，且都引用对方的常量 → 编译失败。
- **代价（接受）**：搬函数要更笨的手工操作。
- **推翻条件**：无。**注意**：编译失败时场景**永不退出**（看起来像死循环），排错要先看编译错误（见 S2 记录）。

### D27 · 降级区必须真的造成伤害（S4）

- **决定**：降级区按规模每回合扣基地生命（每 `ZONE_PER_RESIDUE`×8 点残渣 → 1 点伤害），
  并在回合末结算、写入事件日志；表现层用**覆盖层画扩张中的污染范围**。
- **理由**：只削弱塔的惩罚是**渐进的、不致命的**，玩家永远可以拖——缺少"必须去清理"的理由。
  加上持续伤害后，残渣从"慢慢变弱"变成**有截止时间的威胁**，玩家才会在"再放一张牌"和"先清一清"之间做选择。
- **参数标定（实测）**：最初设"每 2 个单位扣 1 点"（16 点残渣 = 8 点/回合），
  **四个势力里有三个在第 1 关就被打爆**——降级区变成唯一胜负手。改为每 8 个单位扣 1 点。
- **代价（接受）**：早期关卡降级区几乎无感（这是有意的：前几关教经营，末几关才逼人处理污染）。
- **推翻条件**：若末期实测显示玩家仍能无视降级区拖过去，则把系数调回更严厉。

### D28 · 难度标定的瓶颈是**卡池构成**，不是配额曲线（S4 的结论）

- **决定**：**暂停自动调参**，把结论与下一步顺序写进文档，交给下一轮（含人工判断）。
- **依据**：连续多轮按实测改配额、改降级区系数、改放置策略后，**阵营间的差距仍由卡池构成主导**——
  `moves` 势力的卡池里几乎没有"高供电"的卡，导致它每回合只能出很少的牌；
  这类问题**不是调系数能修的**，需要人类设计卡池（或重写生成器的模板体系）。
- **代价（接受）**：当前难度曲线**不是最终值**，且已知 `moves` 偏弱。
- **推翻条件**：卡池重做后重新测量；届时应先扩到 T2（40–60 张）再调整曲线。
