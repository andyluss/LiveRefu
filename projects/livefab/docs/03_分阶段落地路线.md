# 03 · 分阶段落地路线

> 用途＝先做什么、后做什么、每步能看见什么 ｜ 依赖：[02 架构](02_整体架构方案.md)、[04 选型](04_开源件调研与选型.md) ｜ 状态：草案 v0.1 · 2026-10-03

## 一、排期的第一原则：让"整合"本身先跑通

LiveFab 的风险**不在某个件选错**（选错了换掉就是），而在：

> **把四段工具都装上了，却发现它们各自为政、账号不统一、体验割裂——
> 于是"整合"失败，得到一堆比没有更麻烦的网站。**

所以排期的核心不是"覆盖率"，而是**尽早证明整合这件事成立**。
具体做法：**M1 就要跨段取件**（一个前台件 + 一个沟通件 + IdP + 门户），
让它们在 M1 结束时**真的是一个东西**，而不是"四段各装一个"。

## 二、里程碑

### M0 · 决策与地基（1–3 天）

| 项 | 交付 | 验收 |
| --- | --- | --- |
| 回答 [L1–L4](00_决策总表.md) | 决策记录成文 | L2/L3/L4 有结论 |
| 选定 M1 要接的件（L5/L6 各一个） | 选型落到清单 | 每件通过 [02 §六](02_整体架构方案.md) 的五条横向约束 |
| 一台机器 / 一个 Compose 骨架 | `docker-compose.yml` 骨架 + 反代 | `docker compose up` 能起反代与占位页 |

**停下时你拥有什么**：一份可执行的清单 + 一个能跑的空壳。

### M1 · 让整合成立（2–4 周）

**范围（L10 推荐 A）**：门户 + IdP + **一个前台件** + **一个沟通件**。

| 项 | 为什么在 M1 | 验收（可演示） |
| --- | --- | --- |
| **统一反代 + TLS** | 安全边界 | 所有服务只在反代后面，直连端口不对外 |
| **IdP** | [L3](00_决策总表.md)：身份是一切整合的前置 | 一处账号能登录至少两个不同系统 |
| **门户骨架** | 唯一自研件（[L11](00_决策总表.md)） | 门户显示"已登录身份 + 可进入的件列表" |
| **一个前台件**（CMS 或官网） | 证明 A 段能接进来 | 用 SSO 进入后台，发布一条内容 |
| **一个沟通件**（工单或论坛） | 证明 B 段能接进来 | 用**同一个账号**发一条工单/帖 |
| **统一备份 + 一次恢复演练** | 见 [02 §四](02_整体架构方案.md) | 真的恢复出一个件的数据（不是只配 cron） |
| 角色映射（L4 的五级） | 证明分级权限能落地 | 用一个"协作者"账号验证：能进 A 不能进 C |

**M1 明确不做**：C 段（Git/CI/看板/文档/设计）、电商与支付、可观测全家桶、IM。

> **为什么 M1 不碰 C 段**：研发管理我们**现在有 GitHub 在用**，
> 迁移收益最低、风险最高（会把正在进行的项目拖进去）。等 LiveFab 站稳了再谈。

**停下时你拥有什么**：一个**能用的、账号统一的**对外门户 + 沟通入口，且数据有备份。

### M2 · 补全前台与沟通（2–4 周）

- 前台：Newsletter、分析埋点、商品/支付（若确定要卖东西）；
- 沟通：补上论坛或工单中缺的那一个、状态页、反馈投票；
- 分级信息：文档密级落到一个真实场景（如"内部设计稿只对核心成员可见"）。

### M3 · 研发管理（时间待估，**建议最后做**）

- 代码托管与 CI 的自托管评估：**先做"值不值得迁"的判断**，而不是先迁；
- 看板与迭代：先把 [mainline](../../mainline/README.md) 这类项目的议题流接进来；
- 文档协作与设计资产。

> **M3 的门槛**：只有当"外部协作者需要访问、而 GitHub 权限不够用"或
> "CI 用量产生真实成本"时，迁 C 段才划算。**否则它只是把能用的东西换个地方。**

### M4 · 可观测与成熟化（持续）

- 日志/指标/告警、统一恢复演练排期、成本复盘；
- 评估哪些件真的该自研（[L11](00_决策总表.md)）。

## 三、每段的"可暂停"设计

沿用 [mainline](../../mainline/README.md) 已验证的做法——**每个里程碑都要能随时停下而不留半成品债务**：

| 停在 | 你拥有什么 | 不会留下什么 |
| --- | --- | --- |
| M0 后 | 决策 + 清单 + 空壳 | 无 |
| M1 后 | 账号统一的对外门户与沟通入口 + 有备份的数据 | 无（这是最小的可用形态） |
| M2 后 | 完整的前台与沟通 | 无 |
| M3 中途 | 至少 GitHub 仍在正常工作 | 不会"迁到一半两个地方都有代码" |

> **"迁到一半"是这类项目最典型的债务**。所以 M3 必须**一件一件迁、每件迁完立刻停用旧的**，
> 不允许"两边都留一段时间再说"。

## 四、L9：与既有资产的关系（排期上的含义）

- **复用《未来档案》的"闸门"思路**：每个件接入时，定义**可脚本化的验收**
  （如"SSO 能登录""角色映射正确""备份能恢复"），而不是靠人工点一遍；
- **不复用它的内容管线**——那是给知识库用的，LiveFab 没有那种内容源；
- **设计语言可复用**：门户可以直接借用《未来档案》的原子时代配色与对比度闸门，
  让 LiveFab 与工作室其它产品**看起来是一家人**。

## 五、这份路线刻意不确定的东西

- **具体周数**：给的是量级。真实排期取决于 M0 选定的件有多少坑——
  **而"有多少坑"在没有装起来之前是不可知的**（这也是为什么 M0 要真的起一个空壳）；
- **谁来做**：本方案假设"你 + AI 协作"，与工作区现状一致；若要拉人，排期与 IdP 的必要性都会变；
- **C 段是否真做**：取决于 M3 的门槛是否达到（见上）。
