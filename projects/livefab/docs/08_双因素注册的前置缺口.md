# 08 · 双因素（TOTP）注册的前置缺口：通知器坏了

> 状态：**✅ 全部打通并端到端实测**（设备已注册、2FA 登录成功、`/admin/` 可达）｜ 2026-10-05

## 一、起因

目标里的第 ③ 项是「真实 TOTP 双因素流程端到端验证」，
起因是 `/admin/` 的策略写着 `two_factor`，但**从来没有账号注册过 TOTP 设备**。

一开始我把它理解成"没人去做"。**实际不是——当时根本做不到。**

## 二、★ 根因：通知器坏了，而它连带挡住双因素

`/admin/` 要 `two_factor`。要配双因素，就得**注册一台 TOTP 设备**。
而注册设备需要**提权会话**（Authelia 的 elevation 机制：改安全设置前要重新确认身份）。

提权的方式是**发一次性验证码给用户**。而我们的通知器是坏的：

```
Error occurred creating user session elevation One-Time Code challenge for user 'admin':
  error occurred sending the user the notification
  error="failed to open file: open /data/notification.txt: no such file or directory"
```

配置里用的是 `notifier.filesystem` 指向 `/data/notification.txt`，而**容器里没有 `/data`**。

**于是形成一条静默的死链**：

```
配置里写着 /admin/ 需要 two_factor
  → 要注册 TOTP 设备
    → 要提权
      → 要发一次性验证码
        → 通知器写不出去（/data 不存在）
          → 提权失败（403）
            → TOTP 设备永远注册不了
              → /admin/ 的 two_factor 谁也满足不了
```

**全程没有任何"配置错误"的启动报错**——Authelia 正常启动、健康检查通过、
网关鉴权分层（公开区/account/admin）也全部实测正常。
只有当你**真的去注册设备**时，才会在日志里看到上面那行 error。

> 这解释了本项目 README 里那句"目前没有任何账号注册过 TOTP 设备"——
> 它不是"尚未有人做"，而是**做不了**。

## 三、修复

把通知器从"写文件"改成**接 SMTP → Mailpit**（本地邮件捕获器，本项目已有）：

```yaml
notifier:
  smtp:
    address: 'smtp://mailpit:1025'
    sender: 'LiveFab <noreply@livefab.test>'
    disable_require_tls: true   # ⚠️ Authelia 默认强制 STARTTLS
    disable_starttls: true      #    而 Mailpit 的 1025 是明文 SMTP
```

**又踩一个小坑**：改完报

```
notifier: smtp: failed to dial connection:
  STARTTLS mode set to: "TLSMandatory", but target host does not support STARTTLS
```

Authelia 默认要求 STARTTLS。本地捕获器不需要加密，关掉这两项即可
（**生产接真实 SMTP 时应当打开**——这是本地专用的放宽，不能照搬到线上）。

### 卡点的真相（两个都是我自己的问题）

**① 限流是我自己触发的。** Authelia 的防爆破对提权端点按桶限流
（日志 `Rate Limit Exceeded bucket=2 delay=514s`）。我探接口时反复发请求，
**每发一次就把等待重置**，所以等 7 分钟也没用。
`banned_user` / `banned_ip` 表是**空的** → 这不是持久封禁，是**内存限流器**。

> **解**：`docker compose restart authelia` 立刻清掉。实测重启后提权马上返回 200。
> 正确姿势：**先重启清限流，再只跑一次完整流程**，中间不插任何试探请求。

**② 提交验证码是另一个端点，我一直在猜错的路径。**
正解是 **`PUT`**（不是 POST），字段名是 **`otc`**（不是 `code`/`token`）：

```
PUT /api/user/session/elevation   {"otc":"UWNKP2CG"}   → 200 {"status":"OK"}
```

我是**抓浏览器真实请求**抓到的 —— 这个办法本轮用了两次
（`elevation` 端点本身、注册向导的密钥接口都是这么查到的），**比猜路径可靠得多**。

## 五、★ 查明的端点清单（可直接脚本化）

| 端点 | 方法 | 作用 |
| --- | --- | --- |
| `/api/user/session/elevation` | POST `{"password":…}` | 发起提权 → 发验证码邮件 |
| `/api/user/session/elevation` | **PUT** `{"otc":"…"}` | **完成提权** → `{"elevated":true,"expires":…}` |
| `/api/user/session/elevation` | GET | 查提权状态（含 `elevated`） |
| `/api/secondfactor/totp/register` | GET | 取可选算法/位数/周期 |
| `/api/secondfactor/totp/register` | POST | **开始注册 → 返回 `base32_secret` 与 `otpauth_url`** |
| `/api/secondfactor/totp` | POST `{"token":"123456"}` | **完成第二因素登录**（会话升到 level 2） |
| `/api/secondfactor/totp` | DELETE | 删除已注册设备 |
| `/api/user/info` | GET | 查 `has_totp` / `method` |

> 注册设备的**完成**一步（把验证码提交给向导）我没能只靠 API 复现 ——
> 直接在浏览器向导里点完是最省事的。上面其余步骤都已用 curl 跑通。

## 六、✅ 端到端实测结果（目标项 ③ 达标）

```
① POST /api/firstfactor（admin/devpassword）    → 200，authentication_level = 1
② 未过第二因素访问 /admin/                       → 302 跳鉴权（★ 确实被挡住）
③ POST /api/secondfactor/totp {"token":"701999"} → 200 {"status":"OK"}
   验证码是用**注册时拿到的真实密钥**按 RFC 6238 本地算的
   → authentication_level = 2
④ 过了第二因素访问 /admin/                       → **HTTP 200**
   页面内容：「内部区」「当前级别：admin」
```

**这条链证明了 `two_factor` 策略是真的在起作用**：
不是"配了但没人能满足"，而是**没第二因素就进不去、有第二因素就进得去**。
