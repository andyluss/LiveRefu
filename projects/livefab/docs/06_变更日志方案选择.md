# 06 · 变更日志方案选择（待裁决）

> 用途＝变更日志怎么加版本号与"精确到分"的时间，请你选 ｜ 依赖：工作区 [`rules/R05`](../../../rules/R05-changelog.md)、[`tech/changelog-convention.md`](../../../tech/changelog-convention.md) ｜ 状态：**待裁决** · 2026-10-05

## 一、现在的问题（实测，不是印象）

| 问题 | 实测数据 |
| --- | --- |
| **没有版本号** | [`projects/livefab/CHANGELOG.md`](../CHANGELOG.md) 只有一个 `## [Unreleased]`，底下**挤了 32 个 `### ` 小节**；根 `CHANGELOG.md` 同样只有一个 `## [未发布]` |
| **只有日期、没有时间** | 约定要求 `## [<版本>] - <YYYY-MM-DD>`，**精确不到分** |
| **从未打过 tag** | `git tag` 只有一个历史遗留的 `pre-cc-rewrite` |
| **包清单里也没有版本** | `projects/livefab/package.json` 无 `version` 字段 |

> **后果**：想知道"M0 和 M1 各是什么时候完成的"，只能去翻 `git log`。
> 而变更日志本应**独立于人**回答这个问题。

### 一个必须说清的前提

工作区**已有约定**（[R05](../../../rules/R05-changelog.md)）：**Keep a Changelog 类目 + SemVer 版本 + 东八区日期**。
所以本方案不是"从零定规矩"，而是**在既有约定上加两样东西**：版本号切实落地 + 时间精确到分。
⚠️ 凡是与 SemVer 冲突的选项，本文件都会明确标注（需改 R05）。

## 二、可用素材（决定"回填"能不能做）

**能做，而且依据可靠**：git 提交自带**精确到分、东八区**的时间戳。

```

644be14  2026-10-03 19:43  L1–L3 裁决入库 + 逐件选型数据补齐
d05cf83  2026-10-05 19:52  M0 骨架 + 结构校验器；L4–L11 决策入库
63e539e  2026-10-05 20:20  M0 真正跑通（8 容器）+ 修掉 8 个真启动才发现的问题
ae08d42  2026-10-05 20:50  L12 裁决 A+E（单 PG 实例 + MySQL 调优）
0d26118  2026-10-05 21:09  M1 统一备份 + 恢复演练
7d44458  2026-10-05 21:17  M1 门户骨架
6ce8012  2026-10-05 21:29  M1 收口 Ghost 后台
```

**12 个提交天然聚成 3 簇**（这是一个干净的版本切分）：

| 簇 | 提交 | 时间范围 | 含义 |
| --- | --- | --- | --- |
| ① | 3 个 | 10-03 17:39 → 19:43 | **提案阶段**（P0，L1–L11 待裁决 → L1–L3 裁决） |
| ② | 5 个 | 10-05 19:52 → 20:50 | **M0**（骨架 → 真跑通 → 8 个真启动问题 → L12） |
| ③ | 4 个 | 10-05 21:09 → 21:29 | **M1**（备份 / 门户 / 角色映射 / 收口 Ghost） |

## 三、六个决策点

### A · 版本号怎么定

| 选项 | 样子 | 评价 |
| --- | --- | --- |
| **A1. SemVer 从 0.x 起步** | `0.1.0` `0.2.0` `0.3.0` | ✅ **符合 R05**；`0.x` 如实表达"尚未 1.0" |
| A2. SemVer 从 1.0.0 起步 | `1.0.0` `1.1.0` | 符合 R05，但**虚高**：还没对外可用，1.0 应当留给"可上线" |
| A3. CalVer（日期式） | `2026.10.0` | ⚠️ **与 R05 的 SemVer 冲突**，需改规则；好处是时间信息自明 |
| A4. 里程碑式 | `M0` `M1` | ⚠️ 与 R05 冲突；且**里程碑 ≠ 版本**（一个里程碑可能发多个版本） |

**我推荐 A1。**

### B · 时间格式

| 选项 | 样子 | 评价 |
| --- | --- | --- |
| **B1. 日期 + 时分（东八区）** | `2026-10-05 21:29` | ✅ 与既有 `YYYY-MM-DD` **向后兼容**（只多一段）；人读友好 |
| B2. ISO 8601 带偏移 | `2026-10-05T21:29+08:00` | 机器友好、无歧义；但与既有格式差别大，且更啰嗦 |
| B3. 精确到秒 | `2026-10-05 21:29:07` | 比需求更细；**日志级别不需要秒**，反而像噪音 |

**我推荐 B1。**（若你重视"给机器解析"，B2 更好。）

### C · 时间写在哪

| 选项 | 样子 | 评价 |
| --- | --- | --- |
| **C1. 只写版本头** | `## [0.3.0] - 2026-10-05 21:29` | ✅ 清爽；版本内各条共享同一时刻（本来就是同一批发布） |
| C2. 版本头 + 每个 `###` 小节各写 | `### 新增 · 21:09` | 同一版本内时间不同，**信息量低、噪声大** |
| C3. 每条 `- ` 列表项都写 | `- (21:09) …` | 最啰嗦；且多数条目时间相同 |

**我推荐 C1。**

### D · 历史怎么办（有 32 个未归版本的小节）

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| **D1. 按 git 提交时间回填，拆成 3 个版本** | 用第二节那 3 簇，时间取该簇**最后一个提交**的时间 | ✅ **时间真实可考**（来自 git，非脑补）；一次做完，之后就是增量 |
| D2. 只从现在开始 | 历史全留在 `[未发布]`，新改动才带版本 | 最省事，但**"未发布"会永久膨胀**——正是你现在遇到的问题 |
| D3. 全归一个 `0.1.0`，用当前时间 | 一条版本装 32 个小节 | 快，但时间**不真实**（把 10-03 的事记成 10-05） |

**我推荐 D1。** ⚠️ 它需要我做一次"改写历史条目结构"的工作量，
但**每个版本的日期都取自真实提交时间**，不是编的。若你更在意"别动旧文本"，就选 D3。

### E · 要不要打 git tag

| 选项 | 评价 |
| --- | --- |
| **E1. 打轻量 tag**（`livefab-v0.3.0`） | ✅ 让 CHANGELOG 的版本号与 git 对得上；回查"这一版是哪次提交"一步到位 |
| E2. 不打 tag | 只写文档；版本号与提交无硬关联 |

**我推荐 E1**（前缀带项目名，因为本仓库是多项目共存）。

### F · 要不要护栏

| 选项 | 评价 |
| --- | --- |
| **F1. 加校验并进 pre-commit** | ✅ 检查：版本头格式、时间格式、**时间不早于上一版**、`[未发布]` 是空的或在最上。与工作区既有的"链接校验进钩子"一脉相承 |
| F2. 只靠约定 | 省事；但**这类格式最容易随时间腐化**（本仓库已有 2 个自写校验器抓到过真问题） |

**我推荐 F1。**

## 四、三套打包方案（可直接选一个）

| | 方案甲 · **规范**（推荐） | 方案乙 · 轻量 | 方案丙 · 最省事 |
| --- | --- | --- | --- |
| A 版本号 | A1 SemVer `0.x` | A1 SemVer `0.x` | A1 SemVer `0.x` |
| B 时间 | B1 `YYYY-MM-DD HH:mm` | B2 ISO 8601 | B1 |
| C 位置 | C1 版本头 | C1 版本头 | C1 |
| D 历史 | **D1 按 git 时间回填 3 个版本** | D1 回填 | **D3 一条 `0.1.0`** |
| E tag | **E1 打 tag** | E2 不打 | E2 不打 |
| F 护栏 | **F1 加校验进钩子** | F2 无 | F2 无 |
| 代价 | 前期多一次回填 + 写个校验器 | 中 | 最小 |
| 得到 | 版本与提交严格对应，格式由机器守 | 格式统一，但无护栏 | 有个版本号，时间不真实 |

## 五、我的推荐与理由

**推荐方案甲。** 三条理由：

1. **D1 的时间是真实的**——取自 git 提交时间戳，不是"我今天想起来补一个"。
   变更日志的价值有一半在"可信"，编时间会毁掉它。
2. **F1 的护栏是必要的**——这个仓库已经有过 **3 次"变异字符串过期导致检查器误报"**、
   **2 次"检查器自己有 bug"** 的经历。格式约定**不放护栏必腐化**。
3. **A1+B1 与既有约定向后兼容**——既有条目是 `- YYYY-MM-DD`，加时分只是**多一段**，
   不需要改 R05；而 A3/A4 要改规则，代价不成比例。

**若你只是想快点看到效果**，方案丙也完全可用——只是"时间不真实"这一点要接受。
