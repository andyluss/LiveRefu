# 02 · 整体架构方案

> 用途＝LiveFab 整体怎么拼、为什么这么拼、资源要多少 ｜ 依赖：[01 定位](01_定位与角色.md)、[04 选型](04_开源件调研与选型.md) ｜ 状态：草案 v0.1 · 2026-10-03

## 一、先看清这一整个光谱有多宽

四段能力，**没有任一个开源件能同时做好**：

| 段 | 典型能力 | 为什么不能用一个件解决 |
| --- | --- | --- |
| A 前台运营 | 官网、内容、商品、Newsletter | 与"代码托管"完全不同的领域模型 |
| B 用户沟通 | 工单、论坛、IM、反馈 | 面向外部用户，负载与权限模型都不同 |
| C 研发管理 | Git、CI、看板、文档、设计 | 面向内部，与外部用户几乎无交集 |
| D 分级信息（横切） | 身份、权限、密钥、备份、可观测 | 不是"某一段"，而是**贯穿所有段的横切关注点** |

**所以"整合"这个词有两种截然不同的做法**，这就是 L2 要裁的东西。

## 二、L2 的三个候选

### 候选 A：一站式平台（找一个"什么都有"的套件）

例如把**所有**功能都塞进一个大型平台（如一个带插件市场的全能 ERP/门户），或用 GitLab 这类"全家桶"覆盖尽可能多的段。

| 维度 | 评价 |
| --- | --- |
| 上手成本 | 低（只装一个） |
| 覆盖面 | **永远差一截**——没有任何开源件同时做好电商 + 论坛 + 工单 + CI |
| 定制空间 | 受平台插件模型限制；不合意只能忍 |
| 锁定风险 | **高**——所有数据进了同一个库，换不动 |
| 与本项目的契合 | ❌ 你明确说"整合开源项目"，而 A 是"被一个项目整合" |

**结论：不推荐。** 它是"看起来省事、实际处处将就"的方案。

### 候选 B：门户 + 联邦式套件（**推荐**）

**一个自研的薄门户**（统一入口、单点登录、统一设计语言、跨系统的"我的待办"聚合）
**+ 若干成熟开源件各司其职**，通过 **OIDC 统一身份** 与 **统一导航** 串成一个整体。

```
                    ┌──────────────────────────────────────────┐
                    │  LiveFab 门户（自研，薄）                 │
                    │  · 统一入口与导航                        │
                    │  · 单点登录（对接 IdP）                   │
                    │  · 跨系统聚合视图（我的工单/议题/待办）    │
                    │  · 统一设计语言（复用《未来档案》token）   │
                    └───────────────┬──────────────────────────┘
                                    │ OIDC SSO（统一身份）
        ┌───────────────┬───────────┼───────────┬───────────────┐
        │               │           │           │               │
   ┌────▼────┐    ┌─────▼─────┐ ┌───▼────┐ ┌────▼────┐   ┌──────▼──────┐
   │ A 前台  │    │ B 沟通    │ │ C 研发 │ │ D 密钥  │   │ D 可观测    │
   │ CMS/电商│    │ 工单/论坛 │ │ Git/CI │ │ 配置    │   │ 日志/监控   │
   │ 邮件    │    │ IM/反馈   │ │ 看板   │ │         │   │ 状态页      │
   └─────────┘    └───────────┘ └────────┘ └─────────┘   └─────────────┘
                                    │
                    ┌───────────────▼──────────────────────────┐
                    │  统一反向代理（TLS / 路由 / 前置鉴权）      │
                    └───────────────┬──────────────────────────┘
                    ┌───────────────▼──────────────────────────┐
                    │  统一备份（多系统 → 对象存储）             │
                    └──────────────────────────────────────────┘
```

| 维度 | 评价 |
| --- | --- |
| 上手成本 | **中**——要一件件装、逐个接 OIDC |
| 覆盖面 | **全覆盖**，且每段都能选该领域最好的件 |
| 定制空间 | **高**——不满意的件可以单独替换，不影响其它 |
| 锁定风险 | **低**——每个件的数据独立，可单独迁出 |
| 代价 | **需要一个自研的薄门户**（这是唯一没有合适开源件的东西，见 L11）；整合工作量是真实的 |

**为什么推荐它**：

1. **它是唯一能覆盖全光谱的形态**——因为没有全能件；
2. **"前店后厂"要求店与厂是同一套系统的两个面**（[01 §一](01_定位与角色.md)），
   而**只有门户层能提供这个"同一套"的体验**；纯拼工具会得到"一堆互相不知道对方存在的网站"；
3. **符合你"先整合、后自研"的路径**——门户是薄的一层，业务功能全部来自成熟件；
   将来某个件不满足，单独换掉即可。

### 候选 C：最小起步（先只做 A 段，其余以后再说）

只搭官网 + CMS，别的等有需求再补。

| 维度 | 评价 |
| --- | --- |
| 上手成本 | **最低** |
| 覆盖面 | 只覆盖 A 段 |
| 风险 | **会在 L3 上欠债**——若不先立身份，将来每接一个系统都要重做一次账号整合 |
| 与本项目的契合 | 作为"**第一步**"是合理的，作为"**架构**"不合格 |

**结论**：C 不是架构，是**排期策略**。它应该被吸收为 B 的 M1 范围（见 [03](03_分阶段落地路线.md)），
而不是替代 B。

## 三、L3：为什么身份必须最先立

这是本方案里最容易被低估、代价最大的一条。

**如果先接工具、后做身份**，会发生什么：

1. 接第 1 个系统：手工建账号；
2. 接第 2 个系统：**又一套账号**，用户要记两组密码；
3. 接第 3 个系统：开始有人问"为什么论坛的我和工单的我不是同一个人"；
4. 想回头统一：**每个系统都要迁用户表、改外键、处理重复账号**——
   而这时数据已经长起来了，迁移成本和风险都远高于一开始就做好。

**如果先立 IdP 再接工具**：每接一个新件，就是"配一个 OIDC 客户端 + 映射一组角色"，
**每个件的接入成本从"改数据"降为"改配置"**。

> **所以推荐的顺序是**：门户骨架 → **IdP** → 逐个接业务件。
> IdP 本身不产生业务价值，但**它是让后续每一次接入都变便宜的那个投资**。

**同时要说清楚一个反向条件**：**如果 LiveFab 长期只有你一个人用**，
IdP 就是过度设计——单人自用直接一套账号体系足够。
所以 L3 的推荐**以前提"未来会有外部协作者或用户登录"为条件**，
这正是 [01 §五](01_定位与角色.md) 待澄清问题 2 必须先回答的原因。

## 四、四类"横切件"的定位（D 段）

它们不属于任何一段，但每段都要用：

| 横切件 | 作用 | 若缺失的后果 |
| --- | --- | --- |
| **统一反向代理** | TLS、路由、**前置鉴权**（未登录者在网关就被挡掉） | 每个件各自暴露端口，安全边界散落 |
| **统一身份（IdP）** | 一处账号，处处通行 | 见 §三 |
| **统一备份** | 多系统的数据 → 一个对象存储，统一策略 | 每套系统各备各的，必有一套被遗忘 |
| **统一可观测** | 日志、指标、告警、状态页 | 出故障时不知道是哪个件的问题 |

> **一条经验（从《未来档案》继承）**：**未经验证的备份等于没有备份**。
> 多系统备份尤其容易"配置了但从没恢复过"——所以 LiveFab 的备份方案必须自带**恢复演练**，
> 而不是只列一个 cron。

## 五、L8：部署形态与资源预算

**推荐：单机 Docker Compose 起步，按需加机器。**

理由：先用最小代价把"整合"跑通；等某一段真的吃资源了，再单独把那一段挪出去
（联邦式架构的好处正是**可以单独挪**）。

**资源预算（需要在决策时确认上限）**：

| 段 | 大致内存量级 | 备注 |
| --- | --- | --- |
| 门户 + 反代 | 数百 MB | 门户是薄层 |
| IdP | **数百 MB ～ 1 GB+** | 差异很大，是选型的关键指标之一（见 [04 §四](04_开源件调研与选型.md)） |
| A 前台（CMS/电商） | 数百 MB ～ 1 GB | 电商引擎偏重 |
| B 沟通（工单/论坛/IM） | **论坛与 IM 是吃内存大户** | 具体数字见 [04 §二](04_开源件调研与选型.md) |
| C 研发（Git/CI） | **CI runner 是突发吃 CPU 的** | GitLab 系尤其重 |
| D 可观测 | 数百 MB | 取决于留存策略 |

> **诚实的说明**：上表是**量级**而非实测值。具体每个件的资源占用需要在你选定后实测——
> 我没有一个环境能把它们全跑起来量（这与《未来档案》里"部署未在真机验证"是同一个限制）。
> 所以 L8 的正确做法是：**选定后先在一个小 VPS 上跑 M1 范围，量出真实基线，再决定要不要扩。**

## 六、横向约束（给所有件定的规矩）

1. **必须支持 OIDC**——不支持的直接淘汰，否则无法统一身份；
2. **许可证要过一遍**——AGPL/BSL/SSPL 会影响将来的自研与商业化路径（[04](04_开源件调研与选型.md) 逐件标注）；
3. **数据必须能导出**——避免"用得越久越换不动"；
4. **中文可用**——界面或有社区汉化；这点对团队日常使用影响很大；
5. **看维护活跃度**——停止维护的件是负债（[04](04_开源件调研与选型.md) 会标出）。
