## 〇、两个否决项（先看这两条，再看功能）

| 否决项 | 为什么 | 本次核查的结论 |
| --- | --- | --- |
| **许可证** | AGPL 有传染性；BSL/BUSL/MSCL 是"源码可见但非开源"，且可能限制商业化 | **多款热门件的许可已变**：Directus 12 改为 MSCL-1.0-GPL、Vault 改 BUSL、Outline 是 BSL、Vendure 3.x 转 GPLv3 |
| **OIDC 支持** | 它是统一身份的前提（[02 §三](02_整体架构方案.md)） | **大量件的 SSO 被锁在商业版**：Medusa、Chatwoot、Mattermost Team、Plane、OpenProject、Docmost、OpenObserve 都是如此 |

> **一条比功能更重要的经验**：**功能不满意可以忍，许可证踩坑要重做。**
> 所以下面每段的推荐都先过这两道闸。

## 一、A 段 · 前台运营展示

**能力范围**：官网/落地页、内容管理与编辑体验、商品/支付、营销与增长、SEO、前台侧互动。

**强约束**：编辑者可能不是技术人员 → **可视化编辑与预览**权重高；产物对外见人 → 中文与可用性优先。

### 1.1 推荐结论

| 子能力 | 推荐 | 代价（必须认下的） |
| --- | --- | --- |
| 内容管理 | ✅ **已定：Ghost**（用户选；MIT、55k stars、自带会员/订阅/Newsletter） | 自带前端皮 → **用 L5c 的 Astro 前端模式化解**（见 §1.2·补）；另需 MySQL |
| 官网构建 | 复用 Nuxt 栈（与《未来档案》同源） | 无（这是复用既有能力） |
| 电商 | **Saleor** 或 **Spree**（都是 BSD-3 + 内核自带 OIDC） | 两者都要额外服务；**建议整段推迟**，见 §1.3 |
| 简报 | **listmonk**（唯一原生 OIDC 的简报工具） | 无营销旅程编排 |
| 分析 | **Umami**（MIT 最轻）或 **Matomo**（完整报表） | 两者都无内置 OIDC → **放在反代后面用网关鉴权** |

### 1.1·补、核查后发现的两个候选遗漏（应纳入评估）

| 候选 | 是什么 | 为什么值得重新评估 | 代价 |
| --- | --- | --- | --- |
| **Ghost** | 完整的发布平台：内容 + 会员 + 订阅 + Newsletter 一体 | **MIT、55k stars、当日仍在推送**——许可与活跃度都很干净；若"前台 = 博客 + 会员 + 订阅"，它比"无头 CMS + 单独简报工具"**更省事** | 它是**自带前端的整套系统**，与"薄门户 + 联邦式套件"的理念有张力（会多一张自己的皮），定制深度不如无头 CMS |
| **Formbricks / HeyForm** | 表单与调研（A 段原先只写了"表单收集"却没给候选） | 补上这个子类的候选 | 许可都要先过否决项：**HeyForm 是 AGPL-3.0**；Formbricks 的 license 字段是 `NOASSERTION/Other`，**需读原文核实** |

> **判断**：**Ghost 是本次核查最有价值的意外发现**——它可能让 A 段的形态从
> "无头 CMS + 简报 + 分析三件套"简化为"Ghost + 分析"。
> **但这与 L2（门户 + 联邦式套件）有张力**，所以它是一个**值得你单独裁的取舍**，见 [00 §二](00_决策总表.md) 的 L5。

### 1.2 一个重要的选型修正

**先前的默认首选 Directus 已不再合适**：v12 起
① 整体改为 **MSCL-1.0-GPL**（源码可见、**禁止竞品商业化**、四年后转 GPL-3.0）；
② **把 SSO 移出免费档**，并在自托管时加了许可证强制校验（超额会阻断 `/items`、禁用 GraphQL 等）。

对"前店后厂、要做商业交付"的底座来说，这是**实打实的法律约束**，不只是功能阉割。
若坚持用 Directus，只有两条路：锁 11.x（接受无官方安全更新）或买授权。

### 1.2·补、L5c：Ghost + Astro 的整合模式（已核实）

**用户决策：L5 选 Ghost，并整合 Astro。** 这两件事可以并存，方式是
**把 Ghost 当"后台 + 会员系统"，用 Astro 做前台**：

| 模式 | 做法 | 评价 |
| --- | --- | --- |
| A. 纯 Ghost 主题 | 用 Ghost 自带前端与 Handlebars 主题 | ❌ 等于多一张皮，与 [L2 薄门户](02_整体架构方案.md) 冲突 |
| **B. Ghost headless + Astro 前端**（推荐） | **Astro 在构建期经 Ghost Content API 取内容，生成静态站**；会员/订阅仍由 Ghost 提供 | ✅ **官方支持**：Astro 文档有专门的 [Ghost 集成指南](https://docs.astro.build/en/guides/cms/ghost/)，社区还有 `@matthiesenxyz/astro-ghostcms` 集成包 |
| C. 混合（ISR/按需渲染） | Astro 部分页面按需渲染，实时拉 Ghost | 待有"实时"需求再上；静态优先更省资源 |

**推荐 B 的理由**：

1. **保住了 L2**：前台是**我们自己的 Astro 站**，不是 Ghost 的主题——薄门户的理念不被破坏；
2. **保住了 L5 的收益**：Ghost 的内容编辑、会员、订阅、Newsletter 全部照用；
3. **构建期取数 = 静态产物**，性能与《未来档案》同级，且**不产生运行时耦合**；
4. **Astro 与现有技术栈同族**（都是 JS/TS + 静态优先），学习成本低。

**代价（要认下的）**：

- 内容更新需要**触发 Astro 重新构建**（而非 Ghost 改完即时可见）——
  可用 webhook 自动化，但这是**多出来的一环**；
- **两个系统都要维护**（Ghost 升级 + Astro 升级）；
- Ghost 的会员/订阅页仍走 Ghost（那是它的强项，不建议自己重写）。

> **Astro 的定位要说清**：它是**前台的构建器**，不是"又一个 CMS"。
> 它与 [L11](00_决策总表.md) 的"自研只做门户层"并不冲突——
> **门户层很可能就是用 Astro 写的**，二者是同一件事的两个说法。

### 1.4 ⚠️ Ghost 的鉴权缺口（M1 待办）

**Ghost 不原生支持 OIDC**（详见 [research §九](research/01_开源件事实核查.md)）：
后台是邮箱密码，会员读者走 magic link。

**M0 的取舍**：让 Ghost 直接对外（含 `/ghost/`），先把整合跑通；
**M1 必须收口**——把 `/ghost/` 改为只在内网可见，或加前置保护（Authelia `one_factor`）。
⚠️ 前置保护**可能与 Ghost 自身会话冲突**，M1 的验收必须包含"实测两层不打架"。

**这条缺口还带来一个标准修正**（已写进 [research §9.2](research/01_开源件事实核查.md)）：
"支持 OIDC"从"所有件都要满足"**降级为"内部件尽量满足 + 为不满足者准备网关方案"**。
因为面向外部的产品（CMS/论坛/电商）的登录**是产品功能的一部分**，不是可替换的基础设施。

### 1.3 电商整段的判断

**建议推迟，不是不选。**

理由：电商是所有段里**最重、坑最多**（支付、税务、退款、库存、对账），
而 **LiveFab 现阶段（展示 + 沟通）没有它也完全能运转**。
把它排在 M2 之后，等"确实要卖东西"再启动，避免早期把精力烧在没验证的需求上。

## 二、B 段 · 用户沟通与社区

**能力范围**：客服工单、社区论坛、IM、公告与状态页、反馈投票。

**强约束**：

- **论坛与 IM 是吃内存大户**，论坛还要单独解决**中文搜索**；
- **境内可达性**：现方案（Giscus 依赖 GitHub）正是最大风险 →
  **本段的自建论坛直接替掉它，这是 B 段最明确的收益**；
- **反垃圾**是论坛的长期负担。

### 2.1 推荐结论

| 子能力 | 推荐 | 代价（必须认下的） |
| --- | --- | --- |
| 客服工单 | **Zammad** | 官方最低 2 核 6GB **+4GB 给 Elasticsearch**——本类最重 |
| 社区论坛 | **Discourse** | 官方最低 1GB（配 swap）／推荐 2GB+；OIDC 是"官方插件且已内置核心"，SSO 最正规 |
| IM | **Rocket.Chat**（Community 版即可用 OIDC） | Meteor + MongoDB 栈较重；**但见 §2.2②** |
| 状态页 | *（数据缺失，待补）* | — |
| 反馈投票 | *（数据缺失，待补）* | — |

### 2.2 两个需要注意的判断

**① Zammad 的 Elasticsearch 依赖要提前算进预算。**
它是同类里唯一"核心免费 OIDC + 功能无阉割 + 官方中文"的，但 6GB + 4GB 的内存要求
对一个单机底座不是小数。要极低资源就用 FreeScout，但**必须把 SAML/OAuth 模块的钱计入预算**。

**② IM 很可能不该自建。**
用户已经在哪里聊天，就该去哪里。自建 IM 的常见结局是"只有你自己在里面"——
这条与"贴近用户"的定位其实是一致的：**贴近用户意味着去用户在的地方，而不是把用户拉进你的系统。**
所以 IM 建议**先不做**，除非有明确的、自建才能满足的理由（如数据合规）。

### 2.3 论坛选型的另一个候选（值得单独看）

**HumHub** 是本类唯一"核心原生 OIDC + 资源最省（官方：PHP 64MB / 磁盘 600MB）"的组合，
中文也有。代价是 **AGPL-3.0-or-later**（传染性最强）且定位偏**内部社交网络**而非公开社区。
若 B 段的主要用途是**团队/协作者内部沟通**而非公开社区，它值得优先考虑。

> **对照**：Discourse（GPL-2.0、资源重、SSO 最正规、适合**公开社区**）
> vs HumHub（AGPL、资源最省、OIDC 原生、适合**内部网络**）。**用途决定选谁。**

## 三、C 段 · 后台研发管理

**强约束（M3 已把它排最后）**：我们当前在 GitHub，**迁移收益最低、风险最高**。
迁移的**唯一正当理由**是 GitHub 权限粒度或成本满足不了需求。

### 3.1 推荐结论（供 M3 决策时直接用）

| 子能力 | 推荐 | 代价 |
| --- | --- | --- |
| 代码托管 | **Forgejo**（真正 GPL 开源 + OIDC 组映射 + LTS 轨道）／次选 **Gitea**（MIT 最宽松） | Go 单二进制、默认 SQLite，资源与 Gitea 同量级；生态小于 GitLab |
| CI/CD | **Woodpecker CI**（Apache-2.0、两容器、零配置） | ❌ **无自身身份体系**，账号来自所连 forge——若要求 CI 参与 SSO 则不满足 |
| 议题/看板 | **Vikunja**（AGPL，唯一开源版直接支持 OIDC；Go 单二进制 + 可选 SQLite） | 偏任务/看板，缺完整项目集与预算能力 |
| 文档协作 | **BookStack**（MIT + OIDC 免费内建 + 中文现成） | 书/章/页层级偏僵，不如 Outline 现代 |
| 设计工具 | **Penpot**（MPL-2.0 + 1.5.0 起内建 OIDC/LDAP） | 三件套（PG + Valkey + 导出器），中等偏重 |
| 制品仓库 | **Harbor**（Apache-2.0、CNCF 毕业、官方口径 2C4G/40G） | 组件多；嫌重可换 **zot**（单 Go 二进制） |

### 3.2 明确不要碰的

| 件 | 为什么 |
| --- | --- |
| **GitLab CE** | 官方基线 **8 vCPU / 16GB**，对单机底座是重负担。只在"确实需要一体化 + 接受该基线"时才上 |
| **Plane / OpenProject / Docmost** | 三者的 **OIDC 都被锁在付费版**（Plane Business / OpenProject Enterprise add-on / Docmost Enterprise）——**直接触发否决项** |
| **Wiki.js** | 两年无正式版（3.0 长期 beta），有停滞风险 |
| **Vanilla Forums OSS** | 官方已终止，仓库已下线 |

## 四、D 段 · 身份、权限与横切（**必须先做**）

### 4.1 推荐结论

| 子能力 | 推荐 | 代价 |
| --- | --- | --- |
| **IdP / SSO** | **Authelia**（单二进制、**已获 OpenID 官方认证**）作首选；管理能力不足时升 **Keycloak** | Authelia 偏"网关鉴权"，用户/租户管理弱于全套 IAM；Keycloak 是 JVM、资源与运维最重 |
| 反向代理 | **Caddy**（Apache-2.0、自动 HTTPS）或 **Traefik**（MIT） | ⚠️ **两者本体都不做 OIDC**——鉴权必须落到 Authelia |
| 授权引擎 | **先不上**（见 §4.3） | — |
| 密钥管理 | **SOPS + age 起步**（零运维）；需要动态密钥/审计时上 **OpenBao**（MPL-2.0） | Vault 因 **BUSL 非开源**，不建议作新底座 |
| 统一备份 | **Restic**（BSD-2、原生对象存储）+ rest-server | ⚠️ **四个备份候选全都不支持 OIDC 登录** |
| 可观测 | **Uptime Kuma** 先上；随后 **Grafana OSS + Prometheus + Loki** | Grafana/Loki 是 **AGPL-3.0**，需确认合规边界 |

### 4.2 IdP 选型的决定性因素

本段只有一个真正重要的取舍：**资源占用 vs 管理能力**。

- **Keycloak**：协议覆盖最全（OIDC/SAML/LDAP/…）、生态最大，但 JVM 栈在本类里最重；
- **Authelia**：Apache-2.0、**OpenID 官方认证**、单二进制远轻于 Java 系，且与 Traefik 的 ForwardAuth、
  Caddy 的 `forward_auth` 都有官方集成——**若需求是"挡住未登录者 + 提供 SSO"，它更划算**。

> **Zitadel 不考虑**：功能现代但 **AGPL-3.0**，触发否决项（除非你接受 AGPL 边界）。

### 4.3 授权引擎：**现在不需要**（这一条要写死）

本次核查显示 **OpenFGA**（Apache-2.0、CNCF 毕业、原生 OIDC）是这类里最好的选择。
**但现在的结论是：不要上它。**

理由：五级权限（公开/注册/协作者/核心/管理员）**用"IdP 组 + 应用内角色"完全够**。
引入策略引擎意味着多一个常驻服务、多一套策略语言、多一处故障点——
**这是典型的过度设计**。触发条件应该是「出现"按项目 × 按密级 × 按时间"这类三维规则」，
而不是"OpenFGA 看起来很好"。

### 4.4 分级权限模型（L4）——**三层组合，缺一会出漏洞**

| 层 | 落在哪 | 管什么 | 例子 |
| --- | --- | --- | --- |
| **身份层** | IdP 的**组** | 这个人**属于哪一类** | `livefab/core` |
| **应用层** | 各件内部的**角色** | 在这个件里**能做什么** | 论坛版主、Git 写权限 |
| **信息层** | 文档/内容的**密级标记** | 这份东西**给谁看** | 「内部设计稿」标为「核心」 |

**五级定义**：

| 级别 | 谁 | 典型可见 |
| --- | --- | --- |
| **公开** | 任何人（含未登录） | 官网、博客、公开路线图 |
| **注册用户** | 登录的用户 | 论坛、工单进度、投票 |
| **协作者** | 外部/兼职协作者 | 被指派项目的议题与文档 |
| **核心** | 团队核心 | 全项目看板、内部设计稿 |
| **管理员** | 你 | 全部 + 权限配置本身 |

> **为什么必须三层**：IdP 的组只能表达"你是哪类人"，表达不了"这份文档给谁看"；
> 应用内角色只管本应用。**缺了信息层，就会出现"组配对了、但文档没标密级 → 谁都看得到"。**

## 五、推荐组合（可直接作为 M0/M1 的候选清单）

### 5.1 M1 要接的件（对应 [03 §二](03_分阶段落地路线.md) 的范围）

| 位 | 选型 | 为什么是它 |
| --- | --- | --- |
| 反代 + 前置鉴权 | **Caddy + Authelia** | Authelia 是核查中唯一"OpenID 官方认证 + 轻量"的鉴权件；Caddy 自动 HTTPS、Caddyfile 最简 |
| 统一身份 | **Authelia**（管理能力不足时再升 Keycloak） | 见 §4.2 的取舍 |
| 门户 | **自研薄层**（Nuxt，复用《未来档案》的设计 token 与闸门思路） | 唯一没有合适开源件的东西（L11） |
| 前台件 | **Payload CMS** | MIT + 社区最大；认下"自建 OIDC 需开发"这个代价 |
| 沟通件 | **Discourse**（公开社区）或 **HumHub**（内部网络） | **用途决定**，见 §2.3 |
| 备份 | **Restic** + rest-server | BSD-2、原生对象存储、最稳 |
| 可观测 | **Uptime Kuma**（先）→ **Grafana 栈**（后） | 先知道"谁挂了"，再谈观测深度 |

### 5.2 明确推迟的

| 推迟项 | 触发条件 |
| --- | --- |
| 电商（Saleor/Spree） | 确认要卖东西 |
| 研发管理（Forgejo/Woodpecker/Vikunja/BookStack/Penpot/Harbor） | [03 §二](03_分阶段落地路线.md) 的 M3 门槛：外部协作者权限不够 **或** CI 产生真实成本 |
| 授权引擎（OpenFGA） | 出现"项目 × 密级 × 时间"的三维规则 |
| Vault/OpenBao | 出现动态密钥或审计要求（先 SOPS） |
| IM（Rocket.Chat） | 有明确的、自建才能满足的理由（否则去用户在的地方） |
| 邮件自营投递 | 群发量或送达率成为问题 |

### 5.3 ⚠️ 数据缺失、不能据此决策的三类

**反馈投票、状态页、邮件送达**这三个子类在本次核查中**整体缺失数据**
（见 [research §5.1](research/01_开源件事实核查.md)）。
它们**不影响 M1 范围**（都是 M2 的事），但**届时需要单独补一轮核查**再定。
