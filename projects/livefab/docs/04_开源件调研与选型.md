## 一、评价标准（先定尺子，再量东西）

每个候选都按这**七条**评估。前两条是**否决项**，不满足直接淘汰：

| # | 维度 | 为什么 | 否决条件 |
| --- | --- | --- | --- |
| 1 | **支持 OIDC** | 它是统一身份的前提（[02 §三](02_整体架构方案.md)） | 不支持且无成熟桥接 → 淘汰 |
| 2 | **许可证可接受** | AGPL/BSL/SSPL 会影响将来的自研与商业化路径 | 许可证与用途冲突 → 淘汰 |
| 3 | **可完全自托管** | LiveFab 的定位是自持数据 | — |
| 4 | **资源占用** | 决定单机能不能跑全（[02 §五](02_整体架构方案.md)） | 超出预算上限 → 降级 |
| 5 | **中文可用** | 团队日常使用体验；论坛还要考虑中文搜索/分词 | — |
| 6 | **维护活跃度** | 停止维护的件是负债 | 已归档/长期无提交 → 淘汰 |
| 7 | **数据可导出** | 避免"用得越久越换不动" | 无导出路径 → 降级 |

**另加一条元标准**：**这个件是"我们真的需要"还是"看起来很全所以想装"**。
本方案只放**当前有明确用途**的件，不做"以后可能用得上"的囤积。

## 二、A 段 · 前台运营展示

**要覆盖**：官网/落地页构建、内容管理与编辑体验、商品/支付与订单、营销与增长
（邮件列表/表单/分析）、SEO 与社媒分享、前台侧评论互动。

**已知的强约束**：编辑者可能不是技术人员（你 + AI），所以**可视化编辑与预览**是重要权重；
且这一段的产物**要能对外见人**，因此可用性与中文体验优先于功能深度。

**候选方向（待核实后填具体件与数据）**：

| 子能力 | 候选方向 | 备注 |
| --- | --- | --- |
| 站点构建 | 静态站点生成 + 现有 Nuxt 栈复用 | 官网可直接延续《未来档案》的技术栈，减少新学成本 |
| 内容管理 | 无头 CMS（自托管类） | 重点比：非技术编辑体验、预览、草稿流、许可证 |
| 商品/支付 | 电商引擎（自托管类） | **最重的一段**，资源占用与许可证都要看清 |
| 营销 | Newsletter / 表单 / 隐私友好分析 | 邮件送达是长期易踩坑处（IP 声誉） |

> **一个前置判断**：**要不要真的卖东西？**
> 若 LiveFab 现阶段只是"展示 + 沟通"，**电商引擎应当整段推迟**——
> 它是最重、坑最多、且没有它也能运转的一段。

## 三、B 段 · 用户沟通与社区

**要覆盖**：客服工单、在线客服、社区论坛、IM 社群、公告与状态页、反馈投票。

**已知的强约束**：

- **论坛与 IM 是吃内存大户**，且论坛还要单独解决**中文搜索**；
- **境内可达性**：现有方案（Giscus）依赖 GitHub，这是它最大的风险；
  若不满意，本段的自建件正好替掉它（这是 B 段最明确的收益）；
- **反垃圾**是论坛类件的长期负担，选型时要看有没有成熟机制，而不是事后打补丁。

| 子能力 | 候选方向 | 备注 |
| --- | --- | --- |
| 工单/客服 | 自托管工单系统 | 看：多渠道接入、SLA、邮件管道 |
| 论坛 | 自托管论坛 | 重点比：**资源占用**、中文搜索、OIDC、治理模式 |
| IM 社群 | 自托管 IM | 看：是否值得自建（用户可能已在别处） |
| 状态与公告 | 状态页 + 更新日志 | 轻量，容易先上 |
| 反馈投票 | Feature request / 路线图公开投票 | 与 [mainline](../../mainline/README.md) 的路线图可对接 |

> **一个诚实提醒**：**IM 社群很可能不该自建**。
> 用户已经在哪里聊天，就该去哪里；自建 IM 常常变成"只有你自己在里面"。
> 这一项要单独决策，不要因为"开源有"就装。

## 四、C 段 · 后台研发管理

**要覆盖**：代码托管 + Review + CI/CD、议题/看板/迭代、文档与知识协作、
设计资产与评审、制品与发布。

**已知的强约束**：

- **我们当前在 GitHub，迁移收益最低、风险最高**（[03 §二](03_分阶段落地路线.md) M3 已经把它排到最后）；
- 迁移的**唯一正当理由**是：GitHub 的权限粒度或成本满足不了需求（如拉外部协作者）。
- **重型 GitLab 与轻量 Gitea/Forgejo 系的资源差距是数量级的**——这是选型关键，
  也是"为什么不能无脑上 GitLab"的答案。

| 子能力 | 候选方向 | 备注 |
| --- | --- | --- |
| 代码托管 | 轻量自托管 vs 重量级全家桶 | 核心权衡：功能完整 vs 资源占用 |
| CI/CD | 独立 CI（与托管解耦） | 与上一条解耦选型，可单独替换 |
| 看板/迭代 | 自托管项目管理 | 看：是否支持跨项目视图、与 Issue 的联动 |
| 文档协作 | 自托管 Wiki / 协作文档 | 与 D 段的**密级**能力直接相关，要一起看 |
| 设计资产 | 开源设计工具 | 看：成熟度、文件兼容、自托管成本 |

> **M3 的门槛**（写死在这里，避免将来忘了为什么拖）：
> 只有当「外部协作者需要访问但 GitHub 权限不够」**或**「CI 用量产生真实成本」时，
> 才启动 C 段迁移。

## 五、D 段 · 身份、权限与分级信息（含横切）

**要覆盖**：统一身份与 SSO、分级权限模型、密钥管理、分级信息管理、
备份与灾备、可观测性与告警、反向代理与网关。

**这是本方案唯一"必须先做"的一段**（L3）。逐一说明：

| 子能力 | 关键权衡 | 备注 |
| --- | --- | --- |
| IdP / SSO | **资源占用 vs 配置复杂度**是主要分野 | 有的实现很全但吃内存，有的轻但生态薄 |
| 授权引擎 | 是否需要"策略即代码" | 若五级 + 少量例外够用，**应用内角色就够，不必上策略引擎** |
| 密钥管理 | 是否引入独立件，还是先用主机级方案 | **过早上密钥管理系统是典型过度设计** |
| 分级信息 | **文档系统的原生密级能力 vs 外围兜底** | 见下面的模型 |
| 反向代理 | **能否做前置鉴权**（未登录者在网关就被挡） | 这是安全边界，不是可选 |
| 备份 | **必须自带恢复演练** | 见 [02 §四](02_整体架构方案.md)：未经验证的备份等于没有备份 |
| 可观测 | 资源占用 vs 观测深度 | 小站先要"知道谁挂了"，不需要全套 APM |

### 5.1 分级权限模型（L4 的推荐）

推荐**五级**，并用**三层组合**落地：

| 级别 | 谁 | 典型可见内容 |
| --- | --- | --- |
| **公开** | 任何人（含未登录） | 官网、博客、公开路线图 |
| **注册用户** | 登录的用户 | 论坛、工单进度、投票 |
| **协作者** | 外部/兼职协作者 | 被指派项目的议题与文档 |
| **核心** | 团队核心 | 全项目看板、内部设计稿、财务摘要 |
| **管理员** | 你 | 全部 + 权限配置本身 |

**三层组合**（关键在"不要只靠一层"）：

| 层 | 在哪 | 管什么 | 例子 |
| --- | --- | --- | --- |
| **身份层** | IdP 的**组** | 这个人**属于哪一类** | `livefab/core` 组 |
| **应用层** | 各件内部的**角色** | 在这个件里**能做什么** | 论坛版主、Git 写权限 |
| **信息层** | 文档/内容的**密级标记** | 这份东西**给谁看** | "内部设计稿"标记为「核心」 |

> **为什么必须三层**：IdP 的组只能表达"你是哪类人"，表达不了"这份文档给谁看"；
> 应用内角色只能管本应用，跨系统的信息分级要落在**内容自身**上。
> **三层缺一，就会出现"组对了但文档没标密级 → 谁都看得到"这类漏洞。**

**明确不推荐**：现在就上策略引擎（如策略即代码类）。
五级 + 少量例外，用"组 + 角色"完全够；**等出现"按项目 × 按密级 × 按时间"这类复杂规则再引入**。

## 六、推荐组合（待数据补齐后定稿）

**当前只能给出"形态"层面的推荐**（已可决策）：

1. **IdP 先立**，且**选资源占用可接受的那个**（这一条会直接约束候选）；
2. **A 段先只上"站点 + CMS"**，电商整段推迟到确认要卖东西；
3. **B 段先上一个沟通件 + 状态页**；论坛与 Giscus 二选一（境内可达性是决定因素）；
4. **IM 不自建**（除非有明确的、自建才能满足的理由）；
5. **C 段整段推迟**，直到 M3 门槛达到；
6. **D 段的四件横切件（反代/IdP/备份/可观测）必须随 M1 一起上**——它们是地基，不是插件。
