# 01 · 定位与角色

> 用途＝LiveFab 是什么、不是什么、它在这个工作区里站什么位置 ｜ 依赖：[00 决策总表](00_决策总表.md) ｜ 状态：草案 v0.1 · 2026-10-03

## 一、一句话定位

**LiveFab 是一个"前店后厂"的在线工作室底座**：对外它是门面与柜台（展示、沟通、服务），
对内它是车间与档案室（研发、协作、分级信息）。它不是一个产品，而是**运转这个工作室的那套系统**。

| 面 | 面向谁 | 干什么 | 本方案里的段 |
| --- | --- | --- | --- |
| **店（前台）** | 用户 / 访客 / 玩家 | 运营展示、内容发布、商品与订单、Newsletter、品牌门面 | [A 段](04_开源件调研与选型.md) |
| **柜台（沟通）** | 用户 / 玩家 / 合作方 | 客服工单、社区论坛、IM 社群、反馈投票、公告与状态 | [B 段](04_开源件调研与选型.md) |
| **厂（后台）** | 团队自己 | 代码托管、CI/CD、看板与迭代、文档协作、设计资产 | [C 段](04_开源件调研与选型.md) |
| **档案室（横切）** | 按级别授权的人 | 统一身份、分级权限、密钥、备份、可观测性 | [D 段](04_开源件调研与选型.md) |

> **"前店后厂"的关键含义**：店与厂**不是两个系统**，而是同一套系统的两个面。
> 用户在店里看到的版本更新，背后就是厂里的某个里程碑；用户在柜台提的需求，应该能变成厂里的议题。
> **这一条决定了架构不能是"随便拼一堆工具"**——见 [02 §二](02_整体架构方案.md) 的 L2。

## 二、LiveFab 不是什么（先把边界划清）

| 不是 | 为什么重要 |
| --- | --- |
| **不是《未来档案》的替代或合并** | 网站是"给读者看的复古未来主义知识库"；LiveFab 是"运转工作室的管理底座"。两者**用户与目的都不同**，只共享设计语言与部分技术栈 |
| **不是主线游戏的一部分** | 主线项目在 [`../../mainline/`](../../mainline/README.md) 与 [`../../future-debris/`](../../future-debris/README.md)。LiveFab 是**所有项目的公共底座**，包括但不限于主线 |
| **不是 SaaS 产品**（现阶段） | 它是**自用**的工作室系统。将来若对外提供，那是另一个决策 |
| **不是一个"大而全的自研平台"** | 你已明确"先整合成熟开源项目"。本方案**零自研业务功能**（L11） |
| **不是论坛或 CMS 本身** | 那些是它**集成的件**，不是它 |

## 三、L1：放在哪、是不是独立仓库

**推荐：`projects/livefab/` 单目录起步，暂不建独立仓库。**

理由：

1. **现在只有文档、没有代码**——先建独立仓库会让"读文档"和"读代码"分家，反而增加成本；
2. 工作区已有先例：[`../../mainline/`](../../mainline/README.md) 就是"纯策划与决策空间"，
   立项后才把实现落到 `../<项目代号>/`。LiveFab 可以照此办理；
3. **何时该迁到 [`../../../indie/`](../../../indie/README.md)**（那里放独立仓库、根 `.gitignore` 忽略）：
   - 当它**开始有代码**且希望独立发布节奏时；
   - 或当它有**独立的协作者**、不适合让所有人拿到全部工作区历史时；
   - 或当它需要**自己的 CI/密钥**时。

> **我倾向的落点判断**：LiveFab 虽然被你说成"独立项目"，但它与工作区**主题相关、且是这里的底座**，
> 所以我建议放 `projects/`（受根规则约束，链接与提交都要过闸门），
> 而不是 `indie/`（豁免根规则）。**如果你要的是"完全独立、不受工作区规则约束"，那应放 `indie/`**——
> 这是一个需要你明确的点，见待澄清问题。

## 四、与工作区既有资产的关系（L9 的展开）

| 既有资产 | 复用什么 | **不复用**什么 |
| --- | --- | --- |
| [《未来档案》](../../website/README.md) | 设计 token 与主题 CSS 思路、**对比度闸门**（27 组合断言 + 视觉层级守卫）、验收编排器的思路（一条命令跑全套）、`resolveSiteUrl` 这类小工具的思路 | **内容管线**（`sync-content` 是给 `doc/` 知识库用的，LiveFab 没有这种内容源）；Giscus 讨论区（LiveFab 的社区是自建论坛，见 B 段） |
| [refu-game-001](../../refu-game-001/README.md) | **工程分层纪律**（`core/` 纯逻辑不依赖渲染）、四道验收闸门、文件预算意识 | 游戏相关的任何数据表与规则 |
| [mainline](../../mainline/README.md) 的提案体例 | **"一条建议一个文件 + 决策总表 + 讨论记录 + 不回删原文"**的协作方式——本方案就照这个体例写 | 游戏业务内容 |

> **一句话原则**：**复用"怎么做事"的纪律，不复用"做什么事"的内容。**

## 五、待澄清问题（影响 L1 与范围）

1. **"整个光谱"的边界**：你列了"前台运营 / 用户沟通 / 后台研发 / 分级信息"四类。
   是否还包含**财务、合同、人事、法务**这类企业职能？若包含，方案要扩，且选型逻辑不同（那些领域开源件更少）。
2. **使用者规模**：只有你（+AI）？还是未来会拉进外部协作者/兼职？
   这直接决定要不要现在就上 IdP（L3）——单人自用的话 IdP 可能是过度设计。
3. **是否要"对外可见"**：LiveFab 的门户是**只有团队能访问**，还是**用户也要登录进来看东西**（如项目看板公开、路线图投票）？
   这决定门户是"内网后台"还是"对外的第二张脸"。
4. **放 `projects/` 还是 `indie/`**（见 §三）。
