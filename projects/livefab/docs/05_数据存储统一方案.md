# 05 · 数据存储统一方案

> 用途＝现在到底用了几个数据库、能不能合并、代价是什么 ｜ 依赖：[00 决策总表](00_决策总表.md) L8、[04 选型](04_开源件调研与选型.md) ｜ 状态：**待裁决（L12）** · 2026-10-03
> 本文所有内存数字来自 `docker stats` **实测**（M0 骨架空载状态），非官方文档估算。

## 一、现状：三个数据库容器，两个引擎

| 容器 | 引擎 | 谁的 | 实测空载内存 |
| --- | --- | --- | ---: |
| `authelia-db` | **PostgreSQL 16** | Authelia（会话、双因素状态） | 26 MiB |
| `nodebb-db` | **PostgreSQL 16** | NodeBB（论坛数据） | 27 MiB |
| `ghost-db` | **MySQL 8.4** | Ghost（内容、会员） | **469 MiB** |

**全套空载合计约 971 MiB**，其中 MySQL 一家占 **48%**。

## 二、为什么不能"全都用一个库"——三个件的硬约束

这是本节最重要的事实。三个件的数据库支持**不是任意可选的**：

| 件 | 支持的数据库 | 依据（已核实） |
| --- | --- | --- |
| **Ghost** | **MySQL 8 / SQLite** —— ⚠️ **不支持 PostgreSQL** | Ghost 官方有专门的变更记录 *"Dropping Support for PostgreSQL"*；镜像内只装了 `mysql2` 与 `sqlite3` 驱动 |
| **NodeBB** | **MongoDB / PostgreSQL / Redis** —— ⚠️ **不支持 MySQL** | 镜像内 `src/database/` 只有 `mongo/`、`postgres/`、`redis/` 三个目录 |
| **Authelia** | **PostgreSQL / MySQL / MariaDB / SQLite** —— 都可 | 用真实 Authelia v4.39.28 校验 `storage.mysql` 配置 → `parsed and loaded successfully` |

> **结论：Ghost 与 NodeBB 的数据库集合是"互斥"的。**
> Ghost 要 MySQL（或 SQLite），NodeBB 要 PostgreSQL（或 Mongo/Redis），
> **两者没有交集**。所以"全部并到一个引擎"在这三个件上**做不到**。
>
> **能动的只有 Authelia**——它两边都能去，于是决定权在"把它放哪边"。

## 三、四个可选方案（含实测/估算收益）

### 方案 A：合并两个 PostgreSQL（**低风险，推荐先做**）

一个 PostgreSQL 实例，建两个库（`authelia` + `nodebb`）。Ghost 继续用 MySQL。

| 项 | 值 |
| --- | --- |
| 引擎数 | 3 → **2** |
| 容器数 | 8 → **7** |
| 省内存 | **约 26 MiB**（一个空载 PG 实例） |
| 风险 | **低**。同引擎多库是标准做法；两库互不干涉 |
| 代价 | 一处故障影响两个件（Authelia 挂了 → 登录不可用；NodeBB 挂了 → 论坛不可用，但**互不拖累**，只是同容器） |

> **诚实说明**：这个方案**省得不多**（26 MiB）。它的价值主要在**少一个容器要备份、要升级、要监控**，
> 而不是省内存。如果你的动机是省资源，看方案 B。

### 方案 B：Ghost 改用 SQLite，干掉 MySQL（**省最多，但有取舍**）

Ghost 支持 SQLite，此时 **MySQL 容器整个消失**。

| 项 | 值 |
| --- | --- |
| 引擎数 | 3 → **1**（只剩 PostgreSQL） |
| 容器数 | 8 → **6** |
| 省内存 | **约 469 MiB（占总量 48%）** |
| 风险 | **中**。SQLite 是文件库：单写者、无网络并发；Ghost 官方的**生产默认是 MySQL**，SQLite 被视为"小型站点可行"而非推荐配置 |
| 代价 | ① 并发写能力弱（对小型博客站通常够）；② **备份策略要改**（从"导出数据库"变成"备份文件"，且必须处理写锁）；③ 将来流量上来要迁回 MySQL（有官方迁移路径但非零成本） |

> **判断**：如果你的前台是"**工作室官网 + 博客，访客量不大**"，SQLite **很可能够用**，
> 而且省下的是**全套内存的一半**。这是唯一一个"省得动"的杠杆。
> 若预期有较多会员并发登录/评论，则不要走这条路。

### 方案 C：保持现状（3 个数据库容器）

| 项 | 值 |
| --- | --- |
| 引擎数 | 3 |
| 省内存 | 0 |
| 风险 | **最低**（三者完全隔离，一个坏了不影响另两个） |
| 代价 | 三个库都要备份、升级、监控；空载多花约 495 MiB |

### 方案 D：全都放 MySQL —— ❌ **做不到**

NodeBB 不支持 MySQL（见 §二）。**此方案不可行**，列出仅为说明"为什么不能一步到位"。

### 方案 E（附加，可与上面任意组合）：把 MySQL 内存调小

MySQL 8 默认给自己配了不少缓冲。空载 469 MiB 里有相当部分是 `performance_schema` 与各类 buffer。

可调项示例（**需实测验证，我给的是待验证方向**）：
- `--performance-schema=OFF`（多数自托管场景不需要它）
- `--innodb-buffer-pool-size=128M`（默认通常已是 128M，但可显式压低）
- `--innodb-log-buffer-size`、连接数上限等

> **这是"不改架构就能省内存"的路子**，适合"想保留 MySQL 但嫌它胖"的情况。
> 我没有实测过调优后的数字，**不敢给具体承诺**——需要真跑一次 `docker stats` 对比。

## 四、我的建议

**分两步，而且第一步与第二步可以独立决定：**

1. **先做方案 A**（合并两个 PostgreSQL）。
   理由：风险低、是标准做法、少一个容器要维护。**但要知道它只省约 26 MiB**——
   如果你的目标是省资源，别指望它。

2. **再决定方案 B 或 E**（Ghost 这块才是内存大头，469 MiB）：
   - 若你能接受"小型站 + SQLite"→ **方案 B**，一步省掉近一半内存；
   - 若你要保留 MySQL 的并发与成熟度 → **方案 E**，试着调小它的内存；
   - 若你都不确定 → **先按方案 A 合并 PG，MySQL 保持默认，等有真实流量数据再定**。

> **我倾向的建议**：**A + E**。
> 理由：A 是稳的、E 是可逆的（改参数即可回退），
> 而 **B 会改变 Ghost 的存储形态并牵动备份策略**——那是个应该等"确实需要省这 469 MiB"时再做的决定。

## 五、这项决策与既有决策的关系

- **不改 [L8](00_决策总表.md)**（单机 Docker Compose，按需加机器）——本方案是 L8 内部的细化；
- **与 [L5](00_决策总表.md)（选 Ghost）绑定**：Ghost 的数据库限制是它带来的，换件会重置这个约束；
- **与 [04 §4.4 的三层权限模型](04_开源件调研与选型.md)无关**：数据库合并不影响身份/角色/密级三层。

## 六、需要你裁决的（L12）

| 选项 | 一句话 |
| --- | --- |
| **L12-A**（推荐先做） | 合并两个 PostgreSQL 为一个实例（两个库）；Ghost 仍用 MySQL |
| **L12-B** | 在 A 之上，Ghost 改用 SQLite → **干掉 MySQL 容器，省约 469 MiB** |
| **L12-C** | 保持三个数据库容器（最大隔离） |
| **L12-D** | 先做 A，并尝试调小 MySQL 内存（方案 E），实测后再定要不要 B |

**你可以只答一个字母**（例如"L12-A"或"L12-D"）。
