# 05 · 数据存储统一方案

> 用途＝现在到底用了几个数据库、能不能合并、代价是什么 ｜ 依赖：[00 决策总表](00_决策总表.md) L8、[04 选型](04_开源件调研与选型.md) ｜ 状态：**已裁决（L12 = A+E）并实施验证** · 2026-10-03
> 本文所有内存数字来自 `docker stats` **实测**（M0 骨架空载状态），非官方文档估算。

## 一、现状：三个数据库容器，两个引擎

| 容器 | 引擎 | 谁的 | 实测空载内存 |
| --- | --- | --- | ---: |
| `authelia-db` | **PostgreSQL 16** | Authelia（会话、双因素状态） | 26 MiB |
| `nodebb-db` | **PostgreSQL 16** | NodeBB（论坛数据） | 27 MiB |
| `ghost-db` | **MySQL 8.4** | Ghost（内容、会员） | **469 MiB** |

**全套空载合计约 971 MiB**，其中 MySQL 一家占 **48%**。

## 二、为什么不能"全都用一个库"——三个件的硬约束

这是本节最重要的事实。三个件的数据库支持**不是任意可选的**：

| 件 | 支持的数据库 | 依据（已核实） |
| --- | --- | --- |
| **Ghost** | **MySQL 8 / SQLite** —— ⚠️ **不支持 PostgreSQL** | Ghost 官方有专门的变更记录 *"Dropping Support for PostgreSQL"*；镜像内只装了 `mysql2` 与 `sqlite3` 驱动 |
| **NodeBB** | **MongoDB / PostgreSQL / Redis** —— ⚠️ **不支持 MySQL** | 镜像内 `src/database/` 只有 `mongo/`、`postgres/`、`redis/` 三个目录 |
| **Authelia** | **PostgreSQL / MySQL / MariaDB / SQLite** —— 都可 | 用真实 Authelia v4.39.28 校验 `storage.mysql` 配置 → `parsed and loaded successfully` |

> **结论：Ghost 与 NodeBB 的数据库集合是"互斥"的。**
> Ghost 要 MySQL（或 SQLite），NodeBB 要 PostgreSQL（或 Mongo/Redis），
> **两者没有交集**。所以"全部并到一个引擎"在这三个件上**做不到**。
>
> **能动的只有 Authelia**——它两边都能去，于是决定权在"把它放哪边"。

## 三、四个可选方案（含实测/估算收益）

### 方案 A：合并两个 PostgreSQL（**低风险，推荐先做**）

一个 PostgreSQL 实例，建两个库（`authelia` + `nodebb`）。Ghost 继续用 MySQL。

| 项 | 值 |
| --- | --- |
| 引擎数 | 3 → **2** |
| 容器数 | 8 → **7** |
| 省内存 | **约 26 MiB**（一个空载 PG 实例） |
| 风险 | **低**。同引擎多库是标准做法；两库互不干涉 |
| 代价 | 一处故障影响两个件（Authelia 挂了 → 登录不可用；NodeBB 挂了 → 论坛不可用，但**互不拖累**，只是同容器） |

> **诚实说明**：这个方案**省得不多**（26 MiB）。它的价值主要在**少一个容器要备份、要升级、要监控**，
> 而不是省内存。如果你的动机是省资源，看方案 B。

### 方案 B：Ghost 改用 SQLite，干掉 MySQL（**省最多，但有取舍**）

Ghost 支持 SQLite，此时 **MySQL 容器整个消失**。

| 项 | 值 |
| --- | --- |
| 引擎数 | 3 → **1**（只剩 PostgreSQL） |
| 容器数 | 8 → **6** |
| 省内存 | **约 469 MiB（占总量 48%）** |
| 风险 | **中**。SQLite 是文件库：单写者、无网络并发；Ghost 官方的**生产默认是 MySQL**，SQLite 被视为"小型站点可行"而非推荐配置 |
| 代价 | ① 并发写能力弱（对小型博客站通常够）；② **备份策略要改**（从"导出数据库"变成"备份文件"，且必须处理写锁）；③ 将来流量上来要迁回 MySQL（有官方迁移路径但非零成本） |

> **判断**：如果你的前台是"**工作室官网 + 博客，访客量不大**"，SQLite **很可能够用**，
> 而且省下的是**全套内存的一半**。这是唯一一个"省得动"的杠杆。
> 若预期有较多会员并发登录/评论，则不要走这条路。

### 方案 C：保持现状（3 个数据库容器）

| 项 | 值 |
| --- | --- |
| 引擎数 | 3 |
| 省内存 | 0 |
| 风险 | **最低**（三者完全隔离，一个坏了不影响另两个） |
| 代价 | 三个库都要备份、升级、监控；空载多花约 495 MiB |

### 方案 D：全都放 MySQL —— ❌ **做不到**

NodeBB 不支持 MySQL（见 §二）。**此方案不可行**，列出仅为说明"为什么不能一步到位"。

### 方案 E（附加，可与上面任意组合）：把 MySQL 内存调小

MySQL 8 默认给自己配了不少缓冲。空载 469 MiB 里有相当部分是 `performance_schema` 与各类 buffer。

可调项示例（**需实测验证，我给的是待验证方向**）：
- `--performance-schema=OFF`（多数自托管场景不需要它）
- `--innodb-buffer-pool-size=128M`（默认通常已是 128M，但可显式压低）
- `--innodb-log-buffer-size`、连接数上限等

> **这是"不改架构就能省内存"的路子**，适合"想保留 MySQL 但嫌它胖"的情况。
> 我没有实测过调优后的数字，**不敢给具体承诺**——需要真跑一次 `docker stats` 对比。

## 三·补、实施结果（**用户裁决 A+E，已实施并实测**）

### A：两个 PostgreSQL 已合并为一个实例

一个 `db` 容器（PostgreSQL 16）承载两个独立库与两个独立用户：

| 库 | 用户 | 用途 |
| --- | --- | --- |
| `authelia` | `authelia` | Authelia 会话 / 双因素状态 |
| `nodebb` | `nodebb` | NodeBB 论坛数据 |

第二个库由 [`deploy/postgres/init/01-create-nodebb.sh`](../deploy/postgres/init/01-create-nodebb.sh)
在**首次初始化**时创建（官方镜像的 `POSTGRES_DB` 只能建一个库——这是必须自己写脚本的原因）。

**实测收益与我原先的估计有出入，如实修正**：

| 项 | 我原先估的 | **实测** |
| --- | --- | --- |
| 省内存 | "约 26 MiB" | **约 15 MiB**（合并前两实例 26+27=53 MiB → 合并后 38 MiB） |
| 少容器 | — | **8 → 7 个** |

> **修正说明**：我原先按"一个空载 PG 实例 26 MiB"外推，但**一个 PG 同时服务两个库，
> 并不会比服务一个库省下整个实例的开销**——共享的是进程，省下的是那份重复的基线内存。
> 所以方案 A 的真实价值主要在**少一个容器要备份/升级/监控**，而不是省内存。**我估高了，这里更正。**

### E：MySQL 内存调优（**这才是省得动的地方**）

依据实测基线定位可压项：`innodb_log_buffer_size` 竟高达 **64 MiB**（MySQL 默认 16 MiB），
且 `performance_schema` 开着。加入 `deploy/compose.yml` 的参数：

| 参数 | 前 | 后 | 依据 |
| --- | --- | --- | --- |
| `performance_schema` | ON | **OFF** | 自托管小站用不到它的性能诊断，而它自己要占几十 MB |
| `innodb_log_buffer_size` | 64M | **16M** | 回到官方默认值（原本异常偏大） |
| `max_connections` | 151 | **50** | 每连接都有独占缓冲 |
| `table_open_cache` | 4000 | **400** | 这个体量下毫无必要 |
| `innodb_buffer_pool_size` | 128M | **128M（刻意不动）** | ⚠️ 它是**真实性能关键**，压它会让查询变慢，**不属于"白省的内存"** |

**实测结果**（连采 5 次取范围，非单次快照）：

| 项 | 调优前 | 调优后 |
| --- | --- | --- |
| MySQL 容器 | **469–478 MiB** | **171–190 MiB** |
| 省下 | — | **约 290–300 MiB** |

**这是干净的同类对比**（同一个容器、同一个负载状态）。

**全套合计**：约 971 MiB → **约 705 MiB**。
> 但要说清：这不是纯收益的对比——期间 **Ghost 与 Authelia 自己也涨了**
> （Ghost 88→155、Authelia 65→81 MiB，因为栈运行久了、状态更多）。
> 所以**只有 MySQL 那一行是可靠结论**，合计数字仅供量级参考。

### 验证

实施后重跑两项验收，**均通过**：
- `bun run tools/verify-stack.ts` → **7/7**（鉴权分层、Ghost、NodeBB 全部正常）
- `bun run tools/validate-compose.ts` → **41/41**

Ghost 是**读库**验证的：`/rss/` 与 `/sitemap.xml` 都返回 200（这两个页面必须查库才能生成）。

### ⚠️ 顺带发现的一个取舍：隔离网络导致 Ghost 更新检查失败

调优后查看 Ghost 日志，发现它在报：

```
ERROR queryAaaa ESERVFAIL updates.ghost.org
```

**根因**（已实测确认，不是猜测）：

```
ghost 容器（只在 internal 网络）  → 解析 updates.ghost.org 失败：EAI_AGAIN
caddy 容器（有 edge 网络）        → 解析成功
```

即：**`internal: true` 网络阻断了所有出网，这正是我们为隔离刻意设计的**，
而 Ghost 的"检查更新"因此拿不到结果并记一条错误。

**这是真实取舍，不是 bug**：

| 选择 | 得到 | 失去 |
| --- | --- | --- |
| **保持隔离**（当前） | 内部件无法出网 → 攻击面更小、不会意外外泄数据 | Ghost 无法提示更新（日志有噪音） |
| 给 Ghost 单独放行出网 | 能收到更新提示 | **削弱隔离**；且这种"只给一个件开口"的配置日后容易失控 |

**我的建议：保持隔离**。理由：站点功能完全正常（所有页面 200），
而更新提示可以人工查（或将来单独评估）。**没有找到官方"关闭更新检查"的开关**——
检索到的资料多是关于该检查的隐私/数据收集，而非如何禁用；故记录为"未找到，非不存在"。

## 四、我的建议

**分两步，而且第一步与第二步可以独立决定：**

1. **先做方案 A**（合并两个 PostgreSQL）。
   理由：风险低、是标准做法、少一个容器要维护。**但要知道它只省约 26 MiB**——
   如果你的目标是省资源，别指望它。

2. **再决定方案 B 或 E**（Ghost 这块才是内存大头，469 MiB）：
   - 若你能接受"小型站 + SQLite"→ **方案 B**，一步省掉近一半内存；
   - 若你要保留 MySQL 的并发与成熟度 → **方案 E**，试着调小它的内存；
   - 若你都不确定 → **先按方案 A 合并 PG，MySQL 保持默认，等有真实流量数据再定**。

> **我倾向的建议**：**A + E**。
> 理由：A 是稳的、E 是可逆的（改参数即可回退），
> 而 **B 会改变 Ghost 的存储形态并牵动备份策略**——那是个应该等"确实需要省这 469 MiB"时再做的决定。

## 五、这项决策与既有决策的关系

- **不改 [L8](00_决策总表.md)**（单机 Docker Compose，按需加机器）——本方案是 L8 内部的细化；
- **与 [L5](00_决策总表.md)（选 Ghost）绑定**：Ghost 的数据库限制是它带来的，换件会重置这个约束；
- **与 [04 §4.4 的三层权限模型](04_开源件调研与选型.md)无关**：数据库合并不影响身份/角色/密级三层。

## 六、裁决结果（L12 = **A + E**）

用户裁决：**A + E**。已实施并实测（见 [§三·补](#三补实施结果用户裁决-ae已实施并实测)）。

| 项 | 结果 |
| --- | --- |
| 数据库引擎数 | 3 → **2**（PostgreSQL + MySQL） |
| 容器数 | 8 → **7** |
| MySQL 内存 | 478 → **约 180 MiB**（省约 300 MiB） |
| 全套合计 | 约 971 → **约 705 MiB** |
| 未采纳 | 方案 B（Ghost 改 SQLite）——保留为"确需再省内存时的下一步" |
