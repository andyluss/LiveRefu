# 06 · 文件预算与拆分约定

> 卡面：用途＝"一个文件多大算合适"的可执行约定 ｜ 依赖：[工程结构与运行](02_工程结构与运行.md) ｜ 状态：v1.0 · 2026-09-16
> 一句话：**每个 .gd 文件只做一件事**；核心逻辑 ≤50 代码行、界面 ≤100 代码行，由脚本强制，不靠自觉。

## 一、为什么要有这条约定

重构之前，`core/battle.gd` 一个文件 1462 行（1187 行代码）里塞着能量、波次、属性管线、
钩子解释器、羁绊、放置、结算七件事。后果很具体：

- 想改"穿透怎么算"，得在千行文件里翻；想确认"羁绊什么时候触发"，要读完半个文件；
- 两个人同时动战斗逻辑，几乎必然冲突在同一文件；
- 新人（或下一轮 AI）无法"只看一个文件就理解一件事"。

所以定的不是"风格偏好"，而是**可执行的预算 + 一个会失败的检查脚本**。

## 二、预算（决策与口径）

| 层 | 目录 | 代码行 | 物理行 |
| --- | --- | --- | --- |
| 核心逻辑 | `scripts/core/`、`scripts/autoload/`、`scripts/data/`、`scripts/tools/` | **≤50** | ≤100 |
| 界面/表现 | `scripts/app/`、`scripts/view/` | **≤100** | ≤200 |
| 工具脚本 | `tools/*.py`、`*.swift`、`*.sh` | 不在约束内 | —— |

**"代码行"口径**：去掉空行、去掉以 `#` 开头的注释行、去掉三引号块内的行。
于是中文设计注释**不占** 50 行预算（但物理行仍有兜底上限，避免注释淹没代码）。

界面层放宽到 100 的理由：布局与控件装配是"要一眼看到整体"的代码，切碎反而难读；
核心逻辑放宽不了的理由：核心逻辑的每一段都应当能被单独推理与单独测试。

**执行**：`tools/check_file_size.py`（`./run.sh lint`，也已接入 `./run.sh check` 的第一道闸门）。

## 三、怎么拆（四种手法，按优先级）

1. **状态与行为分离**（数据类 → 行为类）
   `battle_state.gd`（字段）/ `battle_api.gd`（只读查询门面）/ `battle.gd`（生命周期与命令）；
   `tower_state.gd` + `tower_unit.gd`、`enemy_state.gd` + `enemy_unit.gd`、`blocker_state.gd` + `blocker_unit.gd`。
   *为什么用继承而不是组合*：GDScript 没有 partial class；把字段搬到基类后，`battle.energy`、
   `tw.hp` 这类**字段直达**的写法一处都不用改，200+ 个调用点零风险。行为侧则一律用**组合**
   （静态系统类），不搞深继承链。链深最多 3 层：`BattleState → BattleApi → Battle`。

2. **按关注点拆系统**（静态类 + 组合）
   `BattleStats`（属性管线）、`BattleEffects`（钩子解释器）、`BattleEnemies`（敌人行为）、
   `BattleWaves`（波次）、`BattlePlacement`（放置）…… 每个系统只被 `BattleLoop` 或门面调用，
   互相之间靠显式调用（`BattleDamage.apply_hit(bt, …)`），没有隐式依赖。

3. **按"一类绘制/一类面板"拆**（表现层）
   `view/battle/` 下六个 painter（底板/塔位/塔/敌人/特效/覆盖层）+ 一个只读上下文；
   `app/battle/` 下若干面板（HUD/手牌/波次预告/底栏/弹窗/结算）。

4. **按"一个用例一段"拆**（工具）
   无头验收拆成 `sim_suites*.gd`（用例）+ `sim_driver.gd`（跑一局）+ `sim_report.gd`（输出）；
   录像拆成 `demo_steps_*.gd`（时间轴）+ `demo_*.gd`（驱动）。

**不做的拆法**：为凑行数把一段连贯算法切成 `part1`/`part2`；用继承链当 mixin（深链会把
"这个方法到底在哪"变成翻找游戏）。判断标准是**能不能给新文件起一个准确的职责名**——
起不出来，说明切错了。

## 四、拆完的账（2026-09-16）

| 项 | 重构前 | 重构后 |
| --- | --- | --- |
| .gd 文件数 | 23 | **128** |
| 代码行合计 | 5268 | ≈5400（多出的是文件头与函数签名） |
| 最大文件（代码行） | 1187（`core/battle.gd`） | ≤100（界面层上限） |
| 超预算文件 | 18 | **0** |
| 对外行为 | —— | **不变**：19 项无头验收全过；`view/` 做了逐字节像素对照（SHA256 相同） |

## 五、这条约定怎么维持

- 新增文件前先看本节第三节的四条手法；
- 每个新文件顶部写 3–6 行 `## 用途 / 依赖 / 不变量`（注释不计预算，别省）；
- 提交前 `./run.sh lint`；`./run.sh check` 会先跑它，超预算直接 FAIL；
- 确实需要超预算时**登记例外**（在检查脚本里加白名单 + 写明原因），而不是悄悄放过；
  当前例外：无。

## 六、已知代价

- 文件数从 23 涨到 128，"找一个方法在哪"从"翻一个文件"变成"按职责猜目录"；
  缓解：`docs/07_代码地图.md` 给了"想改 X → 去哪个文件"的对照表；
- 少量转发方法（如 `BattleApi` 的查询转发）是纯样板；
  代价换来的是**对外接口稳定**——界面与验收脚本在这次重构里一行都不用改；
- 核心逻辑的 50 行上限偏严，写新系统时会频繁遇到"再拆一层"；
  这是刻意的：**逼作者在写之前想清楚职责边界**。
