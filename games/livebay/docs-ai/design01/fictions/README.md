# LiveBay 小说集

> 五篇短篇小说，用来把设定变成“可玩的场景”。**人物、事件、对话都是 AI 虚构，不是 canon**；只有每篇末尾的「场景卡」是设计提案。

## 一、这组小说是干什么的

设定文档回答“世界是什么”，数值文档回答“系统怎么跑”，小说回答一个更具体的问题：

> **玩家在这个世界里，具体会经历怎样的一班？**

每篇都按同一个结构写：

1. **一个班次**：时间、岗位、地点、交接；
2. **一个具体的麻烦**：不是“世界危机”，而是“今天这件事怎么处理”；
3. **一个没有完美答案的选择**：每个选项都有代价；
4. **一张场景卡**：把小说里的动词、资源、分支翻译成玩法。

## 三、建议读法

- **先读 01 与 02**：一篇塔防，一篇沉浸，正好对应两个主玩法；
- **再读 03**：它最轻，但最接近「慢好」的日常质感；
- **04 与 05**：两篇都是“专业岗位”的变体，适合做第二、第三职业的参考。

## 四、从小说到场景

每篇末尾的场景卡都按同一组字段写：

| 字段 | 回答什么 |
| --- | --- |
| 玩法形态 | 塔防 / 沉浸 / 放置 / 限时变体 |
| 玩家目标 | 这一班结束时，什么算“扛过去” |
| 核心动词 | 玩家实际按什么键、做什么决定 |
| 可复用系统 | 现有工程里已经有的系统，还是需要新做 |
| 关键选择 | 两到三个都有代价的选项 |
| 分支后果 | 选择如何改变数值、关系或后续事件 |
| 与现有玩法 | 接塔防、沉浸还是放置 |
| 可复用资产 | 场景、角色、UI、文案 |

使用建议：

1. 先选一篇，把「关键选择」做成一个 3 分钟的纸面原型；
2. 只实现一个选择分支，不要一次做全；
3. 如果玩家在纸面上都犹豫，才值得进引擎；
4. 小说里的角色可以改名、改性别、改结局；**不要因为小说写了就把它当 canon**。

## 五、边界

- 小说中的人名、事件、对话、具体数字都是虚构；与 `numbers/` 冲突时，以数值表为准；
- 小说不新增世界观硬设定；需要新增时，先回到 [11_待人类裁决清单](../11_待人类裁决清单.md)；
- 小说里的“系统提示”“广播文案”是 UI/叙事参考，不是最终文本；
- 人类可以否决任何一篇、任何一段，或只取其中一个场景卡。
