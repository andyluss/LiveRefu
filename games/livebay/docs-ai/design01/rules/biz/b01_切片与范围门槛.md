# BIZ-B1 · 切片与范围门槛

> **一句话**：先做 10 分钟垂直切片；任何新功能都要先证明它服务这个切片，否则不做。
> **形式化**：`admit(f) ⇔ serves(f, Slice) ∧ cost(f) ≤ B ∧ reversible(f)`。

## 一、形式化表述

```text
Slice = (1 profession, 1 map, 5 waves, 1 loop)
B = 当前版本的预算（人时 / 内容量 / 风险）
admit(f) ⇔
  serves(f, Slice) ∧
  cost(f) ≤ B ∧
  reversible(f) ∧
  has_acceptance(f)

Scope(t+1) = Scope(t) ∪ {f} 仅当 admit(f) 且 Gate 通过
```

## 二、通俗解释

「这个功能也不错」是项目最常见的死因。切片规则不是反对好想法，而是要求好想法**先排队**：

- 它让 10 分钟更好玩了吗？
- 它能在当前预算内做完吗？
- 它改错了能撤回吗？
- 它有明确的验收方式吗？

四个都答「是」，才进当前版本；否则进 backlog，不偷偷塞进代码。

## 三、条款

### MUST

1. **M1**：v0.1 只承诺「1 职业 / 1 图 / 5 波 / 1 循环」；超出部分默认不做。
2. **M2**：每个新功能必须有：假设、验收、成本、可逆性；缺一项不立项。
3. **M3**：新增职业、地图、玩法模式必须过 Gate，不得在“顺手”中加。
4. **M4**：功能失败时回退，不保留半成品分支。
5. **M5**：范围变化必须记录到 [11_待人类裁决清单](../../11_待人类裁决清单.md)。

### SHOULD

1. **S1**：每个版本只主推一个“新问题”，不同时加职业、地图、玩法。
2. **S2**：先做纸面原型/数据原型，再进引擎。
3. **S3**：把“砍掉什么”写进版本说明，而不只写“加了什么”。

### MAY

1. **Y1**：纯技术债、工具、测试不计入内容范围，但要有预算上限。
2. **Y2**：外观/文案微调可走 c 层快速通道，不占 Gate。

## 四、判定与验收

```text
Gate(f) ⇔
  f.hypothesis ≠ ∅ ∧
  f.acceptance ≠ ∅ ∧
  f.cost ≤ B ∧
  f.reversible = true ∧
  f.serves ∈ {手, 岗位, 故障, 班次}
```

检查：

- [ ] 功能卡是否写清“验证什么”；
- [ ] 是否能在一周内做出可试玩版本；
- [ ] 是否能用一句话说清“不做会怎样”；
- [ ] 是否能回退到上一个版本。

## 五、反例

- 「既然做了护卫兵，顺手把护理师也做了」；
- 「加一个无尽模式吧，反正塔防通用」；
- 「先做联机框架，以后肯定用得上」；
- 「这个系统很酷，虽然和切片无关」。
