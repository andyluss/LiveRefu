# ROOT-B0 · 规则分层与冲突

> **一句话**：规则分三层：a 层是不可轻易改的公理，b 层是结构约束，c 层是表达约束；冲突时 a > b > c。
> **形式化**：`Layer = {a,b,c}`，`stability(a) > stability(b) > stability(c)`；`Conflict ⇒ priority(a) > priority(b) > priority(c)`。

## 一、形式化表述

```text
Rule = (id, layer, category, status, clauses, acceptance)
layer ∈ {a, b, c}
category ∈ {root, biz, design, art, tech}
stability(a) > stability(b) > stability(c)

priority(r) = (is_root(r), layer_rank(r), specificity(r), date(r))
is_root: root = 1, category = 0
layer_rank: a = 3, b = 2, c = 1
```

冲突处理：

```text
conflict(r1, r2) ⇒ choose argmax priority(r)
if priority(r1) = priority(r2) ⇒ stop ∧ ask(Human)
```

## 二、通俗解释

- **a 层**：这个项目为什么存在。比如「玩家是岗位人」「单一数据源」。改它等于换项目，必须人类拍板。
- **b 层**：项目怎么运转。比如「班次循环」「三环三套语法」。可以调，但要评审并同步文档。
- **c 层**：项目长什么样、怎么写。比如色板、命名、引用格式。可以快速改，但要有验收。

规则不是越多越好。**一条规则只有在能被违反、也能被检查时，才值得存在。**

## 三、条款

### MUST

1. **M1**：每条规则必须有唯一 ID，格式 `<CAT>-<LAYER><N>`，如 `DES-B2`。
2. **M2**：规则文件必须放在对应类别目录；文件名以层字母 `a`/`b`/`c` 开头。
3. **M3**：a 层规则修改必须有人类裁决 + 版本升级；b 层需规则评审；c 层需文档更新与验收。
4. **M4**：每条规则必须写「判定与验收」；没有验收方式的规则视为未生效。
5. **M5**：规则冲突按 `root > category`、`a > b > c`、`具体 > 一般`、`新裁决 > 旧裁决` 处理。
6. **M6**：同层同类的两条规则仍冲突时，停止实现，交人类裁决；不得用代码现状反推。

### SHOULD

1. **S1**：规则正文先给形式化，再给通俗解释；形式化是给检查用的，通俗解释是给人用的。
2. **S2**：每条规则至少给一个反例，帮助判断边界。
3. **S3**：规则引用用 ID + 相对链接，不只写文件名。

### MAY

1. **Y1**：c 层规则可以在版本内调整，不必每次走完整裁决。
2. **Y2**：规则可以引用其他规则；被引规则失效时，引用方必须复核。

## 四、判定与验收

```text
valid(rule) ⇔
  unique(id) ∧
  layer(id) = layer(file) ∧
  category(id) = parent_dir(file) ∧
  has_acceptance(rule) ∧
  referenced_in_index(rule)
```

检查清单：

- [ ] ID 唯一且能在 [README](README.md) 找到；
- [ ] 文件名以 a/b/c 开头；
- [ ] 目录与类别一致；
- [ ] 有形式化、通俗解释、MUST 条款、验收、反例；
- [ ] 被至少一个文档或代码引用（或明确标注「待接入」）。

## 五、反例

- 把一条 a 层规则放进 `c` 文件，降低修改门槛；
- 两条规则对同一个问题给出相反要求，却都不标优先级；
- 规则只写「应该做好玩」，没有可判定的验收；
- 规则 ID 重复，引用时指向另一条规则；
- 代码已经违反规则，却把规则改成「代码现状」。
