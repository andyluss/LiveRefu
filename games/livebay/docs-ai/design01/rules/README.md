# LiveBay 规则体系

> 规则不是建议。规则是**项目在压力下仍然不跑偏的约束**：当想法、工期、AI 建议和玩家反馈互相拉扯时，用它们判断「什么不能做」。

## 一、三层模型

| 层 | 文件名前缀 | 名称 | 稳定性 | 改变方式 |
| --- | --- | --- | --- | --- |
| a | `a` | 底层 / 公理 | 高；数月甚至整项目不变 | 人类裁决 + 版本升级 + 说明代价 |
| b | `b` | 中层 / 结构 | 中；版本之间可调 | 规则评审 + 相关文档同步 |
| c | `c` | 表层 / 表达 | 低；可随版本调整 | 直接改，但需通过验收 |

形式化：

```text
stability(a) > stability(b) > stability(c)
change(a) ⇒ HumanDecision ∧ VersionBump
change(b) ⇒ RuleReview ∧ DocSync
change(c) ⇒ DocUpdate ∧ Acceptance
```

通俗地说：**a 层是“这个项目为什么存在”，b 层是“它怎么运转”，c 层是“它长什么样、怎么写”。**

## 二、四大类 + 根规则

| 目录 | 类别 | 管什么 | 规则数 |
| --- | --- | --- | ---: |
| `rules/` | 根 / 跨类 | 人类裁决、规则冲突、文档契约 | 3 |
| `rules/biz/` | 商业 | 商业模式、范围、对外表达 | 3 |
| `rules/design/` | 设计 | 玩家、社会、循环、选择、故障、数值 | 6 |

| `rules/tech/` | 技术 | 数据源、模拟/视图、可逆、验收 | 4 |

不属于这四类的规则，直接放在 `rules/` 下。

## 四、怎么引用规则

在文档、代码、提交信息里引用规则 ID：

```markdown
本关的故障设计遵循 [DES-B3](../rules/design/b03_故障与低报.md)。
```

```gdscript
# 规则：TECH-A2（模拟与视图分离）
```

引用要求：

1. **文档**：在 YAML 的 `rules` 字段列出 ID；正文首次提到时给相对链接；
2. **代码**：在文件头注释写 `规则：ID（名称）`，关键函数可再写一行；
3. **提交**：涉及规则变更时，在提交正文写 `Rules: ID`；
4. **不引用不存在的规则**：规则 ID 必须能在本索引找到。

## 五、规则冲突怎么判

优先级从高到低：

```text
人类概念 > 人类裁决 > 根规则 > 类别规则 > 其他文档 > 代码
```

同一层内：

```text
a > b > c
根 > 类别
具体 > 一般
新裁决 > 旧裁决
```

无法判定时，**停下来问人类**；不要用代码“事实上已经这样”来反推规则。

## 六、验收

- 新增/修改规则：必须能通过 [ROOT-C0](c00_文档与引用契约.md) 的元数据与链接检查；
- 涉及数值：必须通过 `./run.sh numbers-check`；
- 涉及工程：必须通过 `./run.sh test` 与 `./run.sh check`；
- 涉及 HTML：必须通过 `design/tools/check_html_theme.ts`；
- 规则与文档/代码冲突时，先改文档/代码，或按 [ROOT-B0](b00_规则分层与冲突.md) 修订规则。
