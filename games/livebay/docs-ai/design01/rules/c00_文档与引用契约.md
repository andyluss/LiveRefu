# ROOT-C0 · 文档与引用契约

> **一句话**：文档有统一的元数据、命名与引用方式；生成物从源生成，不手改。
> **形式化**：`Doc = (Meta, Body)`，`Meta ⊇ {title, doc_type, status, date, source, authority}`；`Generated = f(Source)`。

## 一、形式化表述

```text
Doc = (Meta, Body)
ReqMeta = {title, doc_type, status, date, source, authority}
RuleDoc = Doc where Meta ⊇ ReqMeta ∪ {rule_id, layer, category}

Citation = ID × RelLink
valid_link(p) = resolve(dir(p), href) exists

Generated(x) ⇔ x = f(Source) for some Source
hand_edit(Generated) ⇒ invalid
```

## 二、通俗解释

一份文档不只是正文。它还需要回答：**这是什么、谁说了算、什么时候写的、由谁写的**。如果这些信息缺失，读者（包括未来的 AI）就会把「参考」当成「决定」。

规则引用也一样：不要只写「按设计规则」，要写 `DES-B2` 并给出链接。这样规则改名或移动时，引用能被检查出来。

## 三、条款

### MUST

1. **M1**：所有 LiveBay 文档以 YAML frontmatter 开头，至少含 `title`、`doc_type`、`status`、`date`、`source`、`authority`。
2. **M2**：规则文档额外含 `rule_id`、`layer`、`category`；`layer` ∈ `{a,b,c}`，`category` ∈ `{root,biz,design,art,tech}`。
3. **M3**：文件名可排序：设计文档用 `NN_主题.md`；规则用 `aNN_主题.md` / `bNN_` / `cNN_`。
4. **M4**：内部链接用相对路径；链接目标必须存在；不得依赖本机绝对路径。
5. **M5**：生成物（HTML、`game/data/*.json`、PNG 设定图）不得手改；改源后重新生成。
6. **M6**：规则引用写 ID + 相对链接；文档 YAML 的 `rules` 字段列出所遵循的规则。

### SHOULD

1. **S1**：正文简体中文；ID、字段名、代码用英文。
2. **S2**：日期取东八区系统时间；不手写「今天」。
3. **S3**：一篇文档一个主题；超过 4000 字考虑拆分。
4. **S4**：文档之间用「上游/关联」链接，不用复制全文。

### MAY

1. **Y1**：非规则文档可以没有 `rules` 字段；但涉及设计决定时 SHOULD 加。
2. **Y2**：概念图、小说等参考物可以在 YAML 标 `status: 非 canon`。

## 四、判定与验收

```text
valid(doc) ⇔
  yaml_parses(doc) ∧
  ReqMeta ⊆ keys(doc) ∧
  all_links_exist(doc) ∧
  (is_rule(doc) ⇒ rule_meta_valid(doc))
```

命令：

```bash
node tools/check_links.ts --files <文档>
ruby -rdate -ryaml -e 'YAML.safe_load(...)'
node design/tools/check_html_theme.ts <页面...>
./run.sh numbers-check
```

## 五、反例

- 文档以引用块开头写元数据，预览时多行被合并（已改为 YAML）；
- 规则文件没有 `rule_id`，只能靠正文猜；
- 链接写 `/games/livebay/...` 或 `/Users/...` 绝对路径；
- 手改 `game/data/towers.json`，下次导出被覆盖；
- 手改 `docs-ai/design01/html/*.html`，下次生成被覆盖。
