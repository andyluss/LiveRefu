# TECH-B1 · 可逆工程

> **一句话**：能改数据就不改结构；每个改动都要能回退，半成品不进主线。
> **形式化**：`prefer(Data) > prefer(Code)`，`change ⇒ ∃rollback`。

## 一、形式化表述

```text
Change = Data ∪ Code
prefer(Data) > prefer(Code)
∀c ∈ Change: ∃r: apply(r, apply(c, S)) = S

content ∈ Data
logic ∈ Code
half_done ∉ main
```

## 二、通俗解释

塔、敌人、波次、地图、经济参数，都是数据；加一座塔、改一波敌人，不应该改代码。代码只负责“怎么跑”，不负责“具体是什么”。

可逆的意思很具体：

- 改坏了能回退；
- 新功能能用开关/数据关掉；
- 半成品不合并进主线；
- 一次只改一个变量，方便定位。

## 三、条款

### MUST

1. **M1**：内容（塔/敌人/波次/地图/经济）必须数据驱动；不得在代码里写 `if id == ...` 配内容。
2. **M2**：每个功能必须能回退：数据回滚、提交回滚或开关关闭。
3. **M3**：不得把半成品、调试代码、临时资源合并进主线。
4. **M4**：一次提交只做一件事；移动/改名与内容改写尽量分开。
5. **M5**：生成物由源生成，不手改（HTML、JSON、PNG）。

### SHOULD

1. **S1**：先用最小数据改动验证，再决定要不要写代码。
2. **S2**：新系统先做“可关闭”的入口。
3. **S3**：提交信息写清“怎么回退”。

### MAY

1. **Y1**：可以保留调试开关，但必须默认关闭并标注。
2. **Y2**：可以保留旧数据字段一个版本，用于兼容。

## 四、判定与验收

```text
valid(change) ⇔
  content_in_data ∧
  rollback_exists ∧
  no_debug_in_main ∧
  one_purpose(commit)
```

检查：

- [ ] 加一座塔，需要改代码吗？
- [ ] 这个改动怎么回退？
- [ ] 有没有调试代码/临时资源？
- [ ] 提交是否只做一件事？

## 五、反例

- 在 `main.gd` 里写死“第 5 波出 4 个重壳”；
- 新玩法没有开关，失败只能删代码；
- 把 `.tmp`、测试截图、调试打印提交进主线；
- 一个提交同时改名、改逻辑、改数值。
