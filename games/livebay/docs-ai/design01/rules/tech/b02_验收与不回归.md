# TECH-B2 · 验收与不回归

> **一句话**：每次非琐碎改动都要跑对应检查；检查失败不静默绕过。
> **形式化**：`Accept = Tests ∧ ExportCheck ∧ HeadlessCheck ∧ LinkCheck ∧ ThemeCheck`。

## 一、形式化表述

```text
Accept(change) ⇔
  tests(change) = PASS ∧
  export_check(change) = PASS ∧
  headless_check(change) = PASS ∧
  link_check(change) = PASS ∧
  theme_check(change) = PASS

fail(any) ⇒ stop ∧ report
```

## 二、通俗解释

“看起来对”不算验收。不同的改动有不同的证据：

- 改玩法/数值：无头测试 + 启动检查；
- 改数值表：导出检查；
- 改文档链接：链接检查；
- 改生成 HTML：三态检查；
- 改美术：尺寸/文件/链接检查。

验收不是给别人看的，是**防止这次改动把上次的东西弄坏**。

## 三、条款

### MUST

1. **M1**：改玩法/模拟，必须跑 `./run.sh test`，全过。
2. **M2**：改数值表/导出，必须跑 `./run.sh numbers-check`。
3. **M3**：改场景/脚本，必须跑 `./run.sh check`，退出码 0。
4. **M4**：改文档链接，必须跑 `tools/check_links.ts`。
5. **M5**：改生成 HTML，必须跑 `design/tools/check_html_theme.ts`，且满足 R-016。
6. **M6**：检查失败必须报告命令、退出码、关键错误；不得用 `--no-verify` 静默绕过。

### SHOULD

1. **S1**：测试数量只增不减；删测试需说明理由。
2. **S2**：修 bug 时先加一个会失败的断言，再修。
3. **S3**：提交信息写清跑了哪些检查。

### MAY

1. **Y1**：纯文案/图片替换可以只跑链接与尺寸检查。
2. **Y2**：紧急修复可先提交，但必须在同一天补检查并记录。

## 四、判定与验收

```text
PASS ⇔
  ./run.sh test            → 37/37
  ./run.sh numbers-check   → 全部一致
  ./run.sh check           → exit 0
  node tools/check_links.ts → 0 broken
  check_html_theme          → all pass
```

> 测试数量随版本增长，以实际输出为准；当前为 37 项。

## 五、反例

- 改了 `sim.gd` 不跑测试，靠手玩两分钟；
- 改了数值表不导出，JSON 还是旧的；
- 链接 404 但“内容没问题”；
- HTML 只有浅色，深色下不可读；
- 检查失败后用 `--no-verify` 强推。
