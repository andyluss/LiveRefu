# 01 · 塔防生存玩法建议

> **一句话**：让自由模式里的塔防从“杀光这一波”变成“**撑到救援/天亮**”：塔要用电，人要呼吸，舱段会漏，故障会蔓延；玩家不是在清屏，而是在分配一座城剩下的资源。
>
> **推荐第一版**：先做 **「低功率夜班」**——不新增敌人种类，只把“电力”变成塔防与生存共享的资源。它最贴近世界观，也最容易在现有 Sim 之外独立实现。

## 一、为什么是生存，而不是另一种塔防

LiveBay 的世界观不是“指挥官消灭敌人”，而是：

- 外环夜班；
- 设备会坏；
- 故障会扩散；
- 城市在资源不足时做取舍；
- 值班人只能撑到交接/救援。

所以生存玩法的核心不是“更多怪”，而是：

```text
有限资源 × 持续压力 × 不可逆损伤 × 撤离/坚持的选择
```

塔防提供空间压力；生存提供时间压力。两者叠在一起，才像“守一座正在坏掉的城”。

## 二、设计支柱

1. **撑到救援，不是杀光**
   - 胜负由“撑到救援到达”或“城市失去维持条件”决定；
   - 击杀数是手段，不是目标。

2. **资源是共享的**
   - 电力同时供塔、生命维持、舱门、照明；
   - 玩家不能既全功率开火又全功率供氧。

3. **损伤不可完全回滚**
   - 舱段破损、设备降级、储备消耗；
   - 修复要花时间/资源，且可能放弃另一件事。

4. **每局有一个“最后选择”**
   - 撤离还是留下；
   - 保人还是保城；
   - 如实记录还是掩盖。

5. **不惩罚离开**
   - 不做日常/体力/限时登录；
   - 失败留下记录，不删档。

## 三、三个候选原型

### 原型 A：低功率夜班（推荐 P1）

**一句话**：电力是唯一新增资源；塔和生命维持抢电。

| 项 | 设计 |
| --- | --- |
| 生存目标 | 撑到救援抵达（如 10 分钟/8 波） |
| 新资源 | 电力（功率） |
| 电力用途 | 塔开火、氧气循环、舱门、照明 |
| 压力 | 波次越强，塔越需要功率；生命维持不能断 |
| 失败 | 氧气归零 / 保障度归零 / 核心断电 |
| 选择 | 给塔供电还是给氧气？关哪段舱门？ |
| 复用 | 现有塔、敌人、波次、故障 |

**优点**：只加“功率分配”，不改塔防基本操作；和世界观强绑定。

**风险**：容易变成“多一个蓝条”；必须让功率分配有可见后果。

### 原型 B：断缆 90 分钟

**一句话**：外环断缆，氧气储备有限；塔防是争取维修时间。

| 项 | 设计 |
| --- | --- |
| 生存目标 | 90 分钟内完成对接/救援 |
| 新资源 | 氧气、舱压 |
| 压力 | 氧气持续下降；故障/破口加速泄漏 |
| 操作 | 封舱、修破口、开备用氧 |
| 失败 | 氧气归零 / 保障度归零 |
| 选择 | 封哪段舱？放弃哪座塔？ |
| 复用 | 地图、故障、塔位 |

**优点**：最有“生存”感；适合湾口短图。

**风险**：需要破口/舱段/路径变化，系统量较大。

### 原型 C：湾口封舱

**一句话**：湾口进水/失压，玩家用舱门改变敌人路径，同时保压。

| 项 | 设计 |
| --- | --- |
| 生存目标 | 保住湾口主舱到救援 |
| 新资源 | 舱压、舱门状态 |
| 压力 | 开舱门会改变路径，也会泄压 |
| 操作 | 开关舱门、隔离段、修泵 |
| 失败 | 主舱失压 / 保障度归零 |
| 选择 | 放敌人进哪条路？保哪段？ |
| 复用 | 地图几何、敌人路径、塔位 |

**优点**：空间玩法最强；适合后续。

**风险**：需要路径重算/舱段图，超过 P1。

## 四、推荐：先做 A「低功率夜班」

### 4.1 核心循环

```text
准备：分配电力（塔 / 生命维持 / 舱门）
  → 开波
  → 敌人压力上升，电力被塔吃掉
  → 生命维持报警
  → 选择：降塔功率 / 关舱门 / 用备用电池
  → 波次结束，修复/恢复少量电力
  → 下一波
  → 救援抵达：结算
```

### 4.2 资源

只加一个主资源：**功率**。

```text
总功率 = 基础 + 备用电池 + 波次奖励
分配 = 塔组 + 生命维持 + 舱门 + 照明
```

- 塔组功率不足：射速/伤害下降，或部分塔离线；
- 生命维持功率不足：氧气开始下降；
- 舱门功率不足：不能隔离故障/漏过；
- 照明功率不足：HUD 变暗，故障提示延迟（可选，不要做太多）。

### 4.3 失败与胜利

| 结果 | 条件 |
| --- | --- |
| 胜利 | 撑到救援倒计时归零 |
| 失败 | 氧气归零 / 保障度归零 / 核心断电 |
| 灰色结果 | 救援抵达但城市损伤过重（低评级） |

### 4.4 关键选择

- 这一波给塔多少功率？
- 备用电池现在用，还是留到第 7 波？
- 关掉哪段舱门，放弃哪段覆盖？
- 先修氧气还是先修塔？
- 最后 60 秒：撤离还是留下？

## 五、数据与架构

### 5.1 场景声明

```json
{
  "mode": "survival",
  "capabilities": ["towers", "waves", "survival"],
  "survival": {
    "rescue_seconds": 600,
    "power": { "base": 100, "battery": 60 },
    "oxygen": { "seconds": 300, "drain_per_power_gap": 2.0 },
    "hull": { "max": 100 }
  },
  "overrides": {
    "waves": { "hp_scale": 0.9 }
  }
}
```

### 5.2 运行时边界

```text
LabGamePage
  ├── LabLoader（共享数据/覆盖）
  ├── SurvivalModule（lab/ 自有）
  │     ├── power allocation
  │     ├── oxygen / rescue clock
  │     └── failure states
  ├── Sim（共享塔防）
  ├── LabHud（lab/ 自有）
  └── Renderer（共享）
```

原则：

- **不改主线 GamePage**；
- 生存状态只存在 `lab/`；
- `Sim` 只负责塔防；`SurvivalModule` 读取 Sim 状态并给塔/生命维持施加修正；
- 失败条件由 SurvivalModule 判定；
- 候选 diff 只记录生存字段，不污染主线。

### 5.3 与 Mode Adapter 的关系

- P1 是 **tower_defense + survival overlay**，不换 Sim；
- 如果未来做“纯生存/撤离”玩法，再抽 `SurvivalRuntime`；
- 不在 P1 做通用引擎。

## 六、界面

- 顶部：救援倒计时、氧气、功率分配；
- 地图：塔位、舱门、生命维持节点；
- 底部：塔、功率分配、备用电池、修舱；
- 警报：
  - 氧气 <30% 黄；
  - <15% 红；
  - 功率缺口 >20% 闪；
- 结算：
  - 撑到救援 / 失败原因；
  - 是否如实记录；
  - 不写主线存档。

## 七、平衡目标

| 指标 | 目标 |
| --- | --- |
| 单局 | 10–15 分钟 |
| 首次失败 | 能说出“我哪次分配错了” |
| 胜利 | 不是“塔够多”，而是“撑到救援” |
| 电力 | 每波都需要重新分配 |
| 氧气 | 至少触发 1 次黄色警报 |
| 备用电池 | 用在第 6–8 波的抉择 |

## 八、实施切片

| 阶段 | 内容 | 估算 |
| --- | --- | --- |
| **S0** | 本方案拍板 | 0.5 天 |
| **S1** | 低功率夜班：功率/救援倒计时/氧气/失败 | 3–5 天 |
| **S2** | 舱门/备用电池/修舱 | 2–3 天 |
| **S3** | 断缆 90 分钟 / 湾口封舱 | 各 3–5 天 |
| **S4** | 多生存场景 + 候选 | 后续 |

建议只做 **S1** 验证“生存是否让塔防更厚”，不要一次做三个原型。

## 九、验收

- 一局能仅靠功率分配产生至少 3 次不同选择；
- 失败能归因到“缺氧/断电/漏过”，不是“莫名其妙”；
- 胜利条件不是清屏；
- 生存 HUD 不遮挡塔位与倒计时；
- 实验仍不写主线存档；
- 与主线塔防共享的只有 Sim/Data/Renderer/音频等组件。

## 十、风险

| 风险 | 缓解 |
| --- | --- |
| 多一条蓝条，变成负担 | 只做一个主资源（功率） |
| 生存与塔防互相打断 | 生存只做“修正 + 失败条件”，不新增暂停层 |
| HUD 过载 | 顶部三条，地图内只显示警报 |
| 失败太挫败 | 先黄警，再红警，最后失败 |
| 范围膨胀 | S1 不做舱门/破口/路径变化 |

## 十一、需要拍板

1. 第一版选 **低功率夜班**（推荐）/ 断缆 90 分钟 / 湾口封舱？
2. 生存目标选“救援倒计时”还是“撑过 N 波”？
3. 是否接受“氧气归零直接失败”，还是只扣评级？
4. 功率分配是全局滑杆，还是按塔组分配？
5. 生存 HUD 放顶部三条，是否够？
6. 是否把“撤离/留下”留到 S2？

## 十二、我的建议

**先做 S1 低功率夜班，不做三个原型。**

理由：

- 只加一个资源，能最快验证“生存是否真的改变塔防决策”；
- 和“外环夜班/设备故障/城市资源”世界观最贴；
- 可以完全放在 `lab/`，不碰主线；
- 如果 S1 不好玩，再换断缆/封舱，而不是同时做三套。
