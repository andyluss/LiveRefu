# 00 · 自由模式方案（外环试验场）

> **一句话**：做一个和主线并行的「自由模式」：玩家和你都能用**数据而不是改代码**搭出各种实验玩法，打标签、调数值、快速试玩；好设定不直接进主线，而是变成**候选方案**，经过人类评审再吸收。
>
> **建议**：**先做 P1 本地实验场**（标签 + JSON 覆盖 + 3 个样例 + 存档隔离），不要一上来做联网分享或脚本系统。

## 一、为什么需要自由模式

主线是“有约束的岗位塔防”：地图、波次、塔、合同、检查单都要为正式体验负责。它的缺点是：

- 想试一个“无补给”“双倍故障”“放置版外环”，必须改数据/代码，成本高；
- 玩家看到好玩的变体，没有地方试；
- 好设定和坏设定混在一起，难以筛选；
- 实验直接改主线，容易污染正式数值；
- 每次实验都像“改工程”，不像“玩”。

自由模式要解决的是：

```text
先自由试 → 打标签 → 看数据 → 评审 → 只把好的吸收进主线
```

它不是第二套主线，也不是“随便乱搞”。

## 二、定位与非目标

### 2.1 定位

- 与主线**并行**的独立模式；
- 默认**不继承**主线存档、进度与数值；
- 世界观仍属于逍遥湾：外环、中环、湾口、舰队、夜班；实验可以夸张，但不能破坏世界的基本事实；
- 玩法与数值可以自由，但必须**可解释、可复现、可标注**；
- 好实验可以成为**候选方案**，不自动进入主线。

### 2.2 非目标

- 不做第二个正式战役；
- 不做带任意代码的 Mod 平台；
- 不做在线服务/排行榜/每日任务；
- 不替代主线平衡；
- 不承诺“所有实验都好玩”；
- 不把实验数据写进 `game/data` 正式目录。

## 三、核心对象：实验方案

每个实验是一个 `scenario`（实验方案），不是一段散落的代码：

```json
{
  "schema_version": 1,
  "id": "lab.bay01.no_supply",
  "name": "无补给外环",
  "description": "没有补给塔，靠击杀奖励和升级撑过 8 波。",
  "world": "outer_ring",
  "tags": {
    "axis": ["tower_defense"],
    "difficulty": ["hard"],
    "theme": ["outer_ring", "night_shift"],
    "mechanic": ["economy", "wave"],
    "duration": ["standard"],
    "fidelity": ["overrides"],
    "state": ["playable"]
  },
  "base": {
    "map": "bay01",
    "mode": "tower_defense",
    "waves": "bay01"
  },
  "overrides": {
    "balance": { "starting_energy": 60 },
    "towers": { "disabled": ["supply"] },
    "waves": { "hp_scale": 1.15 }
  },
  "provenance": {
    "author": "local",
    "created": "2026-11-06",
    "source": "hand-authored"
  }
}
```

关键约束：

- **只允许白名单字段**，不执行任意脚本；
- 所有覆盖必须可展示、可 diff、可回滚；
- 实验方案不写 `game/data`；
- 有 schema 版本，坏方案不阻塞主游戏。

## 四、标签体系

标签不是装饰，是筛选、推荐与评审的依据。

| 标签组 | 取值 | 用途 |
| --- | --- | --- |
| `axis` 主轴 | `tower_defense` / `idle` / `immersion` / `hybrid` / `toy` | 这个玩法更接近什么 |
| `difficulty` 难度 | `easy` / `normal` / `hard` / `extreme` / `experimental` | 玩家预期与筛选 |
| `theme` 主题 | `outer_ring` / `middle_ring` / `bay_mouth` / `fleet` / `night_shift` | 世界观位置 |
| `mechanic` 机制 | `economy` / `wave` / `tower` / `fault` / `checklist` / `narrative` | 实验重点 |
| `duration` 时长 | `short` / `standard` / `long` | 5 / 10–15 / 30+ 分钟 |
| `fidelity` 保真 | `same_rules` / `overrides` / `toy` | 是主线近似、覆盖，还是独立小玩具 |
| `state` 状态 | `draft` / `playable` / `candidate` / `archived` | 生命周期 |

规则：

- 每个方案有且只有一个 **主 `axis`**，其它可多选；
- `difficulty` 不是“数值大小”，而是“预期体验”；
- `experimental` 不等于“没调好”，而是“明确不保证平衡”；
- 标签由作者填，评审可改；不允许用标签做虚假宣传。

## 五、数值与规则：覆盖层，而不是第二套数据

### 5.1 覆盖层

```text
canonical game/data
  + scenario.overrides
  = 本次实验的运行时数据
```

覆盖只允许：

- `balance`：初始供能、保障度、准备时间等；
- `towers`：禁用/替换/数值覆盖；
- `enemies`：禁用/替换/数值覆盖；
- `waves`：数量/HP/速度/间隔倍率；
- `map`：允许使用已有地图，或实验专用简化地图；
- `rules`：胜负条件、是否允许故障、是否允许合同；
- `ui`：仅限实验 HUD 开关，不改主线。

**不允许**：

- 任意 GDScript；
- 网络请求；
- 写主线存档；
- 动态加载外部二进制。

### 5.2 难度标签与预设

难度标签不是单独一个数字，而是一组预设：

| 标签 | 建议预设 |
| --- | --- |
| `easy` | 供能 +20%，敌人 HP −20% |
| `normal` | 主线标准 |
| `hard` | 供能 −10%，敌人 HP +15% |
| `extreme` | 供能 −20%，敌人 HP +30%，故障 +1s |
| `experimental` | 不保证可胜，必须标“实验” |

作者可以偏离预设，但必须在方案里写明“为什么”。

### 5.3 保真度

- `same_rules`：只换地图/波次，规则与主线一致；
- `overrides`：用主线规则 + 覆盖；
- `toy`：独立小玩法，只借用世界观和素材。

`toy` 不能冒充主线平衡，必须在卡片上标注。

## 六、自由模式界面

### 6.1 入口

主菜单新增：

```text
主线：正式班次
自由模式：外环试验场
```

自由模式默认独立存档：

```text
user://lab/
```

不污染 `user://shift.json`。

### 6.2 实验浏览器

- 搜索；
- 标签筛选（主轴/难度/主题/机制/时长/保真）；
- 排序（最近/难度/时长/作者）；
- 卡片：
  - 名称、一句话；
  - 标签；
  - 主地图/时长；
  - “试玩”“复制参数”“查看 diff”。

### 6.3 试玩中

- 顶部显示 `自由模式 · 实验名`；
- 可打开“实验面板”：
  - 当前覆盖；
  - 重置；
  - 导出方案；
  - “提交候选”（P2）。
- 不显示主线评级，改为“实验记录”，避免混淆。

### 6.4 好设定进主体

不是“一键采纳”，而是：

```text
实验 → 候选 → diff → 人类评审 → 规范化 → 主线数据
```

候选必须包含：

- 变更字段 diff；
- 3–10 次试玩记录；
- 标签与设计意图；
- 风险（是否破坏主线）；
- 建议吸收方式（数值/机制/仅作为变体）。

## 七、架构建议

### 7.1 目录

```text
game/data/lab/
  scenarios/
    lab.bay01.no_supply.json
    lab.bay02.idle.json
  schema/
    scenario.schema.json
```

- `lab/` 是实验数据，不是正式 `game/data`；
- 主线加载器不扫描 `lab/`；
- 自由模式使用独立 `LabLoader` + 同一 `Sim`。

### 7.2 运行时

```text
LabScenario
  → LabOverrideResolver
  → DataLoader/Sim
  → LabSession
  → LabHud
```

- 复用 `MissionRuntime/Sim`；
- 覆盖在加载期解析，运行期不再改规则；
- `toy` 可以用独立轻量循环，但必须走同一输入/音频/存档边界。

### 7.3 校验

- schema 校验；
- 白名单字段校验；
- 数值范围校验；
- 地图/塔/敌引用校验；
- 未知字段 warning，不崩；
- 坏方案跳过，不影响主线。

## 八、版本切片

| 阶段 | 内容 | 估算 |
| --- | --- | --- |
| **P0** | 拍板定位、标签、覆盖范围 | 0.5 天 |
| **P1** | 本地实验场：浏览器 + 标签 + JSON 覆盖 + 3 个样例 + 存档隔离 | 3–5 天 |
| **P2** | 候选/diff/导出 + 评审报告 | 1–2 天 |
| **P3** | 导入/导出分享（本地文件，不做在线） | 2–3 天 |
| **P4（可选）** | 精选实验包/创意工坊式分享 | 高成本，暂不做 |

建议只做 **P1–P2**，先验证“是否真的更快试玩法”。

## 九、验收

- 3 个实验方案不改代码即可创建/试玩；
- 标签筛选可用；
- 覆盖可查看、可 diff、可回滚；
- 实验不写主线数据/存档；
- 坏方案不阻塞主线；
- 确定性：同 seed/同方案可复现；
- 候选能生成人类可读 diff；
- 至少 1 个候选通过评审进入主线，或明确否决。

## 十、风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 变成第二套主线 | 范围翻倍 | 明确非目标；实验不继承主线 |
| 标签泛滥 | 找不到好方案 | 主标签唯一 + 评审清理 |
| 数值污染 | 主线平衡被带偏 | 实验隔离 + 候选评审 |
| 任意代码/MOD | 安全与维护灾难 | JSON 白名单，不执行脚本 |
| 存档损坏 | 玩家丢进度 | `user://lab/` 独立 |
| 实验质量低 | 玩家失望 | `experimental` 明确标注 |
| UI 过重 | 入口复杂 | 先做最小浏览器 |

## 十一、需要你拍板

1. **定位**：自由模式是“并行实验场”（推荐），还是“主线内的作弊/沙盒”？
2. **实现边界**：只允许 JSON 覆盖（推荐），还是允许脚本/MOD？
3. **分享**：先本地（推荐），还是第一版就做导入/导出/在线？
4. **第一切片**：是否按 P1（浏览器 + 标签 + 3 样例）开始？
5. **晋升权**：候选进入主线是否必须人类评审（建议必须）？
6. **命名**：自由模式 / 外环试验场 / 其他？

## 十二、我的建议

**做 P1–P2：本地、JSON、标签、独立存档、候选 diff，不做在线与脚本。**

理由：

- 先用最低成本验证“自由模式是否真的让你和玩家更快试玩法”；
- 保持主线干净；
- 好设定有明确通道进入主线，而不是靠记忆和手工搬运；
- 如果 P1 没人用，P3/P4 的分享与工坊就不值得做。
