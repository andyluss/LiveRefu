../../numbers · 单一数据源

一句话：数值只从 numbers/ 来；文档、UI、场景里出现的数值必须能追溯到表格，不能凭手感写。 形式化：N = Source(numbers/)，JSON = Export(N)，UI ⊆ JSON。

一、形式化表述

N = Source(numbers/)
JSON = Export(N)
UI_values ⊆ JSON
prose(number x) ⇒ ∃entry ∈ N: value(entry) = x

change(N) ⇒ export(N) ∧ test(Sim)

二、通俗解释

数值文档不是“设定集里的插图说明”，它是运行时的源。塔的伤害、敌人的速度、波次的准备时间、评级阈值，都应该先出现在表格里，再由脚本导出到 game/data/。

这样做的原因很实际：

  • 改数值不用改代码；
  • 文档和游戏不会各说一套；
  • 玩家看到的“T-07 停 2.5 秒”和代码里的 2.5 是同一个数；
  • 小说/场景卡里写“11 分钟窗口”时，能标明它是叙事时间还是数值时间。

三、条款

MUST

  1. M1：所有影响玩法的数值必须来自 numbers/ 的表格。
  2. M2：game/data/*.json 由 tools/export_numbers.py 生成，不得手改。
  3. M3：UI 显示的数值必须从数据读取，不得在界面代码里写死。
  4. M4：文档/场景卡引用具体数值时，必须能对应到表格条目；叙事性数字（如“十一分钟”）要标明不是平衡值。
  5. M5：改数值后必须跑 ./run.sh numbers-check 与 ./run.sh test。

SHOULD

  1. S1：先写“这个数解决什么问题”，再写数值。
  2. S2：数值变化写进 06_难度与评级 的版本记录。
  3. S3：场景卡里的“目标/失败条件”优先引用系统名，不复制数值。

MAY

  1. Y1：概念图、小说可以出现非平衡数字（如“12 万贡献点”），但不得被当成运行时数值。
  2. Y2：原型可以临时硬编码，但进入 game/ 前必须回到表格。

四、判定与验收

valid(number) ⇔
  number ∈ N ∧
  exported(number) ∧
  ui_reads(number)

valid(scene) ⇔
  scene.balanceValue ⊆ N ∨ scene.valueType = narrative

五、反例

  • 文档写“塔伤害 12”，表格写 10；
  • UI 里写 30 而不是读 tower.cost；
  • 小说里的“11 分钟”被直接做成关卡倒计时；
  • 手改 game/data/waves.json 加一波，下次导出被覆盖。
