11_待人类裁决清单 · 规则分层与冲突

一句话：AI 可以提方案，但不能替人拍板；人类原始设定高于一切文档与代码。 形式化：∀d ∈ Decision: author(d) ∈ Human，且 Concept ≻ Decision ≻ RootRule ≻ CategoryRule ≻ Doc ≻ Code。

一、形式化表述

设：

  • H = 人类（项目负责人）
  • A = AI
  • P = 提案集合
  • D = 裁决集合
  • C = 概念设定（人类原始文本）
  • R₀ = 根规则
  • R₁ = 类别规则
  • Doc = 其他文档
  • Code = 实现

公理：

1. D ⊆ H × P            （裁决只能由人类做出）
2. A: P → P             （AI 只能把提案变成提案）
3. ∀d ∈ D: author(d) = H
4. C ≻ D ≻ R₀ ≻ R₁ ≻ Doc ≻ Code
5. ¬∃x ∈ Canon: author(x) = A

其中 ≻ 表示“冲突时优先”。

二、通俗解释

AI 很擅长把“下一步”做得看起来很合理：加一个系统、补一段设定、扩一章内容。每一步都对，连起来却可能离开最初想做的游戏。

这条规则的意思是：方向盘必须固定在人的手里。AI 可以画地图、列选项、算代价、写反方论证，但不能把“我觉得好”写成“项目就是这样”。

当文档、规则、代码和人的想法冲突时，不是“代码已经这样了所以算数”，而是按优先级往上找：概念设定最大，其次是人类裁决，再是规则，再是文档，最后才是代码。

三、条款

MUST

  1. M1：所有主题、范围、商业模式、核心体验的决定，必须能追溯到人类；AI 不得自行升级为 canon。
  2. M2：docs-human/ 是人类原始文本；AI 默认只读，只有人类明确要求时才可改，且只改被要求的部分。
  3. M3：每个已裁决问题必须有 D-ID，记录在 11_待人类裁决清单。
  4. M4：概念、裁决、规则与代码冲突时，按 C ≻ D ≻ R₀ ≻ R₁ ≻ Doc ≻ Code 处理；代码是最后一位。
  5. M5：AI 生成的文档必须在元数据里标 source、authority，不得伪装成人类原文。

SHOULD

  1. S1：AI 的每次建议都给出至少两个选项与代价，不只给一个“最佳答案”。
  2. S2：当 AI 不确定人类意图时，停下来问，不要用“为了完整性”替人选。
  3. S3：裁决记录只追加，不回删；落选方案保留并标注「已否决」。

MAY

  1. Y1：AI 可以写虚构、参考、反方论证与原型；只要标明「非决定」。
  2. Y2：AI 可以在 docs-ai/ 里提出新规则草案；生效仍需人类确认。

四、判定与验收

一条内容是否合规，依次问：

1. 它是否声称了某个 canon？        → 是：必须有人类裁决或人类原文
2. 它是否改了 docs-human/？        → 是：必须有人类明确指令
3. 它与更高优先级冲突吗？          → 是：以更高优先级为准
4. 它的元数据是否标明来源与决策权？ → 否：不合规

机器可查的部分：

  • 文档 YAML 是否有 source / authority；
  • 裁决是否有 D-ID；
  • docs-human/ 的 diff 是否只包含人类要求的内容；
  • 规则索引中的 ID 是否唯一。

五、反例

  • AI 在文档里写「项目决定采用 X」，但没有任何人类裁决记录；
  • 代码里已经实现了 X，于是文档把 X 写成「既定设定」；
  • AI 以「整理」为名改写 docs-human/概念设定.md 的正文；
  • 把「AI 建议」当成「人类已定」，跳过 D-ID。

六、引用与变更

  • 被引用处：11_待人类裁决清单、README、项目 README；
  • 变更：只有人类可以修改本规则；修改需提升规则版本，并说明代价；
  • 关联：ROOT-B0、ROOT-C0。
