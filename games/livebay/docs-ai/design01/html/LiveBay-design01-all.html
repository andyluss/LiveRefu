一、这套文档是什么

这是 LiveBay 的第一版策划参考集，按「人类已定的概念 → AI 展开的候选 → 需要人类拍板的问题」三层组织。

它不是：

  • 不是最终 GDD：没有任何一条 AI 候选自动成为设定；
  • 不是工程规格：工程只实现「可逆占位」，见 12_技术方案；
  • 不是人类原始想法的替代：人类原始想法只在 docs-human/概念设定.md，AI 不改写它。

它是：

  • 一份把空白处标出来的地图：哪些已定、哪些可选、哪些必须由人决定；
  • 截至 2026-11-05，D01–D13、D15、D16 已裁决，P0/P1 已清空；NASApunk 轻量包 N1–N3 已选；E1–E4 已按推荐通过；模块化架构见 16，玩法扩展与可插拔架构见 expansions（已裁决方向）：见 11；
  • 一份可以直接拿去拍板的待裁决清单：11_待人类裁决清单；
  • 一份能让工程先动起来的最小共识：把已裁决的方向变成可玩的塔防闭环。

二、状态标记（全文通用）

标记 含义 谁能改
【人类已定】 来自概念设定，或人类在对话中明确拍板 只有人类
【AI 候选】 2–3 个可选方向，附代价；未定 人类选，AI 不选
【AI 建议】 AI 的倾向与理由；可被推翻，不等于决定 人类可采纳/否决
【待裁决】 已登记到 11 的问题 人类
【工程占位】 为了让工程能跑而做的临时选择，不是设计定案 工程可改

阅读时请先看标记再看内容。一段没有标记的叙述，默认是描述性整理，不是决定。

四、AI 的边界（本轮协作约定）

  1. AI 不替人做创意决定：所有世界观、基调、职业、敌人来源、商业模式，均以候选形式给出；人类不选，就不实现。
  2. AI 不扩写人类原文：docs-human/ 只加元数据，不改正文；需要修订时由人类自己改，AI 只在 docs-ai/ 里提建议。
  3. AI 的工程选择必须可逆：数据驱动、单一职责、无硬编码剧情；人类改设定时，工程只需改 JSON，不需重写代码。
  4. AI 不伪造证据：涉及市场、竞品、玩家数据时，标注来源与不确定度；没有数据就写「未知」。
  5. AI 不无限扩张：每篇文档有明确范围；超出范围的想法进 11 或直接丢弃，不偷偷塞进正文。

五、与工程的关系

工程在 games/livebay/game/，当前实现的是「可玩最小闭环」：1 张月牙地图、1 个示例职业、3 种塔、5 波敌人、胜负与结算。它验证的是手感与结构，不是设定。按 D02 裁决，首版目标是自然（A）+ 内部（C）双来源，工程已实现 A+C。

工程里的所有内容（职业名、塔名、敌人名、数值）都是【工程占位】，可以在人类拍板后整体替换。替换方式见 12_技术方案 的「数据契约」。

六、下一步

  1. P0/P1 已清空；D02 的内部故障（C）已落地；
  2. 按 D05 的节奏做 v0.2 护理师，验证「同引擎换职业」；
  3. 把 D06/D07/D08 写进广播、交接记录与外环事故，把 D12 写进内购边界；
  4. 人类试玩 10 分钟，判断「故障是否让防线更有张力」——这一步 AI 不能代劳。

一句话：这套文档的目标不是「写全」，而是让你更快地做出决定，然后更快地试玩。

一、为什么先读这篇

上一版主线项目的问题是「AI 越做越顺，项目越走越偏」：每个下一步都合理，连起来却离开了最初想做的游戏。根源不是 AI 能力不足，而是人的意图没有被外化成可执行的边界。

这套文档用三条规则对抗这种漂移：

  1. 所有创意以候选形式出现，AI 不把「我觉得好」写成「设定如此」；
  2. 所有待定问题集中登记，不散落在正文里，避免「读起来像定了」；
  3. 所有工程选择可逆，人类改主意时不需要重写代码。

二、一条创意怎么变成决定

建议用「决策卡」走完五步。每张卡只回答一个问题。

【问题】一句话，必须是可选择的问句。
【选项】A / B / C，各附一句代价。
【AI 建议】选哪个、为什么；必须写明「可被推翻」。
【人的裁决】人类选择一个，或写「再想想」。
【影响】会改动哪些文档、哪些工程数据。

流程：

步 谁做 产出
1. 提案 AI 在对应文档写候选与代价
2. 登记 AI 在 11 加一行 Dxx
3. 裁决 人类 在 11 的「裁决记录」写选择与理由
4. 回写 AI 更新正文、删掉落选选项或标注「已否决」、同步工程数据
5. 复核 人类 试玩/试读，确认新决定没有破坏原有体验

关键：裁决记录只追加，不回删。将来复盘时，「当时为什么这么选」比「现在是什么」更有价值。

四、AI 在什么情况下必须停

出现以下任一情况，AI 不应继续扩写，而应把问题交回人类：

  • 需要决定主题/体验/审美（例如「这座城市到底好不好」）；
  • 需要决定范围/预算/时间（例如「做几个职业」）；
  • 需要决定商业模式/平台/发行；
  • 两个候选都自洽，但会导向不同的游戏；
  • 现有文档之间出现冲突，且冲突不能靠「以人类原文为准」解决。

停下时，AI 的输出应该是一张决策卡，而不是一篇更长的文档。

五、没有裁决时的默认规则

在人类回答之前，AI 可以继续做不产生创意承诺的工作：

可以做 不可以做
工程占位数据、可逆的 UI 骨架 写死剧情、角色名、阵营立场
数值原型与平衡表 把某个候选写成「官方设定」
竞品/资料调研（标注来源） 编造玩家数据或市场结论
把问题整理得更清楚 用「为了完整性」为由替人选一个

工程侧的默认值是「能跑、能改、能删」：所有内容走 JSON，职业与关卡是数据，不是代码。

六、文档维护规则

  1. 一篇文档一个主题；超过 4000 字就拆，不把世界观、玩法、工程混在一篇。
  2. 链接用相对路径，遵循工作区 R01 与 R03。
  3. 日期取系统时间（东八区），不手写。
  4. 裁决后不回删原文：落选选项保留并标注「已否决（日期）」，保留判断痕迹。
  5. AI 生成的内容必须可识别：每篇头部有「文档类型 / 来源 / 决策权」元数据。

七、这套文档的失败条件

如果出现以下情况，说明这套文档没有起到作用，应停下来重构，而不是继续写：

  • 文档越写越多，但人类仍然说不清「这游戏是什么」；
  • 每个问题都有「推荐方案」，但没有人真正选过；
  • 工程实现了大量内容，但没有一个能被人类试玩判断；
  • 人类每次反馈都被 AI 解释成「再加一个系统」。

文档的目的是减少不确定性，不是增加产出量。如果它没有让你更快做决定，它就是失败的。

三、三个支柱的解释

3.1 岗位视角

玩家不是舰长、不是救世主，而是一个会被排班、会被轮岗、会退休的人。塔防的「塔」不是魔法塔，而是岗位上的设备与流程；「敌人」不是恶魔，而是这份工作要处理的风险。

这条支柱决定了：叙事要往下写，不要往上写。写食堂、值班室、交接班记录，比写议会阴谋更接近这个项目。

3.2 可维修的世界

一切都有标签、接口、备份与检查单。美术上拒绝「无缝全息」，玩法上拒绝「不可解释的魔法」；每个系统都应该能被玩家看懂、拆开、替换。

这条支柱决定了：UI 是世界观的一部分，不是盖在玩法上的皮。

3.3 长线陪伴

玩家会离开，也会回来。游戏不惩罚离开，不制造 FOMO；城市在玩家不在时仍然运转，回来时有一封「这段时间发生的事」的报告。

这条支柱决定了：放置玩法不是附属品，而是「你不在时城市怎么活」的叙事装置。

【人类已定】来自概念设定：

  • 时代：未来人类移民太空的漫长旅途；
  • 主体：人类移民舰队集群成立的一座移动太空城，形状类似月牙；
  • 三环：外环舰队负责护卫与能源资源收集；内环舰队是政治经济文化中心；中环舰队是居民区；

【AI 候选】「舰队集群」可以这样理解：

这个结构的好处是：每一环都可以独立成为关卡。外环是塔防的主战场，中环是沉浸玩法的主场景，内环是叙事与政治的舞台。

四、时间：航行第几代（D06 已裁决）

裁决（2026-11-03）：200 年，第七代。

  • 地球已经变成传说，不是日常记忆；
  • 大多数居民认同「湾民」身份，而不是「地球人」；
  • 祖辈的出发故事仍在节日、菜谱与方言里；
  • 少部分传统派坚持「我们只是路过」。

为什么不是 80 年或「不可考」：

  • 80 年（第三代）离地球太近，冲突容易变成「第一代 vs 第二代」的家庭剧，神秘感弱；
  • 「不可考」叙事空间最大，但会把「历史断裂」变成主要谜题，容易失焦；
  • 200 年刚好：足够让「湾民」成为独立文化，又不至于完全失去出发地的记忆。

「出发多久」本身可以成为一个被低报的数字（D08），但居民日常不会追问。

七、政治、经济与文化

7.1 治理（D07 已裁决）

裁决（2026-11-03）：双轨制——日常由算法配给，危机由议会接管。

  • 日常：保障体系按算法分配资源，规则透明、效率高、无法处理例外；
  • 危机：议会召开特别会议，决定优先级、征用与例外；
  • 甩锅：算法说「这是议会批准的例外」，议会说「这是算法给出的建议」；
  • 申诉：居民可以申诉，但流程漫长，且常常在两条轨道之间被踢回。

这套结构的好处是：它天然产生「谁负责」的戏剧，也贴合「机构」主题。坏处是：它让「没有人负责」成为常态，而这正是 D01=B 想写的东西。

7.2 经济

【AI 候选】

  • 货币：贡献点（工时 + 岗位难度 + 风险系数）；
  • 配给：基本生活免费，额外享受靠贡献点；
  • 限制：不能积累土地/生产资料，避免出现「湾内资本家」；
  • 灰色地带：加餐券、娱乐舱预约、外环走私。

7.3 文化

【AI 候选】

  • 出发地记忆：节日、菜谱、方言、宗教；
  • 湾民身份：新一代的归属感，可能与传统派冲突；
  • 体育/竞技：零重力球类，跨环联赛；
  • 艺术：以「维修美学」为主，废料再创作。

八、秘密与裂缝（D08 已裁决）

裁决（2026-11-03）：埋 低报事故，且只埋线索、不揭开。

九、基调：有裂缝的善意（D01 已裁决）

【已裁决 D01】逍遥湾不是完美乌托邦，也不是坏制度：

  • 体系大体有效，真的救了很多人的命；
  • 但它的效率建立在对少数人的排除上；
  • 居民既依赖它，也怀疑它。

  3. 中环的安稳有代价：有人替他们承担了风险，而他们未必知道。

基调已定，裂缝已定为「低报事故」，具体埋法见第八节。

概念设定给了名字与一句话功能：「为了节约能源与资源，大多数人类大多数时间都在中环消磨时间，在稳定的规划体系下生存生活生产，这个体系叫『慢好三生保障体系』。」 2026-11-03 人类裁决（D03）：三生 = 生存 / 生活 / 生产；慢好 = 慢 + 好。本文按此定义重写。

一、已裁决的定义

1.1 三生

层 保障什么 主要空间 游戏接口
生存 空气、水、食物、医疗、安全、应急 全城（跨三环） 保障度（HP）、失败条件
生活 居住、娱乐、教育、社交、心理、养老、尊严 中环为主 贡献点、关系、沉浸/放置
生产 工作、能源、资源、维护、照护劳动 外环为主，内环负责分配 供能、岗位、塔防/采集

三个词不是并列的部门，而是三种保障对象：

  • 生存是底线：任何情况下不能拿它做交易；
  • 生活是温度：决定居民愿不愿意把这座城当家；
  • 生产是代价：维持前两者所需要的劳动与资源，由少数工作人员承担。

1.2 慢好

字 含义 设计约束
慢 不追求效率最大化；允许发呆、闲聊、走神；制度为人的节奏留余量 不做每日签到/体力/FOMO；轮岗与退役是正常路径；离线不惩罚
好 保障质量与尊严，而不是单纯给得多 不卖数值、不抽卡；规则透明；服务有温度；宁可少而可靠

「慢好」不是「低效」，而是把可持续性放在短期产出之前。它同时约束玩法（不逼玩家上线）与世界观（制度承认人不是机器）。

1.3 三者的关系

        生存（底线）
          ↑
生活 ←—— 人 ——→ 生产
          ↓
        分配（内环）
  • 生产挤占生活 → 倦怠、意义感下降、轮岗率上升；
  • 生活挤占生产 → 维护欠账、故障累积、保障度下降；
  • 生存被击穿 → 直接进入事故状态，其他两层暂停。

内环不直接生产，也不直接生活；它负责分配：预算、配给、选拔、优先级。这也是政治冲突的源头。

1.4 被否决的读法（保留为叙事素材）

  • 生存/生活/生命：把「生命」单列，容易变成心理/意义的抽象层，和「生活」重叠；不采用为主结构。
  • 生产/生活/生态：生态适合做长期经营，但会额外增加一套循环系统；暂不采用。
  • 生/长/老：适合做长线叙事，不适合做核心系统；保留为角色人生阶段的素材。
  • 慢/好/三段人生：其中「三段人生」不占用「三生」的定义；「转岗/退役/回任」仍是职业循环的一部分。

裁决不等于删除讨论。以上读法仍可在具体剧情、舱室或角色身上局部使用，只是不再作为「三生」的主定义。

二、保障体系的日常运作

2.1 配给

  • 生存配额：空气、水、食物、基础医疗、居住，无条件提供；
  • 生活配额：娱乐舱预约、加餐、教育课程、私人空间，用贡献点兑换；
  • 生产配额：工具、备件、能源、培训，按岗位与项目分配；
  • 贡献点：按工时、岗位难度、风险系数发放；
  • 上限：不能购买生产资料、不能雇佣他人、不能转让生存配额（防止阶层固化）。

2.2 保障等级

等级 覆盖 获取
基础 生存必需 所有居民
标准 生活（娱乐/教育/心理） 正常贡献
优先 医疗/养老/育儿/高风险岗位 特殊贡献或实际需要

「优先」是最容易出问题的地方：谁有资格优先？按贡献、按年龄，还是按需要？这是叙事的富矿。

2.3 选拔

【AI 候选】三种机制，可组合：

机制 说明 优点 代价
考试 标准化测试 + 实操 公平、可预期 应试化，忽略软技能
推荐 现有工作人员推荐 有人情味 容易裙带
抽签 随机抽取 绝对公平 不专业，风险高

【AI 建议】考试为主 + 推荐为辅；抽签只用于「稀有岗位」的叙事事件。

2.4 轮岗与退役

  • 轮岗：同一环内换岗，或跨环短期支援；目的是防止 burnout；
  • 退役：不是惩罚，而是「转为顾问/居民」；保留部分福利；
  • 回任：退役后可申请回任，需重新见习。

这套机制的世界观意义：它承认「人不是机器」。这也是「慢」的核心：效率让位于可持续。

三、分层与代价

【AI 候选】任何保障体系都会产生分层。不要假装没有：

群体 位置 得到什么 失去什么
中环居民 大多数 稳定、安全、基本保障 意义感、选择权
三环工作人员 少数 少量奖励、成就感、上升通道 压力、风险、被轮岗
内环精英 更少数 决策权、优先保障 被问责、被孤立
无法工作者 边缘 基础保障 社会参与、尊严

这张表是叙事与玩法的关键。如果游戏只展示前两行，它就是「体制内爽文」；如果它敢展示后两行，它才有资格谈「保障」。D01 已裁决为 B（有裂缝的善意），所以后两行必须被写进内容，而不是只做背景。

四、治理与数据（D07 已裁决）

裁决（2026-11-03）：双轨制——日常算法配给，危机议会接管。

  • 健康监测：养生舱记录身体与心理数据，用于配给与预警；
  • 日常：算法分配资源，规则透明、效率高、处理不了例外；
  • 危机：议会开特别会议，决定优先级、征用与例外；
  • 甩锅：算法说「这是议会批准的例外」，议会说「这是算法给出的建议」；
  • 隐私：数据归机构，个人可申请查看，但不能删除；这是内环政治的核心议题；
  • 申诉：居民可以申诉，流程漫长，常常在两条轨道之间被踢回。

这套结构的戏剧性不在「谁对」，而在「没有人负责」——它让 D01=B 的「有裂缝的善意」有了制度载体。

五、玩法接口

三生 塔防 沉浸 放置
生存 保障度（城 HP） 角色健康/安全 舱室稳定度
生活 建造资源（间接） 关系、对话、心理 贡献点、幸福感

【AI 建议】三种玩法共享一套「保障度/配给/档案」数据，但不强制互相依赖（见 09）。

六、体系的裂缝（D01=B / D08 已裁决）

裁决（2026-11-03）：先埋 低报事故，只埋线索、不揭开。

裂缝 状态 表现 玩法含义
数据偏差 未采用 算法对某类人评分偏低 玩家可以选择修正或无视
低报事故 采用 广播数字与实际不符 塔防结算与新闻不一致
轮岗黑箱 未采用 谁被轮岗由内环决定 玩家被调去「送死」岗位
退役污名 未采用 退役者被视为「不够坚强」 角色关系冲突
代际断层 未采用 新湾民不认同旧制度 教育/广播玩法

低报事故在游戏里的三个落点：

  1. 广播说「外环事故 0 起」，塔防结算却显示漏过；
  2. 交接记录出现「已按惯例处理」；
  3. 第 4 波故障出现时，广播仍说「系统运行正常」。

第一版不解释谁在低报、为什么低报；留白比揭秘更适合长线。

七、基调：有裂缝的善意（D01 已裁决 B）

这不是「坏制度」，也不是「完美乌托邦」，而是：

  • 它真的救了很多人；
  • 它真的排除了少数人；
  • 里面的人既想守护它，也想改变它。

设计上的三个要求：

  1. 不把机构写成反派：机构由具体的人组成，有善意也有惰性；
  2. 不把玩家写成救世主：玩家只能改变一小块，代价要可见；
  3. 不把「逍遥」写成躺平：它是被安排出来的安稳，安稳本身值得怀疑。

八、相关裁决已齐

D01（基调）、D03（三生）、D07（双轨）、D08（低报事故）、D12（买断+内购）均已裁决：

  • 内购只卖外观/扩展内容，不卖数值、不抽卡；
  • 社会系统的冲突不靠「坏人大阴谋」，而靠「制度惯性 + 没人负责」；
  • 下一步是把这些写进广播、交接记录与舱室事件，而不是继续加设定。

四、六个职业的展开示例

4.1 养生舱护理师（中环，最具项目特色）

  • 一班：巡舱 → 发现异常 → 调配护理站 → 处理突发 → 写交接记录。
  • 塔防化：地图是养生舱的俯视图；「塔」是护理站、缓冲舱、巡检无人机；「敌人」不是怪物，而是压力波——沿着舱室蔓延，碰到湾民就降低状态。
  • 资源：「心力」有限，用一次少一次；「保障度」是这一班所有湾民的平均状态。
  • 失败：不是「死人」，而是「有人崩溃，被送进深度恢复」；结算是一份护理报告。
  • 核心张力：你可以把资源集中在一个人身上，也可以平均分配；两种都合理，代价不同。

这是最能体现「塔防 = 岗位」的职业，也是最难做的：敌人抽象、反馈不直观。建议作为第二职业或旗舰职业，不建议作为教学职业。

4.2 护卫兵（外环，最稳的教学职业）

  • 一班：接警戒 → 布防 → 拦截 → 修复 → 交接。
  • 塔防化：传统弧形路径；敌人沿外环弧线推进；塔位在弧内侧。
  • 资源：供能（建造/升级）+ 保障度（漏怪扣）。
  • 失败：舱壁破裂，进入事故报告；可以重试。
  • 核心张力：火力覆盖 vs 误伤民用舱段（可选的第二资源）。

教学成本最低，玩家一看就懂。缺点是「像别的塔防」，项目特色要靠叙事与美术补。

4.3 采集兵（外环，时间压力）

  • 一班：出舱 → 选矿脉 → 布采集臂 → 应对乱流 → 返航。
  • 塔防化：不是「守家」，而是「守采集窗口」；敌人是乱流与时间，不是敌人。
  • 资源：时间（窗口倒计时）+ 氧气。
  • 失败：空手返航，或被迫提前撤离。
  • 核心张力：多采一筐 vs 安全回家。

4.4 能源调度员（外环/内环交界，系统玩法）

  • 一班：监控负载 → 切换电路 → 隔离故障 → 恢复供电。
  • 塔防化：电网图，节点是舱段，边是线路；「敌人」是峰值负载与连锁跳闸。
  • 资源：瓦时 + 备用容量。
  • 失败：全城停电，进入应急状态。
  • 核心张力：保核心舱段（医院、养生舱）还是保全城。

4.5 工程师（内环，故障链）

  • 一班：接报 → 诊断 → 加固 → 验证 → 交付。
  • 塔防化：系统图，故障像波一样沿连接传播；「塔」是泵、阀、冗余回路。
  • 资源：备件 + 预算。
  • 失败：连锁失效，事故报告。
  • 核心张力：修得快 vs 修得对；临时补丁 vs 彻底更换。

4.6 执政官（内环，非传统塔防）

  • 一班：开会 → 听汇报 → 分配预算 → 应对危机 → 广播。
  • 塔防化：地图是「议题/派系/资源」的关系图；「塔」是政策、预算、广播；「敌人」是危机事件与信任流失。
  • 资源：政治资本 + 公信力。
  • 失败：不信任案，提前下台。
  • 核心张力：正确 vs 可接受；短期 vs 长期。

这是最冒险的职业：它可能不再是塔防，而是政治模拟。建议作为后期内容，且明确「它是不是塔防」由人类决定。

五、成长路径

【AI 候选】每个职业三阶，跨职业可迁移：

阶 名称 玩法变化 叙事
1 见习 教学关，塔种类少，敌人单一 刚被选拔
2 正式 完整塔种、资源压力、随机事件 独立值班
3 带班 多目标、手下 NPC、交接责任 要为别人的班负责

跨职业：

  • 转岗：完成一个职业的「带班」后，可申请转岗；保留部分「湾民档案」加成；
  • 退役：不是失败，转为「顾问」，提供被动加成与剧情；
  • 回任：退役后可回任，但需要重新见习。

这套路径的好处是：它把「换工作」变成了玩法循环，而不是重开档。是否采用，按 11 的 D04（主角已裁决为无名岗位人）与 D05（第一职业护卫兵）执行。

一、一句话

你在月牙的外弧上布防，扛过一班；漏过去的不是怪，是这座城的保障度。

一局目标时长：8–12 分钟（5 波）。失败可立即重试，不消耗资源。

【AI 建议】第一版采用弧形路径，因为它是「月牙城」最直接的玩法化：

  • 敌人从左侧尖角进入，沿外弧推进到右侧湾口；
  • 玩家在弧内侧的塔位布防；
  • 漏过的敌人抵达湾口，扣除保障度；
  • 屏幕下方是内环/中环的剪影，作为「你在保护什么」的视觉提示。
  敌人 →  ╭──────────────────────────╮  → 湾口（扣保障度）
          ╰──●────●────●────●────●──╯
               塔位（弧内侧）

3.1 塔位

【工程占位】第一版 7 个固定塔位，沿弧内侧分布。不采用自由建造，原因：

  • 降低操作复杂度，适合 8–12 分钟一局；
  • 让关卡设计可控，方便做「这一班该守哪里」的叙事；
  • 移动端更容易点选。

【AI 候选】后续可加「可移动塔位」「临时路障」「舱段改造」，但第一版不做。

3.2 路径与阻挡

【工程占位】敌人沿固定路径移动，不寻路、不绕行。塔不阻挡路径。

【AI 候选】如果未来要做「路径改变」，需要重新设计寻路与关卡，成本高，建议后置。

四、资源

资源 作用 来源 失败条件
供能 建塔、升级 初始储备 + 击杀奖励 + 补给塔 归零不会失败，只是无法建造
保障度 城的生命值 初始 100，补给塔可小幅恢复 归零则本班失败
职业资源 每个职业的特色资源 见职业表 归零触发特殊失败/减益

【AI 建议】第一版只做「供能 + 保障度」两种，职业资源留到第二职业再加。理由：两种资源已经能产生「建造 vs 保命」的取舍；第三种会让教学变长。

4.1 经济原则

  • 击杀奖励 略低于 建塔成本，迫使玩家做选择，而不是无脑铺满；
  • 补给塔提供「滚雪球」但占用塔位，形成「经济 vs 火力」的取舍；
  • 不设「卖塔返还 100%」——返还 70%，让建错有代价，但不至于惩罚过重。

【已裁决 D02】混合：自然风险 + 内部故障为主，人类冲突作为稀有事件。首版目标 A + C。

  • 已实现（A 自然）：碎片、乱流、重壳；
  • 已实现（C 内部）：故障。它不直接攻击湾口，而是从湾口反向沿外弧扩散，经过塔位时让设施离线 2.5 秒；最多影响 2 座塔后烧毁。玩家可以用射程覆盖或提前击杀来处理；
  • 后置（B 人类）：掠夺者、走私者、失控 AI，作为稀有事件。

C 的设计意图：让玩家不只是「堆火力」，还要考虑「塔被停掉时防线还撑不撑得住」。故障不扣保障度，但会让外部波次更容易漏过去。

3 6 乱流 + 2 重壳 引入坦克，需要爆发
4 10 碎片 + 6 乱流 + 2 重壳 + 1 故障 混合压力；首次出现内部故障
5 12 碎片 + 8 乱流 + 4 重壳 + 1 故障 终波；故障与外部压力叠加

波间节奏：

  • 每波结束有 20 秒 建设时间（可跳过）；
  • 第一波开始前有 30 秒 准备时间（可提前开始）；
  • 波次之间显示「本波损失/获得」简报。

故障从湾口（路径终点）反向生成，因此它会先经过靠湾口的塔，再向中段扩散。玩家如果只守入口方向，会被它从背后停掉关键塔。第 4 波是教学，第 5 波是压力测试。

八、胜负与失败叙事

8.1 胜利

  • 撑过 5 波，保障度 > 0；
  • 结算显示：保障度、击杀、建造数、剩余供能、评级（S/A/B/C）；
  • 评级只影响「湾民档案」的记录与少量奖励，不影响主线解锁（避免逼玩家刷分）。

8.2 失败

【已裁决 D10】重试 + 可跳过复盘。

  • 失败时弹出「事故报告」：哪一波、漏了什么、下次建议；
  • 报告可以一键跳过，然后立即重试；
  • 不做永久损失：不扣资源、不伤角色、不锁关卡。

理由：这个项目的气质是「值班」，不是「惩罚」。失败应该让人想「下一班怎么补」，而不是「我亏了」。工程已按此实现。

候选 形态 玩家在做什么 成本 风险
A 步行模拟 第一/第三人称在舱室间移动 走、看、按、对话 高（3D/2D 场景、动画） 手感与美术要求高

【AI 建议】第一版做 B + D：一个舱室、一个 NPC、一班时间、三到五个选择，用「广播 + 档案 + 对话」推进。理由：成本最低，最能验证「这个世界的人是否可信」；等文本与角色立住，再升级到 A 或 C。

但这是建议。如果你想要「能走动的舱室」，第一版也可以做 A 的极简版（固定视角、点击移动）。

二、核心循环（第一版）

接班（读交接记录）
   ↓
在舱室里走动/查看（3–5 个交互点）
   ↓
遇到 NPC（对话，2–3 个选择）
   ↓
处理一件小事（选择：按规矩 / 通融 / 上报）
   ↓
交班（写记录，影响下一班）

一局时长：5–8 分钟。没有失败，只有不同的记录与关系。

三、最小场景：养生舱的一班

【AI 候选】第一版场景，用来验证基调：

  • 地点：中环养生舱，夜班；
  • NPC：一位不愿进舱的老湾民（害怕被记录）、一位刚被轮岗的年轻护理师；
  • 事件：老湾民的健康数据异常，但本人拒绝上报；年轻护理师想按规矩办；
  • 选择：
    • A 按规矩上报 → 老湾民被强制检查，关系下降，保障度短期上升；
    • B 帮忙隐瞒 → 关系上升，风险累积，下一班可能出事；
    • C 折中：先观察，写一份「待复查」→ 需要消耗自己的休息时间；
  • 后果：写进交接记录，下一班（或塔防关卡）会读到。

这个场景同时测试三件事：基调（D01=B 有裂缝的善意）、岗位感（护理师的日常）、选择的重量（没有完美答案）。

按 D01=B，这个场景没有「正确」选项：两个选项都在伤害某个人，玩家只能选择自己愿意承担哪一种后果。

每天固定时段播报：事故、配给、选拔、节日。广播是最便宜的叙事载体：一段 20 秒的音频 + 字幕，就能交代大量信息。

  5. 与塔防互相绑架：如果打塔防必须收菜，或收菜必须打塔防，两个模式都会失去自由。

概念设定：【人类已定】当前玩法之间暂时联系较弱，没有太多实质性交互影响。 这是一个已知问题，但不是必须马上解决的问题。本文给出四档耦合强度、四种联动方案与一个分阶段建议。D11 已裁决：v0.1 L0（独立），v0.2 L1（共享世界）。

一、先问：为什么要把它们连起来

联动有三个可能的目的，动机不同，做法不同：

  1. 叙事目的：让三种玩法发生在同一个世界、同一批人身上；
  2. 经济目的：让一个模式的产出服务另一个模式，形成长期循环；
  3. 留存目的：让玩家每天有理由回来做多件事。

【AI 建议】先做 1，再做 2，最后才考虑 3。理由：叙事联动便宜且不会伤害体验；经济联动容易变成「日常任务」；留存联动最容易让玩家觉得被绑架。

二、四档耦合强度

档 名称 共享什么 玩家是否必须跨模式 成本 风险
L0 独立 只有世界观 否 低 三个游戏像三个产品
L1 共享世界 NPC、档案、地点、事件 否 低 联动感弱
L2 共享资源 供能、贡献点、材料 部分 中 经济平衡难
L3 共享进度 解锁、主线、职业 是 高 逼玩，体验割裂

【AI 建议】第一版 L0，第二版 L1，第三版视情况 L2；L3 暂不做。

三、四种联动方案

方案 A：档案网络（L1，推荐先做）

  • 每个 NPC 有一页档案，分散在三种玩法里解锁；
  • 塔防里救下的人，会在沉浸玩法里出现；沉浸里做的选择，会写进放置玩法的回归报告；
  • 档案本身不是资源，不提供数值，只提供「这个世界是真的」的感觉。

成本：低（主要是文本与数据结构）。 风险：玩家可能不看档案；需要好的呈现方式（广播、交接记录、档案卡）。

方案 B：资源循环（L2）

塔防 → 供能/素材 → 放置舱室升级 → 塔防初始加成/解锁塔
   ↑                                      ↓
沉浸 → 贡献点/关系 → 解锁岗位/事件 ←──────┘

成本：中（经济平衡、防刷）。 风险：如果塔防产出是放置的必需资源，玩家会被迫打塔防；反之亦然。

方案 C：城市事件（L1–L2）

  • 每周一个「城市事件」（停电、选拔、节日、事故）；
  • 三种玩法各自有一个小任务，完成后共同推进事件；
  • 事件结束给一个叙事结果 + 少量奖励。

成本：中（内容产能）。 风险：需要持续更新；如果产能不足，会变成「空事件」。

方案 D：职业解锁（L2–L3）

  • 塔防通关 → 解锁该职业的沉浸章节；
  • 沉浸章节 → 解锁该职业的放置岗位；
  • 放置岗位 → 提供塔防的被动加成。

成本：高（三条线都要做内容）。 风险：最容易变成「逼玩三遍」；不适合第一版。

四、方案对比

方案 档 叙事收益 经济收益 成本 推荐阶段
A 档案网络 L1 高 低 低 v0.2
B 资源循环 L2 中 高 中 v0.5
C 城市事件 L1–L2 高 中 中 v0.5
D 职业解锁 L2–L3 高 高 高 v1.0 以后

版本 耦合 做什么 不做什么
v0.1 L0 只做塔防；预留 NPC/档案字段 不做跨模式资源
v0.2 L1 加档案网络；塔防里出现 3 个 NPC 不做强制任务
v0.5 L2（待后续裁决） 加一个城市事件；供能可少量互通 不做「必须收菜才能打」
v1.0 L2 资源循环 + 事件轮换 不做 L3 的硬锁

六、如果未来升级到强联动

若后续把耦合从 L1 升到 L2/L3，建议采用单货币 + 单事件的最小实现：

  1. 只共享一种货币（贡献点），三种玩法都能赚、都能花；
  2. 每周一个事件，三种玩法各有一个入口，但完成任意两个就能推进；
  3. 不设「必须按顺序玩」的锁；
  4. 所有联动奖励都是「便利/外观/叙事」，不是「数值门槛」。

七、反模式

  • 日常任务：每天必须打一局/收一次菜；与「不惩罚离开」冲突；
  • 平行经济：三种货币互相兑换，最后一定有人套利；
  • 模式门槛：不打塔防就不能看剧情；会让只想看故事的玩家离开；
  • 虚假联动：只在加载界面写「同一个世界」，玩法里毫无关系；
  • 过度联动：每个模式都为另一个模式服务，自己不好玩。

八、验收问题

联动做完后，问三个问题：

  1. 我只玩一种玩法，会不会觉得缺了什么？（应该不会）
  2. 我玩两种玩法，会不会觉得重复劳动？（应该不会）
  3. 我三种都玩，会不会觉得世界更真实？（应该会）

三个都答「是」，才算联动成功。

九、后续可选项

D11 已裁决：v0.1 L0，v0.2 L1。v0.2 默认采用方案 A 档案网络（NPC/档案共享），不共享资源。

仍可后续再定的：

  • 是否在 v0.5 升级到 L2（资源互通）；
  • 是否做城市事件（方案 C）；
  • 是否把职业解锁做成跨模式链路（方案 D，风险最高）。

六、内容产能与「AI 味」风险

AI 可以批量生成：关卡配置、塔/敌人变体、事件文本初稿、档案条目。但有两个风险：

  1. 同质化：AI 生成的关卡会趋同（同样的波次、同样的数值），玩家很快识破；
  2. 文本塑料感：AI 写的人物对话容易「正确但无趣」，缺少具体的生活细节。

对策：

  • 关卡：人工定「每关一个新鲜动词」，AI 只做数值填充；
  • 文本：人类写关键场景，AI 写支线与档案；所有 AI 文本必须经过人类润色；
  • 美术：人类定风格与关键帧，AI 做变体与量产；
  • 每版本至少一个「只有人才能写出来」的细节（一道菜、一句口头禅、一个习惯动作）。

一、为什么是这三个

当前塔防已经有一个好骨架：弧形路径、3 塔、4 敌、5 波、故障停塔。它的问题是 NASApunk 还停留在视觉：

  • 故障只有「停 / 不停」，没有「怎么坏」；
  • 事故记录只在结算文案里，玩家没有「怎么写」；
  • 模块化、备件、维修都还没有进入决策。

这三个机制分别补上：

机制 对应 NASApunk 原则 玩家新增的决策
班前检查单 检查单、机构流程、低报 花时间复查，还是照惯例签收？
故障降级 冗余、降级、可维修 隔离保安全，还是旁路保覆盖？
事故记录 机构疲惫、低报事故 如实写，还是按惯例？

它们共同回答一个问题：玩家不是「塔的操作员」，而是「这一班的负责人」。

二、范围与非目标

2.1 本次做

  • 只在第 4、5 波加入检查单；
  • 第 4 波故障保持现状（停塔 2.5s），作为教学；
  • 第 5 波故障改为「隔离 / 旁路」二选一；
  • 结算加入「本班记录」三选一；
  • 不新增塔、敌人、地图、职业；
  • 不新增独立资源；复查花准备时间，故障处置花注意力。

2.2 本次不做

  • 模块化塔座（v0.2）；
  • 独立备件资源（v0.2）；
  • 换件 / 三级维修（v0.2）；
  • 身体改造、岗位适配数值；
  • 新塔、新怪、无尽模式。

三、机制一：班前检查单

3.1 出现时机

只在 第 4 波前 和 第 5 波前 出现，避免每波弹窗疲劳。

第 4 波前：T-07 阻尼器异响
第 5 波前：T-07 阻尼器异响 + 广播事故数

检查单出现在准备阶段，打开时暂停准备倒计时；玩家必须做一个选择，或直接关掉（等于照签）。

3.2 两张卡

卡 问题 照签 复查 照惯例
A T-07 阻尼器异响 无消耗，正常开波 花 5 秒准备时间；下一次故障停塔时长 -1s，并显示故障目标 无消耗；低报标记 +1
B 广播事故数对不上 无消耗，正常开波 花 5 秒准备时间；结算多一条「待核」线索 无消耗；低报标记 +1
  • 若准备时间不足 5 秒，复查改为花 5 供能；两者都不够时不可选。
  • 复查的收益是信息与减损，不是直接加伤害；它让玩家在「多花 5 秒」和「可能吃亏」之间选。
  • 照惯例不是「错误选项」：它省时间，但留下一笔记录，后面可能在结算/下一班出现。

3.3 为什么不做随机

v0.1 不做随机成败。检查单的收益固定、可预期，方便测试，也符合「流程是可信的」这个气质。随机可以留给 v0.2 的「虚惊 / 真故障」池。

四、机制二：故障降级

4.1 第 4 波：教学

保持现状：故障经过塔位，塔离线 2.5 秒，最多影响 2 座；不扣保障度。

波末给一条提示：

「故障处置：第 5 波起可尝试旁路。旁路能保住射程，但会拖累相邻塔。」

4.2 第 5 波：二选一

故障命中时，游戏自动暂停，弹出处置面板（不是 QTE，不给倒计时）：

故障命中 T-05 / T-06
[ 隔离 ] 2.5 秒离线，安全，但这段弧没人守
[ 旁路 ] 8 秒 50% 攻速，4 秒后相邻塔也降级 4 秒
  • 隔离：当前行为；被命中的塔离线 2.5 秒，故障继续走/烧毁；无额外风险。
  • 旁路：被命中的塔保持在线，攻速/产出 50%，持续 8 秒；第 4 秒时，相邻塔位也进入 50% 降级 4 秒；故障不继续扩散。
  • 旁路不是严格更优：它保住覆盖，但总输出下降更多，还会拖累邻居；适合「这段弧不能空」的时候。
  • 只对第 5 波生效；第 4 波仍用隔离，保证教学清晰。

4.3 降级状态

塔 正常 降级
拦截炮 单体，1.2/s 单体，0.6/s
脉冲环 范围 + 减速 范围 + 减速，伤害频率 0.4/s
补给塔 +6 供能/5s，+3 维修/波 +3 供能/5s，+1.5 维修/波

降级塔的外观：黄色闪烁边框、状态标签「DEGRADED」、射速/产出数字变黄。不要只靠颜色，加图标与文字。

五、机制三：事故记录

5.1 结算面板

胜利/失败后，在结算页多一行：

本班记录：
[ 如实 ]  [ 按惯例 ]  [ 待复查 ]
选择 文本 影响
如实 「T-07 异响，已复查；广播事故数待核。」 记录真实；下一班简报出现「已知异常」
按惯例 「系统运行正常。」 低报 +1；下一班简报更干净，但档案里留一笔
待复查 「T-07 待复查。」 中性；下一班简报出现「待复查」

v0.1 不做长期存档：记录只影响本局结算文本与下一次重试的简报（内存内），不上传、不扣资源、不加属性。

5.2 为什么不做数值奖励

如果「如实」给奖励，「按惯例」给惩罚，玩家会把它当成刷分按钮。记录应该是表达，不是收益。它的后果留到 v0.2 的审计/档案事件里。

六、数值与验收

6.1 不破坏标准班

现有脚本标准班：2 塔 + 补给 + 1 升级，B、保障度 40、59 击杀、9 漏过。

新增机制必须满足：

  • 完全不使用检查单/旁路，仍能赢，评级不变；
  • 使用复查/旁路，不出现「必选」或「必不选」；
  • 第 4 波故障仍只停塔，不弹选择；
  • 第 5 波旁路最多影响 2 座塔，不无限扩散。

一、为什么分层，而不是继续加模式

LiveBay 已经有三支柱：塔防、沉浸、放置。现在的问题不是「模式不够」，而是：

  • 模块化架构已经能承载「可替换设施」，但玩法上还没有用到。

所以扩展的方向不是「再来一种玩法」，而是：

同一班 → 同一岗位 → 同一座城
L1 班次层：这一班怎么过
L2 岗位层：这个岗位怎么变强/变复杂
L3 城市层：你不在时，城怎么活

范围：8–12 分钟一局；不新增塔/敌人/地图；只加「流程判断」。 第一版就是 14 的 N1–N3，本文补上「班次合同」和落地顺序。

一、核心目标

玩家不是「塔的操作员」，而是「这一班的负责人」。L1 增加的不是数值，而是：

  • 开波前的一次判断；
  • 故障时的一次取舍；
  • 结算时的一次记录；
  • 下一班读到上一班留下的话。

二、一班的流程

接班简报（1 屏）
  ↓
准备（30s，可提前开）
  ↓ 第 4/5 波前：检查单（暂停准备）
开波（5 波）
  ↓ 第 5 波故障：隔离 / 旁路
结算（评级 + 事故记录三选一）
  ↓
交班记录（写入本班档案）
  ↓
下一班简报（读到上一班记录）

三、机制一：班前检查单

只在第 4、5 波前出现，避免每波弹窗。

卡 触发 照签 复查 照惯例
A T-07 阻尼器异响 W4 前 无消耗 花 5s 准备；下次故障停塔 -1s，显示目标 低报 +1
B 广播事故数对不上 W5 前 无消耗 花 5s 准备；结算多一条「待核」 低报 +1
  • 准备时间不足 5s 时，复查改花 5 供能；两者都不够则不可选；
  • 打开检查单时暂停 prep 计时；
  • 照惯例不是「错误选项」：省时间，但留记录。

设计约束：每张卡 ≤2 行；不给论文；不随机。

四、机制二：故障处置

4.1 第 4 波：教学

保持现状：故障经过塔位，塔离线 2.5s，最多 2 座；不扣保障度。波末提示「第 5 波可尝试旁路」。

4.2 第 5 波：隔离 / 旁路

故障命中 T-05 / T-06
[ 隔离 ] 2.5s 离线，安全，但这段弧没人守
[ 旁路 ] 8s 50% 攻速；4s 后相邻塔也降级 4s
  • 隔离 = 安全冗余；旁路 = 覆盖冗余；
  • 旁路不是严格更优：总输出更低，还拖累邻居；
  • 只在第 5 波出现选择；第 4 波不弹面板，保证教学。

五、机制三：事故记录

结算多一行：

本班记录：[ 如实 ] [ 按惯例 ] [ 待复查 ]
选择 文本 后果
如实 「T-07 异响，已复查；广播事故数待核。」 记录真实；下一班简报出现「已知异常」
按惯例 「系统运行正常。」 低报 +1；下一班简报更干净，但档案留一笔
待复查 「T-07 待复查。」 中性；下一班简报出现「待复查」

不做数值奖励：记录是表达，不是刷分按钮。v0.1 只在本局/下一班生效，不做长期惩罚。

六、新增：班次合同（L1 的扩展骨架）

在 N1–N3 之上，加一个 3 班的小合同，用来验证「记录连续性」，不改变塔防规则：

项 规则
长度 3 班
每班 1 张「班次牌」+ 1 条「交接遗产」
班次牌 1 个轻修正：如「夜班：第一波 prep -5s」「检修：故障停塔 +0.5s」
交接遗产 上一班的记录变成下一班的 1 条简报/1 个小事件
奖励 档案条目 + 少量备件（L2 才用）
失败 不中断合同；记录「未完成」，可重试

示例：

合同：外环第七段 · 三班交接
第 1 班：安静的夜班（无修正）
第 2 班：广播检修（W5 故障提前 2s）
第 3 班：交接审计（上一班低报 → 多 1 张检查单）

合同不是「关卡链」：每班仍是 5 波、同一张图；只是把记录串起来。

范围：v0.3 起；在 L1 成立后再做。核心不是「更多塔」，而是「同一座塔长出不同岗位性格」。 一句话：塔座是 ORU 插槽，模块是备件，湾民是岗位，三者都服务于「这一班怎么修、怎么换、怎么扛」。

一、塔座模块化（2 槽）

每座塔有 2 个槽：

槽 作用 例子
核心槽 决定攻击方式/主参数 拦截炮管、脉冲线圈、补给泵
支持槽 改变代价/容错 冷却鳍、电容、旁路继电器、维修臂

规则：

  • 塔的 kind 仍只有 single/aoe/supply；
  • 模块只改「参数 + 一个标签」，不新增一套技能树；
  • 每个槽 1 个模块；换模块只能在准备/波间；
  • 拆下的模块回备件库，不损耗（或 10% 损耗，待试玩）；
  • 模块不随机掉落；通过合同/记录/城市事件获得。

1.1 模块示例

模块 槽 效果 代价
长管 核心 射程 +20% 攻速 -10%
过载电容 支持 攻速 +25% 故障时长 +1s
冷却鳍 支持 故障时长 -1s 造价 +5
旁路继电器 支持 第一次故障免疫 之后故障 +2s
维修臂 支持 每波修复 2 点 输出 -5%

每个模块都应有「不是纯加法」的代价；否则会变成数值堆叠。

1.2 与故障的关系

  • 模块可以被故障「隔离」：只停该模块，不整塔离线（高阶玩法，L2b 再开）；
  • 旁路继电器把「停机」变成「降级」，但增加后续风险；
  • 故障不再只是「停 2.5s」，而是「你装了什么东西，决定它怎么坏」。

二、备件

项 规则
来源 合同完成、记录「如实」、城市事件、拆解
用途 安装/更换模块、维修
上限 软上限，不逼每日刷
不带入 不卖、不抽、不与现实货币挂钩

备件是 L2 的「小资源」，不是第二套主经济；它只影响「这一班能不能换一个模块」。

三、湾民（3 名）

不做抽卡，不做全员养成。第一版只做 3 个有名有岗位的人：

湾民 岗位 特质 效果（小）
阿岚 维修工 手稳 故障停塔 -0.5s
老周 调度 熟流程 检查单复查少花 2s
小满 实习生 学得快 每班首次升级 -5 供能
  • 每个湾民有疲劳/心情，但不死亡、不永久伤病；
  • 分配岗位有 +10% 效率，不匹配 -10%，但可培养；
  • 效果上限小，不能替代塔与操作；
  • 湾民通过剧情/合同加入，不通过抽卡。

四、事故链（3 班合同 → 1 条链）

L2 的「长期对象」不是等级，而是一条 3 班事故链：

第 1 班：发现异响 → 记录
第 2 班：故障升级 → 隔离/旁路
第 3 班：审计/交接 → 选择谁背记录
  • 每班仍是 5 波；
  • 选择改变下一班的 1 个条件（不是永久数值）；
  • 结束后留下 1 个档案条目/1 个模块；
  • 不做多结局树，只做「记录不同」。

五、与 L1 的咬合

L1 产出 L2 用途

班次合同完成 获得模块/湾民

L2 不改变 L1 的规则，只把 L1 的记录变成 L2 的内容。

舱室 产出 升级 叙事

  • 第一版只做 2 间，不做完整舱室树；

  • 与 L2 的 3 名湾民同一批人；

  • 通过合同/剧情加入，不通过付费。

四、城市事件（1 个/月）

事件：外环停电
  ├─ 塔防入口：守一段临时防线
  ├─ 沉浸入口：读广播/做一次选择
  └─ 放置入口：分配维修工/备件

  • 完成任意 2 个入口即可，不强制三模式全玩；
  • 奖励：档案/外观/备件，不给主线硬门槛；

五、职业执照

  • 每个职业 3 级：见习 → 正式 → 带班；

  • 解锁：职业变体/新班次牌/外观，不解锁主线；
  • 不做技能树，不做等级数值膨胀。

六、档案网络

  • NPC、事故记录、班次合同、城市事件共享一套档案 ID；
  • 塔防救下的人、沉浸对话的人、放置照顾的人可以是同一个；
  • 档案只提供「世界是真的」的感觉，不提供数值；
  • 档案可在三种玩法中解锁，不强制跨模式。

一句话：玩法扩展不是往 Sim 里加 if，而是做成可启停的扩展包：有自己的 manifest、内容、模块、存档命名空间和实验开关；关掉它，主体玩法仍然完整。

目标：开发期可以不断试 L1/L2/L3 的新玩法，各自独立启停；只有通过验收的包才进入正式发布预设。

一、问题：为什么现在的扩展还不够“可插拔”

当前架构已经能装模块，但玩法扩展仍容易变成：

  • 在 Sim 或 main.gd 里加一段 if expansion == ...；
  • 新内容直接混进 numbers/ 主表；
  • 新 UI 直接改 HUD；
  • 新存档字段直接写进全局 profile；
  • 试坏了只能回滚代码，不能“关掉这个包”。

这不是模块化，而是把分支藏进主体。可插拔扩展要解决的是：

core = 稳定、可独立运行
expansion = 可选、可启停、可丢弃
core + expansion = 仍能回放/测试/发布

二、术语

词 含义
Core 基础游戏：地图、3 塔、4 敌、5 波、结算
Expansion Pack 一个可启停的玩法扩展包
Expansion Set / Preset 一次运行启用的包集合，如 baseline / l1_experiment / release
Layer L1 班次 / L2 岗位 / L3 城市；是能力标签，不是硬链
Contribution 包向核心贡献的内容/模块/UI/存档字段
Feature Flag 运行期开关；实验包默认关闭
Retired 停用但保留内容与存档，不再默认启用

三、目标架构

presets/
  baseline.json          # core only
  l1_experiment.json     # core + L1 pack(s)
  release.json           # core + stable packs only
        ↓
ExpansionRegistry         # 扫描 expansions/*/pack.json
        ↓ validate / resolve / gate
ExpansionSet              # 本次运行启用的包 + 能力
        ↓
MissionPack + ModuleRegistry + UiContributions
        ↓
MissionRuntime ← 只认接口，不认识具体包

原则：

  • Core 不 import 任何具体扩展包；
  • 包只通过 ExpansionContext 的端口/命令/事件接入；
  • 包关掉后，Core 的内容、存档、回放仍可用；
  • 包的失败不阻塞 Core 启动。

四、Pack Manifest

每个包一个 pack.json：

{
  "schema_version": 1,
  "id": "lb.exp.l1.night_shift",
  "name": "L1 · 夜班检查单",
  "version": "0.1.0",
  "state": "experimental",
  "layer": "L1",
  "variant_group": "L1.shift",
  "core_api": ">=0.1 <1.0",
  "requires": [],
  "optional": ["lb.exp.l2.racks"],
  "conflicts": ["lb.exp.l1.old_checklist"],
  "provides": ["procedure.checklist", "record.shift", "modifier.night"],
  "content": {
    "procedures": "content/procedures.json",
    "contracts": "content/contracts.json"
  },
  "modules": [
    {"id": "lb.exp.l1.night_shift.procedure", "kind": "procedure"}
  ],
  "ui": [
    {"slot": "briefing.extra", "scene": "ui/night_shift_card.tscn"}
  ],
  "flags": {
    "default": false,
    "experiment": true
  },
  "migrations": {"profile": 1}
}

4.1 字段约束

字段 规则
id 全局唯一，建议 lb.exp.<layer>.<name>；所有贡献 ID 加此命名空间
state draft / experimental / stable / retired
layer 主层；一个包只声明一个主层，跨层用 provides
variant_group 可选；同一组内互斥，用于多个 L1 班次实现对比；空表示 additive
core_api 语义化范围；不匹配则拒绝加载
requires 硬依赖；缺失则跳过该包（不阻塞 core）
optional 有则更好，没有也能跑
conflicts 冲突包；按 preset 优先级跳过
provides 能力字符串；其他包依赖能力而不是具体包
content 内容文件；加载后进入独立命名空间
modules 已注册模块 ID；不在运行时加载任意脚本
ui UI 贡献槽；不允许直接改 HUD 私有节点
flags 默认开关与实验开关
migrations 存档/内容迁移版本

五、扩展点

5.1 内容贡献

包可以贡献：

  • 地图、波次、塔、敌人；
  • 塔座模块、备件；
  • 检查单、事故记录、班次合同；
  • 城市事件、档案。

所有 ID 自动加命名空间：

lb.exp.l1.night_shift:procedure/checklist_w4
lb.exp.l2.racks:tower_module/long_barrel

Core 只读 MissionPack 的统一内容表；不关心它来自哪个包。

5.2 模块贡献

包的代码模块必须在构建期注册，运行期只按 modules[].id 启用：

ModuleRegistry
  ├─ core.map
  ├─ core.economy
  ├─ core.wave
  ├─ core.mission
  ├─ core.fault
  ├─ core.enemy
  ├─ core.tower
  └─ lb.exp.l1.night_shift.procedure
  • 不下载/不热加载外部脚本；
  • 包模块只实现 ProcedurePort / ModifierPort 等窄接口；
  • 不能直接 import core 的具体模块；
  • 关掉包 = 不注册模块、不加载内容。

5.3 UI 贡献

HUD/面板提供固定槽位：

briefing.extra
hud.badge
result.extra
settings.section

包提供场景/控件，只能放进槽位；不能替换根 HUD，不能直接操作 Sim。槽位缺失时自动跳过，不影响 core。

5.4 存档与档案

  • Profile 有 expansions 命名空间；
  • 每个包只写自己的键；
  • 包停用后，数据保留但不再读取；重新启用时跑迁移；
  • 档案条目按 pack_id 过滤；
  • 不在 core profile 里写 if pack_x。

六、加载与失败隔离

6.1 启动顺序

1. 读 preset（baseline / l1_experiment / release）
2. 扫描 expansions/*/pack.json
3. schema 校验；未知字段 warning，不崩
4. 解析 requires / optional / conflicts
5. 过滤：core_api 不匹配、状态 retired、flag 关闭
6. 拓扑排序；缺依赖的包跳过（不阻塞无依赖包）
7. 合并内容到 MissionPack；注册模块/UI/事件
8. 启动 MissionRuntime

6.2 失败策略

失败 行为
单个 pack.json 坏 跳过该包，core 启动，写诊断
缺硬依赖 跳过该包及其依赖者
版本不匹配 跳过，提示需要哪个 core_api
冲突 按 preset 优先级保留一个，另一个跳过
内容重复 ID 拒绝该包，不覆盖 core
模块注册失败 禁用该包，不半加载
UI 槽位缺失 跳过该 UI，不影响规则
存档迁移失败 包进入只读/停用，core 存档可用

核心原则：包失败是“这个包没上机”，不是“整座城断电”。

6.3 Feature Flag

  • 包默认开关来自 preset，玩家可在设置中关闭实验包；
  • baseline 永远只含 core；
  • l1_experiment / l2_experiment 是内部预设；
  • 正式发布只使用 release preset；
  • 关闭包不删除存档，只停止读取。

七、分层可插拔

层 包示例 可独立启用 依赖
L1 夜班检查单、3 班合同 是 只依赖 core
L2 塔座 2 槽、备件、湾民 是 只依赖 core API；不强制 L1 包
L3 舱室、城市事件、档案 是 只依赖 core Meta API
跨层 L2 需要读写 L1 记录 可选 通过 requires 或 optional 声明，不直接 import
  • 官方 release 可以按 L1→L2→L3 顺序启用；
  • 开发实验 可以只启用 L2、不启用 L1，验证“模块本身是否成立”；
  • 包可以声明 layer 但不强迫玩家按顺序玩。

八、多个 L1 变体与 A/B 对比

这是本文最需要补的一层：多个 L1 班次包可以同时存在，但不应该无脑叠加。

8.1 两种包：additive / variant

类型 variant_group 行为 例子
additive 空 可与其它包共存；贡献叠加 L1 检查单 + L1 记录
variant 非空 同组互斥；一个 preset 只能选一个 L1 夜班包 A / B / C

规则：

  • 同 variant_group 的包不能同时启用；
  • 不同组可以共存，但仍受 requires / conflicts 约束；
  • 若 preset 没选、组内又有多个可用包：拒绝启用该组并报错，不静默挑一个；
  • baseline 永远不包含任何 variant；
  • 一个 variant 可以依赖 additive 包，例如「L1 夜班 B」依赖「L1 记录基础包」。

8.2 Preset 用槽位选择

{
  "id": "livebay.l1_compare",
  "core_version": "0.1.0",
  "slots": {
    "L1.shift": "lb.exp.l1.night_shift_b"
  },
  "packs": [
    "lb.exp.l1.record_base"
  ]
}
  • slots 选 variant；packs 加 additive；
  • 同一个 variant_group 只能出现在一个 slot 值里；
  • 缺 slot 的 variant 不加载；
  • 这样可以在不改代码的情况下切换 A/B/C 实现。

8.3 多种实现如何对比

建议加一个实验对比器（不进入正式发行）：

  • 对比器可以只在内部 preset/CLI 使用，不暴露给玩家；
  • 黑匣子记录 set_hash，保证对比可复现。

一、一句话

不是「白色 + 橙色」的科幻，而是「有人值班、坏了能修」的未来。

按 D01=B，画面要在「温暖、可靠」的底子上保留磨损、补丁与不平等：干净的公共区域与将就的维修通道并存，不把整座城做成统一的乐园。

二、三条视觉原则

  1. 可维修：每个物件都要有接缝、标签、接口、备份；拒绝无缝全息。
  2. 可读：玩家一眼能分清「这是什么、归谁管、现在什么状态」；UI 是世界观的一部分。
  3. 有人味：允许旧、允许不整齐、允许个人物品；但结构完好、随时可用。

四、形状语言

  • 圆角矩形为主，圆角半径小（4–8px），像面板与屏幕；

  • 标签：小矩形色块 + 等宽字 + 编号，贴在任何东西上；
  • 管线：用 2–3px 的折线，带接头圆点；不要软管乱舞；
  • 仪表：圆表盘、条形表、七段数字；不要全息环；

一句话：可以开发，但第一版不应是独立游戏编辑器，而应是 Godot 编辑器里的 LiveBay Tools 插件：在真实场景上拖塔位、看射程、调波次、即时预览；数据仍走 numbers/ → game/data/ 的单一源。

结论：先做插件 + Python 数据桥（2–3 周 MVP），独立 Web 编辑器作为 v0.3+ 的可选分支，不在现在做。

一、现在的编辑体验

当前做一次「塔位/波次」调整，实际要走：

改 numbers/*.md 表格
  → python3 tools/export_numbers.py
  → ./run.sh test
  → ./run.sh run
  → 看画面 / 试玩
  → 发现问题，回到第一步

问题不是“不能改”，而是：

  • 空间关系靠脑补：塔位坐标、路径距离、射程覆盖，要改完运行才知道；
  • 波次节奏靠读表：count / interval / delay 的叠加效果不直观；
  • 数值与画面分离：表格里改一个数，画面要重启才看到；
  • 试错成本高：每次调整都要跨 Markdown、JSON、Godot 三个界面；
  • 非工程人员门槛高：策划/美术很难独立完成一次“摆一摆看效果”。

这正好是「所见即所得」要解决的问题。

二、对 LiveBay 来说，WYSIWYG 是什么

不是“做一个能造整款游戏的编辑器”，而是：

WYSIWYG ⇔
  编辑的对象 = 运行时真正读取的数据
  ∧ 从编辑到看到结果 ≤ 5 秒
  ∧ 不需要手改 JSON
  ∧ 保存前就能发现非法数据

具体到 v0.1，最有价值的 WYSIWYG 是四件事：

  1. 地图：拖路径点、塔位、基地，实时看弧线、距离、覆盖；
  2. 塔位：把塔拖到槽里，看射程圈、造价、DPS、覆盖到的路径段；
  3. 波次：拖时间轴，看每一组敌人的生成窗口、总 HP、奖励、漏过伤害；
  4. 预览：在当前地图上直接跑 1–5 波，暂停/单步/加速，不用切窗口。

不包含：剧情编辑器、UI 编辑器、动画编辑器、美术资源编辑器、完整关卡生成器。

三、四种方案

方案 A：Godot EditorPlugin（推荐）

在 Godot 编辑器里做一个 LiveBay Tools 插件：

  • Dock：地图、塔、波次、校验；
  • 2D 视口叠加层：路径、塔位、射程、敌人生成点；
  • 选中塔位/路径点后直接拖；
  • 右侧 Inspector 显示数值；
  • 「预览」按钮运行当前场景，或内嵌一个 SubViewport 跑模拟；
  • 保存时写回 numbers/ 表格，调用导出脚本，再重载。

优点：

  • 只有一个渲染器/运行时，不会出现“编辑器里好看、游戏里不一样”；
  • 直接复用 sim.gd、地图数据、塔数据、现有 UI；
  • Godot 自带撤销/重做、场景选择、检查器、快捷键；
  • 开发量最小，2–3 周可做 MVP；
  • 对工程/策划都够用。

缺点：

  • 界面是 Godot 编辑器，非工程人员仍会觉得“像 IDE”；
  • 插件 API 有学习成本，视口叠加的交互要自己写；
  • 移动端/远程协作不友好；
  • 不适合未来“非技术创作者”大规模使用。

方案 B：独立 Web 编辑器

Tauri/Electron + React + Canvas/WebGL，自己做一套编辑界面：

  • 地图/塔位/波次可视化；
  • 通过本地服务调用 Godot headless 或 Python 导出；
  • 预览用 Web 端重画的 2D 渲染器，或嵌 Godot Web export。

优点：界面友好、可远程、易做协作/权限/模板。

缺点：

  • 渲染重复：要么重写一套 2D 渲染，要么嵌 Godot Web，二者都贵；
  • 需要维护第二套 schema、第二套输入、第二套预览；
  • 导出/预览链路长，真正的 WYSIWYG 反而更难保证；
  • 2–4 个月起步，且会持续吃维护成本。

方案 C：独立桌面应用 + 嵌入 Godot 运行时

用 GDExtension / Godot as a library 把运行时嵌进自己的应用：

  • 界面自由，预览真实；
  • 但 Godot 的嵌入能力并不成熟，跨平台打包、输入、调试都复杂；
  • 3–6 个月起步，风险最高；
  • 对当前团队规模不划算。

方案 D：不做编辑器，只做数据工具

  • 改进 Markdown/CSV 编辑体验；
  • 加 live reload、校验、快捷键、表头提示；
  • 3–5 天可做；
  • 但空间关系仍然靠脑补，不是真正的 WYSIWYG。

方案 E：混合（长期）

  • Godot 插件负责地图/塔位/预览；
  • Web 端负责数据表/批量编辑/协作；
  • 共享同一套 schema 与 Python bridge；
  • 适合团队扩大到 3 人以上、内容量明显增加之后。

五、推荐路线

5.1 形态

Godot EditorPlugin，名字 LiveBay Tools，放在：

game/addons/livebay_tools/
  plugin.cfg
  plugin.gd
  dock.tscn / dock.gd
  viewport_overlay.gd
  data_bridge.gd
  commands/…

5.2 数据桥

不要在 GDScript 里重写 Markdown 表格解析器。做一个 Python bridge：

game/addons/livebay_tools/bridge.py
  read   → numbers/*.md → JSON（给编辑器）
  write  → 编辑后的 JSON → numbers/*.md
  export → 调 tools/export_numbers.py
  check  → 调 ./run.sh numbers-check

插件通过 OS.execute("python3", ["…/bridge.py", …]) 调用；Windows/macOS 都可用。这样：

  • 编辑器不拥有第二套 schema；
  • Markdown 仍是唯一源（TECH-A1）；
  • 现有 export_numbers.py 继续做导出；
  • 未来 Web 编辑器也能复用同一个 bridge。

5.3 数据流

numbers/*.md（唯一源）
   ⇅  bridge.py（读写表格）
LiveBay Tools（Godot 插件）
   ↓ 保存
bridge.py write → numbers/*.md
   ↓
export_numbers.py → game/data/*.json
   ↓
Sim / 场景重载 / 内嵌预览

关键约束：编辑器只能通过 bridge 写 Markdown，不能直接写 game/data/*.json；否则会破坏单一源。

11_待人类裁决清单 · 规则分层与冲突

一句话：AI 可以提方案，但不能替人拍板；人类原始设定高于一切文档与代码。 形式化：∀d ∈ Decision: author(d) ∈ Human，且 Concept ≻ Decision ≻ RootRule ≻ CategoryRule ≻ Doc ≻ Code。

一、形式化表述

设：

  • H = 人类（项目负责人）
  • A = AI
  • P = 提案集合
  • D = 裁决集合
  • C = 概念设定（人类原始文本）
  • R₀ = 根规则
  • R₁ = 类别规则
  • Doc = 其他文档
  • Code = 实现

公理：

1. D ⊆ H × P            （裁决只能由人类做出）
2. A: P → P             （AI 只能把提案变成提案）
3. ∀d ∈ D: author(d) = H
4. C ≻ D ≻ R₀ ≻ R₁ ≻ Doc ≻ Code
5. ¬∃x ∈ Canon: author(x) = A

其中 ≻ 表示“冲突时优先”。

二、通俗解释

AI 很擅长把“下一步”做得看起来很合理：加一个系统、补一段设定、扩一章内容。每一步都对，连起来却可能离开最初想做的游戏。

这条规则的意思是：方向盘必须固定在人的手里。AI 可以画地图、列选项、算代价、写反方论证，但不能把“我觉得好”写成“项目就是这样”。

当文档、规则、代码和人的想法冲突时，不是“代码已经这样了所以算数”，而是按优先级往上找：概念设定最大，其次是人类裁决，再是规则，再是文档，最后才是代码。

三、条款

MUST

  1. M1：所有主题、范围、商业模式、核心体验的决定，必须能追溯到人类；AI 不得自行升级为 canon。
  2. M2：docs-human/ 是人类原始文本；AI 默认只读，只有人类明确要求时才可改，且只改被要求的部分。
  3. M3：每个已裁决问题必须有 D-ID，记录在 11_待人类裁决清单。
  4. M4：概念、裁决、规则与代码冲突时，按 C ≻ D ≻ R₀ ≻ R₁ ≻ Doc ≻ Code 处理；代码是最后一位。
  5. M5：AI 生成的文档必须在元数据里标 source、authority，不得伪装成人类原文。

SHOULD

  1. S1：AI 的每次建议都给出至少两个选项与代价，不只给一个“最佳答案”。
  2. S2：当 AI 不确定人类意图时，停下来问，不要用“为了完整性”替人选。
  3. S3：裁决记录只追加，不回删；落选方案保留并标注「已否决」。

MAY

  1. Y1：AI 可以写虚构、参考、反方论证与原型；只要标明「非决定」。
  2. Y2：AI 可以在 docs-ai/ 里提出新规则草案；生效仍需人类确认。

四、判定与验收

一条内容是否合规，依次问：

1. 它是否声称了某个 canon？        → 是：必须有人类裁决或人类原文
2. 它是否改了 docs-human/？        → 是：必须有人类明确指令
3. 它与更高优先级冲突吗？          → 是：以更高优先级为准
4. 它的元数据是否标明来源与决策权？ → 否：不合规

机器可查的部分：

  • 文档 YAML 是否有 source / authority；
  • 裁决是否有 D-ID；
  • docs-human/ 的 diff 是否只包含人类要求的内容；
  • 规则索引中的 ID 是否唯一。

五、反例

  • AI 在文档里写「项目决定采用 X」，但没有任何人类裁决记录；
  • 代码里已经实现了 X，于是文档把 X 写成「既定设定」；
  • AI 以「整理」为名改写 docs-human/概念设定.md 的正文；
  • 把「AI 建议」当成「人类已定」，跳过 D-ID。

六、引用与变更

  • 被引用处：11_待人类裁决清单、README、项目 README；
  • 变更：只有人类可以修改本规则；修改需提升规则版本，并说明代价；
  • 关联：ROOT-B0、ROOT-C0。

一句话：规则分三层：a 层是不可轻易改的公理，b 层是结构约束，c 层是表达约束；冲突时 a > b > c。 形式化：Layer = {a,b,c}，stability(a) > stability(b) > stability(c)；Conflict ⇒ priority(a) > priority(b) > priority(c)。

一、形式化表述

Rule = (id, layer, category, status, clauses, acceptance)
layer ∈ {a, b, c}
category ∈ {root, biz, design, art, tech}
stability(a) > stability(b) > stability(c)

priority(r) = (is_root(r), layer_rank(r), specificity(r), date(r))
is_root: root = 1, category = 0
layer_rank: a = 3, b = 2, c = 1

冲突处理：

conflict(r1, r2) ⇒ choose argmax priority(r)
if priority(r1) = priority(r2) ⇒ stop ∧ ask(Human)

二、通俗解释

  • a 层：这个项目为什么存在。比如「玩家是岗位人」「单一数据源」。改它等于换项目，必须人类拍板。
  • b 层：项目怎么运转。比如「班次循环」「三环三套语法」。可以调，但要评审并同步文档。
  • c 层：项目长什么样、怎么写。比如色板、命名、引用格式。可以快速改，但要有验收。

规则不是越多越好。一条规则只有在能被违反、也能被检查时，才值得存在。

三、条款

MUST

  1. M1：每条规则必须有唯一 ID，格式 <CAT>-<LAYER><N>，如 DES-B2。
  2. M2：规则文件必须放在对应类别目录；文件名以层字母 a/b/c 开头。
  3. M3：a 层规则修改必须有人类裁决 + 版本升级；b 层需规则评审；c 层需文档更新与验收。
  4. M4：每条规则必须写「判定与验收」；没有验收方式的规则视为未生效。
  5. M5：规则冲突按 root > category、a > b > c、具体 > 一般、新裁决 > 旧裁决 处理。
  6. M6：同层同类的两条规则仍冲突时，停止实现，交人类裁决；不得用代码现状反推。

SHOULD

  1. S1：规则正文先给形式化，再给通俗解释；形式化是给检查用的，通俗解释是给人用的。
  2. S2：每条规则至少给一个反例，帮助判断边界。
  3. S3：规则引用用 ID + 相对链接，不只写文件名。

MAY

  1. Y1：c 层规则可以在版本内调整，不必每次走完整裁决。
  2. Y2：规则可以引用其他规则；被引规则失效时，引用方必须复核。

四、判定与验收

valid(rule) ⇔
  unique(id) ∧
  layer(id) = layer(file) ∧
  category(id) = parent_dir(file) ∧
  has_acceptance(rule) ∧
  referenced_in_index(rule)

检查清单：

五、反例

  • 把一条 a 层规则放进 c 文件，降低修改门槛；
  • 两条规则对同一个问题给出相反要求，却都不标优先级；
  • 规则只写「应该做好玩」，没有可判定的验收；
  • 规则 ID 重复，引用时指向另一条规则；
  • 代码已经违反规则，却把规则改成「代码现状」。

一句话：文档有统一的元数据、命名与引用方式；生成物从源生成，不手改。 形式化：Doc = (Meta, Body)，Meta ⊇ {title, doc_type, status, date, source, authority}；Generated = f(Source)。

一、形式化表述

Doc = (Meta, Body)
ReqMeta = {title, doc_type, status, date, source, authority}
RuleDoc = Doc where Meta ⊇ ReqMeta ∪ {rule_id, layer, category}

Citation = ID × RelLink
valid_link(p) = resolve(dir(p), href) exists

Generated(x) ⇔ x = f(Source) for some Source
hand_edit(Generated) ⇒ invalid

二、通俗解释

一份文档不只是正文。它还需要回答：这是什么、谁说了算、什么时候写的、由谁写的。如果这些信息缺失，读者（包括未来的 AI）就会把「参考」当成「决定」。

规则引用也一样：不要只写「按设计规则」，要写 DES-B2 并给出链接。这样规则改名或移动时，引用能被检查出来。

三、条款

MUST

  1. M1：所有 LiveBay 文档以 YAML frontmatter 开头，至少含 title、doc_type、status、date、source、authority。

  3. M3：文件名可排序：设计文档用 NN_主题.md；规则用 aNN_主题.md / bNN_ / cNN_。
  4. M4：内部链接用相对路径；链接目标必须存在；不得依赖本机绝对路径。
  5. M5：生成物（HTML、game/data/*.json、PNG 设定图）不得手改；改源后重新生成。
  6. M6：规则引用写 ID + 相对链接；文档 YAML 的 rules 字段列出所遵循的规则。

SHOULD

  1. S1：正文简体中文；ID、字段名、代码用英文。
  2. S2：日期取东八区系统时间；不手写「今天」。
  3. S3：一篇文档一个主题；超过 4000 字考虑拆分。
  4. S4：文档之间用「上游/关联」链接，不用复制全文。

MAY

  1. Y1：非规则文档可以没有 rules 字段；但涉及设计决定时 SHOULD 加。
  2. Y2：概念图、小说等参考物可以在 YAML 标 status: 非 canon。

  yaml_parses(doc) ∧
  ReqMeta ⊆ keys(doc) ∧
  all_links_exist(doc) ∧
  (is_rule(doc) ⇒ rule_meta_valid(doc))

一句话：基础游戏买断；内购只卖外观与扩展内容，不卖数值、不抽卡、不订阅。 形式化：Revenue = BasePrice + Σ Cosmetics + Σ Expansions，且 IAP ∩ Power = ∅。

一、形式化表述

IAP = Cosmetics ∪ Expansions
Revenue = BasePrice + Σ_{i∈Cosmetics} price(i) + Σ_{j∈Expansions} price(j)
allowed(sku) ⇔ sku ∈ IAP
∀p ∈ Power: p ∉ IAP
¬gacha ∧ ¬subscription ∧ ¬energyGate

Power 包括：属性、伤害、射程、资源产出、关卡解锁、胜率、降低难度。

二、通俗解释

玩家先买游戏，买到的是完整的核心体验。之后愿意花钱，可以买好看（涂装、舱室装饰、原声）或更多内容（扩展章节），但不能买更强。

这条规则不是道德洁癖，而是设计保护：一旦能买数值，关卡难度、经济曲线、掉落奖励都会被迫围绕付费设计，最后游戏会变成另一款游戏。

三、条款

MUST

  1. M1：基础游戏买断，包含完整主线与核心玩法；不得把核心玩法切进内购。
  2. M2：内购只允许外观、装饰、原声、扩展章节。
  3. M3：不得出售属性、伤害、射程、资源产出、关卡解锁、胜率、降低难度。
  4. M4：不得抽卡、不得订阅、不得体力/限时数值礼包。
  5. M5：任何 SKU 上线前必须通过 allowed(sku) 判定，并在商店页写明内容。

SHOULD

  1. S1：免费 Demo 可用于转化，但不承担主要收入。
  2. S2：扩展内容应能独立说明「多了什么」，不靠数值墙逼买。
  3. S3：内购价格与基础游戏价格保持同一量级，不做“一刀 648”。

MAY

  1. Y1：可以做外观捆绑包、原声集、设定集。
  2. Y2：可以做“支持者包”，但内容必须是外观/幕后，不含数值。

一句话：先做 10 分钟垂直切片；任何新功能都要先证明它服务这个切片，否则不做。 形式化：admit(f) ⇔ serves(f, Slice) ∧ cost(f) ≤ B ∧ reversible(f)。

一、形式化表述

Slice = (1 profession, 1 map, 5 waves, 1 loop)
B = 当前版本的预算（人时 / 内容量 / 风险）
admit(f) ⇔
  serves(f, Slice) ∧
  cost(f) ≤ B ∧
  reversible(f) ∧
  has_acceptance(f)

Scope(t+1) = Scope(t) ∪ {f} 仅当 admit(f) 且 Gate 通过

二、通俗解释

「这个功能也不错」是项目最常见的死因。切片规则不是反对好想法，而是要求好想法先排队：

  • 它让 10 分钟更好玩了吗？
  • 它能在当前预算内做完吗？
  • 它改错了能撤回吗？
  • 它有明确的验收方式吗？

四个都答「是」，才进当前版本；否则进 backlog，不偷偷塞进代码。

三、条款

MUST

  1. M1：v0.1 只承诺「1 职业 / 1 图 / 5 波 / 1 循环」；超出部分默认不做。
  2. M2：每个新功能必须有：假设、验收、成本、可逆性；缺一项不立项。
  3. M3：新增职业、地图、玩法模式必须过 Gate，不得在“顺手”中加。
  4. M4：功能失败时回退，不保留半成品分支。
  5. M5：范围变化必须记录到 11_待人类裁决清单。

SHOULD

  1. S1：每个版本只主推一个“新问题”，不同时加职业、地图、玩法。
  2. S2：先做纸面原型/数据原型，再进引擎。

  2. S2：沉浸一局 5–8 分钟，3–5 个选择。

一句话：有意义的选择至少有两个选项，每个选项都有代价，且不存在“永远正确”的选项。 形式化：|Choice| ∈ [2,3]，∀o ∈ Choice: cost(o) > 0，¬∃o: dominates(o)。

一、形式化表述

Choice = {o₁, …, oₙ}
n ∈ {2, 3}
∀o ∈ Choice: cost(o) > 0
¬∃o ∈ Choice: ∀o' ∈ Choice, utility(o) ≥ utility(o') ∧ cost(o) ≤ cost(o')

Consequence = immediate ⊕ delayed

二、通俗解释

好选择不是“选对的”，而是“选你愿意承担哪一种代价”。

  • 按规矩：保护制度，伤害一个人；
  • 通融：帮助一个人，累积风险；
  • 折中：两边都不满意，但把决定留给下一班。

三、条款

MUST

  1. M1：关键选择必须有 2–3 个选项，不得只有“接受/拒绝”。
  2. M2：每个选项至少有一个可见代价（关系、资源、风险、时间、记录）。
  3. M3：不得存在严格支配选项（某选项全面更优且代价更低）。
  4. M4：后果必须能被玩家感知：即时反馈或延迟记录，不能“选了等于没选”。
  5. M5：不得用“隐藏最优解”惩罚玩家；信息可以不全，但不能骗。

SHOULD

  1. S1：代价最好落在不同维度：一个伤关系，一个伤资源，一个伤时间。
  2. S2：允许“没有完美答案”的中间项（如“待复查”）。
  3. S3：选择后果写进交接记录/湾民档案，跨模式可见。

MAY

  1. Y1：可以有“明显更坏”的选项，用于表达角色的道德底线。
  2. Y2：可以有“暂时看不出后果”的选项，但要在后续兑现。

valid(choice) ⇔

一、形式化表述

二、通俗解释

外敌是“碎片、乱流、重壳”；内部威胁是“故障、低报、维护欠账、流程漏洞”。后者更接近这个项目的核心：城不是被一拳打穿的，是被很多“不碍事”磨穿的。

故障的玩法表达要克制：

  • 它不直接扣保障度；
  • 它只让最多 2 座塔离线 2.5 秒；
  • 它从湾口反向来，打乱“只守入口”的布局；
  • 它给玩家一个“要不要为小异常多做一步”的选择。

低报事故不是“反派隐瞒真相”的阴谋剧，而是制度性的轻描淡写：广播说 0 起，记录里有一行“待复查”，玩家可以看见，但游戏不替他下结论。

三、条款

MUST

  1. M1：内部威胁必须与外部威胁有不同的玩法效果，不能只是换皮怪。
  2. M2：故障不得直接扣保障度；它通过停塔间接造成漏过。
  3. M3：故障同时影响塔数 ≤ 2，时长在 v0.1 为 2.5s；提高需人类裁决。
  4. M4：低报事故只能通过记录、广播、NPC 的“按惯例”等线索表达，不得用旁白直接揭晓。
  5. M5：失败结算必须有一份“事故报告”，不能只弹失败。

SHOULD

  1. S1：故障从湾口反向来，迫使玩家在中段留冗余。
  2. S2：广播的“0 起”与记录里的“待复查”形成对照。
  3. S3：玩家可以做“多写一句”的动作；系统提示“超出模板长度”是奖励，不是惩罚。

MAY

  1. Y1：后续可以加“维护欠账”“预算冻结”等内部威胁，但一次只加一种。
  2. Y2：可以让低报在多个班次后才产生后果，但不能永远不兑现。

一句话：sim.gd 只算规则，不画东西；main.gd 只画东西，不算规则；两者用信号通信。 形式化：Sim: (State, Input) → State，View: State → Render，Sim ∩ Draw = ∅。

一、形式化表述

Sim: (State, Input) → State
View: State → Render
Sim ∩ Draw = ∅
View ∩ Rules = ∅
deterministic(Sim, dt) = true

Sim --signal--> View
View --command--> Sim

二、通俗解释

塔防的规则（敌人移动、塔索敌、伤害、波次、评级）放在一个不依赖窗口的模拟层里；画面（节点、动画、特效、HUD）放在视图层。

好处：

  • 可以在无头模式跑测试，几秒验证 5 波；
  • 改画面不会改坏数值；
  • 同一个模拟可以接不同视图（PC、移动、调试）；
  • 回归测试稳定，不靠“看起来对”。

三、条款

MUST

  1. M1：sim.gd 不得引用 Node2D、Control、draw_*、场景树节点或任何渲染 API。
  2. M2：main.gd 不得复制规则（伤害公式、索敌、波次推进、评级）。
  3. M3：模拟必须可在无窗口环境运行，固定步长可复现。
  4. M4：视图只读模拟状态，通过信号更新；不得直接改模拟内部字段。
  5. M5：所有玩法数值从数据加载，不写死在模拟或视图。

SHOULD

  1. S1：模拟状态尽量用纯数据（Dictionary/Array），便于快照与测试。
  2. S2：视图层可以有动画插值，但不得改变模拟结果。
  3. S3：测试直接驱动 Sim.step(dt)，不启动场景。

MAY

  1. Y1：可以为调试在视图层显示模拟内部值，但不得写回。
  2. Y2：可以为演出加“表现时间”，但必须与模拟时间分离。

一句话：能改数据就不改结构；每个改动都要能回退，半成品不进主线。 形式化：prefer(Data) > prefer(Code)，change ⇒ ∃rollback。

一、形式化表述

Change = Data ∪ Code
prefer(Data) > prefer(Code)
∀c ∈ Change: ∃r: apply(r, apply(c, S)) = S

content ∈ Data
logic ∈ Code
half_done ∉ main

二、通俗解释

塔、敌人、波次、地图、经济参数，都是数据；加一座塔、改一波敌人，不应该改代码。代码只负责“怎么跑”，不负责“具体是什么”。

可逆的意思很具体：

  • 改坏了能回退；
  • 新功能能用开关/数据关掉；
  • 半成品不合并进主线；
  • 一次只改一个变量，方便定位。

三、条款

MUST

  1. M1：内容（塔/敌人/波次/地图/经济）必须数据驱动；不得在代码里写 if id == ... 配内容。
  2. M2：每个功能必须能回退：数据回滚、提交回滚或开关关闭。
  3. M3：不得把半成品、调试代码、临时资源合并进主线。
  4. M4：一次提交只做一件事；移动/改名与内容改写尽量分开。
  5. M5：生成物由源生成，不手改（HTML、JSON、PNG）。

SHOULD

  1. S1：先用最小数据改动验证，再决定要不要写代码。
  2. S2：新系统先做“可关闭”的入口。
  3. S3：提交信息写清“怎么回退”。

MAY

  1. Y1：可以保留调试开关，但必须默认关闭并标注。
  2. Y2：可以保留旧数据字段一个版本，用于兼容。

四、判定与验收

valid(change) ⇔
  content_in_data ∧
  rollback_exists ∧
  no_debug_in_main ∧
  one_purpose(commit)

检查：

  • 在 main.gd 里写死“第 5 波出 4 个重壳”；
  • 新玩法没有开关，失败只能删代码；
  • 把 .tmp、测试截图、调试打印提交进主线；
  • 一个提交同时改名、改逻辑、改数值。

一句话：每次非琐碎改动都要跑对应检查；检查失败不静默绕过。 形式化：Accept = Tests ∧ ExportCheck ∧ HeadlessCheck ∧ LinkCheck ∧ ThemeCheck。

一、形式化表述

Accept(change) ⇔
  tests(change) = PASS ∧
  export_check(change) = PASS ∧
  headless_check(change) = PASS ∧
  link_check(change) = PASS ∧
  theme_check(change) = PASS

fail(any) ⇒ stop ∧ report

二、通俗解释

“看起来对”不算验收。不同的改动有不同的证据：

  • 改玩法/数值：无头测试 + 启动检查；
  • 改数值表：导出检查；
  • 改文档链接：链接检查；
  • 改生成 HTML：三态检查；
  • 改美术：尺寸/文件/链接检查。

验收不是给别人看的，是防止这次改动把上次的东西弄坏。

三、条款

MUST

  1. M1：改玩法/模拟，必须跑 ./run.sh test，全过。
  2. M2：改数值表/导出，必须跑 ./run.sh numbers-check。
  3. M3：改场景/脚本，必须跑 ./run.sh check，退出码 0。
  4. M4：改文档链接，必须跑 tools/check_links.ts。
  5. M5：改生成 HTML，必须跑 design/tools/check_html_theme.ts，且满足 R-016。
  6. M6：检查失败必须报告命令、退出码、关键错误；不得用 --no-verify 静默绕过。

SHOULD

  1. S1：测试数量只增不减；删测试需说明理由。
  2. S2：修 bug 时先加一个会失败的断言，再修。
  3. S3：提交信息写清跑了哪些检查。

MAY

  1. Y1：纯文案/图片替换可以只跑链接与尺寸检查。
  2. Y2：紧急修复可先提交，但必须在同一天补检查并记录。

四、判定与验收

PASS ⇔
  ./run.sh test            → 73/73
  ./run.sh numbers-check   → 全部一致
  ./run.sh check           → exit 0
  node tools/check_links.ts → 0 broken
  check_html_theme          → all pass

测试数量随版本增长，以实际输出为准；当前为 73 项。

五、反例

  • 改了 sim.gd 不跑测试，靠手玩两分钟；
  • 改了数值表不导出，JSON 还是旧的；
  • 链接 404 但“内容没问题”；
  • HTML 只有浅色，深色下不可读；
  • 检查失败后用 --no-verify 强推。

  • 被引用处：12_技术方案、项目 README、game/tests/run_sim.gd；
  • 变更：b 层，规则评审 + 检查脚本同步；
  • 关联：TECH-A2、ROOT-C0。
