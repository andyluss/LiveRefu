一句话：可以开发，但第一版不应是独立游戏编辑器，而应是 Godot 编辑器里的 LiveBay Tools 插件：在真实场景上拖塔位、看射程、调波次、即时预览；数据仍走 numbers/ → game/data/ 的单一源。

结论：先做插件 + Python 数据桥（2–3 周 MVP），独立 Web 编辑器作为 v0.3+ 的可选分支，不在现在做。

一、现在的编辑体验

当前做一次「塔位/波次」调整，实际要走：

改 numbers/*.md 表格
  → python3 tools/export_numbers.py
  → ./run.sh test
  → ./run.sh run
  → 看画面 / 试玩
  → 发现问题，回到第一步

问题不是“不能改”，而是：

  • 空间关系靠脑补：塔位坐标、路径距离、射程覆盖，要改完运行才知道；
  • 波次节奏靠读表：count / interval / delay 的叠加效果不直观；
  • 数值与画面分离：表格里改一个数，画面要重启才看到；
  • 试错成本高：每次调整都要跨 Markdown、JSON、Godot 三个界面；
  • 非工程人员门槛高：策划/美术很难独立完成一次“摆一摆看效果”。

这正好是「所见即所得」要解决的问题。

二、对 LiveBay 来说，WYSIWYG 是什么

不是“做一个能造整款游戏的编辑器”，而是：

WYSIWYG ⇔
  编辑的对象 = 运行时真正读取的数据
  ∧ 从编辑到看到结果 ≤ 5 秒
  ∧ 不需要手改 JSON
  ∧ 保存前就能发现非法数据

具体到 v0.1，最有价值的 WYSIWYG 是四件事：

  1. 地图：拖路径点、塔位、基地，实时看弧线、距离、覆盖；
  2. 塔位：把塔拖到槽里，看射程圈、造价、DPS、覆盖到的路径段；
  3. 波次：拖时间轴，看每一组敌人的生成窗口、总 HP、奖励、漏过伤害；
  4. 预览：在当前地图上直接跑 1–5 波，暂停/单步/加速，不用切窗口。

不包含：剧情编辑器、UI 编辑器、动画编辑器、美术资源编辑器、完整关卡生成器。

三、四种方案

方案 A：Godot EditorPlugin（推荐）

在 Godot 编辑器里做一个 LiveBay Tools 插件：

  • Dock：地图、塔、波次、校验；
  • 2D 视口叠加层：路径、塔位、射程、敌人生成点；
  • 选中塔位/路径点后直接拖；
  • 右侧 Inspector 显示数值；
  • 「预览」按钮运行当前场景，或内嵌一个 SubViewport 跑模拟；
  • 保存时写回 numbers/ 表格，调用导出脚本，再重载。

优点：

  • 只有一个渲染器/运行时，不会出现“编辑器里好看、游戏里不一样”；
  • 直接复用 sim.gd、地图数据、塔数据、现有 UI；
  • Godot 自带撤销/重做、场景选择、检查器、快捷键；
  • 开发量最小，2–3 周可做 MVP；
  • 对工程/策划都够用。

缺点：

  • 界面是 Godot 编辑器，非工程人员仍会觉得“像 IDE”；
  • 插件 API 有学习成本，视口叠加的交互要自己写；
  • 移动端/远程协作不友好；
  • 不适合未来“非技术创作者”大规模使用。

方案 B：独立 Web 编辑器

Tauri/Electron + React + Canvas/WebGL，自己做一套编辑界面：

  • 地图/塔位/波次可视化；
  • 通过本地服务调用 Godot headless 或 Python 导出；
  • 预览用 Web 端重画的 2D 渲染器，或嵌 Godot Web export。

优点：界面友好、可远程、易做协作/权限/模板。

缺点：

  • 渲染重复：要么重写一套 2D 渲染，要么嵌 Godot Web，二者都贵；
  • 需要维护第二套 schema、第二套输入、第二套预览；
  • 导出/预览链路长，真正的 WYSIWYG 反而更难保证；
  • 2–4 个月起步，且会持续吃维护成本。

方案 C：独立桌面应用 + 嵌入 Godot 运行时

用 GDExtension / Godot as a library 把运行时嵌进自己的应用：

  • 界面自由，预览真实；
  • 但 Godot 的嵌入能力并不成熟，跨平台打包、输入、调试都复杂；
  • 3–6 个月起步，风险最高；
  • 对当前团队规模不划算。

方案 D：不做编辑器，只做数据工具

  • 改进 Markdown/CSV 编辑体验；
  • 加 live reload、校验、快捷键、表头提示；
  • 3–5 天可做；
  • 但空间关系仍然靠脑补，不是真正的 WYSIWYG。

方案 E：混合（长期）

  • Godot 插件负责地图/塔位/预览；
  • Web 端负责数据表/批量编辑/协作；
  • 共享同一套 schema 与 Python bridge；
  • 适合团队扩大到 3 人以上、内容量明显增加之后。

五、推荐路线

5.1 形态

Godot EditorPlugin，名字 LiveBay Tools，放在：

game/addons/livebay_tools/
  plugin.cfg
  plugin.gd
  dock.tscn / dock.gd
  viewport_overlay.gd
  data_bridge.gd
  commands/…

5.2 数据桥

不要在 GDScript 里重写 Markdown 表格解析器。做一个 Python bridge：

game/addons/livebay_tools/bridge.py
  read   → numbers/*.md → JSON（给编辑器）
  write  → 编辑后的 JSON → numbers/*.md
  export → 调 tools/export_numbers.py
  check  → 调 ./run.sh numbers-check

插件通过 OS.execute("python3", ["…/bridge.py", …]) 调用；Windows/macOS 都可用。这样：

  • 编辑器不拥有第二套 schema；
  • Markdown 仍是唯一源（TECH-A1）；
  • 现有 export_numbers.py 继续做导出；
  • 未来 Web 编辑器也能复用同一个 bridge。

5.3 数据流

numbers/*.md（唯一源）
   ⇅  bridge.py（读写表格）
LiveBay Tools（Godot 插件）
   ↓ 保存
bridge.py write → numbers/*.md
   ↓
export_numbers.py → game/data/*.json
   ↓
Sim / 场景重载 / 内嵌预览

关键约束：编辑器只能通过 bridge 写 Markdown，不能直接写 game/data/*.json；否则会破坏单一源。

六、MVP 功能

6.1 必做

功能 交互 验收
地图叠加 在 2D 视口显示路径、塔位、基地 与运行时坐标一致
路径点编辑 拖动点、增删点、5px 吸附 路径 ≥ 2 点，导出通过
塔位编辑 拖动/增删塔位 塔位 ≥ 1，覆盖圈实时更新
塔位预览 拖塔到槽，显示射程/造价/DPS 数值来自 game/data，不写死
波次时间轴 拖 count/interval/delay，显示生成窗口 总 HP/奖励/漏过实时计算
校验面板 路径、ID、引用、导出检查 错误阻止保存
保存/重载 写回 Markdown + 导出 + 重载 保存后运行结果一致
预览 运行当前场景或内嵌模拟 ≤ 5 秒看到结果

6.2 不做

  • 剧情/对话编辑器；
  • UI 布局编辑器；
  • 动画/骨骼/特效编辑器；
  • 美术资源导入器；
  • 多人协作/云端；
  • 完整游戏生成器。

七、分阶段

阶段 内容 估算 门槛
Phase 0 数据 bridge、live reload、校验按钮 2–3 天 现有数据可读写
Phase 1 地图/塔位叠加编辑 + 预览 2–3 周 能独立摆一张图
Phase 2 波次时间轴 + 数值面板 1–2 周 能独立调一波
Phase 3 内嵌 SubViewport 预览、撤销/重做完善 2–4 周 不切窗口看到运行
Phase 4 独立 Web 编辑器评估 另立方案 内容量/协作需求证明

估算按 1 名熟悉 Godot 的开发者计，不含美术与测试；是量级，不是承诺。

八、风险

风险 表现 缓解
编辑器变成第二套运行时 预览与游戏不一致 只用 sim.gd 与 game/data，不重写规则
数据双源 Markdown 与 JSON 冲突 bridge 单向写 Markdown；禁止手改 JSON
插件 API 复杂 视口拖拽难做 先做 Dock 列表 + 数值编辑，再上视口
非工程人员不会用 只有开发者用 先服务团队内部；Web 版另评估
范围膨胀 想加剧情/UI/动画 MVP 明确“四件事”
过早投入 玩法还没稳定，编辑器先改 先 Phase 0；Phase 1 在 v0.2 数据模型稳定后

九、验收指标

1. 摆一座塔并看到射程：≤ 30 秒
2. 改一波数量并看到预览：≤ 60 秒
3. 保存后运行结果与预览一致：100%
4. 非法数据被保存前拦截：100%
5. 不手改 JSON 完成一次地图调整：是
6. 现有 37 项测试保持通过：是

十、需要裁决

ID 问题 选项 建议
E1 编辑器形态 A Godot 插件 / B 独立 Web / C 嵌入运行时 / D 先不做 ✅ A
E2 数据主权 A Markdown 仍是源 + bridge / B 改为 JSON 源 / C 双源 ✅ A

2026-11-04 人类选择「全按推荐」：E1–E4 均按 A。实现入口：game/addons/livebay_tools/README.md。

十一、结论

  • 可开发，但第一版应是 Godot 插件，不是独立编辑器；
  • 真正的 WYSIWYG 来自「同一套数据 + 同一个运行时 + 短反馈环」，不是来自“自己画一个界面”；
  • 先用 Python bridge 守住 numbers/ 单一源，再逐步加视口编辑、波次时间轴、内嵌预览；
  • Phase 1 MVP 已实现：路径点 / 塔位 / 基地拖动、射程预览、保存写回、校验、运行游戏；见 game/addons/livebay_tools/README.md；
  • 独立 Web 编辑器是 Phase 4 的选项，不是现在的起点。
