# 18 · HTML 数值模拟器方案

> **一句话**：做一个**离线、单页、数据驱动**的 HTML 数值沙盘，让调数值的人不用每次都启动 Godot、打完一局才看到结果。
>
> **不是**把整款游戏搬进浏览器，也不是替代 Godot 的最终裁决。它是一个**设计期的计算器 + 可视诊断工具**，并且必须能和 Godot 的真实结果对账。
>
> **状态**：C-lite 已按推荐实现 P1–P4：解析沙盘、`sim-trace` 对账、离散小模拟；仍不替代 Godot。

## 一、要解决的问题

现在调一个数值的循环是：

```text
改 numbers 表格
  → export
  → 启动 Godot
  → 建造/开波/等波次
  → 看结算
  → 再改
```

问题不在“启动慢”，而在**反馈太粗**：

- 只能看到最终 grade / 击杀 / 漏过，看不到“哪一段弧覆盖不够”“哪一波 HP 超出 DPS”；
- 调整一个塔的 cost 或 range，很难判断是“覆盖率变了”还是“经济变了”；
- 每次试玩都依赖操作，难以做 A/B 数值对照；
- 三张地图、不同波次、不同塔组合，人工穷举成本高。

HTML 模拟器要回答的是：

- 这个塔位在这张图的覆盖窗口是多少？
- 这套塔在某一波的 TTK / 漏过风险是多少？
- 供能曲线是否支撑这个建造顺序？
- 改一个参数，哪几个指标会变？
- 这组数值和 Godot 真实跑出来的差距有多大？

## 二、路线选择

### 方案 A：纯前端“数值计算器”

浏览器里用 JavaScript 重写几何、DPS、TTK、经济公式，不做逐敌人 tick。

- 优点：最快、离线、可交互、易迭代；
- 缺点：不是完整模拟；复杂交互（减速叠加、故障、目标选择）只能近似；
- 适合：调塔/波次/地图的**宏观关系**。

### 方案 B：Godot Web 导出嵌入

把 Godot 游戏导出为 WebAssembly，嵌进 HTML。

- 优点：规则就是游戏本体，最准确；
- 缺点：包体大、加载慢、移动端/音频/文件协议问题；调试 UI 仍要另做；
- 不适合：快速调数值。

### 方案 C：混合（推荐）

**浏览器计算器 + Godot 金标回放对账**：

1. 浏览器负责可交互的解析计算（方案 A）；
2. Godot 提供 `sim-trace` 命令，把标准场景的逐波/逐塔结果导出 JSON；
3. 浏览器导入或对比这些 JSON，显示“模型 vs 真实”的偏差；
4. 只对关键场景做逐 tick 小模拟，不做全游戏。

- 优点：反馈快，且不会脱离真实游戏；
- 成本：比 A 多一个 trace 导出与对账层；
- 推荐作为第一版。

### 方案 D：本地 headless 服务

HTML 调本地 Godot headless API。

- 优点：准确、可实时；
- 缺点：需要服务器，不是单文件；跨平台/权限/端口都变复杂；
- 不符合“HTML 可视化模拟器”的轻量目标。

## 三、推荐方案：C-lite

第一版只做**解析计算 + 覆盖/经济/波次诊断**，不追求逐帧复刻：

```text
地图几何 + 塔数值 + 敌人数值 + 波次表 + 经济
  → 覆盖率 / DPS / TTK / 漏过风险 / 供能曲线 / 评级估算
  → 图表 + 诊断 + A/B 对比
```

### 3.1 第一版能回答

| 问题 | 计算 |
| --- | --- |
| 这个塔位覆盖多长路径？ | 点到折线距离 + 弦长 |
| 这套塔能打掉多少 HP？ | 有效 DPS × 停留时间 × 覆盖目标数 |
| 这波会不会漏？ | 波次 HP / 有效输出 / 漏过阈值 |
| 供能够不够？ | 初始供能 + 击杀奖励 + 补给产出 − 建造/升级 |
| 改 cost 会怎样？ | 建造顺序 / 回本时间 / 可建数量 |
| 哪张图更难？ | 路径长度、塔位覆盖、波次 HP、故障窗口 |
| A/B 哪个好？ | 并排对比 grade 估算、漏过风险、时长 |

### 3.2 第一版不回答

- 每个敌人的逐帧走位与索敌；
- 减速叠加、故障相邻塔、复杂目标选择；
- 玩家操作误差、暂停/倍速；
- 完整战斗动画与音效。

这些留给第二版“离散事件小模拟”，或者直接用 Godot trace 对账。

## 四、界面结构

单页，四块：

```text
┌────────────────────────────────────────────┐
│ 顶栏：地图选择 / 预设 / 导入 trace / 主题   │
├──────────────┬─────────────────────────────┤
│ 左：参数面板 │ 中：地图 + 覆盖可视化        │
│ 塔/波/经济   │ 右：指标卡 + 曲线 + 诊断     │
├──────────────┴─────────────────────────────┤
│ 底部：A/B 对比表 / 事件时间线 / 假设说明     │
└────────────────────────────────────────────┘
```

### 参数

- 地图：bay01/02/03；
- 塔：拦截炮、脉冲环、牵引锚、补给塔；
- 每个塔位：建造/等级/出售；
- 波次：选择某一波或全波；
- 经济：初始供能、奖励倍率、升级策略；
- 故障：是否启用、隔离/旁路、W4/W5 扩展开关。

### 可视化

- 地图路径 + 塔位 + 射程圆/覆盖弦；
- 每波 HP / DPS / 漏过风险柱状图；
- 供能曲线与回本点；
- 塔位覆盖率热力条；
- A/B 两套配置并排。

### 交互

- 点击塔位选中；
- 拖动数值滑杆，图表即时更新；
- “应用推荐建造顺序”；
- “导出场景 URL”；
- “导入 Godot trace”并显示偏差。

## 五、数据流与单一数据源

```text
numbers/*.md
  → export_numbers.py
  → game/data/*.json
  → tools/export_simulator_data.py
  → simulator/data.json（或内联到 HTML）
  → HTML 模拟器
```

约束：

- 不手写第二份塔/敌人/波次数据；
- 生成物带 source hash；
- 数据变化后 `--check` 能发现模拟器过期；
- 模拟器只读，不写回 `game/data`。

## 六、与 Godot 的对账

新增一个只读 trace 命令：

```bash
./run.sh sim-trace --map bay01 --scenario standard --json
```

输出：

```json
{
  "map": "bay01",
  "scenario": "standard",
  "result": {"grade": "B", "integrity": 40, "kills": 60, "leaked": 9},
  "waves": [{"index": 1, "hp": 180, "leaked": 0}],
  "towers": [{"slot": 3, "damage": 1234}],
  "data_hash": "sha256:..."
}
```

HTML 模拟器导入后：

- 对比 grade / integrity / kills / leaked；
- 显示每波偏差；
- 超过容差时明确标记“模型不可信”，而不是假装准确。

第一版容差建议：

| 指标 | 容差 |
| --- | ---: |
| 总 HP | 0%（直接读表） |
| 击杀/漏过 | ±10% |
| 保障度 | ±10 点 |
| grade | 必须同档，否则标红 |

## 七、实施阶段

| 阶段 | 内容 | 估算 |
| --- | --- | --- |
| P0 | 本方案拍板；确定技术栈与目录 | 0.5 天 |
| P1 | 数据导出 + 单页壳 + 地图/覆盖率/DPS | 2–3 天 |
| P2 | 波次/经济/诊断 + A/B 对比 + URL 场景 | 1–2 天 |
| P3 | `sim-trace` + 对账面板 + 黄金场景 | 1–2 天 |
| P4 | （可选）离散事件小模拟 | 3–5 天 |

第一版建议只做 **P1–P2**，先验证“它是否真的减少了调数值的往返次数”。P3 是对账，不建议省。

## 八、验收标准

- 无网络、单文件/本地目录可打开；
- 三张地图与全部塔/敌人/波次来自生成数据；
- 改动一个参数，图表与诊断即时更新；
- 同一场景可导出 URL，刷新后恢复；
- 与至少 6 个 Godot 黄金场景对账；
- 误差超过容差时明确提示；
- 支持 system / light / dark 三态（R-016）；
- 不修改游戏数据，不引入后端服务。

## 九、风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 模型与 Godot 漂移 | 用错误数字做决策 | 强制 trace 对账 + 容差标红 |
| 解析模型过度简化 | 复杂交互失真 | 第一版只承诺宏观指标，不承诺逐帧 |
| 前端代码变成第二套规则 | 维护双份 | 数据生成 + 公式集中 + 测试 |
| 范围膨胀 | 变成浏览器版游戏 | 明确“不是游戏”，不加入完整战斗 |
| 浏览器性能 | 大数据卡顿 | 单图/单波计算；必要时 Web Worker |

## 十、需要你拍板

1. **路线**：选 A（纯计算器）/ **C-lite（推荐：计算器 + Godot 对账）** / B（Godot Web）/ D（本地服务）？
2. **第一版范围**：只做解析计算（推荐），还是一开始就做逐敌人 tick？
3. **目录**：放 `docs-ai/design01/simulator/`（推荐，靠近设计文档），还是 `game/tools/simulator/`（靠近工程）？
4. **对账容差**：接受 ±10% 击杀/漏过、±10 保障度，还是更严格？
5. **是否允许新增 `./run.sh sim-trace`** 作为只读 trace 命令？

## 十一、我的建议

**先做 C-lite 的 P1–P2，不做完整战斗复刻。**

它最可能解决“改一个数就要打一局”的问题，同时保留 Godot 作为最终事实来源。等它证明能减少往返次数，再考虑 P4 的离散事件模拟。
