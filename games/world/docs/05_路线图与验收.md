# 05 · 路线图与验收

> **一句话**：先用 3–4 周证明「无引擎也能跑」，再用 8–12 周证明「作者能自己做内容」，
> 然后用 6–8 周证明「Godot 能跑同一局」，最后用 4–6 周证明「换一个宿主还是同一局」。
> 每一步都有可执行的退出标准，不靠感觉判断「差不多了」。

## 一、阶段总览

工期以 **2 名核心工程师全职 + 1.0 名兼职（适配器/内容）**计；不含美术/音频/内容量产的排期。
范围变更时先改退出标准，再改工期。

| 阶段 | 目标 | 工期 | 关键交付 | 退出标准（一句话） |
| --- | --- | --- | --- | --- |
| **M0** | 合同与钉子 | 3–4 周 | ABI v0、包 schema v0、无头 Demo、确定性基线 | 无引擎跑 600 tick，两次哈希一致，存档往返一致 |
| **M1** | 内容闭环 | 8–12 周 | TS DSL、编译器、8 个套件（core + 7）、Web 预览/编辑器 | 非工程作者 2 小时做出可玩房间 |
| **M2** | 第一生产适配器 | 6–8 周 | Godot 适配器、资产管线、CTS 基础组 | Headless 与 Godot 跑同一包，600 tick 哈希一致 |
| **M3** | 第二宿主与替换演练 | 4–6 周 | Web 宿主、CTS 全量、swap-check | 三个宿主同一局；替换报告全绿 |
| **M4** | 生产硬化 | 8–12 周（持续） | 存档迁移、mod 沙箱、编辑器 beta、试点迁移 | 一个真实游戏切片跑在新层上 |

```text
M0 ──▶ M1 ──▶ M2 ──▶ M3 ──▶ M4
 │      │      │      │      │
 │      │      │      │      └─ 真实切片、迁移、发布
 │      │      │      └─ 换引擎证明
 │      │      └─ 真实引擎证明
 │      └─ 作者证明
 └─ 无引擎证明
```

**每个阶段结束做一次「继续 / 收窄 / 改道」复核**（见 [04 §八](04_选型对比与推荐.md#八什么情况下应该改选)）。

## 二、第一个垂直切片：港湾值班室

不选塔防、不选开放世界，选一个**小到能做完、又横跨所有关键能力**的场景：

| 要素 | 内容 | 验证什么 |
| --- | --- | --- |
| 1 个区域 | 20×20 米的值班室 + 一扇气闸 | Zone、空间、导航 |
| 1 个 NPC | 值守的湾民，有「站岗 → 闲逛 → 睡觉」日程 | 角色、日程、世界时钟、AI |
| 1 个道具 | 需要钥匙卡才能打开的气闸 | 交互、条件、规则 |
| 1 个物品 | 钥匙卡（可拾取、可放入背包） | 物品、背包、交互 |
| 1 段对话 | 三段式，含一个条件选项 | 对话、条件、本地化 |
| 1 个任务 | 「和 NPC 说话 + 打开气闸」 | 任务、目标、奖励、标记 |
| 1 次存档/读档 | 中途存档，重载后状态一致 | 存档、迁移、确定性 |
| 1 条黄金回放 | 固定输入跑 600 tick | 回放、哈希、跨宿主 |

**为什么是它**：

- 它覆盖了「世界层」最核心的八件事，但演示级内容量只有半天到一天；
- 它不依赖任何特定游戏类型，塔防/RPG/经营都能从中取用；
- 它可以在 Godot 与 Web 上都做出「看起来像个游戏」的演示，便于评审；
- 它足够小，能在 M1 结束前由**真实作者**独立完成，而不是工程代做。

> **状态**：✅ 2026-11-23 完成（macOS 本地；三平台 CI 待跑）。记录见 [06](06_M0实现与验收.md)。

> **目标**：把「架构假设」变成「可运行的最小事实」。M0 不追求好玩，只追求**可复现**。

### 3.2 退出标准

- [ ] `cargo test` 全绿；无 `unsafe` 泄漏到公共 API（FFI 边界除外）。
- [ ] 无头 Demo 跑 600 tick，**两次运行哈希一致**；Linux/macOS/Windows 三平台哈希一致（Det1）。
- [ ] **非 Rust 宿主**通过 C ABI 跑同一包 600 tick，哈希与 Headless 一致；C 头文件由 schema 生成。
- [ ] save → load → save 的哈希一致；损坏存档返回错误码而不是 panic。
- [ ] 回放能复现最终哈希；首个分歧 tick 能被定位。
- [ ] `worldc validate` 对 5 类故意写错的包给出稳定错误码。
- [ ] 基准数据落盘（机器、commit、数值），后续阶段可对比。
- [ ] `wasm32-unknown-unknown` 构建通过；QuickJS 在 WASM 内跑通一条规则（否则记录降级为 JS 桥）。
- [ ] 决策记录完成，未决项明确标注「待拍板」。

### 3.3 不建议在 M0 做的事

- 不做编辑器 UI（先用 CLI + JSON）；
- 不做 Godot/Unity/Unreal 适配器；
- 不做完整套件（只做能跑通切片的最小系统）；
- 不做性能优化（先有基线，再优化）；
- 不做联网/rollback。

## 四、M1 · 内容闭环

> **状态**：M1 **主要切片**（TS DSL + Web 预览 + 3D 演示 + 编辑器 v0.5 + 移动/寻路 + 导航/资产基础版 + 内容测试 + 5k 合成基准）✅ 2026-11-23；ScriptHost/动态导航/真实 5k 仍待。
> 记录见 [07 · M1 切片](07_M1实现与验收.md)。

> **目标**：让**作者**而不是工程师，完成一个可玩场景。M1 的验收对象是「作者的时间」，不是「代码行数」。

### 4.1 交付物

| # | 交付 | 说明 |
| --- | --- | --- |
| 1 | TS DSL | `defineActor`/`defineProp`/`defineQuest`/`defineDialogue`/`on`/`cmd` 等；类型由 schema 生成 |
| 2 | 编译器 | TS/JSON → 规范化内容包；确定性输出；sourcemap |
| 3 | 8 个套件（core + 7） | `core`、`interaction`、`stats`、`inventory`、`quest`、`dialogue`、`director`、`save_profile` |
| 4 | 脚本宿主 | QuickJS 嵌入；事件/命令/查询 API；预算与错误隔离 |
| 5 | Web 预览 | WASM 内核 + Three.js 最小场景；WASD/交互/对话/任务/存档 |
| 6 | Web 编辑器 v0 | 布局、数据表单、规则编辑、对话图、试玩、inspector |
| 7 | 校验与错误 | 9 类校验；稳定错误码；`worldc explain` |
| 8 | 内容测试 | `@refu/world-testing`；黄金回放；覆盖率 |
| 9 | 教程 | 「2 小时做出值班室」；模板库 |

### 4.2 退出标准

- [ ] 一位**没有引擎经验**的作者（真实试用者）在 2 小时内完成值班室；全程不打开 Godot/Unity。
- [ ] 改一句文案到预览可见 ≤ 2 秒（热重载）。
- [ ] 内容测试 ≥ 3 条：无钥匙不开门、有钥匙开门、任务完成。
- [ ] 黄金回放 600 tick 通过；同 tick 跑两遍哈希一致。
- [ ] 所有内容错误都有错误码与修复建议；至少 5 个 fixture 测试校验器。
- [ ] 内核 crate 不依赖任何引擎 crate（CI 依赖图检查）。
- [ ] 作者能在编辑器里看到：实体、组件、标记、事件流、任务进度。

### 4.3 M1 的最大风险

| 风险 | 表现 | 缓解 |
| --- | --- | --- |
| 编辑器吞掉工期 | 布局/表单/对话图/试玩全要做 | v0 只做「能完成教程」的最小集；复杂编辑回退到 JSON/TS |
| DSL 设计过度 | 作者学不会，或表达力不足 | 先写 10 条真实规则，再定 API；不先设计「通用语言」 |
| 脚本性能 | 每 tick 跑大量脚本 | 预算 + 性能 lint；热路径下沉 Rust |
| 作者不参与 | 工程自嗨，作者不用 | 从 M1 第一周就拉真实作者试用，每周一次 |

> 如果只能给 6 周：砍掉对话图编辑器、撤销/重做、覆盖率报告；只保留布局/数据/规则/试玩 + 3 个套件。
> 工期不能靠「加人」压缩——工具链需要作者反馈，反馈周期是固定的。

## 五、M2 · 第一生产适配器（Godot）

> **目标**：证明「同一个包，在真实引擎里跑出同一局」。M2 的验收不是「画面好看」，而是「哈希一致」。

### 5.1 交付物

| # | 交付 | 说明 |
| --- | --- | --- |
| 1 | Godot 适配器 | GDExtension；`WorldNode`；输入/资产/视图/音频/存档 |
| 2 | 资产管线 | 逻辑 ID → Godot 资源；glTF/纹理/音频导入配方 |
| 3 | 坐标/单位 | 3D 零转换；2D 轴映射；单位统一 |
| 4 | 视图池 | 角色/道具/特效的最小池化；插值 |
| 5 | 存档 | `user://` 原子写；读档；损坏处理 |
| 6 | CTS 基础组 | L/T/I/E/V/Z/A/S/X；Godot 全绿 |
| 7 | 性能基线 | 5k 实体场景的 tick/渲染数据 |
| 8 | 演示 | 值班室在 Godot 里可玩；与 Web 版同内容 |
| 9 | C ABI 回归 | M0 的 C/C# 冒烟宿主继续通过；Godot 适配器不得绕过 ABI 直接链接内核 |

### 5.2 退出标准

- [ ] Headless 与 Godot 跑同一包、同输入 600 tick，**状态哈希与逻辑事件序列一致**。
- [ ] 存档互通：Headless 存的档，Godot 能读；反之亦然。
- [ ] 60 FPS（目标机器，5k 活跃实体以下）不出现 tick 追帧告警。
- [ ] 适配器代码 ≤ 2,000 行（不含资产配方/平台打包）。
- [ ] 适配器 crate 只依赖 `world-abi`，**不依赖 `world-core` / 任何 `world-kits-*`**；关键词扫描无玩法词。
- [ ] CTS 基础组全绿；错误路径（坏包/坏档/panic）有测试。
- [ ] 作者仍通过 Web 编辑器改内容，Godot 只负责跑；不需要开 Godot 编辑器做内容。

### 5.3 为什么 M2 不接 Unity/Unreal

- Godot 是当前主线，验证价值最高；
- Unity/Unreal 的接入成本（IL2CPP、C++ 模块、平台打包）会把 M2 拖成 M4；
- 「第二个引擎」的说服力由 M3 的 Web 宿主提供，成本低得多；
- 等 ABI 与内容格式稳定后，Unity/Unreal 的适配器才不会反复改。

## 六、M3 · 第二宿主与替换演练

> **目标**：把「可替换引擎」从设计承诺变成**可执行的验收**。

### 6.1 交付物

| # | 交付 | 说明 |
| --- | --- | --- |
| 1 | Web 宿主（发布级） | WASM + Three.js；资产加载、输入、音频、存档 |
| 2 | CTS 全量 | 10 组测试；Headless/Godot/Web 三宿主矩阵 |
| 3 | `worldc swap-check` | 跑多宿主、比对哈希/事件、生成报告 |
| 4 | 替换演示 | 同一包在三个宿主上跑同一段输入；录屏/报告 |
| 5 | 适配器开发文档 | 新引擎从零到 CTS 通过的清单 |
| 6 | 性能报告 | 三宿主 tick/帧/内存对比 |

### 6.2 退出标准

- [ ] 三宿主跑同一包、同输入 600 tick，`final_hash` 一致，逻辑事件序列一致。
- [ ] 变换误差 ≤ 1e-4；可见实体集合一致。
- [ ] 任一宿主存档，其余宿主可读（同 schema/版本）。
- [ ] `swap-check` 报告全绿；差异能被定位到 tick 与事件。
- [ ] 新增一个宿主的基础适配器 ≤ 2,000 行、≤ 3 周（用 Web 或 Bevy 做实测）。
- [ ] 适配器 CTS 在 CI 中运行；失败阻断合并。

### 6.3 替换演练的「反作弊」

- 比的是**内核状态哈希**，不是截图；
- 适配器不能自行推进 tick、不能改世界状态；
- 逻辑事件（伤害、任务、物品）必须一致；表现事件允许适配器差异，但要在报告里列明。

| **Q8** | 团队与预算 | 1 Rust + 1 TS + 0.5 适配器 + 0.5 内容 | **至少 2 人全职到 M2** | 决定工期是否可信 |
| **Q9** | 目标规模 | 活跃实体/区域数/存档大小 | **5k 活跃 / 20k 总 / 10 MB 存档** | 决定性能与存档设计 |
| **Q10** | 是否要求迁移 LiveBay | A. 不要求；B. M4 试点一个切片；C. 全量迁移 | **B** | 全量迁移会与主线争资源 |

### 7.2 最关键的三项

1. **Q1 首发试点**：没有真实切片，所有验收都会退化成「Demo 能跑」。

## 九、测试与 CI

### 9.1 测试金字塔

| 层 | 测什么 | 工具 | 频率 |
| --- | --- | --- | --- |
| 单元 | 内核系统、套件状态机、schema | `cargo test` | 每次提交 |
| 属性 | 存档往返、确定性、边界值 | `proptest` | 每次提交 |
| 内容 | 规则/任务/对话 | `worldc test` | 每次提交 |
| 黄金回放 | 固定输入 → 哈希 | `worldc replay` | 每次提交 |
| 适配器 | CTS 10 组 | `worldc cts` | 每次提交（Headless）+ 每日（Godot/Web） |
| 替换 | 多宿主哈希 | `worldc swap-check` | 每日/发布前 |
| 性能 | tick/事件/内存 | `worldc bench` | 每日 + 发布前 |
| 模糊 | 包解析、存档解析 | `cargo fuzz` | 每日 |

### 9.2 CI 矩阵

| 维度 | 值 |
| --- | --- |
| OS | Linux、macOS、Windows |
| Rust | stable（固定 minor）、wasm32-unknown-unknown |
| Node | 22 LTS+（工具链/编辑器） |
| 宿主 | Headless（全平台）、Godot（Linux 容器）、Web（Playwright） |
| 检查 | `cargo fmt --check`、`clippy -D warnings`、测试、确定性、链接/变更日志（工作区） |

### 9.3 确定性 CI

```bash
# 三平台同跑，比较哈希
worldc test --pack demo.harbor --ticks 600 --hash-out hashes/$OS.json
# 汇总比对
worldc test --compare hashes/linux.json hashes/macos.json hashes/windows.json
```

失败即阻断合并。**不要**用「重跑一次就过了」处理确定性失败——那说明有未受控的随机源。

## 十、指标与节奏

### 10.1 指标

| 指标 | 目标 | 怎么测 | 频率 |
| --- | --- | --- | --- |
| 作者上手时间 | ≤ 2 小时（值班室） | 真实作者计时 | 每季度/大版本 |
| 内容迭代延迟 | ≤ 2 秒（热重载） | `worldc dev` 计时 | 每次提交 |
| 内核 tick P95 | ≤ 2 ms @ 5k 活跃 | `worldc bench` | 每日 |
| FFI 开销 | ≤ 50 µs/帧 | 微基准 | 每日 |
| 适配器基础代码 | ≤ 2,000 行 | `tokei` | 每月 |
| 换宿主时间 | ≤ 3 周（基础适配器） | 实际记录 | 每次新增 |
| 存档迁移成功率 | 100%（fixture） | `worldc test` | 每次提交 |
| 内容 bug 逃逸 | 下降趋势 | 线上/测试对比 | 每月 |
| 崩溃率 | < 0.1% 会话 | 上报 | 发布后 |

### 10.2 节奏

- **每周**：作者试用一次；确定性/性能报告一眼；阻塞项清零。
- **每阶段末**：复核「继续/收窄/改道」；更新 [04](04_选型对比与推荐.md) 的结论与风险。
- **每月**：适配器代码量、内容作者反馈、存档兼容性审计。
- **发布前**：`swap-check` 全绿、迁移 fixture 全绿、性能不回归。

## 十一、团队与分工

### 11.1 最小团队（到 M2）

| 角色 | 投入 | 负责 |
| --- | --- | --- |
| Rust 系统工程师 | 1.0 | `world-core`、`world-abi`、套件、确定性、性能 |
| TS 工具/内容工程师 | 1.0 | DSL、编译器、编辑器、预览、教程 |
| 引擎适配器工程师 | 0.5 | Godot 适配器、资产管线、平台打包 |
| 内容/设计 | 0.5 | 值班室内容、作者试用、模板、文档 |

> 名义合计 3.0 FTE，其中 **2.0 是核心全职**；适配器与内容可由主线兼职。
> 如果只有 1 人全职，目标应收缩到 M0 + M1 的最小集，不要同时承诺 M2/M3。

### 11.2 到 M3/M4 的增量

- 第二适配器（Unity/Unreal/Web 发布）需要 0.5–1.0 人；
- Mod 沙箱/安全需要 0.5 人；
- 文档/社区需要 0.5 人（若开源）。

### 11.3 不建议的分工

- 让一个人同时写内核、编辑器、适配器：三个方向的反馈周期不同，会互相阻塞；
- 让内容作者兼职做工具：作者的时间应该花在内容上，工具由工程做；
- 让适配器工程师改内核：边界会失守，最后适配器里长出规则。

### 11.4 投入估算

| 阶段 | 工期 | 有效人力 | 约人周 |
| --- | --- | ---: | ---: |
| M0 | 3–4 周 | 2.0 | 6–8 |
| M1 | 8–12 周 | 2.0 | 16–24 |
| M2 | 6–8 周 | 2.5 | 15–20 |
| M3 | 4–6 周 | 2.5 | 10–15 |
| **到 M3 合计** | **21–30 周** | —— | **47–67 人周（约 11–15.5 人月）** |
| M4 | 8–12 周 | 3.0 | 24–36（持续） |

说明：

- 不含内容量产、美术、音频、本地化与平台认证；这些按项目另算。
- 估算假设「决策不反复、依赖不重选、首发只做一个生产适配器」；任一前提被打破，按 1.5–2 倍重估。
- 最大的机会成本是**与 LiveBay 主线争人**；如果只有 1 人全职，建议把目标收窄到 M1（作者闭环），
  把 Godot 适配器交给主线顺手做，而不是独立立项。
