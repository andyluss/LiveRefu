# 01 · 世界模型与运行时

> **一句话**：内核只做一件事——在固定 tick 上，用**确定性的状态转移**把「命令 + 时间」变成「新状态 + 事件」。
> 其余一切（渲染、资产、输入设备、存档介质）都在内核之外。

## 一、范围与不变量

本文件定义 `world-core` 的运行时语义。以下不变量是硬约束，任何套件、脚本、适配器都不得违反：

| # | 不变量 | 违反的后果 |
| --- | --- | --- |
| I1 | 世界状态只有一个写入者：内核 | 引擎/脚本私改状态 → 回放与存档失真 |
| I2 | 固定 tick 内不读系统时间 | 同输入不同结果，回放失败 |
| I3 | 所有随机来自显式随机流 | 无法复现、无法对账 |
| I4 | 遍历顺序稳定（按 ID 或插入序） | 同机两次运行都可能不同 |
| I5 | 命令先校验后生效；事件只描述已发生的事实 | 非法状态、事件语义混乱 |
| I6 | 外部（玩家/脚本/编辑器）不能直接写组件 | 绕过规则、无法审计 |
| I7 | 存档/回放只依赖包哈希 + 种子 + 命令/输入日志 | 换机器/换引擎无法复现 |
| I8 | 内核不调用引擎（无回调） | 跨语言生命周期与线程模型失控 |

## 二、World / Zone / Session

### 2.1 三个概念

```text
World（持久世界，存档单位）
├── Zone A（空间分区，可激活/休眠）
│   ├── Entity ...（NPC、门、道具、生成器）
│   └── Entity ...
├── Zone B
└── Session（一次游玩/一局；可多个，串行或并行）
    ├── 读写的 World 状态子集
    └── 会话级状态（波次、比分、临时实体）
```

| 概念 | 职责 | 不负责 |
| --- | --- | --- |
| **World** | 持久状态、世界时钟、跨区关系、存档根 | 单局规则、单局 UI |
| **Zone** | 空间边界、实体归属、流式加载、区域事件 | 跨区寻路（由世界级导航图处理） |
| **Session** | 一局的开始/进行/结算、会话级实体与计分 | 持久进度（写回 World/Profile） |

### 2.2 生命周期状态机

```text
World:    Created ──load──▶ Loading ──ready──▶ Running ──suspend──▶ Suspended
                                                │  ▲                    │
                                                │  └──────resume────────┘
                                                └──close──▶ Closed

Zone:     Dormant ──request──▶ Activating ──ready──▶ Active
              ▲                    │                   │
              └────deactivate──────┴───────────────────┘

Session:  Created ──start──▶ Running ──pause──▶ Paused ──resume──▶ Running
                                │                                  │
                                └──────────end──▶ Ending ──▶ Ended ─┘
```

约束：

- `World` 在 `Running` 之外不推进 tick；`Suspended` 用于切后台/暂停，世界时钟冻结。
- `Zone` 的 `Activating` 只表示**逻辑激活**；表现层可以更晚准备好（见 §十一）。
- `Session` 结束时只产生「结算事件」，持久化由 `save_profile`/`world_save` 显式完成，内核不隐式存档。

### 2.3 Zone 的激活与休眠

| 状态 | 模拟频率 | 表现事件 | 典型用途 |
| --- | --- | --- | --- |
| `Active` | 每个 tick | 全量（受视锥/可见性影响） | 玩家所在区域 |
| `Activating` | 每个 tick | 缓冲到可见 | 加载中 |
| `Dormant` | 每 N tick 粗粒度（默认 60）或纯事件 | 无 | 隔壁房间、远处城市 |
| `Unloaded` | 不模拟，只保留摘要 | 无 | 极端省内存；需要时从摘要重建 |

**为什么休眠区还要模拟**：模拟经营/开放世界需要「NPC 在你看不见的地方也过日子」。
但全速模拟所有区域会浪费 CPU，所以休眠区用粗粒度推进，并且只跑「世界级系统」（日程、经济、势力），
不跑「表现级系统」（动画、音效、粒子）。

**休眠区的确定性**：粗粒度推进也必须是固定步长、固定顺序、固定随机流；不能因为「玩家走开了」就换一套规则。

### 2.4 会话与世界的写回

Session 对 World 的写入必须是**显式的、可审计的**：

```rust
// 会话结束：只提交声明过的结果，不直接改 World 任意字段
session.commit(&mut world, SessionOutcome {
    quest_progress: ...,
    inventory_delta: ...,
    flags: ...,
})?;
```

禁止：Session 内部持有 `&mut World` 并随意写。允许的写回通道：

1. `SessionOutcome`（推荐，集中、可测试）；
2. 通过命令写入（`world.cmd`）；
3. 通过套件提供的领域端口（如 `QuestPort::record`）。

## 三、实体与组件

### 3.1 实体 ID

```rust
#[repr(C)]
#[derive(Clone, Copy, PartialEq, Eq, Hash, PartialOrd, Ord)]
pub struct EntityId {
    pub index: u32,       // 槽位
    pub generation: u32,  // 世代，防悬垂引用
}
```

| ID | 生命周期 | 用途 |
| --- | --- | --- |
| `EntityId` | 本次运行 | 系统内部引用、事件载荷、视图绑定 |
| `ContentId` | 内容包版本内稳定 | 作者引用（`demo.keeper`）、任务目标、存档迁移 |
| `PersistentId` | 存档内稳定 | 跨会话/跨存读档引用（`zone.harbor/npc/keeper`） |

规则：

- 事件与存档中**不得**只写 `EntityId`；必须同时带 `ContentId` 或 `PersistentId`，否则重载后无法定位。
- `EntityId` 的世代在销毁时递增；复用槽位不会让旧引用「复活」。
- 内容作者永远只接触 `ContentId`；`EntityId` 是工程概念。

### 3.2 组件

组件是「类型化数据」，不是行为。行为在系统里。

```rust
#[derive(Clone, Debug)]
pub struct Transform {
    pub translation: Vec3,
    pub rotation: Quat,
    pub scale: Vec3,
}

#[derive(Clone, Debug)]
pub struct Health {
    pub current: f32,
    pub max: f32,
}
```

约定：

- 每个组件有稳定的 `ComponentId`（字符串 → 编译期/加载期 intern 成 `u16`），用于存档与网络。
- 组件 schema 由套件声明；内容包只能填 schema 允许的字段。
- 组件不持有引擎对象、文件句柄、回调、`Rc<RefCell<...>>`。
- 可选组件用 `Option<T>` 或「没有该组件」表达；不要用 `health = -1` 这类哨兵值。

### 3.3 面向内容作者的「门面」

内容作者不应该看到 ECS。给作者的是少量**语义对象**：

| 作者看到 | 内核里可能是 | 说明 |
| --- | --- | --- |
| `Actor` | `Identity + Transform + Brain + Stats + Inventory` | 有身体、能行动的东西 |
| `Prop` | `Identity + Transform + Interactable` | 门、箱子、按钮 |
| `Trigger` | `Identity + Transform + TriggerVolume` | 进入区域触发 |
| `Spawner` | `Identity + Transform + SpawnRule` | 按规则生成 |
| `Zone` | 区域定义 + 导航图 | 空间容器 |

门面不是「另一套运行时」，只是内容 schema 与默认组件组合的别名。作者写 `kind: "actor"`，
编译器展开成组件；运行时仍然只有组件。

### 3.4 生成与销毁

- 生成：`world.spawn(prefab, transform)` 或命令 `Spawn`；生成在当前 tick 的 `apply_commands` 阶段生效。
- 销毁：标记 `PendingDespawn`，在 tick 末尾统一清理；系统在本 tick 内仍可安全读取。
- 父子关系：`Parent`/`Children` 组件；变换继承在 `post_sim` 统一计算，避免一 tick 内多次更新。
- 生成/销毁的顺序：按命令序号，再按实体 ID；不得依赖哈希表顺序。

## 四、空间模型

### 4.1 坐标约定

内核使用 **右手坐标系、+Y 向上、-Z 向前**（与 glTF/Godot 一致）。

| 模式 | 约定 | 适配器职责 |
| --- | --- | --- |
| 3D | `(x, y, z)`，米 | 转换到引擎坐标（Unity +Z 前、Unreal +X 前等） |
| 2D | 使用 `(x, y, 0)`，+Y 向上；旋转只用绕 Z 轴 | 转换到引擎 2D 坐标 |

**为什么不让内核跟随某个引擎的约定**：一旦跟随，所有内容、导航、工具都会被那个约定污染；
坐标转换放在适配器是一次性的、可测试的薄层。

### 4.2 形状与碰撞

| 形状 | 用途 | 备注 |
| --- | --- | --- |
| `Aabb` | 静态体积、触发区、粗略碰撞 | 轴对齐；旋转体用 OBB 或分解 |
| `Sphere` | 角色/投射物/感知范围 | 最快 |
| `Capsule` | 角色 | 2D 退化为圆 |
| `Obb` | 旋转的门/箱子 | 仅静态或低频 |

碰撞层用 32 位掩码：`layer` + `mask`。套件声明自己使用的层段，避免冲突：

| 层段 | 用途 |
| --- | --- |
| 0–7 | 世界几何 |
| 8–15 | 角色 |
| 16–23 | 交互/触发 |
| 24–31 | 套件自定义 |

### 4.3 空间索引与查询

- 索引：2D 用均匀网格，3D 用松散的 BVH/八叉树；每 tick 增量更新。
- 查询 API：
  - `within(center, radius, filter) -> Vec<EntityId>`（物化 + 按 EntityId 排序；不返回借用迭代器，避免与 `&mut World` 冲突）
  - `aabb_overlap(aabb, filter)`
  - `raycast(origin, dir, max_dist, filter) -> Option<RayHit>`（2D/3D）
  - `line_of_sight(a, b, filter) -> bool`
- 所有查询结果是**稳定排序**的；调用方不得依赖「先找到谁」的偶然顺序。
- 如果内部用 `bevy_ecs`：archetype 迭代顺序会随组件增删变化，**不能直接暴露给玩法逻辑**；
  查询必须物化并按 `EntityId` 排序后再使用。

### 4.4 导航

- 导航图由内容包编译期烘焙（`worldc bake nav`）：`NavGraph { nodes, edges, zone_id }`。
- 寻路：A*，启发式用欧氏距离；开放集用二叉堆；**相同代价按 node id 排序**，保证确定性。
- 动态障碍：`NavObstacle` 修改边代价或临时禁用节点；不重建整张图。
- 局部避让：v0 可选；若启用，必须是固定顺序的确定性算法，不能依赖物理引擎。
- 跨区：世界级导航图连接 Zone 的入口节点；跨区寻路返回「路径段 + 区域序列」，由 Session 决定是否加载。

### 4.5 引擎物理的边界

| 模式 | 碰撞/物理由谁做 | 确定性 | 适用 |
| --- | --- | --- | --- |
| `arcade`（默认） | 内核：运动学 + 形状查询 + 简化响应 | Det1/Det2 | 塔防、RPG、经营、叙事 |
| `engine_physics` | 引擎：刚体/角色控制器；内核只读结果 | 不保证 | 需要真实刚体的动作游戏 |

`engine_physics` 是**逃生舱**，不是默认：

- 内核仍然拥有「逻辑位置」与「游戏规则」；引擎物理只提供碰撞结果。
- **仍然没有回调**：适配器在 tick 前把 `PhysicsFrame`（位置、接触、射线结果）提交给内核，内核把它当作权威输入；
  内核不向引擎查询、不持有刚体句柄。
- 该模式下回放仍可工作，但只保证同引擎/同平台；跨引擎替换不承诺。
- 内容包 manifest 必须显式声明 `sim_profile`，工具据此给出警告。

## 五、时间模型

### 5.1 固定 tick

```rust
pub const DEFAULT_TICK_HZ: u32 = 60;
pub struct Tick(pub u64);
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `tick_hz` | 60 | 逻辑频率；30/60/120 可选，但一个包内固定 |
| `max_catchup_ticks` | 4 | 单帧最多追多少 tick，防止死亡螺旋 |
| `dt` | `1/tick_hz` | 逻辑步长；不随渲染帧变化 |

```text
accumulator += frame_dt
while accumulator >= dt && ticks_this_frame < max_catchup:
    tick_once()
    accumulator -= dt
    ticks_this_frame += 1

if ticks_this_frame == max_catchup && accumulator >= dt:
    report(TickOverrun { dropped_micros: accumulator })
    accumulator = 0   // 明确丢弃，不静默累积
```

**禁止**：用 `Time.delta` 直接推进逻辑；根据帧率改变 `dt`；在系统内读系统时间。

### 5.2 暂停、倍速、后台

| 操作 | 语义 | 实现 |
| --- | --- | --- |
| 暂停 | 世界时钟冻结，表现继续 | 不推进 tick；适配器仍可插值/播放 UI 动画 |
| 倍速 | 每秒执行更多 tick；`dt` 不变 | 调整 accumulator 的输入速率，不改 `dt` |
| 后台 | 停止 tick，保留状态 | `World::suspend()`；恢复时按策略补算或冻结 |
| 离线推进 | 用粗粒度模拟补时间 | `advance_offline(seconds)`，固定步长、可哈希 |

### 5.3 世界时钟与日程

- `WorldClock` 由 `tick` 与配置推导：`day`、`minute_of_day`、`season` 等。
- 日程（NPC 上班/回家）用**世界分钟**表达，不直接绑 tick；套件把分钟映射到 tick。
- 时区/夏令时不属于游戏世界；世界历法是内容配置，不是系统时间。

## 六、命令、事件、查询

### 6.1 命令（意图）

```rust
pub struct CommandEnvelope {
    pub id: u64,                 // 调用方提供，用于去重/关联 UI
    pub source: CommandSource,   // Player | Script | System | Editor | Replay
    pub issued_tick: Tick,
    pub payload: CommandPayload, // 类型化，非任意 JSON
}

pub enum CommandSource {
    Player { input_id: u64 },
    Script { module: InternedStr, handler: u32 },
    System { name: InternedStr },
    Editor,
    Replay,
}
```

规则：

- 外部命令必须**先校验**：`validate(world) -> Result<(), CommandError>`。
- 拒绝要有稳定错误码：`insufficient_funds`、`out_of_range`、`wrong_phase`、`locked`、`cooldown`。
- 命令不直接改组件；由对应套件的 `apply` 执行。
- 同一 tick 内命令按 `(priority, source_rank, seq)` 排序；`source_rank` 固定为
  `System < Editor < Player < Script`，避免脚本抢先于玩家输入。
- 命令结果返回给调用方（UI 用），并写入黑匣子。

### 6.2 事件（事实）

```rust
pub struct EntityRef {
    pub runtime: Option<EntityId>,       // 本次运行有效
    pub content_id: Option<ContentId>,   // 内容包内稳定
    pub persistent_id: Option<PersistentId>, // 存档内稳定
}

pub struct EventEnvelope {
    pub seq: u64,              // 全局单调
    pub tick: Tick,
    pub kind: EventKind,       // interned
    pub source: Option<EntityRef>, // 全局事件可为 None
    pub payload: EventPayload,
}
```

规则：

- 事件是**不可撤销的已发生事实**；不能拿事件当「请求别人做事」。
- 事件在 tick 的 `flush_events` 阶段定序；消费者只能读，不能改。
- 同一 tick 内事件顺序 = 系统执行顺序 + 系统内发射顺序；两者都稳定。
- 引用持久实体的事件必须填 `content_id` 或 `persistent_id`；只引用当帧临时对象（如投射物）时才允许只带 `runtime`。
- 事件可以带 `trace_id`，把「玩家点击 → 命令 → 事件 → 表现」串起来。

### 6.3 查询（只读）

| 查询 | 用途 | 返回 |
| --- | --- | --- |
| `get(entity, component)` | 单实体读取 | `Option<&T>` |
| `by_tag(tag)` | 按标签筛选 | 稳定排序的 `EntityId` 列表 |
| `within(center, radius)` | 空间查询 | 稳定排序 |
| `first_matching(predicate)` | 规则条件 | `Option<EntityId>`（按 ID 排序后取第一个） |
| `count(predicate)` | 统计 | `usize` |

脚本侧只暴露**值拷贝/只读视图**，不暴露 Rust 引用；脚本不能通过查询拿到可变句柄。

## 七、调度与阶段

### 7.1 阶段

```text
Tick N
├─ Input       适配器输入已入队（不在内核 tick 内做设备轮询）
├─ Command     应用上一 tick 排队的命令；校验失败只记录，不中断
├─ PreSim      时间推进、日程、生成队列、导航请求预处理
├─ Sim         按顺序执行系统（套件与内核系统）
├─ PostSim     父子变换、空间索引更新、销毁清理、状态哈希
├─ Script      事件处理器运行；命令排到 tick N+1
├─ Checkpoint  黑匣子/关键帧哈希（可配置频率）
└─ Present     生成表现事件与可见快照（适配器在 tick 后轮询）
```

**为什么 `Script` 在 `PostSim` 之后**：脚本看到的是「本 tick 已完成的世界」，发出的命令下一 tick 生效。
这是一 tick 的固定延迟，换来无重入、可排序、可回放。

### 7.2 系统注册与顺序

```rust
pub struct SystemSpec {
    pub name: &'static str,
    pub phase: Phase,
    pub order: i32,                    // 同 phase 内升序
    pub after: &'static [&'static str],
    pub before: &'static [&'static str],
}
```

- 排序键：`(phase, order, after/before 拓扑序, name)`；最后用 `name` 字典序兜底，保证稳定。
- 套件声明自己的系统与顺序；两个套件声明同一 `order` 不报错，按名字兜底，但工具会警告。
- 禁止系统在 `run` 里再注册系统（启动期一次性注册）。

### 7.3 系统契约

```rust
pub trait System {
    fn name(&self) -> &'static str;
    fn run(&mut self, ctx: &mut SystemContext<'_>) -> Result<(), SystemError>;
}

pub struct SystemContext<'a> {
    pub world: &'a mut World,
    pub commands: &'a mut CommandQueue,
    pub events: &'a mut EventWriter,
    pub rng: &'a mut RngStreams,
    pub tick: Tick,
    pub diagnostics: &'a mut Diagnostics,
}
```

约束：

- 系统只通过 `SystemContext` 拿能力，不持有全局单例。
- 系统内禁止 I/O（文件、网络、日志文件）；日志走 `diagnostics` 的内存环形缓冲。
- 系统必须可重入地跑「同一个 tick 两次得到同样结果」；测试会直接这样验。
- 系统失败：核心系统失败 = 世界进入 `Faulted`，停止 tick；可选套件失败 = 禁用该系统并继续（manifest 声明 `required`）。

## 八、确定性契约

### 8.1 等级

| 等级 | 含义 | 本方案目标 | 验证方式 |
| --- | --- | --- | --- |
| **Det0** | 同机、同二进制、同输入 → 同结果 | 必须 | 同进程跑两次比对哈希 |
| **Det1** | 同一工具链版本、同一优化档，在不同 OS/架构上构建 → 同结果 | 必须 | CI 三平台跑黄金回放 |
| **Det2** | 跨宿主（Godot/Web/Headless）→ 同结果 | 必须（`arcade` 模式） | 替换演练 |
| **Det3** | 跨编译器版本/不同优化级别逐位一致 | 不承诺 | —— |

### 8.2 随机

```rust
pub struct RngStreams {
    seed: u64,
    streams: BTreeMap<StreamId, Pcg64>,
}

impl RngStreams {
    pub fn stream(&mut self, name: &str) -> &mut Pcg64 { ... }      // 按名字哈希
    pub fn for_entity(&mut self, name: &str, e: EntityId, t: Tick) -> Pcg64 { ... }
}
```

规则：

- 一个逻辑域一个流：`combat`、`loot`、`ai`、`world`、`dialogue`；不要所有系统抢一个全局 RNG。
- 需要「每实体独立」时用 `for_entity`，避免执行顺序影响随机结果。
- 流状态必须进存档与状态哈希。
- 禁止 `rand::thread_rng()`、`SystemTime`、`/dev/urandom`。

### 8.3 浮点

| 规则 | 原因 |
| --- | --- |
| 逻辑用 `f32` 或 `f64`，一个包内统一 | 混用会引入隐式转换差异 |
| 禁止 `sin/cos/tan/exp/log/pow` 直接进逻辑，除非走 `world_math` 的确定性实现 | 各平台 libm 结果可能不同 |
| 禁止 `-ffast-math` / `target-cpu=native` 进发布构建 | 改变舍入与指令选择 |
| 哈希前规范化：NaN → 固定位型、`-0.0` → `+0.0`、次正规数按固定策略处理 | 原生/WASM/ARM 的 NaN 位型与 FTZ/DAZ 可能不同 |
| 状态哈希用**规范化后的精确位**；`1e-4` 只用于调试容差比较 | 量化会在桶边界翻转，不能保证「误差小 ⇒ 同哈希」 |
| `arcade` 模式位置/旋转由内核算；`engine_physics` 模式物理结果经 `PhysicsFrame` 提交并记录，属 Det0/同平台 | 引擎物理不保证跨引擎一致 |

> 这不是「数学洁癖」：只要有一个系统在逻辑里用了 libm 的 `sin`，Det1 就可能在某些 ARM 设备上失败，
> 而失败通常只在发售后才被发现。NaN/次正规数同理——它们不会在 Demo 里出现，只会在跨平台回放时出现。

### 8.4 遍历与容器

| 允许 | 禁止 |
| --- | --- |
| `BTreeMap`、`BTreeSet` | `HashMap` / `HashSet` 进入模拟逻辑 |
| `IndexMap`（插入序） | 依赖 `HashMap` 迭代顺序 |
| 按 `EntityId` / `ContentId` 排序后遍历 | 按对象地址、指针、线程完成顺序遍历 |
| 固定顺序的数组/Vec | 并行归约后不排序就使用 |

工程手段：

- `world-core` 的 `#![deny(clippy::disallowed_types)]` 配置禁止 `HashMap`（或封装成 `StableMap`）。
- 代码评审清单包含「新增容器是否稳定排序」。
- 确定性测试：同一 tick 跑两遍，比较完整状态哈希。
- ECS 选择：`bevy_ecs` 的 archetype 顺序不稳定，所有玩法遍历必须经过 `world-core` 的排序门面；
  这也是不把 ECS 暴露给套件/内容的原因之一。

### 8.5 状态哈希

```rust
pub fn state_hash(world: &World) -> u64 {
    // 按 ComponentId 排序，按 EntityId 排序，规范化编码，xxh3
}
```

- 调试构建：每 tick 计算；发布构建：每 N tick（默认 60）或关键节点。
- 哈希不包含纯表现状态（动画相位、粒子），只包含逻辑状态 + RNG + 时钟。
- 哈希不一致时：开发期 `panic!`/断言；发布期记录「首个分歧 tick + 双方哈希 + 命令日志尾部」，不静默继续。

### 8.6 脚本的确定性

| 允许 | 禁止 |
| --- | --- |
| 同步函数、纯计算 | `async`/`await`、`setTimeout`、`Promise` 参与逻辑 |
| `world.rng.*` | `Math.random()`（运行时替换为抛错） |
| `world.time.*` | `Date.now()`、`performance.now()`（运行时替换为世界时间或抛错） |
| `world.math.sin/cos/...`（确定性实现） | 直接 `Math.sin/cos/tan/exp/log/pow`（宿主替换为确定性实现或抛错） |
| `Map`/`Set`（规范保证插入序） | 依赖 `Intl`/本地化排序 |
| 注册顺序确定的处理器 | 动态 `import()`、运行时加载模块 |

## 九、脚本宿主

> 详细作者 API 见 [02](02_内容作者与工具链.md)。这里定义运行时的边界。

### 9.1 脚本用来做什么

| 适合 | 不适合 |
| --- | --- |
| 内容规则：交互、条件、对话分支、任务目标、过场编排 | 每帧遍历上千实体的热循环 |
| 游戏特有的「胶水」逻辑 | 物理/寻路/空间索引等内核能力 |
| 原型与实验 | 需要严格内存/性能预算的底层系统 |
| UI 数据编排（通过 UI 模型） | 直接操作引擎节点/渲染 |

**默认策略**：能声明就不写脚本；能写进套件 schema 就不写脚本；只有「这个游戏独有」的逻辑才写 TS。

### 9.2 执行模型

```text
tick N: [Sim] → [PostSim] → [Script]
                              ├─ 读取本 tick 事件（只读）
                              ├─ 调用注册的事件处理器（固定顺序）
                              ├─ 处理器可以查询只读状态
                              └─ 处理器只能通过 world.cmd.* 排队命令（N+1 生效）

tick N+1: [Command] 应用脚本排队的命令
```

- 脚本在**内核线程**上同步执行；没有异步、没有回调到引擎。
- 处理器顺序 = 模块加载顺序（按包内路径排序）+ 注册顺序；两者都稳定。
- 每个处理器有执行预算；超时用 QuickJS 的 interrupt 机制中断，记录并跳过剩余处理器。
- **预算是尽力而为，不是抢占式超时**：interrupt 只在解释器回边触发；长时间的原生调用无法中断。
  因此跨语言 API 必须短小、有界，不能把大循环藏进 `world.query` 的宿主实现里。
- 处理器抛错：记录 `ScriptError`（模块、处理器、事件、堆栈），隔离该处理器；连续 3 次失败则禁用并告警。

### 9.3 脚本状态与存档

脚本状态**不自动序列化**。需要持久化的脚本必须显式实现：

```ts
export function saveState(): unknown { return { talkedToKeeper: true }; }
export function loadState(data: unknown): void { /* 校验并恢复 */ }
```

- **v0 的脚本是全局模块，不绑定实体**；实体级状态必须放进组件/套件，不能藏在模块变量里。
  未来若要「每个实体一段脚本」，应做成显式的脚本组件，而不是共享模块变量。
- 存档里保存 `script_state`（JSON/CBOR）与包哈希；加载时若包不匹配，拒绝或走迁移。
- 回放时：脚本状态从快照恢复，不重新执行历史脚本；命令日志用于对账。
- 不鼓励在脚本里存大量状态；能放进组件/套件的状态，优先放组件。

### 9.4 沙箱与能力

| 能力 | 默认 | 说明 |
| --- | --- | --- |
| 读写世界（经命令/查询） | 允许 | 受 schema 与权限约束 |
| 文件系统 | 禁止 | 编辑器工具链除外 |
| 网络 | 禁止 | 需要时由宿主显式授予（如 Web 预览的调试通道） |
| 引擎对象 | 禁止 | 脚本看不到任何引擎类型 |
| 原生扩展 | 禁止 | 需要原生性能的逻辑写成 Rust 套件 |

## 十、存档、回放、迁移

### 10.1 存档信封

```rust
pub struct SaveEnvelope {
    pub format_version: u32,
    pub core_version: Version,
    pub pack_id: String,
    pub pack_version: Version,
    pub pack_hash: [u8; 32],
    pub seed: u64,
    pub tick: Tick,
    pub world: Vec<u8>,        // 规范化快照
    pub scripts: Vec<u8>,      // 脚本显式状态
    pub checksum: [u8; 32],
}
```

| 原则 | 做法 |
| --- | --- |
| 快照与包解耦 | 快照只存组件 ID + 值；组件注册表由包提供 |
| 未知组件可保留 | 前向兼容：未知 kit/组件按 `(id, version, bytes)` 原样保存 |
| 原子写 | 临时文件 + fsync + rename；保留上一份备份 |
| 损坏检测 | checksum + 结构校验；损坏时明确报错，不「尽量加载」 |
| 迁移显式 | `worldc migrate` 或运行时迁移表；迁移必须可测试 |

### 10.2 存档分层

| 层 | 内容 | 频率 |
| --- | --- | --- |
| `profile` | 玩家设置、解锁、跨世界统计 | 低 |
| `world` | 持久世界（Zone 摘要、任务、关系、经济） | 中 |
| `session` | 一局临时状态（可丢弃） | 高/不存 |
| `replay` | 输入/命令日志 + 关键帧哈希 | 按需 |

**不要**把 profile 和 world 混在一个大 JSON 里：这会让「换一个存档」和「换一个玩家」互相牵连。

### 10.3 回放与黑匣子

```text
Replay {
  header: { pack_hash, seed, tick_hz, core_version, sim_profile },
  inputs: [ { tick, input } ],
  commands: [ { tick, command } ],
  physics: [ { tick, frame } ],   // 仅 engine_physics；arcade 为空
  keyframes: [ { tick, hash } ],
  final_hash: u64
}
```

- 回放校验：包哈希、种子、tick 频率、`sim_profile`。
- 黑匣子：内存环形缓冲最近 N tick 的事件/命令/哈希；崩溃时落盘，便于事后分析。
- 回放差异定位：二分 keyframe，找到首个哈希不同的 tick，再 diff 该 tick 的命令与事件。

## 十一、表现边界

内核只产出**表现事件**与**只读快照**，不知道引擎节点、材质、音频总线。

| 数据 | 何时产生 | 适配器做什么 |
| --- | --- | --- |
| `EntitySpawn { id, content_id, view, transform }` | 实体进入可见范围 | 创建/复用节点，绑定资产 |
| `EntityUpdate { id, anim, flags }` | 逻辑状态变化时 | 驱动动画/可见性；**变换不走这里**，走 POD 快路径 |
| `EntityDespawn { id }` | 实体销毁或离开可见范围 | 回收节点/池 |
| `Effect { kind, at, params }` | 一次性表现 | 粒子/音效/镜头震动 |
| `Audio { id, at, params }` | 一次性/循环 | 播放/停止 |
| `UiPatch { path, value }` | UI 模型变化 | 更新 HUD/面板 |
| `ZoneVisible { zone_id }` | 区域激活完成 | 显示/隐藏区域根节点 |

### 11.1 视图注册表

- 适配器维护 `EntityId -> ViewHandle`；内核不持有句柄。
- 同一 `ContentId` 的多个实例共享资产，不共享状态。
- 插值：适配器保存上一 tick 与当前 tick 的变换，按 `alpha` 插值；`teleport` 标记跳过插值。
- 池化：适配器负责；内核不假设「销毁即可回收」。

### 11.2 UI 模型

- 套件产出**只读 UI 模型**（键值/列表/条），不产出具体控件。
- 适配器把模型映射到引擎 UI；不同引擎可以有不同外观。
- 文案用本地化 key，绝不在模型里放硬编码中文/英文。

## 十二、线程与并发

| 约束 | 说明 |
| --- | --- |
| 内核单线程 | `World` 只在创建它的线程上调用；不提供内部并行系统 |
| 适配器可异步 | 资产加载、贴图上传可在后台线程；**回到主线程**再调用内核 |
| 无回调 | 内核不调用引擎；适配器轮询事件/快照 |
| 事件批量 | 一帧一次 `poll_events`，不要每个实体一次跨语言调用 |
| 共享只读 | 快照是不可变字节/值；适配器可在渲染线程读，但生命周期由主线程管理 |

> 如果内部使用 `bevy_ecs`，只取其存储/查询/资源能力，**不使用它的并行调度器**；
> 系统顺序由 `world-core` 显式决定。ECS 是内部实现，不是并发模型。

> 为什么不做并行 ECS：v0 的实体规模（5k 活跃）单线程足够；并行会引入顺序不确定性，
> 与「确定性优先」冲突。等有真实性能瓶颈，再在**只读查询**上做确定性并行。

## 十三、数据所有权矩阵

| 数据 | 所有者 | 可写 | 可读 |
| --- | --- | --- | --- |
| 世界状态 / 组件 | `world-core` | 内核系统 | 系统、脚本（只读查询）、适配器（快照） |
| 套件状态 | 对应 `world-kits-*` | 该套件系统 | 其他套件（经端口/事件） |
| 命令队列 | 内核 | 玩家/脚本/系统/编辑器 | 内核 |
| 事件流 | 内核 | 内核系统 | 脚本、套件、适配器 |
| 随机流 | 内核 | 内核系统 | 只读派生 |
| 脚本状态 | 脚本模块 | 脚本自身（显式 load/save） | 存档 |
| 存档 | 内核 + 适配器存储 | 内核序列化，适配器落盘 | 内核 |
| 资产 | 适配器 | 适配器 | 内核只知道逻辑 ID |
| 渲染/音频/输入设备 | 适配器/引擎 | 适配器/引擎 | 适配器 |

## 十四、失败与降级

| 失败 | 默认行为 | 可配置 |
| --- | --- | --- |
| 脚本异常 | 隔离处理器，记录，继续 | `strict_scripts` 下失败即停 |
| 脚本超预算 | 中断当前处理器，跳过剩余 | 预算可配 |
| 内容包哈希不匹配 | 拒绝加载 | 调试模式可 `--allow-mismatch` |
| 存档版本不匹配 | 尝试迁移；失败则拒绝并给出报告 | —— |
| 资产缺失 | 占位 + `AssetMissing` 事件 | 严格模式构建期失败 |
| 可选套件失败 | 禁用该套件并继续 | manifest `required: true` 则停机 |
| 核心系统失败 | `World` 进入 `Faulted`，停止 tick | —— |
| tick 超预算 | 记录并丢弃积压（有上限） | 阈值可配 |
| 状态哈希分歧 | 开发期断言；发布期记录首个分歧 tick | 可关闭但强烈不建议 |

**一条底线**：宁可明确停机并给报告，也不要「带着坏状态继续跑」。后者会把问题推迟到玩家存档里。
