# 02 · 内容作者与工具链

> **一句话**：内容作者只跟「世界里的东西」和「动词」打交道——门、钥匙、NPC、任务、对话、时间段；
> 不跟节点、场景、资源路径、引擎 API 打交道。工具负责把作者写的东西编译成引擎中立的内容包。

## 一、读者与目标

| 读者 | 需要什么 | 不需要什么 |
| --- | --- | --- |
| 内容策划 | 摆放、填表、写规则、试玩、改文案 | 引擎工程、构建系统、着色器 |
| 叙事作者 | 对话图、任务链、条件、本地化 | 状态机代码、序列化格式 |
| 系统策划 | 数值、掉落、经济、难度曲线 | 内存布局、线程、FFI |
| 技术美术 | 资产逻辑 ID、导入配方、表现事件 | 玩法规则 |
| 工程 | schema、套件、适配器、性能 | 替作者写每一条内容 |

**成功判据**：一个没写过 Godot/Unity 的人，照 [§十二](#十二两小时做出一个可玩房间) 的教程，
**2 小时内**做出一个可玩房间（1 个 NPC、1 段对话、1 个任务、1 扇需要钥匙的门），并能保存/重载。

> **不会写代码不是障碍**：摆放、对话、任务、物品、数值都可以在 Web 编辑器里用表单/图形完成；
> TypeScript 只是「复杂规则的上限」，不是入门门槛。工具会在需要时把图形操作落成可读的 TS/JSON。

## 二、作者看到的世界

作者不需要知道 ECS、tick、组件注册。给作者的概念只有七个：

| 概念 | 作者怎么理解 | 怎么写 |
| --- | --- | --- |
| **区域 Zone** | 一个房间/一层楼/一片地图 | 画边界、放导航、摆东西 |
| **角色 Actor** | 有身体、会行动的东西 | 选模板、改属性、排日程 |
| **道具 Prop** | 门、箱子、按钮、可交互物 | 选模板、配动词 |
| **物品 Item** | 背包里的东西 | 填 ID、名称、图标、堆叠 |
| **规则 Rule** | 「当……且……就……」 | 写 TS 或填表 |
| **任务 Quest** | 一串目标 + 奖励 | 填目标、前置、奖励 |
| **对话 Dialogue** | 一棵带选项的树 | 画节点、写选项 |

其余（组件、系统、命令、事件、快照）由工具展开，作者只在「高级模式」里看到。

## 三、动词优先：作者写什么，不写什么

| 作者想表达 | 作者写 | 作者不写 |
| --- | --- | --- |
| 有钥匙才能开门 | `if (!hasItem(actor, "item.keycard")) return` | `get_node("Door/Collision").disabled = false` |
| 打开气闸 | `cmd.setFlag("flag.airlock.open", true)` | `$AnimationPlayer.play("open")` |
| 给玩家一个物品 | `cmd.giveItem(actor, "item.coffee", 1)` | 直接改背包数组 |
| 开始任务 | `cmd.startQuest(actor, "quest.first_shift")` | 往任务管理器里塞状态 |
| 播放音效 | `cmd.playSound("sfx.airlock.open")` | 拿到 `AudioStreamPlayer` 引用 |
| 显示提示 | `cmd.toast(actor, loc("airlock.locked"))` | 拼 HTML/控件 |

**原则**：作者表达「意图」，内核决定「怎么发生」。意图可校验、可回放、可换引擎；
引擎调用不可校验、不可回放、换引擎即失效。

### 3.1 套件给作者的「动词」

作者不需要学每个套件的内部状态机，只需要知道**能对世界做什么**：

| 套件 | 作者可用的动词/字段 | 例子 |
| --- | --- | --- |
| `interaction` | `interact`、`verb`、`requires`、`prompt` | 门、按钮、可拾取物 |
| `stats` | `health`、`damage`、`modifier`、`immune` | 受伤、加护甲、中毒 |
| `inventory` | `giveItem`、`hasItem`、`removeItem`、`equip` | 钥匙卡、消耗品、装备 |
| `quest` | `objective`、`reward`、`requires`、`onComplete` | 跑腿、击杀、收集 |
| `dialogue` | `node`、`choice`、`condition`、`effect` | 分支对话、条件选项 |
| `director` | `spawn`、`wave`、`pacing`、`budget` | 刷怪、波次、节奏 |
| `ai` | `schedule`、`patrol`、`brain`、`perception` | 上班/闲逛/睡觉、巡逻 |
| `world_sim` | `calendar`、`offline`、`population` | 昼夜、离线收益、人口 |
| `save_profile` | `unlock`、`stat`、`setting` | 解锁、跨周目统计 |

**上限**：套件没提供的动词，作者可以写自定义规则（TS），但不能绕过命令直接改状态。
如果一条自定义规则被三个内容包重复使用，就应该把它上升为套件。

## 四、内容包结构

一个内容包是一个可独立版本化、可单独加载的目录：

```text
demo.harbor/
├── pack.json                     # 清单：ID、版本、依赖、套件、入口
├── world/
│   ├── harbor.world.json         # 世界根：默认区域、世界时钟、全局标记
│   ├── zones/
│   │   └── harbor.zone.json      # 区域边界、导航、摆放
│   ├── actors/
│   │   └── keeper.actor.ts       # 角色定义
│   ├── props/
│   │   └── airlock.prop.ts       # 道具定义
│   └── items/
│       └── keycard.item.json     # 物品定义
├── rules/
│   └── airlock.rule.ts           # 规则
├── quests/
│   └── first_shift.quest.ts      # 任务
├── dialogue/
│   └── keeper.dlg.json           # 对话
├── ui/
│   ├── hud.json                  # 声明式 HUD 布局
│   └── dialogue.json             # 对话框布局
├── schedules/
│   └── keeper.schedule.json      # 日程
├── balance/
│   └── economy.json              # 数值
├── loc/
│   ├── zh-CN.json                # 文案
│   └── en-US.json
├── assets/
│   └── assets.index.json         # 逻辑资产 ID → 文件
├── scripts/
│   └── reactor.js               # 事件作用域脚本（可选）
└── tests/
    └── first_shift.test.ts       # 内容测试（无头）
```

约定：

- **一个定义一个文件**，文件名用 `snake_case` 或 `kebab-case`，与 ID 对应；不要把所有东西塞进一个巨大 JSON。
- **ID 命名空间**：`demo.keeper`、`item.keycard`、`quest.first_shift`、`flag.airlock.open`；包内唯一，跨包用包前缀。
- **源文件可读**：TS/JSON 都要能 diff、能 review；不要生成不可读的中间文件再提交。
- **资产只写逻辑 ID**：`mesh.keeper`，不写 `res://`、`.prefab`、`Assets/...`。
- **导航是烘焙产物**：`zone.nav` 指向 `world/nav/<id>.json`；用 `worldc bake nav` 从 Zone 边界 + 静态 Prop AABB 生成，
  不手写格子。M1 是 1m 网格、4 邻接；门按静态障碍烘焙。
- **资产索引**：`pack.assets` 指向 `assets/assets.index.json`；actor/prop/item 的 `visual` 引用逻辑 ID，
  校验只检查引用，不检查源文件存在（导入/打包留给适配器）。
- **脚本是事件补充**：`scripts/*.js` 由 ScriptHost 执行，不替代声明式规则；脚本文件参与包哈希；没有脚本时不创建 QuickJS 运行时。

## 五、清单 `pack.json`

```json
{
  "schema": 1,
  "id": "demo.harbor",
  "version": "0.1.0",
  "core_api": ">=0.1 <0.2",
  "kits": ["interaction", "inventory", "quest", "dialogue", "director", "save_profile"],
  "entry": {
    "world": "world/harbor.world.json",
    "start_zone": "zone.harbor"
  },
  "sim_profile": "arcade",
  "tick_hz": 60,
  "assets": "assets/assets.index.json",
  "loc": ["loc/zh-CN.json", "loc/en-US.json"],
  "requires": [],
  "optional": ["demo.extra.shift"],
  "conflicts": []
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `schema` | 是 | 清单格式版本；与内容 schema 分开 |
| `id` / `version` | 是 | 包 ID 与 SemVer |
| `core_api` | 是 | 兼容的**内容 API** 范围（与 C ABI 版本分开）；不匹配则拒绝加载 |
| `kits` | 是 | 启用的玩法套件；未声明的套件不参与编译 |
| `entry` | 是 | 世界根与起始区域 |
| `sim_profile` | 是 | `arcade`（默认）或 `engine_physics` |
| `tick_hz` | 否 | 默认 60；一个包内固定 |
| `requires` / `optional` / `conflicts` | 否 | 包依赖与互斥（mod/DLC 用） |

**依赖规则**：`requires` 缺失 → 加载失败；`optional` 缺失 → 警告并降级；`conflicts` 同时存在 → 加载失败。
版本范围用 SemVer 范围语法；解析结果写入构建清单，运行时不重新解析。

## 六、三种写法，一个契约

| 写法 | 适合 | 优点 | 代价 |
| --- | --- | --- | --- |
| **JSON** | 物品、对话、摆放、数值 | 工具友好、非程序员可填 | 无类型、写逻辑笨重 |
| **TypeScript DSL** | 角色、规则、任务、复杂条件 | 类型、补全、可复用函数 | 需要 Node 工具链 |
| **可视化编辑器** | 摆放、对话图、简单规则 | 无需写代码 | 复杂逻辑仍需落到 TS |

三者最终编译到**同一个规范化内容包**；运行时只认包。这样：

- 非 TS 工具（Python 脚本、Excel 导入、未来的 C# 编辑器）也能产出包；
- 作者可以混合使用：摆放用编辑器、规则用 TS、对话用 JSON；
- 引擎适配器完全不需要知道源格式。

### 6.1 规范化内容 schema

- 用 JSON Schema 描述每类定义；`worldc` 在构建期校验，编辑器用它生成表单。
- 规范化输出按 ID/字段排序、去除无意义空白，保证**同一源 → 同一哈希**。
- schema 带 `version`；不兼容变更走主版本 + 迁移工具。

## 七、作者写法示例

以下示例是 **M1 已实现的对象式 DSL**（`define*`）。示例中的 `on/cmd` 简写是后续糖，不在 M1 范围内。
作者 import 使用包内 import map `#world-authoring`，不需要 `node_modules`。

### 7.1 角色 `world/actors/keeper.actor.ts`

```ts
import { defineActor } from "#world-authoring";

export default defineActor({
  id: "demo.keeper",
  name: "loc:actor.keeper.name",
  tags: ["npc", "human", "harbor"],
  body: { shape: "capsule", radius: 0.35, height: 1.7 },
  stats: { health: 100, speed: 3.2 },
  brain: { profile: "schedule", schedule: "schedule.keeper" },
  inventory: { items: [{ item: "item.radio", count: 1 }] },
});
```

### 7.2 规则 `rules/airlock.rule.ts`

```ts
import { defineRule } from "#world-authoring";

defineRule({
  id: "rule.airlock",
  on: "interact",
  target: "demo.airlock",
  when: [{ kind: "has_item", item: "item.keycard" }],
  then: [
    { kind: "play_sound", id: "sfx.airlock.open" },
    { kind: "set_flag", flag: "flag.airlock.open", value: true },
    { kind: "emit", event: "airlock.opened" },
  ],
  else: [{ kind: "toast", text: "loc:airlock.locked" }],
});
```

读法：**当**有人交互**且**目标是气闸、**且**有钥匙卡 → 播放音效、置标记、发事件；
**否则**提示。作者不需要知道气闸是节点、动画还是模型。

### 7.3 任务 `quests/first_shift.quest.ts`

```ts
import { defineQuest } from "#world-authoring";

export default defineQuest({
  id: "quest.first_shift",
  title: "loc:quest.first_shift.title",
  summary: "loc:quest.first_shift.summary",
  objectives: [
    { id: "talk_keeper", kind: "talk", target: "demo.keeper", count: 1 },
    { id: "open_airlock", kind: "flag", flag: "flag.airlock.open", count: 1 },
  ],
  rewards: [
    { kind: "item", item: "item.coffee", count: 1 },
    { kind: "flag", flag: "flag.quest.first_shift.done" },
  ],
});
```


### 7.5 区域与摆放 `world/zones/harbor.zone.json`

```json
{
  "id": "zone.harbor",
  "name": "loc:zone.harbor.name",
  "bounds": { "min": [-20, 0, -20], "max": [20, 8, 20] },
  "nav": "nav.harbor",
  "placements": [
    {
      "actor": "demo.keeper",
      "at": [4, 0, -2],
      "yaw": 180,
      "persistent_id": "keeper"
    },
    {
      "prop": "demo.airlock",
      "at": [0, 0, 6],
      "yaw": 0,
      "persistent_id": "airlock"
    }
  ]
}
```

`persistent_id` 是存档锚点：区域卸载再加载、存档再读档，都靠它找回同一个对象。**不要用数组下标**。

道具的碰撞体在 prop 定义里声明（`body: { shape: "aabb", size: [...] }` 或 `capsule`），
由 `worldc bake nav` 连同静态几何一起烘焙成 `nav.harbor`；作者不手写导航网格。

### 7.7 内容测试 `tests/first_shift.test.ts`

```ts
import { test, expect, world } from "@refu/world-testing";

test("没有钥匙卡时气闸不开", () => {
  const w = world.load("demo.harbor");
  const keeper = w.spawn("demo.keeper", { zone: "zone.harbor" });
  const airlock = w.findByContentId("demo.airlock");

  w.cmd.interact(keeper, airlock);
  w.tick(2);

  expect(w.flag("flag.airlock.open")).toBe(false);
  expect(w.lastToast(keeper)).toBe("loc:airlock.locked");
});
```

内容测试跑在无头内核上，不需要引擎；`@refu/world-testing` 是 M2 目标，M1 用 `web/test_preview.cjs` 与 `worldc replay` 验收。

### 7.8 脚本 `scripts/reactor.js`

脚本是**事件作用域**的补充层：每个文件定义 `onEvent(ctx)`，拿到只读上下文快照，返回命令数组。
适合「一条声明式规则表达很别扭、但又不需要独立系统」的逻辑；大段玩法仍应优先 JSON 规则/套件。

```js
function onEvent(ctx) {
  if (ctx.event.kind !== "reactor.opened") return [];
  const reactor = ctx.entities.find((e) => e.content_id === "demo.reactor");
  return [
    { op: "set_flag", flag: "flag.script.reactor_seen", value: true },
    { op: "toast", text: "脚本：反应堆事件已记录" },
    { op: "open_door", target: reactor.id }
  ];
}
```

上下文：`tick / event / flags / quests / entities / player / zone_id`。`entities` 里是只读快照（含
`id`、`content_id`、`transform`、`inventory`、`door` 等）；用 `content_id` 找对象，命令里用实体 `id`。

命令：`interact`、`talk`、`pickup`、`give_item`、`set_flag`、`start_quest`、`toast`、`play_sound`、
`emit`、`activate_zone`、`move`、`move_to`、`open_door`。命令在事件的下一 tick 进入正常 `Command` 管线，
所以仍会做距离/门/背包等校验，脚本不能绕过世界规则。

运行时预算：QuickJS 内存 16 MB、栈 1 MB、单事件最多 128 条命令、20k 次中断计数；异常变成 `script_error`
事件与 `last_error`。当前**没有**持久脚本状态、模块 import、异步调度、墙钟抢占和热重载。

## 八、编译产物

```bash
worldc build demo.harbor --out dist/
```

```text
dist/demo.harbor/
├── pack.data              # 规范化内容包（编码版本化；v0 为确定性 JSON）
├── manifest.json          # 最终清单：id/version/hash/core_api/kits/assets
├── assets.index.json      # 逻辑资产 ID → 源文件 + 角色（mesh/skeleton/anim/tex/sfx）
├── loc/
│   ├── zh-CN.json
│   └── en-US.json
├── schema/
│   └── world.schema.json  # 供编辑器/外部工具生成表单
├── types/
│   └── world.d.ts         # 供 TS 作者与 IDE
└── sourcemap.json         # 编译产物 → 源文件位置（错误定位/热重载）
```

| 产物 | 谁消费 | 是否提交 |
| --- | --- | --- |
| `pack.data` | 内核 | 发布时提交/打包；开发时生成 |
| `manifest.json` | 内核/适配器 | 发布时提交 |
| `assets.index.json` | 适配器 | 是（源） |
| `loc/*.json` | 内核/UI | 是（源） |
| `schema/*.json` | 编辑器 | 生成，可不提交 |
| `types/*.d.ts` | 作者 IDE | 生成，可不提交 |
| `sourcemap.json` | 工具/调试 | 开发时生成 |

**哈希**：`manifest.json` 里的 `hash` 覆盖 `pack.data` + 资产清单 + 套件版本 + schema 版本；
存档/回放绑定这个哈希，任何内容改动都会显式失效，而不是「悄悄变了」。

## 九、校验与错误

### 9.1 校验层级

| 级别 | 含义 | 默认行为 |
| --- | --- | --- |
| `error` | 一定导致运行错误/内容不可用 | 构建失败 |
| `warning` | 可能不是作者本意 | 构建通过，汇总显示 |
| `info` | 建议/风格 | 只在详细模式显示 |

### 9.2 校验类别

| 类别 | 例子 | 典型级别 |
| --- | --- | --- |
| Schema | 字段类型错、必填缺失、枚举越界 | error |
| 引用 | 任务引用不存在的角色、规则引用不存在的物品 | error |
| 可达性 | 对话节点从 `start` 不可达、任务目标永远无法完成 | warning/error |
| 本地化 | 文案 key 缺失、占位符数量不一致 | error |
| 资产 | 逻辑 ID 没有对应文件、格式不支持 | error |
| 确定性 | 规则里用了 `Math.random`/`Date.now`/`async` | error |
| 性能 | 每 tick 遍历全场的脚本、超大对话图 | warning |
| 命名 | ID 未加命名空间、重复 `persistent_id` | warning/error |
| 存档 | `persistent_id` 冲突、迁移缺字段 | error |

### 9.3 错误长什么样

作者看到的不是 Rust 堆栈，而是「哪个文件、哪一行、哪个 ID、怎么修」：

```text
error[E-REF-001] quest.first_shift
  目标 talk_keeper 引用了不存在的角色 "demo.keeper2"
  --> quests/first_shift.quest.ts:7:5
   |
 7 |     { id: "talk_keeper", kind: "talk", target: "demo.keeper2", count: 1 },
   |                                             ^^^^^^^^^^^^^^^
   |
   = 候选: demo.keeper
   = 帮助: worldc explain E-REF-001
```

错误码稳定、可检索、可测试；`worldc explain <code>` 给出原因与修法。

### 9.4 校验即测试

- 每个 `error` 类别至少有一个 fixture（故意写错的内容包），确保校验器不会静默退化。
- 校验器本身是 Rust 库，可被编辑器/CI/构建脚本复用；不重复实现两套规则。

## 十、Web 世界编辑器

> **M1 已交付 v0.5**：布局拖拽 + 字段表单 + 定义/规则 JSON + 对话图 + 撤销/重做 + 校验/构建/试玩；
> 更完整的 schema 驱动表单仍在后续（见 [07](07_M1实现与验收.md)）。编辑器编辑 JSON 包，TS 源不自动同步。

编辑器是「作者主界面」的推荐形态：打开浏览器就能用，不需要装引擎、不需要配工程。

### 10.1 模式

| 模式 | 作者做什么 | 背后 |
| --- | --- | --- |
| **布局 Layout** | 画区域、摆角色/道具、调朝向、看导航 | 读写 zone JSON |
| **数据 Data** | 填属性、物品、掉落、经济 | schema 生成表单 |
| **逻辑 Logic** | 写/改 TS 规则，带补全与错误 | 调 `worldc` 编译 |
| **对话 Dialogue** | 画对话图、选项、条件 | 读写 dialogue JSON |
| **试玩 Play** | 在内置 WASM 内核里跑，热重载 | Web 宿主 |
| **测试 Test** | 跑内容测试、看覆盖、看黄金回放 | 无头内核 |

### 10.2 作者工作流

```text
打开项目
  → 布局：拖一个房间，放一个 NPC
  → 数据：给 NPC 配日程、给门配钥匙需求
  → 逻辑：写一条规则（或从模板插入）
  → 对话：画三段对话
  → 任务：加两个目标
  → 试玩：WASD 走动、交互、看任务完成
  → 保存：内容源文件写回仓库
  → 测试：一条内容测试通过
```

### 10.3 编辑器必须有的能力

| 能力 | 为什么必须 |
| --- | --- |
| 热重载 ≤ 2 秒 | 作者改一句文案不该等构建 |
| 错误内联到字段 | 错误在文件末尾等于没提示 |
| 撤销/重做/自动保存 | 内容作者不是工程师，不能靠 git 救命 |
| 试玩内 inspector | 看实体、组件、标记、事件流 |
| 内容 diff | 改了什么、影响哪些引用 |
| 模板库 | 「一扇门」「一个可拾取物」「一段对话」开箱即用 |
| 多语言并排编辑 | 文案作者不该手改 JSON |
| 不依赖引擎 | 这是「作者不需要引擎知识」的物理保证 |

### 10.4 与引擎编辑器的关系

- **内容包是唯一事实源**；Web 编辑器、Godot 插件、未来的 Unity 窗口都读写同一份源文件。
- 引擎编辑器插件只做两件事：把引擎里看到的空间/资产映射到内容 ID；启动试玩。
- 不允许「在 Godot 里改完场景，再导出成内容包」——那会让 Godot 成为隐形的唯一事实源。

## 十二、两小时做出一个可玩房间

这是 M1 的验收教程，也是「作者不需要引擎知识」的实测。按 8 步，每步 5–20 分钟：

| 步 | 做什么 | 作者学到 | 时间 |
| --- | --- | --- | --- |
| 1 | `worldc new demo.harbor`，打开 Web 编辑器 | 项目/区域/试玩按钮 | 5 min |
| 2 | 画一个 20×20 的房间，放一扇门 | 区域、边界、摆放 | 10 min |
| 3 | 放一个 NPC，配「站岗 → 闲逛 → 睡觉」日程 | 角色、日程、世界时间 | 15 min |
| 4 | 放一个钥匙卡物品，配「拾取」 | 物品、交互 | 10 min |
| 5 | 写规则：有钥匙卡才能开门 | 事件、条件、命令 | 20 min |
| 6 | 画三段对话，加一个「问班次」选项 | 对话、条件、本地化 | 20 min |
| 7 | 加任务：和 NPC 说话 + 开门 | 目标、奖励、标记 | 15 min |
| 8 | 试玩、存档、重载、跑内容测试 | 确定性、存档、测试 | 15 min |

**验收**：一个没写过引擎的人独立完成；全程不打开 Godot/Unity；内容测试通过；重启后存档能恢复。

> 这是 **M1 的验收目标，不是当前事实**。编辑器不成熟时，首次作者可能要 4–6 小时；
> 超出 2 小时的部分应视为**工具缺陷**去修，而不是要求作者「再学学」。

## 十三、本地化与可访问性

### 13.1 本地化

- **所有面向玩家的文本**用 key：`loc:actor.keeper.name`，源文件里不写死中文/英文。
- 文案表按语言分文件；缺失 key 在严格模式下是 error，宽松模式回退到默认语言并 warning。
- 占位符用命名参数（`{name}`），构建期校验参数集合一致。
- 对话/任务/物品的文本也走同一套 key，不在各自 JSON 里另起炉灶。
- 复数/性别：v0 只支持简单的 `one/other` 与显式变体；复杂规则交给套件，不引入 ICU 到内核。

### 13.2 可访问性

内容层能提供的：

| 能力 | 作者怎么写 | 表现层怎么用 |
| --- | --- | --- |
| 字幕/文本替代 | 对话/音效事件带 `loc` key | UI 显示字幕 |
| 高对比/大字号 | 不写死颜色/字号，用语义 token | 适配器主题 |
| 交互提示 | `Interactable` 自带动词与提示 key | UI/准星显示 |
| 无音频可玩 | 关键信息不只靠音效 | 事件同时带视觉提示 |

**边界**：具体控件、对比度、字体缩放是表现层/设计系统的责任；内容层只保证「信息有文本替代、不写死外观」。

## 十四、版本、依赖、迁移、Mod

### 14.1 版本

| 对象 | 版本 | 兼容规则 |
| --- | --- | --- |
| 内核 `world-core` | SemVer | 主版本破坏 ABI/schema |
| 内容 schema | 整数 | 不兼容则主版本 + 迁移 |
| 内容包 | SemVer | 作者发布单位 |
| 套件 | SemVer + `core_api` | 套件声明兼容的内核范围 |
| 存档 | 整数 `format_version` | 迁移表逐版本升级 |

### 14.2 依赖与 Mod

- 包可以 `requires` / `optional` / `conflicts` 其他包；解析在构建期完成，运行时不解析。
- Mod 与官方包同构：同样的 manifest、schema、沙箱；默认不允许文件/网络。
- 加载顺序：按依赖拓扑排序；同层按包 ID 字典序；内容冲突（同一 ID 被两个包定义）默认 error，允许 `override` 显式声明。
- 未来可加签名；v0 至少做哈希与来源记录。

### 14.3 迁移

- 内容迁移：`worldc migrate --from 0.1 --to 0.2`，基于规则表（改名/删字段/默认值/拆分）。
- 存档迁移：运行时迁移表；每个迁移有测试（旧存档 fixture → 新版本 → 哈希/字段断言）。
- **迁移必须显式**：不猜、不「尽量兼容」；迁移失败给出可操作的报告。

## 十五、测试与发布

### 15.1 内容测试

| 类型 | 做什么 | 跑在哪 |
| --- | --- | --- |
| 单元规则测试 | 给定世界状态 + 命令，断言事件/标记 | 无头内核 |
| 任务链测试 | 从开始到完成，断言每步状态 | 无头内核 |
| 对话覆盖 | 所有节点至少被走到一次 | 无头内核 |
| 黄金回放 | 固定种子 + 输入轨迹 + 哈希 | CI |
| 确定性测试 | 同 tick 跑两遍，比较哈希 | CI |
| 适配器测试 | 同一包在两个宿主跑，比较哈希/事件 | M3 swap-check |

### 15.2 覆盖率

- 规则命中：哪些规则文件/处理器被执行过；
- 任务目标：哪些目标被完成/失败过；
- 对话节点：哪些节点可达/被访问；
- 标记：哪些 flag 被读写但从未被消费（死内容）。

### 15.3 发布

```bash
worldc build --release --platform desktop
worldc test --release
worldc swap-check --pack demo.harbor   # 至少两个宿主
```

发布产物包含：`pack.data`、`manifest.json`、`loc/`、`assets.index.json`、各平台导入配方。
**不含**源 TS/JSON（可选保留 sourcemap 供调试）。

## 十六、反模式

| 反模式 | 为什么错 | 正确做法 |
| --- | --- | --- |
| 内容里写 `res://` / `Assets/` 路径 | 换引擎即失效 | 逻辑资产 ID + 导入配方 |
| 内容里写死中文/英文 | 无法本地化 | `loc:` key |
| 每 tick 用脚本遍历全场 | 脚本不是热路径 | 写成 Rust 套件系统 |
| 用 `EntityId` 做存档/任务目标 | 重载后失效 | `ContentId` / `persistent_id` |
| 所有规则塞进一个文件 | 不可 review、冲突多 | 一文件一主题 |
| 直接改组件/引擎节点 | 绕过校验、无法回放 | 发命令 |
| 复制粘贴一整套定义 | 改一处漏十处 | 模板/继承/组合 |
| 用系统时间/随机数 | 不可复现 | `world.time` / `world.rng` |

## 十七、工程师的边界：什么放 Rust，什么放 TS

| 放 Rust（内核/套件） | 放 TS（内容/扩展） |
| --- | --- |
| 空间索引、导航、碰撞查询 | 单条规则的条件与命令 |
| 背包/任务/对话/属性的状态机 | 游戏特有的目标、奖励、条件组合 |
| 存档/回放/迁移 | 内容测试 |
| 每 tick 大循环、性能敏感逻辑 | 过场编排、UI 数据组装 |
| 确定性随机、时间、状态哈希 | 原型与实验规则 |

**判断标准**：如果一段逻辑会被「每 tick × 上千实体」执行，或者它定义了一个可复用的机制，放 Rust；
如果它是「这个游戏独有的一条规则」，放 TS。两者之间通过命令/事件/查询连接，不共享可变状态。
