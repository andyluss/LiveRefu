# 04 · 选型对比与推荐

> **一句话**：推荐 **方案 A —— Rust 权威内核 + TypeScript 内容层 + 版本化 C ABI + 薄引擎适配器**。
> 它不是「最先进」的方案，而是**同时满足「作者快、引擎可换、能落地」**的那一个。

## 一、评估方法

### 1.1 先过硬约束

任何方案先过四道硬约束，不过的直接淘汰，不进入评分：

| # | 硬约束 | 不过意味着 |
| --- | --- | --- |
| H1 | 能表达上层玩法（任务/对话/背包/技能/AI），不是只能填表 | 内容作者遇到逻辑就要找工程 |
| H2 | 能替换引擎（核心不依赖引擎类型） | 「跨游戏中间层」名不副实 |
| H3 | 能嵌入 PC/移动/主机/Web 中至少三类 | 只能做工具，不能做产品 |
| H4 | 2 人全职可维护，5–7 个月能到 M3 可用版本 | 架构再漂亮也交付不了 |

### 1.2 再加权评分

| 维度 | 权重 | 为什么这个权重 |
| --- | ---: | --- |
| 内容作者上手速度 | 15% | 这是本项目的第一目标（G1） |
| 引擎可替换性 | 20% | 这是与「普通游戏框架」的核心差异（G5） |
| 玩法表达力/上限 | 10% | 不能为了简单牺牲「上层玩法」 |
| 确定性与可测性 | 15% | 回放、测试、存档都靠它（G4） |
| 性能与规模 | 10% | 不能做一个只能跑 Demo 的层 |
| 多语言/多宿主扩展 | 5% | 未来要接 C#/C++/Lua/WASM |
| 交付风险与工期 | 15% | 1–2 人团队的现实约束 |
| 生态与人才 | 10% | 招人、找库、查文档的成本 |

评分 `1–5` 是**判断**，不是测量；它的作用是暴露取舍，不是制造精确感。真正重要的是后面的「为什么」与「何时改选」。

## 二、五个整体方案

### 方案 A：Rust 权威内核 + TypeScript 内容层 + C ABI

```text
内容（TS/JSON） → worldc 编译 → 内容包
                                  │
                          Rust 内核（权威、确定性）
                                  │ C ABI
                    ┌─────────────┼─────────────┐
                 Godot          Web/Bevy       Unity/Unreal
```

- 内核：Rust，拥有世界状态、tick、空间、规则、存档、回放。
- 内容：TS DSL + JSON，编译为语言中立内容包。
- 脚本：QuickJS 嵌入内核，脚本只能发命令/查询。
- 边界：版本化 C ABI，适配器轮询，内核不回调。
- 适配器：Godot/Web/Unity/Unreal/Bevy/Headless。

**强项**：引擎可换、确定性好、性能可控、多语言可接、内容作者体验可做到最好。
**弱项**：双语言 + IDL 的维护成本；Rust 门槛；首版工期比纯 TS 长。
**适合**：认真做「跨游戏、跨引擎」的中间层，且愿意投入 5–7 个月打地基（到 M3）。

### 方案 B：TypeScript 权威内核

```text
内容（TS） → Node/Deno/引擎内 JS 运行时（权威）
                              │
                    Godot/Unity/Web 适配（JS 桥）
```

- 内核用 TS 写，跑在 Node/Deno/浏览器/引擎内 JS 引擎。
- 内容与内核同语言，工具链统一。

**强项**：作者与工程同语言；迭代最快；生态最大；单语言心智负担低。
**弱项**：嵌入主机/移动/Unity/Unreal 困难（V8/Node 体积、GC、线程、平台限制）；确定性受 JS 引擎与 GC 影响；性能上限低。
**适合**：Web 优先、单平台、团队全是 TS、不追求主机/嵌入式。

### 方案 C：引擎原生框架 + 数据驱动

```text
Godot/GDScript 或 Unity/C#（权威）
        │
   数据表 / Resource / ScriptableObject
```

- 直接在引擎里做模块化框架 + 数据驱动；不引入第二语言。
- 内容作者仍在引擎编辑器里工作。

**强项**：最快出活；与引擎贴合；调试方便；团队不需要新语言。
**弱项**：换引擎 = 重写；内容作者必须懂引擎；跨游戏复用靠复制。
**适合**：明确只做一个引擎、一个项目，短期上线优先。

### 方案 D：现成 ECS/框架（Bevy/Flecs）为核心 + 引擎桥

```text
Bevy ECS / Flecs（权威）
        │
   Godot/Unity/Unreal 桥（同步实体与视图）
```

- 用成熟 ECS 作为内核，自己写引擎桥与内容层。

**强项**：ECS 成熟、性能好、Rust 生态；Bevy 可直接做原生游戏。
**弱项**：ECS 是「实现模型」，不是「内容模型」；作者仍要理解组件/系统；Flecs 引入 C 依赖；引擎桥仍要自己做；跨语言内容层缺失。
**适合**：Bevy 原生团队，或只需要一个高性能内核、不打算做通用内容工具。

### 方案 E：纯声明式数据规则（无通用脚本）

```text
内容（JSON/YAML 表）
        │
  通用规则解释器（条件/动作表）
```

- 所有玩法用「条件 → 动作」表表达，不提供通用脚本。

**强项**：最安全、最可控、作者门槛最低；工具与校验最容易做。
**弱项**：表达力上限低；复杂玩法会催生一门「越来越像编程语言」的配置语言；难做 AI/过场/复杂任务。
**适合**：内容形态稳定、玩法简单、以数据/叙事为主的项目；也适合作为方案 A 的**子集**。

## 三、评分矩阵

| 维度（权重） | A | B | C | D | E |
| --- | ---: | ---: | ---: | ---: | ---: |
| 内容作者上手（15） | 4 | **5** | 3 | 2 | 4 |
| 引擎可替换（20） | **5** | 3 | 1 | 2 | 4 |
| 玩法表达力（10） | **5** | 4 | 3 | 4 | 2 |
| 确定性与可测（15） | **5** | 2 | 2 | 4 | 4 |
| 性能与规模（10） | 4 | 2 | 4 | **5** | 4 |
| 多语言扩展（5） | **5** | 4 | 1 | 3 | 4 |
| 交付风险与工期（15） | 3 | **5** | 4 | 2 | **5** |
| 生态与人才（10） | 4 | **5** | 4 | 3 | 3 |
| **加权总分（/5）** | **4.35** | 3.70 | 2.70 | 2.95 | 3.85 |

### 3.1 怎么读这张表

- **A 不是每一项都第一**：它在「工期/生态」上输给 B、C、E，在「作者上手/性能」上也没有满分——
  这两项是**目标**，不是已验证事实；A 仍然在「引擎可替换 + 确定性 + 表达力」上明显领先。
- 评分是**引入约束后的判断**：A 的作者体验 4 分（而非 5）是因为它依赖尚未建成的编辑器；性能 4 分（而非 5）
  是因为尚未基准验证。D 的性能 5 分来自已发布的 ECS 实现。
- **E 总分第二**，但它在「玩法表达力」只有 2——而本项目的需求明确包含「上层玩法机制」，所以 E 不能单独作为方案。
- **C 的工期/生态不差**，但「引擎可替换」是 1，直接违背项目前提。
- **B 是 A 的最强竞争者**：如果目标只有 Web、团队只有 TS，B 更务实。
- **D 的问题是「内核 ≠ 内容层」**：它解决性能与 ECS，不解决作者体验与跨引擎内容。

### 3.2 硬约束筛选结果

| 方案 | H1 玩法表达 | H2 换引擎 | H3 多平台 | H4 可维护 | 结论 |
| --- | --- | --- | --- | --- | --- |
| A | ✅ | ✅ | ✅（架构支持；移动/主机在 M4 实测） | ✅（需纪律） | **通过** |
| B | ✅ | ⚠️ | ⚠️ | ✅ | 有条件通过（仅 Web/桌面） |
| C | ✅ | ❌ | ✅ | ✅ | 不通过（违背前提） |
| D | ⚠️ | ⚠️ | ✅ | ⚠️ | 不通过（缺内容层） |
| E | ❌ | ✅ | ✅ | ✅ | 不通过（表达力不足） |

## 四、逐项分析

### 4.1 A 的关键风险与对策

| 风险 | 为什么发生 | 对策 |
| --- | --- | --- |
| 双语言 + IDL 维护成本 | 两套类型、两套工具、两处漂移 | 一份 schema 生成 Rust/TS/C# 类型；CI 比对；不允许手写两份 |
| Rust 门槛/编译时间 | 团队不熟；crate 多 | 内核保持小（4–6 个 crate）；CI 缓存；核心 API 面窄 |
| 首版工期长 | 内核 + 工具 + 两个宿主 | 先做 M0/M1 的垂直切片，不追求四个引擎 |
| 过度设计 | 想一次做完所有套件 | 非目标清单 + 「一个套件两个消费者才做」 |

### 4.2 B 的关键风险与对策

| 风险 | 为什么发生 | 对策 |
| --- | --- | --- |
| 主机/移动嵌入 | V8/Node 体积、JIT 限制、GC | 换 QuickJS/WASM，但那就逐渐变成 A 的脚本层 |
| 确定性 | GC、JIT、异步 | 固定 tick + 禁用异步 + 严格随机，但跨平台仍难保证 |
| 性能 | GC 停顿、单线程 | 热路径用 WASM/原生，但那就是 A |

**判断**：B 不是「错的方案」，而是「范围更小的方案」。如果目标收窄为 Web/Steam 单平台，B 的性价比最高。

### 4.3 C 的关键风险与对策

| 风险 | 为什么发生 | 对策 |
| --- | --- | --- |
| 换引擎 | 规则、存档、编辑器都绑引擎 | 无解；只能重写 |
| 作者门槛 | 必须懂场景/节点/资源 | 只能在引擎编辑器里做简化工具 |

**判断**：C 适合「先活下来」；如果项目的真实目标只是把一个游戏做出来，C 比 A 更理性。
本项目的前提是「跨游戏中间层」，所以 C 出局。

### 4.4 D 的关键风险与对策

| 风险 | 为什么发生 | 对策 |
| --- | --- | --- |
| 作者模型 | ECS 概念对策划不友好 | 必须再加一层门面/content schema，等于补 A 的 L4 |
| 跨引擎桥 | Bevy/Flecs 不提供引擎集成 | 自己写，和 A 的适配器工作量相同 |
| 语言扩展 | ECS 类型泄漏 | 需要 C ABI + IDL，还是 A 的边界 |

**判断**：D 可以是 A 的**内部实现**（A 确实推荐先用 `bevy_ecs`），但不适合作为**产品架构**。

### 4.5 E 的关键风险与对策

| 风险 | 为什么发生 | 对策 |
| --- | --- | --- |
| 表达力 | 复杂条件/过场/AI 无法用表表达 | 加脚本 → 变成 A；不加 → 内容受限 |
| 配置语言化 | 规则表越来越像编程 | 接受它，或直接用 TS |

**判断**：E 是 A 的子集。A 的「声明式优先」策略已经吸收了 E 的优点：简单内容填表，复杂逻辑写 TS。

## 五、子决策推荐

整体方案定了之后，还有十二个必须拍的技术选择。下表是推荐与改选条件。

| # | 决策 | 推荐 | 备选 | 何时改选 | 主要风险 |
| --- | --- | --- | --- | --- | --- |
| D1 | 权威内核语言 | **Rust** | C++ / TS | 团队无 Rust 且 3 个月内必须上线 | 人才、编译时间 |
| D2 | 内容语言 | **TS DSL + JSON** | 纯 JSON / Lua | 作者群体完全不写代码 | 工具链门槛 |
| D3 | 内核边界 | **C ABI + 轮询** | 进程内 Rust trait / WASM 组件 | 只服务 Rust 宿主 | ABI 稳定性 |
| D4 | 脚本运行时 | **QuickJS-NG（`rquickjs`）** | V8/deno_core / Lua / WASM | 需要大量 npm 生态或强沙箱 | 性能、WASM 边界 |
| D5 | ECS | **内部 `bevy_ecs` + 门面** | 自研 sparse-set / Flecs | 需要 C 互操作或极致可控 | 依赖升级 |
| D6 | 空间/物理 | **核心逻辑空间 + 引擎表现** | 引擎物理权威 | 玩法以刚体物理为核心 | 表达力受限 |
| D7 | 世界形态 | **World + Session + Zone** | 仅 Session（关卡制） | 游戏完全没有持久世界 | 过度设计 |
| D8 | 首批宿主 | **Headless + C/C# ABI 冒烟 + Web + Godot** | 只做 Godot | 只关心一个引擎 | 工期 |
| D9 | 作者界面 | **Web 编辑器优先** | 引擎插件优先 | 作者全是引擎老手 | 编辑器工作量 |
| D10 | 资产引用 | **逻辑 ID + 每引擎导入配方** | 直接路径 | 只做一个引擎 | 管线复杂度 |
| D11 | 网络 | **v0 不做，留 rollback 口** | 一开始做 lockstep | 首发就是多人 | 返工 |
| D12 | 许可/治理 | **待定** | 内部 / 开源 | 商业化/社区策略明确后 | 生态与贡献 |

### 5.1 为什么 D4 选 QuickJS 而不是 V8

| 维度 | QuickJS-NG | V8 / deno_core |
| --- | --- | --- |
| 体积 | 小（约 1 MB 级） | 大（数十 MB 级） |
| JIT | 无 | 有；主机/移动常受限 |
| 嵌入 | 简单，C API | 复杂，平台绑定多 |
| 确定性 | 无 JIT，行为稳定 | JIT 优化可能影响浮点/时序 |
| 性能 | 足够跑事件处理器 | 高，但脚本不该是热路径 |
| 生态 | 标准 ES2020 | 完整 Node/npm |

**结论**：脚本只做「内容规则」，不做热循环；QuickJS 的体积与确定性更重要。
如果将来需要在脚本里跑重计算，应该把它下沉为 Rust 套件，而不是换 V8。

### 5.2 为什么 D5 用 `bevy_ecs` 但藏起来

- 借它的成熟度：实体分配、查询、资源、变更检测、调度基础。
- 不借它的「世界观」：内容作者看不到 `Entity`/`Query`/`SystemParam`；他们看到 Actor/Prop/Quest。
- 门面层（`world-core` 的 `World` API）是唯一被套件与适配器依赖的接口；未来换 ECS 实现不影响上层。
- 代价：一层薄封装与少量拷贝；换来的是可替换性与作者友好。

### 5.3 为什么 D6 把物理放核心

- 引擎物理（PhysX/Godot Physics/Chaos）结果不可跨引擎一致，甚至跨版本不一致。
- 塔防/RPG/经营只需要「运动学 + 形状查询 + 简化响应」，核心足够。
- 需要真实刚体的游戏，用 `engine_physics` 逃生舱；明确牺牲跨引擎一致性，而不是假装没有。

### 5.4 为什么 D8 先做 Web 而不是 Unity/Unreal

- Web 同时是「作者预览」与「换引擎证明」，一石二鸟。
- 不需要安装/授权/平台打包，CI 与作者机器都能跑。
- Unity/Unreal 的接入成本高，应该在「内核与内容闭环已验证」之后做。

## 六、推荐结论

### 6.1 推荐

**采用方案 A，按以下组合落地：**

```text
权威内核：Rust（world-core / world-abi / world-pack / world-kits-*）
内容层：  TypeScript DSL + JSON，worldc 编译为规范化内容包
脚本：    QuickJS-NG（rquickjs），只做内容规则
边界：    版本化 C ABI，轮询，无回调
ECS：     bevy_ecs（内部实现，门面隔离）
空间：    核心逻辑空间/导航/碰撞；引擎只做表现
世界：    World + Session + Zone
宿主：    Headless（CI）→ Web（作者预览/第二宿主）→ Godot（首个生产适配器）
编辑器：  Web 世界编辑器优先
资产：    逻辑 ID + 每引擎导入配方
网络：    v0 不做，命令日志/快照留 rollback 口
```

### 6.2 五条理由

1. **它同时满足三个硬目标**：作者快（TS/编辑器）、引擎可换（C ABI/适配器）、玩法有上限（TS + Rust 套件）。
2. **它把「确定性」放在架构里，而不是事后补**：固定 tick、显式随机、稳定顺序、状态哈希、回放。
3. **它的每一层都能独立验收**：内核无引擎可跑；内容可无头测试；适配器有 CTS；换引擎有 swap-check。
4. **它能渐进落地**：M0 就能跑无头 Demo；M1 作者可用；M2 接 Godot；不需要停主线。
5. **它不把宝押在某个引擎/某个语言上**：C ABI + IDL + 语言中立内容包，为 C#/C++/Lua/WASM 留了门。

### 6.3 三条前提

- **团队至少有一名熟悉 Rust 的工程师**，或者接受 M0–M1 的学习曲线。
- **首发只做一个生产适配器**（Godot）与一个预览宿主（Web），不要一开始铺四个引擎。
- **内容作者要参与工具设计**：Web 编辑器不是「程序员顺手做的后台」，而是产品。

## 七、为什么不是别的

| 方案 | 一句话拒绝理由 | 什么情况下会改选 |
| --- | --- | --- |
| B TS 内核 | 主机/移动嵌入与确定性是硬伤 | 只做 Web/Steam、团队纯 TS、3 个月内上线 |
| C 引擎原生 | 换引擎即重写，违背项目前提 | 只做一个引擎、一个项目，先活下来 |
| D ECS 为核心 | 解决性能不解决作者与跨引擎内容 | Bevy 原生团队，或只做 Rust 原生游戏 |
| E 纯数据 | 表达力撑不起「上层玩法机制」 | 叙事/轻玩法为主，不需要通用逻辑 |

**注意**：拒绝的是「作为整体方案」，不是「作为组件」。A 实际上吸收了 B 的语言（TS）、C 的工程务实、D 的 ECS 实现、E 的声明式优先。

## 八、什么情况下应该改选

设定「改选信号」，避免一条路走到黑：

| 信号 | 触发条件 | 建议动作 |
| --- | --- | --- |
| S1 团队现实 | 没有 Rust 能力，且 3 个月内必须有可玩版本 | 降级为 C（单引擎）或 B（Web） |
| S2 平台收窄 | 明确只做 Web/Steam，不做主机/移动 | 重新评估 B，A 仍可行但优势变小 |
| S3 物理核心 | 玩法以刚体/破坏/布娃娃为核心 | A 的 `engine_physics` 可能不够；考虑 C 或引擎物理权威 |
| S4 内容形态 | 主要是叙事/对话，规则很少 | E + Ink 类方案更轻 |
| S5 强 UGC | 需要安全加载玩家脚本/资产 | A + WASM 沙箱；QuickJS 可能不够 |
| S6 性能天花板 | 单 tick 5k 实体仍不够 | 核心并行/分片；或 D 的高性能 ECS |
| S7 维护崩塌 | 双语言/IDL 导致持续漂移 | 收缩到单语言（B/C），或砍掉非核心套件 |

**决策复核点**：M0 结束、M1 结束、M2 结束各复核一次；每次只回答「继续 / 收窄 / 改道」。

## 九、风险登记

### 9.1 最该盯的三个

1. **R1 范围蔓延**：这是所有「中间层」项目最常见的死法。非目标要写进 README，评审时直接引用。
2. **R3 确定性**：它不会在 Demo 暴露，只会在上线后暴露；所以 Det1 CI 必须从 M0 就有。
3. **R7 作者不买账**：架构再对，作者不用就失败；所以 M1 必须让真实作者试用，而不是工程自嗨。
