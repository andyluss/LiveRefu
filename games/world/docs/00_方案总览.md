# 00 · 方案总览

> **一句话**：把「世界怎么运转」从引擎里拿出来，做成一个**确定性、可测试、可替换引擎**的 Rust 内核；
> 内容作者用 TypeScript 与数据描述世界，引擎只负责把世界画出来、放出声音、接收输入。

## 一、问题：为什么现在的内容离不开引擎

把规则写进引擎工程，短期最快，长期会同时卡住三件事：**换引擎、换语言、换作者**。
具体表现不是抽象的「耦合」，而是下面这些每天都在发生的摩擦：

| # | 症状 | 真实代价 |
| --- | --- | --- |
| 1 | 内容作者必须懂节点、场景、资源路径、信号 | 策划改一个交互要排工程的期；新人上手以周计 |
| 2 | 规则、存档、编辑器都绑定引擎类型 | 换引擎等于重写；上主机/新平台要再评估一次 |
| 3 | 规则只能在引擎里跑 | 无头测试要起场景；回归慢、覆盖低 |
| 4 | 背包、任务、对话、状态、AI 每个游戏重写一遍 | 上层玩法机制没有复用，只有复制 |
| 5 | 数值、文案、逻辑、代码混在一起 | diff 不可读；回滚粒度粗；mod 无法安全加载 |
| 6 | 确定性靠运气 | 出现「这局为什么漏了」只能复现，不能回放对账 |

LiveBay 的模块化改造（[16](../../livebay/docs-ai/design01/tech/16_模块化技术架构_NASApunk.md)）已经证明：
**命令/事件总线 + 模块端口 + 内容包 + 黑匣子回放**能把一个真实的 Godot 塔防拆干净，并做到无头跑完 5 波。
本方案要做的，是把这套已经被验证的做法从「一个游戏的架构」提升为「跨游戏、跨引擎、跨语言的中间层」。

### 1.1 关键判断：中间层应该拥有什么

| 应该拥有 | 不应该拥有 |
| --- | --- |
| 世界状态、时间、实体、空间逻辑、规则、存档、回放 | 渲染、GPU 资源、音频混音、平台窗口、输入设备轮询 |
| 内容 schema、校验、编译、版本迁移 | 资产建模/贴图/动画制作 |
| 确定性、可测试性、诊断 | 某个引擎的节点/组件/场景对象 |
| 上层玩法套件（背包、任务、对话、AI…） | 特定游戏的数值与关卡设计 |

一句话：**中间层拥有「世界的事实」，引擎拥有「世界的呈现」**。

## 二、目标与非目标

### 2.1 目标

| ID | 目标 | 可验收的表现 |
| --- | --- | --- |
| G1 | 内容作者不需要引擎知识 | 非工程人员照教程 2 小时内做出可玩房间 |
| G2 | 同一内容包跨宿主一致 | 两个宿主跑同一包、同输入，600 tick 状态哈希一致 |
| G3 | 上层玩法机制可复用 | 至少 8 个套件跨两个内容包复用（分阶段：M1 七个，M2 补 AI） |
| G4 | 确定性、可回放、可自动测试 | 固定种子 + 输入轨迹可复现；存档往返哈希一致 |
| G5 | 引擎可替换 | 基础适配器 ≤ 2,000 行；适配器内零玩法规则；CTS 全绿 |
| G6 | 多语言可接入 | C ABI + IDL + 语言中立数据；新增宿主语言不改内核 |
| G7 | 性能不牺牲 | 5,000 活跃实体 P95 tick ≤ 2 ms（桌面，待基准验证） |
| G8 | 渐进落地 | 新层可独立跑；现有游戏按切片接入，不需要停机重写 |

### 2.2 非目标（v0 明确不做）

| ID | 不做 | 原因 |
| --- | --- | --- |
| N1 | 渲染器 / 刚体物理 / 音频引擎 | 引擎的强项；自己做会拖垮进度且不增加可替换性 |
| N2 | 通用 DCC / 资产创作 | 只定义逻辑资产 ID 与导入配方 |
| N3 | 联网 / MMO / 完整 rollback 网战 | v0 单机；但命令日志与快照为将来留口 |
| N4 | 可视化节点编程 | 规则先用 TS/数据；节点图是编辑器成熟后的表面 |
| N5 | 替代引擎编辑器 | 内容包是唯一事实源，编辑器只是视图 |
| N6 | ECS 教条 / 微服务 / 原生插件热插拔 | 单进程、模块化单体；ECS 只是内部实现 |
| N7 | 跨编译器逐位浮点一致 | 目标是 Det1/Det2（见 [01 §八](01_世界模型与运行时.md#八确定性契约)） |
| N8 | 绑定某个游戏类型 | 塔防、RPG、生存、叙事都应能用同一内核 |
| N9 | 通用 UI 框架（v0） | 只做声明式 HUD/对话/背包布局；复杂自定义 UI 仍由适配器实现 |

## 三、十条设计原则

这十条是后面所有取舍的「宪法」。出现分歧时，先回到这里。

| # | 原则 | 含义 | 反面案例 |
| --- | --- | --- | --- |
| P1 | **单一权威** | 世界状态只存在于内核；引擎不得私改玩法状态 | 在 Godot 节点上存血量，再同步回内核 |
| P2 | **硬接口，软表面** | ID/命令/事件/schema 必须硬；布局/动画/文案/颜色必须软 | 把 UI 文案写进规则，或把规则写进动画回调 |
| P3 | **内容即数据** | 可编译、可校验、可 diff、可版本化、可哈希 | 内容散落在场景文件与脚本常量里 |
| P4 | **动词优先** | 作者写「开门 / 给物品 / 开始任务」，不写节点 API | 作者要 `get_node("Door").play("open")` |
| P5 | **确定性优先** | 固定 tick、显式随机流、稳定遍历顺序、每 tick 状态哈希 | 用系统时间、全局随机、哈希表遍历顺序 |
| P6 | **适配器要薄** | 适配器只做映射；用一致性测试约束，不允许长规则 | 在 Unity 适配器里写伤害公式 |
| P7 | **先证伪再扩展** | 先证明「无引擎也能跑」，再证明「第二个宿主也能跑」 | 一上来做四个引擎适配器 |
| P8 | **失败可诊断** | 内容错误指向内容 ID；运行时黑匣子可回放 | 报错只有 `NullReferenceException` |
| P9 | **渐进迁移** | 新层独立可跑；旧游戏按切片接入 | 为了新架构停掉主线三个月 |
| P10 | **一次只加一个抽象** | 没有第二个消费者，就不抽象 | 先做「通用技能系统」，结果只有一个游戏用 |

## 四、总体架构

```text
┌────────────────────────────────────────────────────────────────────┐
│ L4 内容层 · Content Packs                                          │
│   zones / actors / items / quests / dialogue / rules / loc / tests │
│   作者写 TypeScript 或 JSON；worldc 编译成规范化内容包              │
└───────────────────────────────┬────────────────────────────────────┘
                                │ 编译、校验、哈希、迁移
┌───────────────────────────────▼────────────────────────────────────┐
│ L3 玩法套件 · Gameplay Kits（可选、可组合、可单独测试）             │
│   interaction · stats · inventory · quest · dialogue               │
│   ai · director · combat · economy · progression · social          │
└───────────────────────────────┬────────────────────────────────────┘
                                │ 只依赖 core 与显式声明的套件契约
┌───────────────────────────────▼────────────────────────────────────┐
│ L2 世界内核 · World Core（Rust，权威、确定性）                      │
│   World / Zone / Session / Entity / Component / Query              │
│   Time · Tick · Scheduler · Command · Event · Spatial · Nav        │
│   RNG · Save · Replay · Diagnostics · Script Host                  │
└───────────────────────────────┬────────────────────────────────────┘
                                │ 版本化 C ABI，轮询模型，内核从不回调引擎
┌───────────────────────────────▼────────────────────────────────────┐
│ L1 引擎适配器 · Engine Adapters（薄）                               │
│   Input · Asset · View · Animation · Audio · UI · Platform Storage │
│   Godot · Unity · Unreal · Web · Bevy · Headless                   │
└───────────────────────────────┬────────────────────────────────────┘
┌───────────────────────────────▼────────────────────────────────────┐
│ L0 引擎与平台 · Engine / OS / GPU                                   │
└────────────────────────────────────────────────────────────────────┘

旁路工具链（不在运行时关键路径）：
  worldc CLI · Web 世界编辑器 · 类型生成 · 内容校验 · 回放查看器 · 调试器
```

### 4.1 五层职责

| 层 | 拥有 | 不拥有 | 主要语言 |
| --- | --- | --- | --- |
| L4 内容 | 定义、摆放、规则、任务、对话、数值、文案、测试 | 引擎资源路径、渲染参数 | TypeScript / JSON |
| L3 套件 | 可复用的玩法状态机与规则（背包、任务、AI…） | 特定游戏的内容 | Rust（核心）+ TS（扩展钩子） |
| L2 内核 | 世界状态、时间、空间、命令/事件、存档、回放 | 任何引擎类型 | Rust |
| L1 适配器 | 输入、资产、视图、动画、音频、UI、平台存储 | 玩法规则、数值、内容 schema | 各引擎原生语言 |
| L0 引擎 | 渲染、物理、音频输出、平台 | 世界事实 | 引擎自身 |

### 4.2 为什么这样切

- **切在「事实 / 呈现」之间**，而不是切在「前端 / 后端」之间：换引擎时，事实不用搬家。
- **内核不回调引擎**：C ABI 只有「适配器调用内核」一个方向。没有回调，就没有跨语言生命周期、线程与异常的地狱。
- **内容编译成规范化包**：运行时只认包，不认 TS/JSON 源文件；这样非 TS 工具、非 Rust 宿主都能产出与消费。
- **套件与内容分离**：套件是「怎么玩」，内容是「玩什么」；同一个任务套件可以服务塔防与 RPG。

## 五、一次 tick 的完整路径

以 60 Hz 固定 tick 为例。适配器在渲染帧里驱动内核，内核可能在一帧内执行 0..N 个 tick。

```text
渲染帧（可变，例如 16.7 ms）
│
├─ 1. 适配器收集输入
│     键鼠/手柄/触屏 → InputFrame → world_input()
│
├─ 2. 适配器调用 world_tick(dt)
│     内核累加 dt，决定执行 N 个固定 tick（有追帧上限，防止死亡螺旋）
│
│     ┌─ 每个固定 tick（1/60 s）──────────────────────────────┐
│     │ a. apply_commands   校验并应用上一阶段排队的命令        │
│     │ b. run_systems      按显式顺序跑内核/套件系统           │
│     │ c. flush_events     生成「已发生事实」事件              │
│     │ d. run_scripts      事件处理器 → 把命令排到下一 tick    │
│     │ e. checkpoint       可选：状态哈希 / 黑匣子记录         │
│     └────────────────────────────────────────────────────────┘
│
├─ 3. 适配器轮询 world_poll_events()
│     视图生成/更新/销毁、动画、音效、UI 模型、镜头事件
│
├─ 4. 适配器读取 world_copy_transforms()（可见实体 POD 数组）
│     alpha 由适配器按累加器计算；world_snapshot() 仅用于调试/UI 等低频读取
│     渲染在显示刷新率上进行，逻辑不跟着渲染走
│
└─ 5. 存档 / 回放（按需）
      存档 = 包版本 + 种子 + 快照 + 脚本状态 + 哈希
      回放 = 包版本 + 种子 + 输入/命令日志 + 关键帧哈希
```

**为什么脚本在事件之后、命令在下一 tick 生效**：

- 避免「脚本读到半个 tick 的状态」；
- 避免「脚本在系统执行中途改状态」导致顺序不确定；
- 换来的是**一 tick 的固定延迟**，这是可预期、可测试的，比不可预期的重入便宜。

## 六、世界模型速览

详细定义见 [01](01_世界模型与运行时.md)。这里只给内容作者与工程都能达成共识的最小词汇表。

| 概念 | 是什么 | 生命周期 | 例子 |
| --- | --- | --- | --- |
| **World** | 一个持久世界的根；存档单位 | 天/月/整个游戏 | 逍遥湾存档、一个战役档 |
| **Zone** | 世界中的空间分区；可流式加载 | 进入/离开时激活/休眠 | 港湾、外环、某层楼 |
| **Session** | 一次游玩/一局/一场任务 | 开始到结算 | 塔防一局、一次副本、一段对话场景 |
| **Entity** | 世界中的对象；只有 ID 与组件 | 生成到销毁 | 一个 NPC、一扇门、一颗子弹 |
| **Component** | 挂在实体上的类型化数据 | 随实体 | `Transform`、`Health`、`Inventory` |
| **Prefab / Definition** | 可复用的实体模板 | 内容包内静态 | `demo.keeper`、`item.keycard` |
| **Command** | 意图，需校验后才生效 | 一 tick 内排队 | `OpenDoor`、`GiveItem`、`StartQuest` |
| **Event** | 已发生的事实，不可撤销 | 生成后广播 | `DoorOpened`、`ItemAcquired` |
| **Query** | 只读查询 | 即时 | 「半径 5 米内的友方」 |
| **Rule** | 事件 → 条件 → 命令/效果 | 内容包内静态 | 「有钥匙卡才能开气闸」 |
| **Kit** | 一组组件 + 系统 + 命令 + 事件 + schema | 随包启用 | 背包套件、任务套件 |
| **Pack** | 一次可运行的内容单位 | 版本化 | `demo.harbor@0.1.0` |
| **Save** | World 的持久化快照 | 版本化、可迁移 | 玩家存档 |

### 6.1 为什么同时需要 World 与 Session

- 塔防需要「一局」：开始、波次、结算、重开。这就是 **Session**。
- RPG/模拟经营需要「持续世界」：NPC 有日程、势力有态度、离线也在走。这就是 **World**。
- 两者不是二选一：World 可以包含多个 Session；Session 可以只读写 World 的一个子集。
- 如果只做 Session，就会重蹈「每个游戏都写一套元进度」；如果只做 World，塔防的「重开一局」会变得别扭。

### 6.2 为什么 Zone 要能休眠

- 内容作者希望「一个世界」而不是「一堆关卡」；但引擎不可能同时加载整座城市。
- 内核保留 Zone 的逻辑状态；激活的 Zone 全速 tick，休眠的 Zone 用粗粒度推进（例如每 60 tick 一次）或纯事件推进。
- 这样「隔壁城的 NPC 也在过日子」与「只加载眼前房间」可以同时成立。

## 七、上层玩法套件

套件是「跨游戏复用的玩法机制」。每个套件都是可选的，只有被内容包声明启用时才参与编译与运行。

| 套件 | 提供什么 | 关键组件/概念 | 优先级 |
| --- | --- | --- | --- |
| `core` | 身份、变换、标签、生命周期、区域、时间 | `Identity`、`Transform`、`Tags`、`ZoneMember` | P0（必选） |
| `interaction` | 交互动词、提示、条件、冷却 | `Interactable`、`Verb`、`Prompt` | P0 |
| `stats` | 属性、修正器、伤害/治疗管线 | `Attributes`、`Modifier`、`DamageEvent` | P0 |
| `inventory` | 物品、堆叠、容器、装备、配方 | `ItemStack`、`Container`、`Recipe` | P0 |
| `quest` | 目标、进度、奖励、链、前置 | `Quest`、`Objective`、`QuestState` | P0 |
| `dialogue` | 对话节点、选项、条件、效果 | `DialogueGraph`、`Choice` | P0 |
| `director` | 生成、波次、节奏、难度调节 | `Spawner`、`Wave`、`Director` | P0 |
| `save_profile` | 跨世界/跨会话的玩家档案 | `Profile`、`Unlock` | P0 |
| `ai` | 感知、状态机/行为树、巡逻、日程 | `Brain`、`Perception`、`Schedule` | P1 |
| `economy` | 货币、价格、交易、商店 | `Wallet`、`Price`、`Shop` | P1 |
| `combat` | 命中、投射物、波次战斗 | `Health`、`Hitbox`、`Projectile` | P1 |
| `world_sim` | 昼夜、日程、离线推进、人口 | `Calendar`、`Schedule`、`OfflineSim` | P1 |
| `progression` | 经验、等级、解锁、天赋 | `Xp`、`Level`、`Unlock` | P2 |
| `social` | 势力、声望、关系 | `Faction`、`Reputation` | P2 |
| `building` | 网格建造、升级、拆除 | `Placeable`、`Grid`、`Upgrade` | P2 |

**套件的三条硬规则**：

1. 套件只能依赖 `core` 与它显式声明的其他套件；禁止偷偷 import 兄弟套件的内部类型。
2. 套件之间通过命令/事件协作，不通过共享可变状态。
3. 每个套件必须自带：schema、内容作者文档、契约测试、确定性测试、性能基线。

### 7.1 跨游戏复用的三个层次

| 层次 | 复用什么 | 怎么复用 | 例子 |
| --- | --- | --- | --- |
| **内核复用** | 时间、实体、空间、命令/事件、存档、回放 | 所有游戏链接同一个 `world-core` | 塔防与 RPG 共享 tick/存档/回放 |
| **套件复用** | 背包、任务、对话、属性、AI… | 内容包在 manifest 里挑套件 | 两个游戏都用 `inventory` + `quest` |
| **内容复用** | 定义、规则、数值、文案、资产引用 | 包依赖/可选包/覆盖 | 共享「湾民」角色包、节日活动包 |

**反例**：把「塔防的波次」做成内核的一部分。它应该是 `director` 套件里的一个策略；
另一个游戏不需要波次，就不启用这个套件。**内核只保留所有游戏都需要的语义。**

## 八、引擎替换如何成立

「可替换引擎」不是一句承诺，而是三个可执行的证明：

| 证明 | 做法 | 失败意味着什么 |
| --- | --- | --- |
| **证明 1：无引擎** | Headless 宿主只链接内核，跑完 600 tick，产出状态哈希与事件序列 | 内核仍然依赖某个引擎 |
| **证明 2：第二个宿主** | Web（WASM）或 Bevy 跑同一个包、同一输入，哈希与事件序列一致 | 「跨引擎」只是口号 |
| **证明 3：适配器契约** | 每个适配器通过同一套 CTS（输入/资产/视图/音频/存档/生命周期） | 适配器偷偷长了规则 |

配套的工程约束：

- **适配器依赖白名单**：适配器 crate 不得依赖任何 `world-kits-*`；CI 直接检查依赖图。
- **规则禁止出现在适配器**：代码评审 + 简单的静态检查（适配器里出现伤害/任务/背包等关键词即告警）。
- **换引擎演练**：`worldc swap-check --pack demo` 跑所有可用宿主，比对哈希与事件；差异即失败。
- **内容包不认引擎**：包里的资产只写逻辑 ID（`mesh.keeper`），不写 `res://` 或 `.prefab` 路径。

详细契约见 [03 · 引擎适配与替换](03_引擎适配与替换.md)。

## 九、与 LiveBay 的关系

LiveBay 是当前主线，也是本方案最重要的现实约束：**不能为了一个新层停掉主线**。

| 方面 | 关系 |
| --- | --- |
| 概念 | 继承命令/事件总线、端口、固定 tick、MissionPack、黑匣子、扩展包启停 |
| 实现 | 不直接复用 GDScript 代码；把模式移植到 Rust，把内容格式升级为语言中立包 |
| 范围 | LiveBay 的 MissionRuntime 偏「一局」；本方案扩展为「持久 World + Session」 |
| 迁移 | 先做独立 Demo；再用 LiveBay 的一个切片（如自由模式或单张地图）做试点；最后决定是否整体迁移 |
| 风险 | 两套运行时并存期间，内容与工具会分叉；用「同一内容包、两个宿主」的验收来防止 |

**不建议**把 LiveBay 现有代码直接改造成新内核：那会把「验证新架构」和「保证主线稳定」两件事绑在一起。
推荐顺序是「新层先自证 → 单切片试点 → 再谈迁移」。

## 十、术语表

| 术语 | 英文 | 含义 |
| --- | --- | --- |
| 世界层 | World Layer | 本项目的整体称呼：介于引擎与内容之间的中间层 |
| 世界内核 | World Core | Rust 编写的权威运行时 |
| 世界包 / 内容包 | World Pack / Content Pack | 可运行的内容单位，含定义、规则、资产引用、文案、测试 |
| 套件 | Kit | 可复用的玩法机制包 |
| 适配器 | Adapter | 把内核接到某个引擎/平台的薄层 |
| 宿主 | Host | 承载内核的进程/运行时（Godot、Unity、Web、Headless…） |
| 适配器契约测试 | Adapter CTS | 所有适配器必须通过的同一套测试 |
| 替换演练 | Swap Drill | 同一内容包在两个宿主上跑出同一局的验收 |
| 黄金回放 | Golden Replay | 固定种子 + 输入轨迹 + 期望哈希，作为回归基线 |
