## 二、M0 目标（3–4 周）

用最小实现证明五件事：

1. 无引擎可跑：Headless 跑「港湾值班室」600 tick。
2. 可复现：同进程双跑、三平台 CI（Det1）哈希一致。
3. 可换语言/宿主：C 宿主通过 C ABI 跑同一包，哈希与 Headless 一致。
4. 可存档/回放：save→load→save 哈希一致；坏档明确报错；回放能定位首个分歧 tick。
5. 内容可校验：5 类坏包给出稳定错误码。

## 三、M0 技术选择

| 项 | M0 选择 | 与方案的关系 |
| --- | --- | --- |
| 权威内核 | Rust `world-core` | 一致 |
| 内容格式 | JSON（schema v0） | TS DSL 延后到 M1；JSON 是规范化格式，不是最终作者体验 |
| 规则 | Rust 解释 JSON 规则 | QuickJS 在 M0 只做 spike；规则引擎是内容无关的 |
| 存储 | 确定性 slab 存储 + 门面 | **偏差**：M0 不引入 `bevy_ecs`，避免在验证边界时同时验证第三方 ECS；M1 在门面后替换 |
| 空间 | `Transform` + `Aabb` 占位校验 | 导航/碰撞烘焙 M1 再做 |
| 边界 | C ABI（`world-ffi`）+ 手写 `world.h` | M0 先冻结函数面；M1 由 schema 生成头文件 |
| 存档 | JSON 信封 + 校验和 | 二进制/CBOR 在 M2 评估 |
| 回放 | JSON trace + 关键帧哈希 | 一致 |
| 依赖 | serde / serde_json / sha2 / hex / xxhash-rust | 许可为 MIT/Apache-2.0，内部私有不受限 |

### 3.1 为什么 M0 先用 slab 存储

- M0 要验证的是「边界 + 确定性 + 内容闭环」，不是 ECS。
- `bevy_ecs` 的 archetype 顺序会随组件增删变化；若在 M0 同时引入，会把「排序门面是否正确」与「ECS 行为」混在一起。
- 门面（`world-core` 的 `World` API）已经按「ECS 可替换」设计；M1 在门面后替换为 `bevy_ecs`，套件与适配器不受影响。
- 这项偏差在 M1 复核：若届时仍不需要 ECS 的查询性能，保留 slab 也可以；ADR-005 记录最终选择。

## 四、M0 非目标

- Web 编辑器 UI（M1）
- TS DSL 编译器（M1）
- Godot/Unity/Unreal 适配器（M2/M3）
- 导航烘焙、碰撞响应、休眠区模拟（M1/M2）
- 联网、rollback（M3+）
- 性能优化（M0 只建基线）
