## 二、遇到的主要问题

- **placeholder vs 正式 UI**：M1 不做整套正式 UI，也不做裸灰盒——用"最小可用面板 + 磁带频道轻量 Token 皮肤"跑通换肤管线；灰盒验证不了"不打断的手感"（计时呈现/降噪表达）。
- **三态边界**：开发计划验收 #3"三态可切换" vs 设置/图鉴后置 M3——已定为 M1 测漫游↔专注，设置/图鉴只定骨架（issues design-003）。
- **中文字体回退**：复古终端字在中文下易乱码（合订本 v1→v2 教训）；正文走系统回退（PingFang SC / Microsoft YaHei）、装饰字只做标题；数字用等宽 tabular figures 防空跳。

## 三、心得 / 经验

- **"共用骨架 + Token 换肤"是核心**：三态 = 同一套 ChannelShell 上的信息密度档位（一套图层可见度 + 焦点不劫持），不是三套窗口；换肤 = 各面板 `@export var skin: ChannelSkin`，脚本零硬编码 hex，换频道=换 .tres。
- **事件驱动解耦**：UI 只订阅 event_bus 状态（state_changed/card_collected），不持有逻辑真值——Shell 只改可见度、面板只读 skin/数据，职责清晰。
- **可读性是硬线**：动效（CRT 扫描线）不盖 UI 或控强度，中文字体回退、等宽数字都是"可读性优先"；引用字体兼容教训确立"须先显式验证双端渲染"。
- **Token 挂主美术**：UI 色值全部取自主美术 channel skin token，不自拟——避免与主美术色板不一致。

## 四、关键决策 / 变更
