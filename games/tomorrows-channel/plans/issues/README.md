# issues · 问题与困难汇总

> 汇总《明日频道》各角色**开发过程中遇到的主要问题与困难**（技术阻塞、设计难点、内容缺口、流程/协作问题、风险/未决项）。
> 问题以**单文件**记，跨角色聚合；与 [`decisions/`](../decisions/)（已定决策）、[`progress/`](../progress/)（已完成）区分——本目录记**未解/受阻/待研**的问题与困难。

## 一、分类子目录

| 子目录 | 内容 |
| --- | --- |
| [`technical/`](technical/) | 技术问题：Godot/渲染/接口/性能/编译/引擎能力 |
| [`design/`](design/) | 设计/体验问题：玩法手感、频道基调、三态/换肤、边界取舍 |
| [`content/`](content/) | 内容问题：卡池/素材缺口、版权/合规、内容量产 |
| [`process/`](process/) | 流程/协作问题：git 并行冲突、文档规范、依赖串行 |
| [`risk/`](risk/) | 风险/未决：平台缺口、范围蔓延、高影响不确定 |

## 二、文件命名约定

- 每问题一个文件：`YYYYMMDD-HHMM-{序号}-{关键词}.md`（时间戳精确到分 + 递增序号，可追溯）。
- 例：`20260908-1400-001-godot-shader-scanline-verify.md`（技术类，扫描线 shader 待验证）。
- 序号在**类内**递增（每类独立 `001/002/...`），不跨类共享。

## 三、单问题文件体例

```
# 问题：<一句话标题>
> 状态：<open(未解) / in_progress(处理中) / blocked(受阻) / resolved(已解) / wontfix(不做)>
> 发现：YYYY-MM-DD HH:MM · 发现人：<角色>
> 类型：<technical/design/content/process/risk> · 优先级：<高/中/低>

## 现象 / 问题描述
<遇到了什么问题，影响什么（是否阻塞 M1/M2/某验收）>

## 影响 / 卡点
<阻碍了哪一步、波及哪些角色/模块、不解决会怎样>

## 尝试 / 参考
<已尝试什么、参考哪份文档/研究>

## 解决方向 / 需求
<初步思路、需要谁（角色）提供什么>

## 变更记录
- YYYY-MM-DD HH:MM：登记。
- （解决时）YYYY-MM-DD HH:MM：状态→resolved，说明。
```

## 四、运转约定

- 各角色发现主要问题/困难时，**登记**到本目录（找到 `### 头部` 里的状态标记）。主持人（主策划）定期**盘点**未解项，按优先级分配角色处理。
- 问题解决后状态改 `resolved` + 变更记录；不删文件（保留决策/追溯）。
- 与 `decisions/` 关系：某问题**定策解决**时，已定的结论入 ADR（`decisions/`），问题文件可标 `resolved` 引用该 ADR。
